# 개발자 블로그 작성

독자가 겪는 문제와 실제로 확인한 근거를 연결해 기술 글을 쓴다. 저자의 경험과 의견은 저자가
제공하거나 확인한 범위에서만 사용하고, 코드·출처·실행 결과로 기술 설명을 보강한다.

## 자료와 작성 범위를 확인한다

요청을 `plan`, `draft`, `revise`, `audit` 중 하나로 분류한다. 사용자가 제공한 메모와 저자가
확인한 경험, 허용된 repository 자료와 출처를 구분해 모은다. 글 작성만 요청받았다면 채팅에
골격과 초안을 반환하고 파일 생성·게시·Git 작업으로 확대하지 않는다.

요청 유형별 반환 범위는 다음과 같다.

- `plan`: 흐름 의사코드, 절별 근거 공백과 글을 바꾸는 질문까지만 반환하고 본문을 만들지 않는다.
- `draft`: 흐름 의사코드 뒤에 확인된 근거 범위의 새 본문을 반환한다.
- `revise`: 원문의 흐름을 먼저 확인하고 지정한 제목·문단과 그 수정에 꼭 필요한 인접 연결만
  바꾼다. 지정되지 않은 제목·문단·코드·링크와 주장 순서는 보존하며, 불가피하게 바꾼 연결은
  반환할 때 범위를 밝힌다.
- `audit`: 원문을 수정하지 않는다. 현재 글에서 읽은 흐름을 기준으로 위치·근거 상태·저자성 또는
  한계의 문제·영향·최소 수정 방향을 finding으로 반환한다.

`revise`와 `audit`에서 원문에 흐름 의사코드가 없으면 현재 글로부터 최소한으로 복원하되 원문에
없던 저자 의도나 인과관계를 채우지 않는다. `revise`에서는 변경 전후 흐름 중 영향받은 필드를,
`audit`에서는 판단 기준으로 사용한 필드를 보여 주고 나머지 원문은 그대로 둔다.

저자의 1인칭 경험·동기·감정·의사결정 이유는 코드, commit history나 외부 자료에서 추론하지
않는다. 글의 핵심인 저자 정보가 부족하면 가능한 각도, 흐름 의사코드와 필요한 질문까지만
반환하고 초안을 만들지 않는다. 핵심 저자 정보는 충분하지만 세부 사실만 부족하면 확인된 범위로
초안을 쓰고 나머지는 초안 밖의 미확인 사항으로 남긴다. 사실의 확실성, 시점, 수치, 이름, 링크와
인과관계를 보존하며 순서가 같다는 이유로 원인이라고 쓰지 않는다.

## 글의 흐름을 먼저 고정한다

TIL, debugging, technical-decision, deep-dive 중 독자의 질문에 맞는 모드를 고른다. 본문보다 먼저
다음 필드를 짧은 `흐름 의사코드`로 보여 준다.

```text
reader: 이 글을 읽을 사람
reader_problem: 독자가 막힌 지점이나 내려야 할 결정
main_answer: 글이 전달할 한 가지 핵심 답
section_sequence: 답에 도달하는 절의 순서
evidence_by_section: 각 절의 코드·출처·관찰 근거
ending_and_limits: 독자가 적용할 다음 행동과 남은 경계
```

새 본문을 작성하는 `draft`에서는 여섯 필드의 이름과 값을 생략하지 않는다. `plan`도 같은 필드로
본문의 방향을 고정한다. `revise`와 `audit`은 위 반환 계약에 따라 현재 흐름과 영향받은 필드를
보존·표시한다. 짧은 TIL은 각 값을 한 줄로 줄일 수 있지만 실행 순서만 적어 독자·핵심 답·근거와
한계를 잃지 않는다. 검증 결과로 논지가 바뀌면 본문을 쓰기 전에 이 흐름 의사코드도 갱신한다.

모드별 절의 역할과 연결 방법은 [글의 골격과 문단 흐름](references/article-shapes.md)에서 선택해
읽는다. 제목 수나 문단 수, SEO 키워드와 일률적인 서론·결론을 강제하지 않는다.

짧은 TIL이거나 논지와 근거가 충분하면 흐름 의사코드 뒤에 같은 응답으로 초안을 작성한다.
장문에서 저자의 경험·논지 선택이 결과를 바꾸는 데 필요한 정보가 없으면 골격과 집중된 질문에서
멈춘다. 사용자가 한 번에 써 달라고 했으면 중대한 저자 정보가 빠지지 않은 범위에서 골격과
초안을 함께 반환한다.

## 필요한 근거를 직접 확인한다

핵심 기술 주장이 현재 자료만으로 뒷받침되지 않으면 먼저 확인 가능한 주장인지 판단한다. 안전한
local inspection, 기존 test·build와 local browser 확인으로 판정할 수 있으면 글의 근거에 필요한
최소 범위만 실행한다. 새 재현 코드는 tracked 파일이 아닌 격리된 임시 디렉터리에 만들고 정리한다.

검증 전 `environment`, `input`, `command`, `expected`를 정하고, 실행 뒤 `observed`와 적용 한계를
기록한다. 결과가 예상과 다르면 증거를 골라내지 말고 논지와 흐름을 관찰 결과에 맞춘다. 상세한
상태 구분과 실행 경계는 [기술 근거와 직접 검증](references/technical-evidence.md)을 따른다.

운영 환경, 사용자 데이터, 유료 서비스, 배포, 원격 쓰기나 tracked 파일 수정이 필요하면 글 작성
권한만으로 실행하지 않는다. 확인하지 않은 부분을 `not_run`으로 남기고 필요한 권한이나 자료를
별도로 설명한다. 실제 제품 결함의 진단·수정이 주목적이면 사용할 수 있는 Engineering 절차가
그 작업을 맡고, 이 스킬은 전달받은 근거로 글을 구성한다.

## 근거에서 문단을 작성한다

한 문단은 하나의 주장·질문·결정을 맡는다. 독자가 따라갈 수 있도록
`주장 또는 질문 → 근거·메커니즘 → 의미·다음 문단으로의 연결` 순서로 쓴다. 코드는 주장 전체를 대신하지 않게 앞뒤에
무엇을 보여 주는지 설명하고, 실제 코드에서 글의 핵심과 무관한 부분만 덜어 낸다.

본문에는 읽는 데 필요한 근거와 한계를 자연스럽게 포함한다. 작성 판단용 evidence ledger를
그대로 본문 형식으로 강요하지 않는다. 설명이 필요할 때만 초안 뒤에 `observed`,
`source-confirmed`, `inference`, `unknown`, `not_run`을 구분한 근거와 미확인 사항을 둔다.

외부 다중 출처 조사가 결과를 좌우하면 사용할 수 있는 Codex·Claude의 `research:research` 또는 OMP의
`skill://research`를, 출력 언어의 표현을 다듬을 때는 해당 Fluent 스킬을 선택적으로 함께 적용한다. 어느 플러그인도 설치된 것으로
가정하지 않는다. 여러 차례 이어지는 장문·여러 파일 작성만
[작업 연속성](../task-continuity/SKILL.md)에 기록한다.

## 반환 전에 대조한다

흐름 의사코드와 본문이 같은 핵심 답을 향하는지, 각 실질적 주장이 제공 자료·출처·관찰 중 하나에
연결되는지 확인한다. 1인칭과 의견, 원인·결과, 성공·검증 범위가 근거보다 강해지지 않았는지
대조한다. 실행하지 않은 검증과 다른 환경의 동작을 현재 확인 결과로 쓰지 않는다. 설명이나 평가를
요청받지 않았다면 골격, 초안과 실제로 남은 근거 사항만 간결하게 반환한다.
