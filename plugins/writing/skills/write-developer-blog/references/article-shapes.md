# 글의 골격과 문단 흐름

독자의 질문과 현재 자료에 맞는 한 가지 골격을 고른다. 모든 항목을 제목으로 만들 필요는 없으며,
근거가 없거나 독자의 답에 기여하지 않는 단계는 억지로 채우지 않는다.

## TIL

작게 막힌 문제와 그때 얻은 재사용 가능한 이해를 짧게 연결한다.

```text
막힌 지점
  → 배운 내용
  → 실제 최소 예제
  → 그렇게 동작하는 이유
  → 적용되는 경우와 적용되지 않는 경우
  → 재현 방법 또는 출처
```

독자가 바로 시험할 수 있는 명령·입력·출력을 남긴다. 한 가지 배움을 전달하는 글에 기술의 전체
역사, 대안 비교나 장문의 배경을 붙이지 않는다.

## Debugging

정답만 나열하지 않고 잘못된 mental model이 어떤 증거로 바뀌었는지 보여 준다.

```text
관찰한 현상
  → 최초 mental model과 예상
  → 예상과 충돌한 증거
  → 실제 메커니즘
  → 시도와 기각 이유
  → 해결
  → 같은 입력의 검증 결과
  → 아직 확인하지 못한 경계
```

시도한 순서가 해결의 원인이었다고 자동으로 쓰지 않는다. 실패한 시도는 독자의 오해를 줄이거나
최종 메커니즘을 설명할 때만 남긴다.

## Technical decision

결론을 숨기지 않고, 그 결론이 어떤 조건에서 유효한지 설명한다.

```text
현재 결정
  → 결정이 필요했던 맥락
  → 판단 기준
  → 검토한 대안
  → 기각한 이유
  → 선택하면서 부담한 비용
  → 현재 구현·운영 상태
  → 결정을 재검토할 조건
```

개인이나 팀의 선호와 합의된 결정, 실행된 상태를 구분한다. 선택하지 않은 기술을 일반적으로
열등하다고 표현하지 않고 현재 조건과 맞지 않은 이유를 쓴다.

## Deep dive

독자의 mental model을 바꾸어야 하는 기술 설명에 사용한다.

```text
독자가 겪는 문제
  → 흔한 초기 이해
  → 그 이해와 맞지 않는 관찰
  → 내부 메커니즘
  → 가능한 대안과 tradeoff
  → 이 글의 판단
  → 실제 구현 또는 예제
  → 검증
  → 적용 한계
```

메커니즘은 문제와 관찰을 설명하는 데 필요한 깊이까지만 내려간다. 독자가 이미 받아들인 전제를
다시 가르치거나, 내부 구현 세부를 이해 자체와 동일시하지 않는다.

## 흐름 의사코드를 점검한다

`main_answer`는 한 문장으로 적고 각 절이 그 답을 지지하거나 한계를 정하는지 확인한다.
`evidence_by_section`에는 자료의 위치나 검증 상태를 연결한다. 근거 없는 절을 그럴듯한 연결 문장으로
메우지 않고 자료를 더 모으거나 범위를 줄인다.

짧은 글에서도 `reader`, `reader_problem`, `main_answer`, `section_sequence`,
`evidence_by_section`, `ending_and_limits`를 모두 유지한다. 각 값은 짧게 줄일 수 있지만 단계 나열만
남겨 독자·답·근거를 숨기지 않는다.

끝부분은 내용을 반복해 요약하는 데 그치지 않는다. 독자가 적용할 수 있는 조건, 재현 방법,
선택을 다시 검토할 시점이나 아직 모르는 경계 중 필요한 것을 남긴다.

## 문장과 문단을 연결한다

한 문단은 하나의 질문·주장·결정에 답한다.

```text
첫 문장: 이 문단이 답할 주장이나 질문
중간: 코드, 관찰, 출처 또는 메커니즘
끝: 근거가 뜻하는 바와 다음 문단이 필요한 이유
```

연결어만으로 관계를 만들지 않는다. 앞 문단의 결과가 다음 문단의 질문이 되게 배치한다. 원인,
대조, 예외와 시간 순서를 실제 자료가 보여 주는 관계에 맞춰 쓴다.

코드 예제는 실제 코드나 확인한 재현에서 시작하고 무관한 의존성·이름·설정만 제거한다. 축약이
동작 조건을 바꾸면 별도 예제가 아니라 확인하지 않은 새 주장으로 취급한다.
