# 코드 주석: 계약과 이유를 드러낸다

주석은 코드만으로 알기 어려운 호출 규약이나 구현 이유를 보충한다. 요청받은 주석의 범위에서 다듬고 코드·식별자·자료형·수치·프로토콜 토큰을 바꾸지 않는다. 계약이나 원인이 확인되지 않았다면 코드를 보고 추측해 보증하지 않는다. 생성 코드 표식, lint·type 억제 지시, 라이선스와 도구가 읽는 주석의 구문을 보존한다.

## 호출자에게 필요한 계약을 쓴다

공개 API에는 무엇을 얻는지 먼저 쓰고, 호출자가 잘못 사용할 수 있는 입력·출력 조건을 보충한다. 필요할 때 형식·단위·시간대·빈 값·오류·부수 효과를 설명하되 코드와 확인된 사양에 있는 내용만 담는다. 이름이나 타입만 자연어로 반복하지 않는다. docstring·JSDoc 등 프로젝트의 기존 형식을 따른다.

김혜빈의 한국어 원문 [5. Technical Writer, 사라질 결심](https://toss.tech/article/technical-writing-5)은 `date: string`에 다음 설명을 보완하는 사례를 제시한다.

> 결제가 완료된 날짜예요. YYYY-MM-DD 형식으로 입력해요. (예: 2025-09-22)

타입에 의미 → 입력 형식 → 예시를 보탠 구조다. 저자가 정리한 문서 작성 지침이며 주석의 필수 항목 목록은 아니다. 아래는 별도의 가상 API에서 `null`의 의미가 사양으로 확인됐다고 가정한 로컬 예시다.

```typescript
// 약한 설명: ID로 송장을 조회한다.
/** 송장을 반환한다. 해당 ID의 송장이 없으면 null을 반환한다. */
```

반환값에 다른 실패 의미가 있다면 그대로 구분한다. 위 예시만 보고 네트워크 오류도 `null`이라고 설명해서는 안 된다.

## 구현 안에서는 비자명한 이유를 쓴다

루프·대입·함수 호출을 다시 읽어 주는 주석보다, 그렇게 해야 하는 이유·유지해야 할 불변 조건·피하는 실패를 쓴다. 우회 코드에는 확인된 제약과 적용 범위를 남기고, 추적 가능한 이슈가 있으면 연결한다. 제거 가능한 조건이 합의되어 있으면 보존하되 임의의 해결 시점이나 버전을 약속하지 않는다.

다음은 SDK의 결함과 해당 우회 동작이 확인됐다고 가정한 로컬 예시다.

```typescript
// 약한 설명: 응답이 비어 있으면 파싱하지 않는다.
// SDK 2.4가 204 응답을 JSON으로 파싱해 실패하므로 빈 응답만 우회한다.
```

첫 문장은 동작을 반복하고, 둘째 문장은 제약 → 실패 → 우회 범위를 연결한다. 원인이 미확인이면 이렇게 확정해서 쓰지 않는다. 설명할 비자명한 정보가 없는 코드에 형식적으로 주석을 추가하지 않는다.

## 일본어·영어 원문에서 확인한 차이

[LINEヤフー의 설명 첫 문장 사례](https://techblog.lycorp.co.jp/ja/20240523a)는 일본어 원문에서
API 설명을 반환값의 의미 → 문장·단어의 정의 → 제외 대상 → 입출력 예로 고친다. 같은 글의
workaround는 존재 이유부터, TODO는 원하는 변경부터 설명한다. 모든 주석에 `왜`만 쓰는 규칙으로
합치지 않는다. TODO에는 합의된 변경과 선행 조건·현재 못 하는 이유를 남기되 없는 결정을 만들지 않는다.

영어 원문 [Go Doc Comments](https://go.dev/doc/comment#funcs)의 짧은 예는
“HasPrefix reports whether the string s begins with prefix.”다. 호출자가 받는 결과를 첫 문장으로
설명한다. 문서 주석은 호출 계약과 중요한 예외를, 함수 안 주석은 구현 세부사항을 다룬다는 구분을
참고한다. Go의 선언·문장 형식을 다른 언어의 주석 형식에 그대로 강제하지 않는다.
