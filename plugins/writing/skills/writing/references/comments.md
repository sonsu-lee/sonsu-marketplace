# 코드 주석: 계약과 이유를 드러낸다

주석은 코드만으로 알기 어려운 호출 규약이나 구현 이유를 보충한다. 요청받은 범위에서 확인된 계약과 이유를 다듬고, 코드·식별자·자료형·수치·프로토콜 토큰을 유지한다. 생성 코드 표식, lint·type 억제 지시, 라이선스와 도구가 읽는 주석 구문도 보존한다.

## 호출자에게 필요한 계약을 쓴다

공개 API에는 호출 결과를 먼저 쓰고, 잘못 사용하기 쉬운 입력·출력 조건을 보충한다. 형식·단위·시간대·빈 값·오류·부수 효과 중 호출자에게 필요한 내용을 확인된 코드와 사양에 근거해 설명한다. docstring·JSDoc 등 프로젝트의 기존 형식을 따른다.

김혜빈의 한국어 원문 [5. Technical Writer, 사라질 결심](https://toss.tech/article/technical-writing-5)은 `date: string`에 다음 설명을 보완하는 사례를 제시한다.

> 결제가 완료된 날짜예요. YYYY-MM-DD 형식으로 입력해요. (예: 2025-09-22)

타입에 의미 → 입력 형식 → 예시를 보탠 저자의 작성 사례다. 아래 로컬 예시는 별도의 가상 API에서 `null`의 의미가 사양으로 확인됐다고 가정한다.

```typescript
// 약한 설명: ID로 송장을 조회한다.
/** 송장을 반환한다. 해당 ID의 송장이 없으면 null을 반환한다. */
```

반환값에 다른 실패 의미가 있으면 구분한다. 위 예시는 네트워크 오류도 `null`을 반환한다는 근거가 되지 않는다.

## 구현 안에서는 비자명한 이유를 쓴다

구현 주석에는 동작의 이유·불변 조건·피해야 할 실패를 쓴다. 우회 코드에는 확인된 제약과 적용 범위, 추적 가능한 이슈를 남긴다. 제거 조건이나 해결 시점·버전은 합의된 내용이 있을 때 쓴다.

다음은 SDK의 결함과 해당 우회 동작이 확인됐다고 가정한 로컬 예시다.

```typescript
// 약한 설명: 응답이 비어 있으면 파싱하지 않는다.
// SDK 2.4가 204 응답을 JSON으로 파싱해 실패하므로 빈 응답만 우회한다.
```

첫 문장은 동작을 반복하고, 둘째 문장은 확인된 제약 → 실패 → 우회 범위를 연결한다. 원인이 미확인이면 그 상태를 유지한다. 코드만으로 알 수 있는 내용은 주석을 생략한다.

## 주석의 역할에 맞게 첫 문장을 쓴다

[LINEヤフー의 설명 첫 문장 사례](https://techblog.lycorp.co.jp/ja/20240523a)는 일본어 원문에서
API 설명을 반환값의 의미 → 문장·단어의 정의 → 제외 대상 → 입출력 예로 고친다. 같은 글의
workaround는 존재 이유부터, TODO는 원하는 변경부터 설명한다. `왜`가 필요한 구현 주석과
호출 계약을 설명하는 API 주석을 구분한다. TODO에는 합의된 변경과 선행 조건·현재 실행할 수 없는 이유를 쓴다.

영어 원문 [Go Doc Comments](https://go.dev/doc/comment#funcs)의 짧은 예는
“HasPrefix reports whether the string s begins with prefix.”다. 호출자가 받는 결과를 첫 문장으로
설명한다. 문서 주석은 호출 계약과 중요한 예외를, 함수 안 주석은 구현 세부사항을 다룬다는 구분을
참고하고, 구체적인 선언·문장 형식은 해당 프로젝트의 언어와 관례를 따른다.
