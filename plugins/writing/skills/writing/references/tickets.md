# 티켓의 내용과 양식

티켓을 새로 쓰거나 고칠 때 읽는다. 작성자는 문제·요청·합의된 제약을 전달하고, 작업자는 미정인 원인 분석과 해결 방법을 정한다. 이 문서는 글의 구성 기준이다. 실제 공간의 양식 조회, 필수 필드 확인, 티켓 분할·연결과 게시 판단은 Workflow가 맡는다.

## 주어진 양식을 먼저 따른다

사용자가 지정한 양식, 전달받은 대상 공간의 양식·지침, 요청 목적에 맞는 기본형 순으로 적용한다. 주어진 양식의 제목·순서·필수 항목·체크리스트·고정 문구를 보존하고, 그 항목에 내용을 채운다. 기본형의 제목을 뒤에 덧붙이지 않는다. HTML comment는 자동화 표식이나 숨은 지침일 수 있으므로 양식이 제거·치환하도록 지정한 부분만 바꾼다.

Writing만으로 쓰는 플랫폼 중립 초안은 아래 기본형을 사용할 수 있다. 양식 확인이 안 된 초안은 임시임을 본문 밖에서 알린다. 글을 썼다는 사실로 원격 양식의 부재, 접수 가능 여부나 게시 준비 완료를 판단하지 않는다. 기존 티켓의 부분 수정은 현재 구조와 요청받지 않은 내용을 보존하며, 전체 재작성을 요청받았을 때만 양식을 바꾼다.

| 요청한 최종 작업 | 기본형 | 각 항목의 역할 |
| --- | --- | --- |
| 기능·개선·리팩터링·문서 등 변경·추가·정리 | [일반 작업](../assets/templates/default.md) | 배경은 왜 필요한지, 작업 내용은 무엇을 요청하는지, 참고는 추가 조건·자료를 설명한다. |
| 잘못된 동작 수정 | [버그](../assets/templates/bug.md) | 현상은 실제·기대 동작, 재현 정보는 알려진 조건·순서·자료, 고려 사항은 추가 제약을 담는다. |
| 질문에 대한 답변이나 판단 근거 마련 | [조사 작업](../assets/templates/investigation.md) | 확인할 질문은 의문과 배경, 남길 결과는 필요한 답변·근거, 고려 사항은 조사 범위를 설명한다. |

버그 수정에 원인 조사가 포함되어도 버그형을 쓴다. 조사 결과 자체를 전달하는 것이 요청이면 조사형을 쓴다. 이 구분은 본문 양식이며 tracker의 type·label·status를 지정하지 않는다. 문제나 질문을 이해할 수 있으면 알려진 내용으로 작성하고, 무엇을 다루는지도 불명확하면 보존 가능한 초안과 필요한 입력을 반환한다.

## 문제와 요청을 분리해 구체적으로 쓴다

제목은 주된 문제나 요청을 바로 드러낸다. 본문은 담당자가 외부 논의를 모두 읽지 않아도 이해할 만큼 맥락을 담는다. 배경과 작업 내용에서 같은 문장을 반복하지 않는다. 한 문단에는 관련된 내용을 모으고, 재현처럼 순서가 있는 절차는 번호 목록으로 쓴다. 주체·조건·이유가 바뀌는 지점에서 문장을 나눈다.

관찰, 가설, 제안, 선호, 합의와 실행 결과를 구분한다. “Next.js를 선호한다”를 필수 조건으로 바꾸지 않는다. 원인·해결 방법·코드 구조·작업 순서·구체적 테스트를 새로 지시하지 않는다. 이미 합의된 설계·ADR, 보안·호환성, 전환 순서·복구 조건처럼 방법 자체가 제약인 내용은 보존한다. 조사 결과의 보고서·비교표 형식과 일정도 요청되거나 합의된 경우에만 지정한다.

완료조건·종료조건을 기본 항목으로 요구하거나 만들어 내지 않는다. 합의된 조건은 일반형의 `참고`, 버그·조사형의 `고려 사항`에 담는다. 여러 조건을 각각 확인해야 하고 적용 양식이 허용할 때만 별도 항목으로 묶는다. 예를 들어 “회귀가 없다”라는 합의의 의미가 불명확하면 필요한 입력을 표시한다. 이미 합의된 동작이 “빈 검색 결과에서 다운로드 버튼을 숨긴다”라면 그 동작을 보존하며 임의의 테스트 명령으로 대체하지 않는다.

외부 논의의 핵심 결론은 요약하고 근거를 연결한다. 긴 계획이나 회고는 필요한 부분만 요약하며 상세 계획을 새로 만들지 않는다. 합의가 바뀌면 최신 결론과 중요한 변경 이유·기존 근거를 함께 남긴다. 코드·수치·의무 수준·티켓 ID·URL은 문체를 다듬을 때도 보존한다.

## 짧은 사례: 관찰에서 원인을 만들지 않는다

다음은 이 저장소의 작성 기준을 설명하기 위한 로컬 예시다. 입력은 “다운로드한 CSV의 한글이 깨진다. 원문대로 표시되어야 한다”뿐이며, 환경·재현 순서·원인은 아직 모른다고 가정한다.

- 잘못된 확장: “UTF-8 BOM 누락을 수정하고 CSV 라이브러리를 교체한다.” 원인과 방법을 새로 결정했다.
- 작성 예시:

```markdown
## 현상
다운로드한 CSV의 한글이 깨져 표시됩니다. 원문의 한글이 그대로 표시되어야 합니다.

## 재현 정보
CSV를 다운로드한 뒤 확인한 현상입니다. 사용 환경, 파일을 연 프로그램과 재현 순서는 미확인입니다.
문제가 나타난 파일이나 화면 자료는 아직 확보하지 못했습니다.
```

알려진 현상 → 기대 동작 → 확인된 발생 상황 → 남은 정보 순서다. 미확인 정보는 숨기지 않되 원인·재현 단계·자료를 만들어 채우지 않는다. 기본형의 작성 안내와 빈 선택 항목은 제거한다. 주어진 양식의 필수 빈 항목에는 이 삭제 규칙을 적용하지 않는다.

영어 원문 [Mozilla의 Bug Writing Guidelines](https://bugzilla.mozilla.org/page.cgi?id=bug-writing.html)는
“Cancelling a File Copy dialog crashes File Manager”를 좋은 제목의 예로 제시한다.
발생 조건·동작과 문제가 생기는 대상을 함께 알려 주기 때문이다. 재현 절차와 실제·기대 결과를
구분하는 구조도 참고한다. 버그 보고 지침이므로 기능 제안·조사 티켓에 재현 절차를 강제하는 근거는 아니다.

## 범위와 결과를 정확히 남긴다

부모·자식 티켓도 각각의 요청 목적에 맞는 양식을 쓴다. 부모는 전체 문제와 자식별 범위를, 자식은 맡은 작업과 필요한 공통 제약을 설명한다. 부모의 긴 배경을 복사하지 않는다. 이미 정해진 분해 경계·제외 범위·전체 제공 및 검증 조건을 보존하며, 단계가 생겼다는 이유로 글쓰기 중 새 티켓을 요구하지 않는다.

실제 결과가 생겼을 때만 보강한다. 접수·채택과 구현 완료, 장애 복구와 재발 방지, 회고와 후속 개선, 검증 수행과 기준 충족, 일부 전환과 전체 전환을 구분한다. 한 자식의 완료나 코드 merge를 전체 작업 완료로 표현하지 않는다. 초안과 실제 게시 결과, `not_run`·`unknown`과 성공도 구분한다.
