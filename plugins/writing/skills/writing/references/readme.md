# README: 독자가 이해하고 실행하게 쓴다

README는 처음 방문한 독자가 프로젝트의 용도와 적합성을 판단하고 사용을 시작하며 상세 문서를
찾게 한다. 일부 수정 요청은 해당 구간과 필요한 연결 문장에 한정한다. 사용자가 지정한 포함 내용과
양식을 우선하고, 의미·편집 범위는 [보존 지침](integrity.md)을 따른다.

## 주요 안내가 달라질 때 갱신한다

프로젝트의 용도·주요 기능·사용 대상·설치·첫 사용·중요한 제약·상세 문서의 진입 경로가 바뀌면
해당 안내를 갱신한다. 개별 작업을 완료했거나 검사를 실행했다는 사실만으로 내용을 추가하지 않는다.
주 독자가 기여자인 저장소라면 로컬 실행·개발 절차도 첫 사용에 필요한 안내가 될 수 있다.

전체 옵션·API·설계 이유·운영 절차는 첫 사용에 필요한 만큼만 설명하고 담당 문서로 연결한다.
분량이나 제목 수를 고정하지 않으며, 짧은 프로젝트는 README 안에서 완결할 수 있다.
공통 정보 선별·문단 구성·링크 기준은 [구성 지침](composition.md)을 적용한다.

## 첫 화면에서 다음 행동까지 연결한다

첫 문단에 프로젝트의 역할과 대상 독자 또는 해결하는 문제를 쓴다. 입력과 결과, 필요한 적용 범위를 구체적으로 설명하고, 사용 여부를 바꾸는 제한은 시작 전에 알린다.

빠른 시작은 가장 짧은 정상 경로 하나를 보여 준다. 필요한 환경·설치·입력 → 명령이나 코드 → 기대 결과 순서로 구성한다. 단계마다 실행 위치와 목적을 밝히고, 명령 뒤에는 성공을 알아볼 수 있는 결과를 둔다. 명령·버전·출력·설치법·지원 환경은 확인된 자료에 근거한다.

사용자 설치 절차와 기여자 개발 절차를 구분하고, 제목과 순서는 프로젝트의 특성에 맞춘다.
도움받을 곳·기여 안내·라이선스는 사용과 참여에 필요한 설명과 실제 문서의 링크를 제공한다.

예를 들어 선택적 로그 보관 옵션을 추가했고 기존 설정 참조 문서가 있다면 그 문서에 옵션과
조건을 반영한다. 용도·첫 실행·중요한 제약이 같으면 README는 유지한다. 반면 최소 실행 환경이
변경됐다면 상세 문서뿐 아니라 README의 빠른 시작도 수정한다. 내부 리팩터링과 일회성 테스트
결과만 있다면 작업 보고에 남기며, 이를 옮기기 위한 새 문서를 만들지 않는다.

## 짧은 사례: 명령 다음에 결과를 보여 준다

다음 로컬 예시는 가상의 CLI가 설치되어 있고, 저장소 루트에 `sample.csv`가 있으며, 아래 출력이 확인됐다고 가정한다. 실제 README에는 해당 프로젝트의 확인된 사실을 쓴다.

약한 안내는 “설정 후 `csv-inspect sample.csv`를 실행하세요”로 끝나서 무엇을 확인했는지 알 수 없다.

```markdown
# CSV Inspect

CSV 파일의 열 이름과 행 수를 확인하는 CLI입니다. 데이터를 가져오기 전에 파일 구조를 확인할 때 사용합니다.

## 빠른 시작

CLI를 설치했다면 저장소 루트에서 예제 파일을 검사하세요.

    csv-inspect sample.csv

다음 결과가 나오면 두 열과 10개 데이터 행을 읽은 것입니다.

    Columns: name, email
    Rows: 10
```

목적 → 준비된 입력 → 실행 → 결과의 의미를 연결한 구조다. 출력은 해당 예시의 결과이며, 실제 문서에 설치 안내가 필요하면 확인된 선행 절차를 앞에 연결한다.

한주연의 한국어 원문 [그 많은 개발 문서는 누가 다 만들었을까 (2)](https://toss.tech/article/tech-writer-2)는 설명·예제·미리보기를 연결해 개발자가 결과를 보며 학습하도록 문서를 개선한 실무 사례다. 위 CLI 문안은 별도로 만든 예시다. 원문은 제품 문서 작성 경험을 다루며, 미리보기나 샌드박스의 필요성은 프로젝트에 따라 판단한다.
