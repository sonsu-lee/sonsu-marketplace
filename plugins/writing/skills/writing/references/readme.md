# README: 독자가 이해하고 실행하게 쓴다

README는 독자가 이 프로젝트가 무엇인지, 자기 상황에 맞는지, 다음에 무엇을 해야 하는지 판단하게 한다. 기존 README의 일부만 고치는 요청이면 해당 구간과 필요한 연결 문장만 수정한다. 프로젝트가 지정한 양식·제목·지원 범위·명령을 보존하고 아래 구성을 일괄 덧붙이지 않는다.

## 첫 화면에서 다음 행동까지 연결한다

첫 문단에 프로젝트의 역할과 대상 독자 또는 해결하는 문제를 쓴다. “강력하고 유연한 도구”처럼 판단 근거가 없는 수식어 대신 입력과 결과, 필요한 경우 적용 범위를 설명한다. 중요한 제한이 사용 여부를 바꾸면 시작 전에 알린다.

빠른 시작은 가장 짧은 정상 경로 하나를 보여 준다. 실행에 필요한 환경·설치·입력 → 명령이나 코드 → 기대 결과 순서로 구성한다. 단계마다 어디서 무엇을 실행하는지 알 수 있게 쓰고, 명령 앞에는 목적을, 뒤에는 성공을 알아볼 수 있는 결과를 둔다. 실제로 확인된 명령·버전·출력만 사실로 적으며, 자료에 없는 설치법이나 지원 환경을 만들어 내지 않는다.

상세 설정·API 전체·운영 설명은 빠른 시작을 막지 않는 위치에 두거나 연결한다. 연결 문구는 “여기” 대신 독자가 얻는 내용으로 쓴다. 설치 안내를 따라야 하는 사용자와 저장소를 수정하려는 기여자의 절차는 대상에 맞는 위치에 둔다. 라이브러리·CLI·서비스에 같은 제목 목록을 강제하지 않는다.

## 짧은 사례: 명령 다음에 결과를 보여 준다

아래는 가상의 CLI를 위한 로컬 예시다. CLI 설치 완료, 저장소 루트의 `sample.csv`, 아래 출력이 확인됐다는 입력을 가정한다. 실제 README에는 해당 프로젝트의 확인된 사실을 사용한다.

약한 안내는 “설정 후 `csv-inspect sample.csv`를 실행하세요”로 끝나서 무엇을 확인했는지 알 수 없다.

```markdown
# CSV Inspect

CSV 파일의 열 이름과 행 수를 확인하는 CLI입니다. 데이터를 가져오기 전에 파일 구조를 확인할 때 사용합니다.

## 빠른 시작

CLI를 설치했다면 저장소 루트에서 예제 파일을 검사하세요.

    csv-inspect sample.csv

다음 결과가 나오면 두 열과 10개 데이터 행을 읽은 것입니다.

    Columns: name, email
    Rows: 10
```

이 구조는 목적 → 준비된 입력 → 실행 → 결과의 의미를 연결한다. 출력 예시는 확인된 범위의 예시이며 모든 입력의 결과를 약속하지 않는다. 설치 안내가 필요한 실제 문서에서는 확인된 선행 절차를 앞에 연결한다.

한주연의 한국어 원문 [그 많은 개발 문서는 누가 다 만들었을까 (2)](https://toss.tech/article/tech-writer-2)는 설명·예제·미리보기를 연결하고 개발자가 결과를 보며 학습하도록 문서를 개선한 실무 사례다. 위 CLI 문안은 그 원문의 인용이 아닌 별도 예시다. 제품 문서의 저자 경험을 참고한 것이므로 모든 README에 미리보기나 샌드박스를 요구하지 않는다.
