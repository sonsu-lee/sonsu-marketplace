# README: 독자가 이해하고 실행하게 쓴다

README는 용도와 적합성을 판단하고 첫 사용과 상세 문서로 연결하는 입구다. 사용자 지정 양식·포함 내용과 프로젝트 관례를 우선한다. 부분 수정은 해당 구간과 필요한 연결에 한정하며 [보존 지침](integrity.md)과 [구성 지침](composition.md)을 따른다.

## 표준 구성

[GitHub의 README 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)와 [standard-readme](https://github.com/RichardLitt/standard-readme/blob/main/spec.md)를 README의 진입점 역할에 맞게 번안한 구성이다. 제목은 README 언어로 쓰고, 선택 항목은 비어 있으면 생략한다.

1. **제목**: 프로젝트 이름. 언어 링크·배지는 필요할 때 바로 아래에 둔다.
2. **한 줄 설명**: 별도 제목 없이 역할과 대상 또는 해결할 문제를 쓴다.
3. **짧은 긴 설명(선택)**: 별도 제목 없이 릴리스 상태·사용 대상·사용 여부를 바꾸는 핵심 제약을 알린다.
4. **설치**: 필요한 환경과 확인된 설치 절차를 쓴다.
5. **사용**: 가장 짧은 정상 경로 하나와 기대 결과를 보여 준다.
6. **필요한 추가 절(선택)**: 첫 사용에 필요한 내용만 둔다.
7. **문서·도움을 받을 곳**: 상세 문서와 실제 지원 경로를 연결한다.
8. **기여**: 참여 방법과 개발 가이드로 연결한다.
9. **라이선스**: 실제 조건과 원문 링크를 마지막에 둔다. 확인되지 않은 라이선스를 만들지 않는다.

목차는 긴 README에서만 둔다(standard-readme는 100줄 이상을 기준으로 삼는다). GitHub의 자동 개요로 충분하면 수동 목차를 중복하지 않는다. 분량을 채우려고 절이나 자리표시자를 만들지 않는다.

## README에 두지 않는 것

다음 내용은 담당 문서에 두고 README에는 필요한 경우 한 줄 링크만 남긴다.

- 내부 구조·아키텍처·생성/배포 메커니즘 → 아키텍처 문서
- 이전 버전에서 옮겨 오는 절차와 변경 이력 → migration 문서·CHANGELOG
- 모든 옵션·설정 레퍼런스 → 참조 문서
- 첫 실행 이후의 문제 해결 → 문제 해결 가이드·런북
- 하위 패키지·모듈별 상세 사용법 → 각 하위 README
- 다른 구성 요소와의 조합 규칙 → 조합·라우팅 문서
- 설계 이유 → ADR
- 평가·검증 결과 → 평가 문서·작업 보고
- 개발자 로컬 실험 주의사항 → 기여·개발 가이드

일회성 검사 결과나 작업 경위만 옮기려고 새 문서를 만들지 않는다.

## 주요 안내가 달라질 때만 갱신한다

용도·주요 기능·대상·설치·첫 사용·핵심 제약·문서 진입 경로 등 표준 절의 내용이 달라질 때만 README를 고친다. 작업 완료나 검사 실행 자체는 갱신 이유가 아니다. 새 구성 요소는 목적과 링크를 담은 표 한 행 또는 링크 한 줄까지만 추가하고, 설명이 짧은 한 문단을 넘으면 담당 문서로 옮긴다.

모노레포·플러그인 모음의 루트에는 구성 요소별 한 줄 목적과 링크를 두고, 하위 README도 같은 골격을 따른다. 다국어판은 절과 범위를 맞추되 저장소의 기존 파일명을 유지한다.

선택적 로그 보관 옵션은 기존 설정 참조에 반영한다. 첫 실행이 같으면 README는 유지하고, 최소 실행 환경이 바뀌면 설치·빠른 시작을 고친다. 내부 리팩터링과 일회성 테스트 결과는 작업 보고에 남긴다. 주 독자가 기여자라면 개발 절차가 첫 사용일 수 있지만 사용자 설치와 구분한다.

## 빠른 시작은 명령 다음에 결과를 보여 준다

환경·설치·입력 → 명령이나 코드 → 기대 결과 순서로 쓴다. 실행 위치와 목적, 성공을 알아볼 결과를 밝힌다. 명령·버전·출력·지원 환경은 확인된 자료에 근거한다.

다음은 가상 CLI가 설치되어 있고 저장소 루트에 `sample.csv`가 있으며 아래 출력을 확인했다고 가정한 로컬 예시다. 실제 README에는 확인된 사실을 쓴다. “설정 후 실행하세요”만으로 끝내지 않는다.

```markdown
# CSV Inspect

CSV 파일의 열 이름과 행 수를 확인하는 CLI입니다. 데이터를 가져오기 전에 파일 구조를 확인할 때 사용합니다.

## 사용

CLI를 설치했다면 저장소 루트에서 예제 파일을 검사하세요.

    csv-inspect sample.csv

다음 결과가 나오면 두 열과 10개 데이터 행을 읽은 것입니다.

    Columns: name, email
    Rows: 10
```

목적 → 입력 → 실행 → 결과의 의미를 연결한다. 설치 안내가 필요하면 확인된 절차를 앞에 둔다.

한주연의 [그 많은 개발 문서는 누가 다 만들었을까 (2)](https://toss.tech/article/tech-writer-2)는 설명·예제·미리보기를 연결한 실무 사례다. 링크만 참고하며 위 CLI 문안은 별도로 만들었다. 미리보기·샌드박스의 필요성은 프로젝트에 따라 판단한다.
