# 문서 유형

장문의 새 문서를 쓰기 전에 독자가 이 문서로 무엇을 하려는지 정하고, 그 필요에 맞는 유형 하나를 고른다.

## 독자의 필요로 유형을 고른다

| 독자의 필요 | 유형 | 문서가 하는 일 |
| --- | --- | --- |
| 처음 배운다 | 튜토리얼 | 정해진 경로를 따라가며 한 번 성공하게 한다 |
| 특정 작업을 끝낸다 | how-to | 이미 아는 독자가 목표까지 가는 단계를 준다 |
| 값을 찾아본다 | 참조 | 옵션·필드·명령을 빠짐없이, 같은 형식으로 나열한다 |
| 왜 그런지 이해한다 | 설명 | 배경·설계 이유·대안과의 차이를 풀어 쓴다 |

한 문서에는 한 유형만 담는다. 튜토리얼 중간에 옵션 전체 목록을 넣거나 참조 문서에 설계 배경을 길게 쓰면, 두 독자 모두 필요한 부분을 찾기 어려워진다. 다른 유형이 필요하면 별도 문서로 나누고 링크한다.

이 네 갈래 구분은 [Diátaxis](https://diataxis.fr/)의 개념을 참고했다.

## 사내 문서 골격

사내 문서는 읽는 사람이 먼저 결론을 알고 필요할 때 근거로 내려가도록 결론을 앞에 둔다.

| 문서 | 순서 |
| --- | --- |
| 제안서 | 결론과 요청 → 배경 → 검토한 대안 → 비용·위험 → 결정 요청 |
| 보고서 | 결론 → 근거 → 의미 → 다음 행동 |
| 회의록 | 결정 → 담당·기한 → 미결 사항 |
| 기술 결정 메모 | 맥락 → 목표·비목표 → 대안 → 결정 → 결과 |

골격은 순서의 기준이다. 내용이 없는 항목은 만들지 않는다. 결론을 앞에 두는 구성은 [Barbara Minto의 피라미드 원칙](https://www.barbaraminto.com/concept)을, 기술 결정 메모의 항목은 [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)을 참고했다.
