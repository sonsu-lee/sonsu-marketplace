# 동료에게 보내는 설명과 요청

독자가 무엇을 이해하거나 결정하거나 해 주어야 하는지 먼저 드러낸다. 필요한 배경과 근거를 이어 쓰고, 답하는 데 필요한 질문이나 선택지를 구체화한다. 원문의 의도·관계·정중함과 확신 정도를 보존하며 메시지 초안 작성이 전송 권한을 뜻하지는 않는다.

## 요청·결정과 근거를 연결한다

요청은 상대가 할 일을, 결정 공유는 합의된 결론과 영향 범위를 먼저 쓴다. 맥락이 없으면 오해할 수 있는 경우에는 필요한 배경 한 문장을 먼저 둔다. 과거 작업을 모두 나열하지 말고 현재 판단에 필요한 관찰·제약·근거만 연결한다. 긴 로그·논의는 결론을 요약한 뒤 관련 위치를 연결한다.

관찰과 해석, 질문과 지시, 필수 수정과 제안을 구분한다. 원문에 없는 담당자·기한·긴급도·승인·완료 사실을 넣지 않는다. 일정이 실제 의사결정 조건이면 이미 정해진 기한과 이유를 명시한다. 여러 독립 요청은 목록으로 나누되 한 가지 요청에 형식적인 제목 목록을 강제하지 않는다.

## 짧은 사례: 모호한 확인 요청을 답할 수 있게 쓴다

다음은 “실패한 두 요청 모두 날짜가 비어 있고 400 응답을 받았으며, 빈 날짜의 허용 여부는 아직 정하지 않았다”는 입력을 가정한 로컬 예시다.

- 수정 전: “날짜 쪽에서 계속 실패하는데 확인 부탁드립니다.”
- 수정 후: “빈 날짜를 오류로 처리하는 게 맞는지 확인 부탁드립니다. 실패한 두 요청 모두 날짜가 비어 있고 400 응답을 받았습니다. 빈 날짜의 허용 여부를 정하면 현재 응답을 유지할지 수정할지 판단할 수 있습니다.”

답할 질문 → 관찰 근거 → 답이 필요한 이유 순서다. 실패를 서버 버그로 단정하거나 상대에게 구현 방법을 지정하지 않는다. 반대로 수정이 이미 합의된 요청을 단순한 의견 문의로 약화하지 않는다.

결정 공유라면 결론과 실제 상태를 구분한다. 예를 들어 합의가 “빈 날짜를 허용하지 않고 안내 문구만 고친다”라면 “빈 날짜는 계속 오류로 처리하고 안내 문구를 수정하기로 했습니다”라고 쓴다. 아직 작업하지 않았다면 “수정했습니다”로 바꾸지 않는다.

정진규의 한국어 원문 [코드 리뷰 in 뱅크샐러드 개발 문화](https://blog.banksalad.com/tech/banksalad-code-review-culture/)는 리뷰 의견의 중요도와 처리 기한을 명시하는 팀 규칙을 설명한다. 여기서 참고할 점은 상대가 요청의 강도를 추측하지 않게 한다는 것이다. 이 실무 사례의 표기법을 모든 팀에 적용하거나 원문에 없는 우선순위·기한을 만드는 근거로 사용하지 않는다.

일본어 원문 [LINEヤフー의 리뷰 메시지 개선 예](https://techblog.lycorp.co.jp/ja/20240516a)는
긴 배경 뒤의 요청을 앞으로 옮기고 코드 예와 이유를 이어 붙인다. 저자가 제시한 개선 사례이며
독자 실험은 아니다. 교육 목적의 설명에서는 전제와 예를 거쳐 결론에 도달할 수 있다는 원문의
예외도 유지한다. “항상 결론부터”라는 공통 규칙으로 확대하지 않는다.
