# 동료에게 보내는 설명과 요청

독자가 이해·결정·행동할 내용을 드러내고, 필요한 배경과 근거를 연결한다. 원문의 의도·관계·정중함과 확신 정도를 보존한다. 초안 작성과 전송 권한은 구분한다.

## 요청·결정과 근거를 연결한다

요청은 상대가 할 일을, 결정 공유는 합의된 결론과 영향 범위를 먼저 쓴다. 맥락이 없으면 오해할 수 있는 경우에는 필요한 배경 한 문장을 앞에 둔다. 현재 판단에 필요한 관찰·제약·근거를 연결하고, 긴 로그·논의는 결론을 요약한 뒤 해당 위치를 링크한다.

관찰과 해석, 질문과 지시, 필수 수정과 제안을 구분한다. 담당자·기한·긴급도·승인·완료 상태는 확인된 내용만 쓴다. 일정이 의사결정 조건이면 정해진 기한과 이유를 밝힌다. 여러 독립 요청은 목록으로 나누고, 한 가지 요청은 연결된 짧은 글로 쓴다.

## 짧은 사례: 모호한 확인 요청을 답할 수 있게 쓴다

다음은 “실패한 두 요청 모두 날짜가 비어 있고 400 응답을 받았으며, 빈 날짜의 허용 여부는 아직 정하지 않았다”는 입력을 가정한 로컬 예시다.

- 수정 전: “날짜 쪽에서 계속 실패하는데 확인 부탁드립니다.”
- 수정 후: “빈 날짜를 오류로 처리하는 게 맞는지 확인 부탁드립니다. 실패한 두 요청 모두 날짜가 비어 있고 400 응답을 받았습니다. 빈 날짜의 허용 여부를 정하면 현재 응답을 유지할지 수정할지 판단할 수 있습니다.”

답할 질문 → 관찰 근거 → 답이 필요한 이유 순서로 미확인 원인과 미결정을 남긴다. 수정이 이미 합의된 요청이라면 그 요청의 강도를 유지한다.

결정 공유라면 결론과 실제 상태를 구분한다. 예를 들어 합의가 “빈 날짜를 허용하지 않고 안내 문구만 고친다”라면 “빈 날짜는 계속 오류로 처리하고 안내 문구를 수정하기로 했습니다”라고 쓴다. 아직 작업하지 않았다면 “수정했습니다”로 바꾸지 않는다.

정진규의 한국어 원문 [코드 리뷰 in 뱅크샐러드 개발 문화](https://blog.banksalad.com/tech/banksalad-code-review-culture/)는 리뷰 의견의 중요도와 처리 기한을 명시하는 팀 규칙을 설명한다. 요청의 강도를 분명하게 전달하는 사례이며, 구체적인 표기법·우선순위·기한은 해당 팀의 합의를 따른다.

일본어 원문 [LINEヤフー의 리뷰 메시지 개선 예](https://techblog.lycorp.co.jp/ja/20240516a)는
긴 배경 뒤의 요청을 앞으로 옮기고 코드 예와 이유를 이어 붙인 저자의 개선 사례다. 독자 실험은
아니며, 같은 원문은 교육 목적의 설명에서 전제와 예를 거쳐 결론에 도달하는 순서도 허용한다.
