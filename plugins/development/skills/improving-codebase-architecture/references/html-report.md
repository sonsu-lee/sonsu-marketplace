# Architecture report

When a visual HTML report and its file creation are authorized, compare the
candidates with before/after diagrams. A report card should identify affected
files, the observed problem, proposed change, locality and leverage benefits,
test implications, recommendation strength, and any evidence-backed ADR
conflict. End with the top recommendation and ask which candidate to explore.
Use dependency or flow diagrams for graph-shaped relationships and a suitable
visual for module depth when that better explains the change. Do not open a
browser or write a report without the applicable permission. Respect the target
project's visual and accessibility constraints.
