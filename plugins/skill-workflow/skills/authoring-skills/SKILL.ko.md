# 스킬 작성

> 영문 정본: [SKILL.md](SKILL.md) (`5b362ef` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

하나의 일관된 작업에 필요한 판단과 최소한의 절차를 가르친다. 기계적인 실행과
검사는 기존 도구에 맡긴다. 스킬은 도구 사용법을 빠짐없이 적은 매뉴얼이 아니다.
대상 프로젝트의 작성 요구사항을 따른다.

## 작업과 부가 가치 정하기

스킬은 실제 요청, 성공한 작업, 수정 사항, 프로젝트 산출물에 근거해 만든다. 원하는
결과, 적용되는 때, 제외되는 인접 작업을 분명히 한다. 사용 가능한 맥락으로 해결할
수 없는 중대한 공백에 대해서만 묻는다.

텍스트로만 제안하라는 요청에는 텍스트로 답한다. 쓰기가 금지된 상황에서는 임시
파일을 포함해 어떤 파일도 만들지 않는다. 작성 중 수행하는 검사는 쓰기, 설치,
게시 권한을 주지 않는다.

이 지침을 빼면 의미 있는 실수가 생기는가? 도메인 지식, 프로젝트 관례, 판단 기준,
자명하지 않은 제약은 남긴다. 일반 상식과 평범한 도구 사용법은 뺀다. 확신이 없는
삭제는 세부 내용이 많을수록 안전하다고 가정하지 말고 직접 시험해 본다.

재사용 가능한 하나의 작업 단위로 범위를 잡는다. 독립적으로 쓸모 있는 워크플로
단위로 스킬을 나누고, 원문 문서의 챕터 단위로 나누지 않는다. 목차를 채우려고 없는
전문성을 지어내지 않는다.

## 대상 환경 파악

요청과 프로젝트 근거에서 의도한 사용 대상을 파악한다. 작성 중인 클라이언트나
이식 가능한 매니페스트만으로 판단하지 않는다. 명시된 대상이 우선한다. 해당하는
클라이언트 레퍼런스만 읽는다.

| 의도한 사용 대상 | 조건부 레퍼런스 |
| --- | --- |
| omp | [omp 작성 시 고려사항](references/omp.md) |
| Claude Code, claude.ai, Claude API | [Claude 작성 고려사항](references/claude.md) |
| Codex | [Codex 작성 시 고려사항](references/codex.md) |

대상이 확정되지 않았다면 이식 가능한 상태를 유지하고, 모든 클라이언트 레퍼런스를
로드하거나 클라이언트 메타데이터를 추가하지 않는다. 선택이 필수 기능에 영향을 줄
때만 묻는다. 공유 스킬이라면 명시된 각 대상을 확인하고, 공유 내용은 표준으로
유지하며, 서로 호환되지 않는 확장을 섞지 말고 각 클라이언트를 따로 검증한다.

## 책임을 알맞은 곳에 두기

- **SKILL.md:** 일반적인 실행에 필요한 목적, 판단 기준, 기본값, 최소 워크플로,
  중대한 제약.
- **references/:** 명시한 조건에서만 필요한 작업별 세부 내용. 각 파일을 언제 읽을지
  적는다. 본문에서 빼고도 항상 로드한다면 컨텍스트 비용이 줄지 않는다.
- **설정과 자산:** 실행 가능한 규칙 값과 재사용 가능한 출력 구조. 짧은 규칙은
  생성을 안내할 수 있지만, 검증기의 구현을 글로 복제하지 않는다.
- **기존 도구:** 기계적 실행과 결정적 검사. 새 래퍼보다 직접 호출을 선호한다.
- **scripts/:** 기존 도구와 단순한 호출로는 충분히 다룰 수 없는 반복 로직. 실제
  실행에서 반복적으로 다시 만들어지거나 명령 구성 오류가 중대하게 나타날 때
  번들하며, 디렉터리를 추가하려고 만들지 않는다.

설치, 마켓플레이스 등록, 평가 절차는 그것이 스킬의 작업이 아닌 한 프로젝트 문서에
둔다. 평가 케이스는 스킬의 `evals/` 디렉터리에 둔다. 지원 파일은 필요할 때만
만들고, 빈 디렉터리로 구성된 표준 세트를 만들지 않는다.

## 실행 가능한 지침 쓰기

메타데이터와 레이아웃은 [Agent Skills 명세][specification]를 사용한다. 명세의
크기 안내는 목표도, 로딩에 대한 보증도 아니다. 클라이언트의 한도는 해당
레퍼런스에서 확인한다. `compatibility`는 실제 요구사항에만 설정한다.

사용자 의도, 암묵적 사용, 인접 작업과의 경계를 설명한다. 구현 단계나 실패한 개별
프롬프트용 키워드가 아니라 핵심 사용 사례를 앞에 둔다. 클라이언트의 표현 선호는
공통 형식 규칙이 아니다.

명확한 제목과 직접적인 표현으로 조건, 제약, 판단 기준을 쉽게 구분할 수 있게 한다.
최소 길이가 아니라 충분한 지침을 목표로 하고, 올바른 판단에 필요한 정보는
보존한다.

입력에서 관찰 가능한 결과까지 짧은 경로를 제시한다. 기본값을 고르고, 유용하면
이유를 설명하며, 달라지면 정확성이나 안전이 위험해지는 곳에서는 정확한 단계를
지정한다. 유연한 판단을 경직된 체크리스트로 바꾸지 않는다.

기본값과 구속력 있는 호스트, 보안, 프로젝트, 사용자 제약을 구분하고, 기본값이
언제 물러나는지 적는다. 스킬이 권한이 있는 작업을 멈추거나 다른 방향으로 돌릴
때는 근거가 되는 지침을 인용한다. 승인을 지어내거나 권한 경계를 약화하지 않는다.

예시는 모호함을 해소할 때만 쓴다. 중대한 주의점은 에이전트가 실수하기 전에 보이게
두고, 조건부 레퍼런스에는 알아볼 수 있는 트리거를 둔다.

## 계약을 잃지 않고 실행 위임하기

대상 저장소의 도구, 버전, 설정을 먼저 재사용한다. 실행 환경이 없다면 버전을 고정한
적절한 기존 CLI를 사용한다. 설정이 없는 것과 실행기가 없는 것은 별개의 문제다.
기존 도구가 실패했다고 해서 다른 검증기로 우회해도 된다는 뜻은 아니다. 스킬을 쓰기
위해 훅을 설치하거나 프로젝트 설정을 바꾸지 않는다.

도구의 트리거, 정확한 입력, 성공 근거, 남는 판단을 명시한다. 기계적 통과가 의미적
정확성을 증명하지는 않는다. 일반적인 플래그와 플랫폼별 예외 전체는 도구 문서에
둔다.

번들 스크립트는 [Using scripts][scripts]를 읽는다. 비대화형 입력, 도움이 되는
오류, 의미 있는 종료 상태, 제한되거나 구조화된 출력을 제공한다. 인가와 검증을
구분하고 부수 효과를 공개한다. 지침은 훅, CI 강제, 권한 경계가 아니다.

## 검증과 개선

형식, 탐색, 메인 프롬프트의 완전한 로딩은 새 파서가 아니라 프로젝트 절차와 공식
검증기로 확인한다. 이 검사들이 스킬이 도움이 된다는 것을 보여 주지는 않는다.

동작은 [Agent Skills 루프][evaluation]로 확인한다. 스킬의 `evals/evals.json`에
현실적인 프롬프트를 두고, 스킬이 있을 때와 없을 때 또는 이전 버전으로 새
컨텍스트에서 실행한 뒤 단언 채점, 벤치마크, 사람의 리뷰를 거친다. 검사와 실행기를
고를 때는 [평가 방식 선택](references/evaluation.md)을 읽는다.

실패한 단언, 피드백, 트랜스크립트로 수정한다. 불필요한 레퍼런스, 반복되는 헬퍼,
관련 없는 검사, 범위 확장을 찾아본다. 관찰, 스킬의 책임, 수정 방안을 따로
판단한다. 도구 예시가 없다는 것만으로는 결함이 아니다. 반복되는 실패는 삭제를
포함해 충분한 가장 작은 변경으로 일반화한다.

새 스킬이나 동작이 바뀌는 수정이라면, 서식만 바꾼 수정이거나 본인이 그 리뷰어인
경우가 아닌 한 전달 전에 스킬 기준에 따른 독립 리뷰를 받는다. 새 리뷰어에게는
목적, 사용 대상, 변경된 파일, 요구사항, 리뷰 질문을 주고 작성 근거는 주지 않는다.
실행이나 리뷰의 디스패치는 하나의 컨트롤러가 맡으며 중복하지 않는다. omp에서는
`skill-workflow-reviewer`를 쓰고, Codex나 Claude Code에서는 이 `SKILL.md`의 절대
경로를 준 범용 워커를 쓴다. 리뷰를 받을 수 없으면 그 사실을 밝히고, 지적은 검증한
뒤 수정에 반영한다. 리뷰는 동작 검사를 대신하지 않는다.

요청받은 스킬이나 수정을, 실제로 수행한 검사와 중요한 한계와 함께 전달한다. 작성
단계의 평가는 결과 스킬의 사용자가 매 작업마다 수행해야 하는 절차와 분리해 둔다.
