# 스킬 작성

> 영문 정본: [SKILL.md](SKILL.md) (`57da0f4` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

스킬은 하나의 일관된 작업에 필요한 판단과 최소한의 절차를 에이전트에게 가르친다.
도구 설명서가 아니다. 기계적인 실행과 검사는 기존 도구에 맡긴다. 대상 프로젝트의
작성 규칙이 우선한다.

## 작업 흐름

1. **작업 근거 잡기:** 실제 요청, 성공한 작업, 수정 사항, 프로젝트 자료에서
   시작한다. 결과, 적용 조건, 제외할 인접 작업을 정한다. 맥락으로 답할 수 없는
   중요한 공백만 묻는다.
2. **범위를 하나로:** 스킬 하나에 재사용 가능한 작업 단위 하나. 원문 문서의 장이
   아니라 독립적으로 쓸모 있는 작업 흐름 단위로 나눈다.
3. **사용 클라이언트 확인:** 실행 중인 클라이언트가 아니라 요청과 프로젝트 근거로
   정한다. 해당하는 참고 문서만 읽는다.

   | 사용 클라이언트 | 참고 문서 |
   | --- | --- |
   | omp | [omp](references/omp.md) |
   | Claude Code, claude.ai, Claude API | [Claude](references/claude.md) |
   | Codex | [Codex](references/codex.md) |

   대상이 정해지지 않았으면 이식 가능하게 두고 클라이언트 메타데이터를 넣지 않는다.
4. **실수를 막는 것만 남기기:** 지시마다 빼면 의미 있는 실수가 생기는지 묻는다.
   도메인 지식, 프로젝트 관례, 판단 기준, 드러나지 않는 제약은 남기고 일반 지식과
   통상적인 도구 사용법은 뺀다. 불확실하면 시험한다.
5. **책임 배치**(아래) 후 지침을 쓴다.
6. **검증과 개선**(아래).

## 책임 배치

- **SKILL.md:** 목적, 판단 기준, 기본값, 최소 작업 흐름, 매번 필요한 제약.
- **references/:** 특정 조건에서만 필요한 세부. 언제 읽는지 적는다.
- **assets/와 설정:** 재사용 출력 구조와 실행 가능한 규칙 값. 검증기의 로직을
  글로 다시 쓰지 않는다.
- **기존 도구:** 기계적 실행과 결정론적 검사. 새 래퍼 없이 직접 호출한다.
- **scripts/:** 실제 실행에서 에이전트가 반복해서 다시 만들거나 틀리는 로직만.
  [스크립트 사용][scripts] 참고.
- **evals/:** 평가 케이스. 설치, 등록, 평가 절차는 프로젝트 문서에 둔다.

## 지침 작성

- 메타데이터와 구조는 [Agent Skills 명세][specification]를 따른다.
  `compatibility`는 실제 요구사항일 때만 쓴다.
- **description:** 사용자 의도, 암묵적 사용, 인접 작업과의 경계. 핵심 용도를
  먼저 쓴다. 실패한 프롬프트 하나를 위한 키워드는 넣지 않는다.
- **본문:** 명확한 소제목과 직접적인 문장. 순서가 있는 작업은 번호 목록, 독립된
  규칙은 목록, 이유가 필요한 판단만 줄글로 쓴다.
- **기본값:** 하나를 정하고 대안은 짧게 언급한다. 변형이 정확성이나 안전을
  해칠 때만 정확히 지시한다.
- **제약:** 기본값과 호스트·보안·프로젝트·사용자의 구속 제약을 구분하고, 기본값이
  양보하는 조건을 적는다. 승인을 지어내거나 권한 경계를 약하게 하지 않는다.
- **주의할 점:** 드러나지 않는 사실은 에이전트가 실수하기 전에 읽는 곳에 둔다.
  조건부 참고 문서에는 알아볼 수 있는 계기를 준다.
- **예시:** 모호함을 풀 때만.

## 도구에 위임

- 대상 저장소의 도구, 버전, 설정을 먼저 쓴다. 설정이 없으면 버전을 고정한 기존
  CLI를 쓴다.
- 도구마다 실행 계기, 정확한 입력, 성공 근거, 에이전트에게 남는 판단을 적는다.
  기계적 성공은 의미상 정확성이 아니다.
- 번들 스크립트는 비대화식 입력, 도움이 되는 오류, 의미 있는 종료 코드를 갖추고
  부작용을 밝힌다.

## 검증과 개선

1. **형식과 로딩:** 프로젝트 검사와 공식 검증기를 실행한다. 스킬이 도움이 되는지는
   보여 주지 않는다.
2. **동작:** `evals/evals.json`으로 [Agent Skills 평가 루프][evaluation]를 스킬
   유무 또는 이전 버전과 비교해 실행한다. 검사와 실행기는
   [평가 선택](references/evaluation.md)을 읽고 고른다.
3. **개선:** 실패한 assertion, 피드백, transcript로 고친다. 반복되는 실패는 삭제를
   포함한 가장 작은 변경으로 일반화한다.
4. **리뷰:** 새 스킬이나 동작 변경은 독립적인 스킬 기준 리뷰를 받는다. 목적,
   사용 클라이언트, 바뀐 파일, 요구사항, 리뷰 질문을 주고 작성자의 근거는 주지
   않는다. omp는 `skill-workflow-reviewer`, Codex나 Claude Code는 이 파일의 절대
   경로를 받은 일반 작업자를 쓴다. 지적은 확인한 뒤 반영한다.
5. **보고:** 실제로 수행한 검사와 한계를 보고한다.

## 주의할 점

- 항상 읽히는 참고 문서로 옮기면 컨텍스트가 줄지 않는다.
- 명세의 크기 지침은 로딩을 보장하지 않는다. 클라이언트 한도는 해당 참고 문서에서
  확인한다.
- 작성 검사는 쓰기, 설치, 게시 권한을 주지 않는다. 쓰기가 금지되면 제안을 글로
  돌려주고 파일을 만들지 않는다.
- 스킬이 작업을 멈추거나 돌릴 때는 그 근거가 되는 지시를 인용한다.
