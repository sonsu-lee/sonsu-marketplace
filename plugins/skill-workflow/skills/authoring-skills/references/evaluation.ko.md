# 평가 방식 선택

> 영문 정본: [evaluation.md](evaluation.md) (`fe462ed` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

형식, 탐색, 완전한 프롬프트 로딩, 출력 품질, 활성화는 서로 다른 주장이며, 하나에
대한 근거가 다른 것을 증명하지 않는다. 변경이 영향을 주는 동작에 맞는 검사를
고른다.

## 변경에 맞는 검사 고르기

- **메타데이터 또는 패키징:** 공식 형식 검증기와 대상 클라이언트의 탐색 검사를
  쓴다. 이와 별도로 설치된 스킬을 호출해 이벤트와 주입된 내용을 확인하고, 메인
  파일이 경고 없이 완전히 로드되는지 본다. 클라이언트의 실제 호출 이름과 버전별
  한도를 사용한다. 탐색은 메타데이터만 확인해 본문 잘림을 놓칠 수 있다.
- **작업 지침:** 스킬의 `evals/evals.json`에 대해 출력 품질 루프를 실행한다.
  스킬이 있을 때와 없을 때, 또는 이전 버전과 비교한다. 최종 답변만이 아니라
  행동과 트랜스크립트를 확인한다.
- **도구 또는 설정 동작:** 대표적인 유효 입력과 무효 입력으로 실제 도구를 실행한다.
  기계적 규칙에는 결정적 검사를 쓴다. LLM의 의견은 검증기 결과를 대신하지 못한다.
- **description 또는 범위:** 이전 description과 새 description에 대해
  `evals/eval_queries.json`으로 트리거 여부를 측정하고, 클라이언트가 실제로 스킬을
  로드하는지 관찰한다. 모델이 스킬을 쓰겠다고 말하는 것은 활성화의 근거가 아니다.
- **서식만 바꾼 수정:** 동작 벤치마크를 억지로 만들지 않는다.

수동 검사는 격리된 작업 공간에서 실행하고, 티켓, 풀 리퀘스트, 메시지 같은 테스트
산출물을 실제 프로젝트에 게시하지 않는다.

로더에 맞추려고 내용을 나눌 때는 핵심 워크플로와 안전 지침을 메인 파일에 두고,
옮긴 세부 내용에는 명시적인 로딩 조건을 준다. 옮긴 내용이 필요한 작업을 다루는
평가를 추가하고, 그 레퍼런스를 읽는다는 단언을 넣는다. 크기 검사나 프롬프트 캡처는
레퍼런스 사용도 작업 성공도 증명하지 않는다.

## 클라이언트에 맞는 실행기 고르기

프로젝트에 기존 평가 설정이 있으면 그것을 쓰고, 없으면 다음을 쓴다.

- **Claude Code:** Anthropic의 [skill-creator 플러그인][creator].
- **omp와 Codex:** `evaluating-skills` 스킬.
- **그 밖의 클라이언트:** 클라이언트 자체 도구로 [출력][outputs] 가이드와
  [description][descriptions] 가이드를 따른다.

모든 실행기는 스킬 디렉터리의 `evals/evals.json`, `evals/eval_queries.json`,
`evals/files/`를 읽는다. 일부 클라이언트는 중첩된 스킬 파일을 등록하므로 `evals/`
아래에 `SKILL.md`라는 이름의 파일을 두지 않는다. 작업 공간은 설치된 패키지 밖에
둔다. 결과는 실행한 클라이언트, 모델, 노력 수준에서만 유효하다. 여러 클라이언트가
공유하는 description은 어느 클라이언트에서도 통과하던 트리거 쿼리를 잃어서는 안 된다.

## 발견한 내용을 작성에 반영하기

출력 실패, 사람의 피드백, 트레이스를 함께 사용한다. 더 분명한 판단 기준, 유용한
예시, 더 단순한 지침, 필요하다면 재사용 가능한 도구로 근본 원인을 해결한다. 안전
장치를 쌓기보다 효과 없는 요구사항을 제거하는 쪽을 택한다. 변경 후에는 영향받은
케이스를 다시 실행하고, 스모크 관찰은 비교 측정이나 반복 측정과 구분해 보고한다.
평가 픽스처와 보고서는 스킬의 일상적인 실행 경로 밖에 두고, 하위 사용자에게
작성용 벤치마크를 실행하게 하지 않는다.
