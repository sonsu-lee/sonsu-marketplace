# 리뷰 댓글

> 영문 정본: [review-comments.md](review-comments.md) (`7cd88a9` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

리뷰 댓글을 작성하거나 리뷰 게시를 명시적으로 요청받았을 때 이 참조를 읽는다.
일반적인 로컬 지적에는 불러올 필요가 없다.

## 지적은 보존하고 표현은 다듬기

리뷰어나 리뷰 과정이 아니라 코드에 대해 개발자에게 쓴다. 관련된 조건, 그
결과, 충분한 가장 작은 수정이나 필요한 결과를 밝힌다. 정확한 위치와 뒷받침하는
증거를 넣고, 문제를 이해할 만큼 주변 컨텍스트를 함께 적는다. 설계 우려는
가설적인 미래의 취향이 아니라 현재의 책임이나 유지보수 비용을 설명한다.
저장소의 댓글 형식과 공개 규칙을 따르고, 그렇지 않다면 평이하고 짧은 글을
쓴다.

정형화된 라벨이나 문구 틀 없이도 의도가 분명하게 드러나도록 쓴다.

- **버그**는 증거가 있는 결함과 무엇을 바꿔야 하는지를 밝힌다. 필수 수정을
  선택적인 제안으로 누그러뜨리거나 수사적인 질문 속에 숨기지 않는다. 트리거에
  대한 불확실성은 그대로 명시한다.
- **질문**은 소스, 호출자, 요구 사항, 기존 논의로도 해소되지 않은 중대한
  불확실성을 짚는다. 어떤 의도나 동작을 확인해야 하는지 밝힌다. 검증되지 않은
  버그를 확정된 것처럼 제시하지 않는다.
- **선택적 제안**은 현재 접근이 유효함을 인정하고 구체적인 이점을 밝힌다.
  비차단으로 표시한다. 취향뿐인 조언과 요청하지 않은 사소한 지적은 뺀다.
  관련된 기존 문제도 비차단이며, 이 변경이 만든 결함과 섞지 말고 따로 둔다.

코드 조건이 더 많은 정보를 주는 경우에는 "안전하다"나 "더 깔끔하다" 같은
모호한 형용사를 피한다. 저장소가 그 구조를 요구하지 않는 한 상투적인 제목,
형식적인 칭찬, 긴 서두를 생략한다. 댓글 본문에 신뢰도 점수를 넣거나 증거로
쓰지 않는다. 필요한 신뢰도와 정확성 필드는 네이티브 리뷰 보고서에 보존한다.
지적 할당량을 채우거나 더 확실하거나 더 공손하게 들리도록 증거를 고쳐 쓰지
않는다. 자연스러운 어조가 사람인 척하라는 뜻은 아니다. 개인적인 런타임 경험,
정체성, 독립적인 검증을 지어내지 않는다. 요구되는 AI 공개는 보존한다.
댓글 글을 쓰거나 고칠 때 해당 언어 스킬이 목록에 있으면 그것도 읽고, 이
리뷰 규칙을 유지한다. 언어 지침이 의무, 범위, 불확실성, 기술적 사실, 증거를
바꾸어서는 안 된다.

## 예시이며 지적이 아님

이 예시들은 지어낸 것이다. 표현을 보여 줄 뿐 링크된 프로젝트의 지적이나 필수
문구가 아니며, 어떤 점검이 실행되었다는 주장도 아니다.

**버그, 확인된 요구 사항과 추적한 호출 경로가 있는 경우:**

> With `readOnly` enabled, this branch still calls `saveSettings()`, so opening
> the preview overwrites the settings file. Skip the save on the read-only path;
> the preview needs to leave the file unchanged.

**질문, 의도가 아직 해소되지 않은 경우:**

> Is this frame selection meant to find the first user-authored frame? It now
> stops at the generated wrapper, which would change which location we show.

**선택적 제안, 현재의 유지보수 이점이 확인된 경우:**

> Non-blocking: both branches build the same error message. Building it once
> after the branch would leave one place to update the wording. The current
> behavior is correct.

첫 번째 예시는 실행으로 재현한 것이 아니라 추적한 부수 효과를 단언한다. 런타임
점검을 실제로 했다면 점검 내용과 관찰한 결과를 따로 밝힌다. 단지 의심하는 호출
경로를 그런 단언으로 바꾸지 않는다.

## 로컬 초안 또는 명시적 게시

사용자가 원격 게시를 명시적으로 허가하지 않는 한 결과를 로컬에 둔다. 초안
요청은 로컬 텍스트만 허용하며, 원격의 대기 리뷰는 허용하지 않는다. 소스를
수정하거나, 제안을 적용하거나, 커밋, 푸시, 승인하거나, `REQUEST_CHANGES`를
제출하지 않는다. 게시는 `COMMENT`를 쓰고 요청한 범위만 대상으로 한다. 지적
하나를 게시해도 된다는 허가가 보고서 전체를 게시해도 된다는 허가는 아니다.

허가된 GitHub 리뷰의 절차는 다음과 같다.

1. PR head SHA를 다시 읽어 고정된 리뷰 SHA와 비교한다. 이전 리뷰와 스레드를
   읽고, 근본 원인 기준으로 중복을 제거하며, 새로운 증거 없이 확정된 결정을
   다시 열지 않는다. head가 움직였다면 게시 전에 새 대상과 조정해야 한다.
   오래된 지적을 새 줄에 붙이지 않는다.
2. 저장소가 요구하는 인증된 GitHub 도구를 쓰고 그 스키마를 확인한다. GitHub
   MCP에서는 `pull_request_review_write`로 대기 리뷰를 만들고,
   인라인 댓글은 `add_comment_to_pending_review`로 추가한 뒤,
   `pull_request_review_write`로 이벤트 `COMMENT`와 함께 `submit_pending`
   한다. 허가된 지적은 모두 리뷰한 리비전에 고정해 하나의 통합 리뷰에 담는다.
   관련 없는 대기 리뷰를 재사용하거나 제출하지 않는다. 필요한 도구를 쓸 수
   없으면 도구를 조용히 바꾸거나 게시했다고 주장하지 말고 로컬 초안을 유지한
   채 차단 요인을 보고한다.
3. 제출 전에 head SHA를 다시 확인한다. 바뀌었다면 제출을 멈추고 이미 만들어진
   원격 대기 상태를 보고한다. 리뷰 사이클을 자동으로 다시 시작하거나 관련
   없는 초안을 삭제하지 않는다.
4. 결과로 생긴 리뷰와 댓글을 다시 읽고 링크, 제출된 상태, 빠진 항목을 보고한다.
   타임아웃이나 모호한 쓰기 응답은 실패의 증거가 아니다. 재시도하기 전에 원격
   상태를 확인한다. 쓰기를 무턱대고 반복하거나, 부분 리뷰를 완전한 것처럼
   제출하거나, 확인되지 않은 응답을 근거로 성공을 주장하지 않는다. 원격 상태를
   여전히 알 수 없으면 멈추고 그렇게 말한다.

## 지침의 근거가 된 공개 사례

이 발췌문들은 소통 방식의 선택을 보여 줄 뿐, 새 대상에 결함이 있다는 증거나 거기에
같은 구현을 강요할 권한이 아니다.

- [toss/slash #21](https://github.com/toss/slash/pull/21#discussion_r991756463)
  은 "안전하다"를 Web Storage를 쓸 수 없는 구체적인 환경으로 바꿨다. 모호한
  보증 대신 지원되는 조건을 명시한다.
- [vite #23744](https://github.com/vitejs/vite/pull/23744#discussion_r4268202745)
  는 감지가 "starts eagerly on import instead of when we call it"이라고
  설명하고 함수 호출을 유지하자고 제안한다. API 선택을 타이밍 효과와 연결하되
  원래 댓글의 불확실성을 보존한다.
- [vite #23741](https://github.com/vitejs/vite/pull/23741#discussion_r4269403491)
  은 의도가 "to find out the first user (authored) code"인지 묻는다. 막연한
  "왜?"라고 묻거나 뒷받침되지 않는 결함을 단언하지 말고 구체적인 목적을
  확인한다.
