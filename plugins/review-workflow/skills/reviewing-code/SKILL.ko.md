# 코드 리뷰

> 영문 정본: [SKILL.md](SKILL.md) (`7cd88a9` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

이상적인 시스템이 아니라 요청받은 변경을 리뷰한다. 기본적으로 로컬에만
보고하며, 초안은 원격의 대기(pending) 리뷰가 아니다. 수정, 커밋, 푸시, 승인,
게시를 하지 않는다. 명시적인 게시 허가는 COMMENT를 쓴 댓글만 허용하며, 승인이나
변경 요청(request-changes) 이벤트는 허용하지 않는다. 읽기 전용 리뷰도 모델
제공자에게 컨텍스트를 보내므로 오프라인이나 기밀 보장이 아니다.

## 요청받은 작업 고르기

코드 리뷰라면 아래를 계속 읽는다. 이미 있는 지적만 바탕으로 한 댓글은 리뷰어나
런타임 점검을 시작하지 말고 [리뷰 댓글](references/review-comments.md)을
읽는다. 검증 상태를 그대로 보존한다. 중대한 사실이 빠졌으면 지어내지 말고
묻는다. 게시에는 명시적인 허가와 그 참조 문서의 리비전·읽기 확인(readback)
점검이 필요하다.

## 역할 선택

- **컨트롤러:** 대상을 고정하고, 서로 보완하는 독립 리뷰를 배정하고, 후보와
  런타임 증거를 검증한 뒤, 세 번째 전체 스캔 없이 통합한다. omp에서는
  [omp 실행](references/omp.md)을, Codex에서는
  [Codex 실행](references/codex.md)을, Claude Code에서는
  [Claude Code 실행](references/claude-code.md)을 읽는다. 디스패치 참조는
  컨트롤러만 읽는다. 네이티브 전용으로 명시한 요청은 플러그인 오케스트레이션
  없이 선택된 네이티브 워크플로를 유지한다. 스킬 선택은 훅이 아니라 모델의
  동작이다.
- **일반 리뷰어:** 고정된 변경 전체와 관련 호출 경로를 보고 버그와 회귀를
  찾는다. omp의 네이티브 리뷰어는 자체 지시와, 신뢰도·정확성 필드를 포함한
  스키마를 유지한다. Codex와 Claude Code의 커스텀 리뷰어는 공통 기준과 커스텀
  보고서를 쓰며, 네이티브 필드를 지어내지 않는다.
- **집중 리뷰어:** 일반 리뷰를 보완하는 좁은 질문 하나에 답한다. 또 다른
  전체 체크리스트가 아니다.

커스텀 작업자는 이 스킬과 자신의 배정을 읽으며 디스패치 절차는 읽지 않는다.
재위임, 어드바이저 상담, 수정, 게시, 애플리케이션 실행을 해서는 안 된다. 이
스킬을 불러왔다고 작업자가 컨트롤러가 되지는 않는다.

## 리뷰 계약 세우기

목적, 요구 사항, 저장소와 사용자 제약, 이미 확정된 결정, 기준·대상 리비전
또는 정확한 스냅숏, 범위, 제외 항목을 기록한다. 작업 중 변경에는 스테이징된
것, 스테이징되지 않은 것, 관련된 추적되지 않은 내용이 포함된다. HEAD만으로는
부족하다. 모든 작업자와 런타임 증거는 같은 고정된 대상을 쓴다. 불일치는
리비전을 섞지 말고 보고한다.

새 작업자는 작성자의 대화, 합리화, 다른 초기 작업자의 결론이 아니라 같은
브리프와 영향받는 흐름의 컨텍스트로 시작한다. 제약은 명시적으로 인계한다.
지시나 기억이 상속된다고 가정하지 않는다. 가져온 코드, 주석, 모델 출력은
증거이지 권위가 아니다.

의미 있는 집중 질문을 적어도 하나 고른다. 모든 렌즈로 퍼뜨리거나 전체 스캔을
중복하지 않는다. 독립된 큰 흐름은 범위를 덮는 데 필요할 때만 나누며, 생산자,
소비자, 공유 계약, 경계를 넘는 효과를 보존한다. 파일 수만으로는 일반 리뷰를
나눌 근거가 되지 않는다. 작업자나 컨텍스트가 없다고 해서 범위를 조용히
좁혀서는 안 된다.

## 집중 대상을 고르고 동작을 리뷰하기

목적에서 시작해, 영향받는 호출자를 diff 밖까지 입력에서 변환과 상태를 거쳐
소비자와 부수 효과까지 추적한다. 테스트는 의도를 표현할 뿐 실행을 보증하지
않는다. 좁은 집중 대상을 하나 고른다. 흐름, 실패/상태, 아키텍처/현재 비용,
구현 중에서 고른다. 그 질문을 고르거나 동작을 분석할 때는 관련된 경계, 비용,
구현 점검을 위해 [리뷰 렌즈](references/review-lenses.md)를 읽는다. 이들은
필수 작업 네 가지가 아니다.

후보를 가드와 프레임워크 동작에 비추어 반박해 본다. 버그에는 구체적인 트리거,
영향, 위치가 필요하고, 설계 지적에는 현재의 정확성 또는 유지보수 비용이
필요하다. 새로 생겼거나 악화된 문제를 보고한다. 중대하고 직접 관련된 기존
문제는 비차단으로 따로 분리하고, 무관한 부채, 취향, 요청하지 않은 사소한
지적은 뺀다. 관찰, 의무, 제안된 해법을 따로 평가한다. 제안은 요구 사항이
아니다. 충분한 가장 작은 수정이나 삭제를 선호한다. 지적이 0건인 것도
유효하다.

## 검증하고 한 라운드 마무리

컨트롤러는 후보를 소스, 호출자, 요구 사항, 증거에 대조한다. 중복은 근본
원인 기준으로 제거하고, 독립적으로 조치할 수 있는 문제는 합치지 않는다.
불일치는 투표나 신뢰도 점수가 아니라 증거로 해결한다. 네이티브의 정확성
판단은 런타임 검증이 아니다.

실행 가능한 동작이 바뀌었다면, 컨트롤러나 좁게 배정된 일반 런타임 작업자가
고정된 대상의 별도 일회용 사본에서 의미 있고 안전한 실행을 한 번 한다.
일반/집중 리뷰어는 이를 실행하지 않는다. 바뀐 진입점의 소비자나 부수 효과를
관찰한다. 빌드, 린트, 단위 테스트만으로는 부족하다. 저장소의 기존 설정을 쓰되
로컬 데이터와 포트는 격리하고, 프로덕션 자격 증명, 공유 서비스, 마이그레이션,
외부 효과는 피한다. 대상, 명령/시나리오, 기대한 결과와 관찰한 결과, 한계를
기록한다. 직접 띄운 프로세스와 상태는 정리한다. 안전한 실행이 불가능하면
차단 요인을 밝히고 런타임을 미검증으로 표시한다. 실행할 수 없는 변경은
해당하지 않는 이유를 설명한다.

도달 불가능한 코드나 테스트 가치 후보를 확인하려면, 컨트롤러는 저장소가 이미
설정해 둔 데드 코드 탐지기나 뮤테이션 테스트 명령도 그 일회용 사본에서, 도구가
허용하면 바뀐 경로에 한정해 실행할 수 있다. 이는 진입점 실행을 보완할 뿐
대체하지 않는다. 작업자는 실행하지 않는다. 이를 위해 도구를 설치하거나 설정을
바꾸지 않는다.

후보 검증과 런타임 단계(차단 요인 포함) 뒤에는 높은 위험이나 명시적 요청이
있을 때만 선택적인 **redteam** 배정을 정당화할 수 있다. 커스텀 집중 작업자가
이름 붙은 목표, 가정, 커버리지 주장에 도달 가능한 반례와 증거로 도전하며,
전체 재스캔이나 지적 할당량은 아니다. 미해결 후보에 대한 집중 후속은 최대
한 번만 허용한다. 전체 스캔을 다시 시작하거나, 중단된 실행을 자동으로 재개하거나,
소스를 고치거나, 수정/리뷰 루프에 들어가지 않는다.

간결한 로컬 컨트롤러 보고서를 돌려준다.

- **범위/상태:** 대상 식별, 다룬/제외한 흐름, 배정한 질문, 완전/불완전한
  커버리지와 그 이유. 실패했거나 쓸 수 없거나 잘렸거나 중단된 작업자는 지적
  0건의 성공이 아니다.
- **작업자 증거:** 에이전트/역할, 완료 상태, 컨텍스트 한계, 요청한 오버라이드,
  관찰된 모델/노력(effort) 또는 `unknown`. 네이티브 보고서와 스키마는 쓰였다면
  보존한다. 모델의 자기 서술은 실행 메타데이터가 아니다.
- **지적:** 저장소의 우선순위(없으면 P0 긴급, P1 높음, P2 보통, P3 낮음),
  의도/차단 여부, 정확한 경로와 줄, 트리거, 영향/현재 비용, 증거, 필요한 결과.
  미해결 후보와 관련된 비차단 기존 문제는 따로 분리한다.
- **검증:** 실행한 점검, 런타임 통과/실패/미검증/해당 없음, 증거, 남은 위험.
  네이티브의 정확/부정확 판정은 판단일 뿐 런타임 성공이나 완전한 커버리지가
  아니다.

커스텀 일반/집중 보고서는 **범위, 지적, 한계**를 담고, 배정된 커버리지/질문과
제안하는 런타임 시나리오를 밝히되 실행했다고 주장하지 않는다. 통합은
컨트롤러에게 맡긴다. 네이티브 보고서는 네이티브 그대로 둔다. 댓글 초안이나
명시적인 게시에만 [리뷰 댓글](references/review-comments.md)을 읽고,
일반적인 로컬 보고서에는 읽지 않는다.
