# Metadata

Use this for metadata on both GitHub Issues and Linear.

## Workflow

1. **Inspect** actual fields, allowed values, template defaults, and repository
   or team conventions. Apply explicit user choices and established rules before
   proposing metadata.
2. **Choose or propose fields.** Offer grounded candidates for missing metadata
   rather than leaving everything blank; distinguish proposals from established
   values.
   - **Labels and type:** Choose existing classifications matching the problem
     and affected area; do not create near-duplicates or add every match.
   - **Assignee:** Use an explicit assignment or established ownership rule.
     A plausible owner is a proposal, not proof of assignment.
   - **Priority:** Use known impact, severity, and time constraints with the
     team's scale.
   - **Estimate:** Check the team's scale and available scope; propose only with
     a defensible basis. Leave it unset when investigation or assignee judgment
     is needed.
   - **Project and milestone:** Use existing destinations whose goals match the
     outcome, respecting their scope; a similar name alone is insufficient.
3. **Present metadata separately** from the draft body, with brief reasons for
   proposals and material unresolved choices. Do not duplicate tracker fields in
   the body unless the selected template requires it. Leave optional unknowns
   unset; batch questions only for required or consequential choices that
   context cannot resolve.

## Gotchas

- Do not assume the reporter or current user should be assigned the work.
- A bug is not automatically high priority.
- Unknown is not zero; points are not hours unless the team defines them so.
