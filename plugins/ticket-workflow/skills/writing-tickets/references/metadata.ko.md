# 메타데이터

> 영문 정본: [metadata.md](metadata.md) (`5cdc0e5` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

GitHub Issues와 Linear의 메타데이터에 모두 적용한다.

## 작업 순서

1. **확인한다.** 실제 필드, 허용 값, 템플릿 기본값, 저장소나 팀의 관례를
   살펴본다. 메타데이터를 제안하기 전에 사용자가 명시한 선택과 확립된 규칙을
   적용한다.
2. **필드를 선택하거나 제안한다.** 빠진 메타데이터를 모두 비워 두는 대신 근거
   있는 후보를 제안하고, 제안과 확립된 값을 구분한다.
   - **레이블과 유형:** 문제와 영향받는 영역에 맞는 기존 분류를 고른다. 거의
     중복되는 레이블을 만들거나 맞는 것을 전부 붙이지 않는다.
   - **담당자:** 명시적인 배정이나 확립된 담당 규칙을 쓴다. 그럴듯한 담당자는
     제안이지 배정의 증거가 아니다.
   - **우선순위:** 알려진 영향, 심각도, 시간 제약을 팀의 척도에 맞춰 쓴다.
   - **추정치:** 팀의 척도와 이용 가능한 범위 정보를 확인하고 타당한 근거가
     있을 때만 제안한다. 조사나 담당자의 판단이 필요하면 설정하지 않는다.
   - **프로젝트와 마일스톤:** 목표가 결과와 맞는 기존 대상을 범위에 맞게 쓴다.
     이름이 비슷하다는 것만으로는 충분하지 않다.
3. **메타데이터를 따로 제시한다.** 초안 본문과 분리해 제시하고, 제안에는 짧은
   이유를, 해결되지 않은 중요한 선택에는 그 사실을 덧붙인다. 선택한 템플릿이
   요구하지 않는 한 트래커 필드를 본문에 중복해서 쓰지 않는다. 선택 사항 중
   모르는 것은 설정하지 않고, 필수이거나 결과에 영향을 주는 선택 중 맥락으로
   해결할 수 없는 것만 묶어서 질문한다.

## 주의할 점

- 보고자나 현재 사용자가 작업을 맡아야 한다고 가정하지 않는다.
- 버그가 자동으로 높은 우선순위인 것은 아니다.
- 모름은 0이 아니며, 팀이 그렇게 정의하지 않았다면 포인트는 시간이 아니다.
