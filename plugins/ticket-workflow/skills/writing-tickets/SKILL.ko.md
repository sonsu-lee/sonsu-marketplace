# 티켓 작성

> 영문 정본: [SKILL.md](SKILL.md) (`41b3e28` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

문제와 관찰 가능한 결과에 합의하고, 해결책은 담당자에게 맡긴다. 쉬운 말과
널리 쓰이는 기술 용어를 쓴다. 문장을 작성하거나 고칠 때는 해당 언어 스킬이
목록에 있으면 함께 읽는다.

## 작업 순서

1. **요청을 파악한다.** 티켓은 요청받았을 때만 만들거나 수정한다. 초안 작성,
   제안, 정리, 초안 분할은 하위 티켓을 포함한 게시, 메타데이터 변경, 연동 설정,
   구현, 브랜치, PR을 허락하지 않는다. 무관한 작업을 보고해도 될 때는 범위를
   넓히지 말고 초안을 제안하고, 게시도 요청받았을 때만 한다. 집중 리뷰의 제외
   범위를 존중한다.
2. **맥락을 찾는다.** 요청과 프로젝트 지침에서 저장소 또는 Linear
   워크스페이스·팀과 주 트래커를 확인한다. 선택한 플랫폼의 차이를 설명하는
   [GitHub Issues](references/github-issue.md) 또는
   [Linear](references/linear.md)를 읽는다. 관련 티켓, 논의, 증거와 지침을 읽는다.
   생성 전 해당 범위에서 검색하고 중복 가능성을 확인한다. 다른 사람의 이슈를
   고쳐 쓰지 말고 기존 이슈를 재사용하거나 링크한다. 기존 동기화를 존중하며
   독립적인 상대 티켓을 만들거나 동기화를 설정하지 않는다.
3. **형식을 고른다.** 회귀를 포함해 제품, 문서 또는 계약의 약속과 동작이 다르면
   [버그](references/bug.md)를 읽는다. 독립적으로 완료할 수 있는 부분들이 목표를
   공유하거나 상위 티켓, 에픽, 프로젝트를 만들거나 쪼개면
   [상위 티켓](references/parent.md)을 읽는다. 그 밖의 종류에는 종류별 참조 문서가
   필요 없다.

   프로젝트 규칙 안에서 명시적으로 요청된 해당 템플릿을 우선하고, 다음으로 해당
   저장소·팀·이슈 유형의 템플릿을 쓴다. 맞는 템플릿이 없을 때만
   [본문 지침](assets/ticket-body.md)을 쓴다. 실질적으로 다른 템플릿 선택지가
   남으면 확인한다. 내용과 속성을 살펴보고 필수 필드, 메타데이터, 자동화 표지를
   두 번째 템플릿이 아니라 선택한 형식 안에 유지한다. 조회하지 못했다면 템플릿이
   없다고 하지 말고 초안에 밝힌다. 게시 전에 필수 필드를 해결한다. CLI/API로
   생성하더라도 필수 항목이 면제되지는 않는다.
4. **작성한다.** 문제나 목적을 짧은 제목으로 쓰고 원본 메모가 아닌 관련 사실을
   고른다. 제목만으로 요청이 전달되면 형식상 필요하지 않은 한 본문을 생략하고,
   그렇지 않으면 제목에서 분명하지 않은 내용만 더한다.
   - **문제:** 동작이나 필요, 조건, 중요한 이유. 기능 요청을 버그로 다루지 않는다.
   - **결과:** 구현 절차가 아닌 관찰하고 판단할 수 있는 결과. 한 문장으로 충분할
     수 있으며, 기본 체크리스트가 아니라 서로 다른 결과만 나열한다.
   - **맥락:** 필요한 결정, 제약, 증거, 의존성. 혼자 읽어도 이해되게 요약하고
     세부 내용은 링크하며 불필요하면 생략한다.

   위 내용은 필수 섹션이 아니라 선택 사항이다. 보안, 호환성, 외부 계약, 중요한
   미확정 사항을 비롯해 작업이나 완료 판단에 영향을 주는 세부 사항은 남긴다.
   일반적인 주의 사항, 빠짐없는 제외 목록, 일상적인 테스트와 명령은 생략한다.
   해결책이 아니라 복구할 능력을 서술한다. 필수가 아니면 저장 방식, 타이밍,
   코드 구조는 담당자에게 맡기고 제안한 접근법은 잠정적이라고 표시하거나
   생략한다. 유지보수는 비용이나 위험을 서술한다. 합의되었거나 외부에서 요구한
   변경은 그 자체가 결과일 수 있다. 현재 변경에 속하는 사소한 부채는 티켓으로
   올리지 않고 제목을 `Follow-up`으로 짓지 않는다.
5. **범위를 정하고 연결한다.** 하나의 문제와 일관된 결과를 목표로 하며 독립적으로
   우선순위를 정하거나 미루거나 완료할 수 있는 부분은 나눈다. 크기를 줄이려고
   코드, 필요한 테스트, 필수 문서를 분리하지 않는다. 파일 수와 시간은 기준이
   아니다. 기존 관계를 읽고 보존한다. 상위·하위 관계와 의존 관계는 본문에
   적는 데 그치지 말고 지원되는 작업으로 기록한다. 정말 불확실한 부분은 질문과
   필요한 결정이나 산출물을 밝히고, 결과물을 미리 약속하거나 단순히 "조사"에
   그치지 않는다.

   일반적인 순서는 티켓, 작업, PR이며 브랜치 이름을 정하기 전에 이슈 ID를
   확정한다. 브랜치와 PR에는 `git-workflow`의 `naming-branches`와
   `writing-pull-requests`를 쓰되 저장소 규칙을 우선한다. 여러 티켓에 걸친
   작업은 주 티켓의 브랜치 ID를 쓰고 PR에 각 관계를 설명한다. 티켓과 PR이
   반드시 일대일일 필요는 없다. 부분 작업은 닫지 않고 참조한다. 완료 링크는
   실제 트래커 자동화에서 결과가 충족되었을 때만 사용하며, 배포나 검증이 남아
   있으면 사용하지 않는다.
6. **메타데이터를 검토한다.** 실제 필드, 허용 값, 템플릿 기본값, 저장소·팀의
   관례를 확인한다. 빠진 값의 근거 있는 후보를 제안하기 전에 명시적인 선택과
   확립된 규칙을 적용한다.
   - **레이블·유형:** 문제와 영역에 맞는 기존 분류를 쓴다. 가능한 모든 분류나
     거의 중복되는 분류를 붙이지 않는다.
   - **담당자:** 명시적인 배정이나 확립된 담당 규칙을 쓴다. 보고자나 현재
     사용자가 담당한다고 가정하지 않으며, 다른 담당자는 제안으로 구분한다.
   - **우선순위:** 알려진 영향, 심각도, 시간 제약을 팀의 척도에 맞춰 쓴다.
     버그가 자동으로 긴급한 것은 아니다.
   - **추정치:** 실제 척도와 근거 있는 범위를 사용한다. 조사나 담당자 판단이
     필요하면 설정하지 않는다. 모름은 0이 아니며 팀의 정의 없이는 포인트를
     시간으로 보지 않는다.
   - **프로젝트·마일스톤:** 이름만 비슷한 곳이 아니라 목표와 범위가 결과에 맞는
     기존 대상을 쓴다. 프로젝트가 미정이면 마일스톤도 미정으로 둔다.

   템플릿이 요구하지 않는 한 메타데이터를 본문과 분리한다. 제안에는 짧은 이유를
   덧붙인다. 선택 사항 중 모르는 것은 설정하지 않고, 필수이거나 결과에 영향을
   주는 선택 중 맥락으로 해결할 수 없는 것만 묶어서 질문한다. 게시 전에 모호한
   식별 대상을 확인한다. 제안을 배정이나 약속으로 바꾸거나 티켓을 채우려고
   레이블, 필드, 마일스톤, 프로젝트를 만들지 않는다. 도구가 필드를 읽거나 쓸 수
   없으면 밝힌다.
7. **전달한다.** 초안은 제목, 필요한 본문, 메타데이터 제안, 관계, 중요한 질문을
   반환하고 빈 항목은 생략하며 ID를 지어내지 않는다. 허가된 생성이나 수정에는
   템플릿과 확립된 메타데이터를 적용하되 무관한 내용과 속성을 보존한다. 이슈,
   관계, 별도로 저장된 필드를 다시 읽어 의도한 결과를 각각 확인한다. 실제 ID,
   URL, 끝내지 못한 작업과 적용하지 못한 추천을 따로 보고한다. 초안이나 실패한
   작업을 게시되었다고 부르지 않는다.

## 주의할 점

- 보안 취약점이 의심되면 공개(disclosure)로 다룬다. 프로젝트 보안 정책이나
  비공개 제보 채널을 따르고, 공개 티켓이나 공개 동기화되는 티켓에 익스플로잇
  세부 내용이나 재현 방법을 절대 넣지 않는다. 비공개 경로가 없으면 저장소
  파일이 아닌 답변으로 초안을 돌려주고 그 사실을 알린다.
- 관찰, 추정 원인, 제안된 해결책을 구분한다. 유용한 피드백은 원문 그대로
  보존하고 출처를 알면 링크한다. 영향, 재현 단계, 임계값, 이전 결정, 이슈 ID를
  지어내지 않는다. 문제, 범위, 위치, 완료 기준의 중요한 공백을 맥락으로 메울 수
  없을 때만 질문한다.
- CLI나 API가 명시한 본문에 UI 템플릿을 적용하지 않을 수 있다.
- 본문은 합의된 문제, 범위, 결과에 맞춘다. 바뀌면 대체된 계획이나 진행 로그를
  쌓지 말고 변경과 이유를 기록하며 기존 논의나 설계 기록을 링크한다. 성공의
  정의를 조용히 바꾸지 않는다. 자세한 구현과 검증 증거는 PR에 둔다.
