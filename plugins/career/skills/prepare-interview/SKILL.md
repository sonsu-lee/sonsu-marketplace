# prepare-interview: 면접 준비

경력 원본과 회사 자료로 회사·라운드별 면접 준비 자료를 만든다. 면접관이 체크리스트로 합격 여부를
정한다는 전제로 준비 항목을 그 체크리스트에 맞춘다. 사실이 없는 답변은 만들지 않는다.

## 계약

- [작업 공간 계약](../../references/workspace.md)과 [근거 규칙](../../references/evidence-rules.md)을
  따른다.
- 쓰는 파일은 다음과 같다.
  - `companies/<slug>/prep.md`: 템플릿 [prep.md](../../assets/workspace/prep.md)
  - `companies/<slug>/product.md`: 템플릿 [product.md](../../assets/workspace/product.md)
  - JD가 주어졌는데 `jd.md`가 없으면 `companies/<slug>/jd.md`: 템플릿
    [jd.md](../../assets/workspace/jd.md)
  - `profile/core-answers.md`: 없으면 템플릿 [core-answers.md](../../assets/workspace/core-answers.md)에서
    만든다.
  - `questions.md`
- 작업 공간이 없으면 `blocked`로 멈추고 `career-inventory`로 경력 원본부터 만들자고 안내한다. 사실
  없이 만든 답변은 근거가 없기 때문이다.
- 모드는 요청으로 정한다.
  - 회사 준비: 회사가 주어지면 `## 입력 확인`부터 `## 결과`까지 모든 섹션을 수행한다.
  - 공통 답변: 회사 없이 자기소개·이직 사유·강점·약점·실패 경험을 요청받으면
    `## HR 기본 질문`의 공통 답변 부분만 수행한다.
  - 곤란한 질문: 회사 없이 곤란한 질문을 요청받으면 `## 곤란한 질문`의 회사 없는 모드만 수행한다.
  - 프로덕트 분석: 회사 프로덕트 분석만 요청받으면 `## 프로덕트 분석`만 수행한다. 약점 질문은
    `questions.md`에 반영한다.
  - 공통 답변, 곤란한 질문, 프로덕트 분석 모드는 `prep.md`를 만들지 않는다.
- 모든 답변 초안은 [답변 형식](../../references/answer-shapes.md)을 따른다. 특히 다음 두 가지를
  지킨다.
  - 경험·의견 질문에는 이유를 붙인다.
  - 부정적 사건에는 해결·대응과 결과를 붙인다.

## 입력 확인

- 확인할 것은 회사, 직무, market(`us`/`jp`), 면접 언어(`en`/`ja`), 라운드·날짜·형식·면접관
  역할이다. 초대 메일 내용이 있으면 그것이 우선한다.
- 라운드 정보가 없으면 [면접 라운드](../../references/interview-rounds.md)의 일반 흐름을 쓰고
  `[일반적 흐름]`이라고 표시한다.

## 회사 맥락

- `jd.md`와 사용자 자료를 읽는다. 호스트 웹 검색을 쓸 수 있으면 사업, 최근 소식, 엔지니어링
  블로그를 본다.
- 출처 URL은 `prep.md`에 남긴다.
- 여러 출처를 교차 검증해야 하면 Research 플러그인을 runtime에서 조합하라고 안내한다. 확인하지
  못한 회사 정보는 만들지 않는다.

## 요구사항 대응

- `jd.md`에 `## 요구사항 대응` 표가 없으면 `write-career-documents`의 JD 대응표와 같은 열·규칙으로
  만든다: `JD 표기`(공고 문구 그대로), must/nice, `연수 요구`, Matched(F-/S-)/Missing/Unknown.
- 인접 경험을 Matched로 올리지 않고, 요구사항 문구 자체를 근거로 쓰지 않는다.

## 프로덕트 분석

결과는 `companies/<slug>/product.md`에 쓴다. `prep.md`에는 프로덕트 분석을 옮겨 적지 않고 링크만
건다.

### 1. 공개 자료

- 호스트 웹 검색으로 공식 사이트, 문서, 릴리스 노트, 앱 스토어 리뷰, 엔지니어링 블로그를 본다.
- `## 개요`에 무엇을, 누구에게, 핵심 사용자 흐름 3개를 출처 URL과 함께 쓴다.
- 공개 자료에서 확인한 불편은 `관찰자: 공개 자료`와 URL을 붙여 `## 관찰`에 기록한다.

### 2. 에이전트 사용 시도

- 다음 조건을 모두 만족하면 핵심 흐름 3개를 직접 써 보고, 관찰을 `관찰자: agent`,
  `본인 확인: no`로 기록한다.
  - 호스트에 브라우저 도구가 있다.
  - 웹 프로덕트다.
  - 로그인·결제 없이 쓸 수 있다.
- 계정 생성, 구매, 개인 정보 입력 폼 제출은 하지 않는다.
- 관찰 근거로 화면 위치, URL, 날짜를 남긴다.
- 성공하면 `## 시도 기록`에 `done`과 날짜를 적는다.
- 조건이 맞지 않거나 시도가 실패하면 `## 시도 기록`에 `not_run: <이유>`와 날짜를 적고 agent
  관찰은 만들지 않는다. 이유는 다음 중 하나다: 브라우저 없음, 로그인 필요, 네이티브 앱, 접근 차단,
  오류.

### 3. 사용 체크리스트

- 시도 결과와 상관없이 `## 사용 체크리스트`를 항상 만든다.
- 내용은 사용자가 직접 해 볼 핵심 흐름과 기록할 것(막힌 곳, 느린 곳, 헷갈린 문구, 접근성 문제)이다.
- 결과 보고에서 "면접 전에 직접 써 보고 관찰을 알려 달라"고 요청한다.
- 사용자가 알려 준 관찰은 `관찰자: 본인`, `본인 확인: yes`로 추가한다. 사용자가 agent 관찰을
  확인하면 그 행을 `본인 확인: yes`로 바꾼다.

### 4. 개선 제안

관찰 3개를 고른다. 우선순위는 본인 > 확인된 agent > 공개 자료다. 관찰마다 `## 개선 제안` 아래
`### U-0xx <제목>`으로 다음을 쓴다.

- 사용자 영향
- 원인 가설: "추정"으로 표시한다.
- 해결안
- 구현 방식: 프론트엔드 관점의 컴포넌트 구조, 상태·데이터 흐름, 필요한 API("추정"으로 표시),
  성능, 접근성, 단계적 배포(feature flag, A/B)
- 트레이드오프
- 효과 측정 지표
- 내 근거: 비슷한 일을 한 F-/S-

### 5. 약점 질문 답변

- "What do you think is a weakness of our product?" / 「弊社サービスの弱点は何だと思いますか」를
  `questions.md`에 `분류: company`로 추가한다. 같은 의도의 질문이 있으면 그 행을 재사용한다.
- 답변 형식은 관찰 1개(사실) → 왜 문제인지(사용자 영향) → 해결·구현 방향 → 관련 내 경험이다.
- `본인 확인: yes`인 관찰이나 `공개 자료` 관찰만 쓴다. 공개 자료 관찰은 "리뷰에서는"처럼 출처를
  밝혀 말한다.
- 쓸 관찰이 없으면 답변을 쓰지 않는다. 질문 상태를 `unprepared`로 둔 채, 먼저 직접 써 보라고
  안내한다.

## 면접관 체크리스트

면접관도 체크리스트로 합격 여부를 판단한다는 전제로, `prep.md`의 `## 면접관 체크리스트`에 round마다
표를 만든다. 전체에 `[추정]`을 표시한다.

```
| 항목 | 필수(yes/no) | 확인 질문 | 채울 답(Q-/S-/core-answers 키/U-) | 상태 |
```

- 항목의 출처와 `필수` 값은 다음과 같다.
  - 그 round의 고정 확인 항목([면접 라운드](../../references/interview-rounds.md)): yes
  - 기술 round: `jd.md`의 must 요구사항은 yes, nice 요구사항은 no
  - HR round: HR 기본 질문 6종은 yes
- 채울 답이 없는 항목은 `unprepared`로 두고 `## 준비 계획` 맨 앞에 올린다.

## HR 기본 질문

- 6종을 항상 준비한다: 자기소개, 이직 사유, 지원 동기, 강점, 약점, 실패 경험. HR은 어느
  단계에서든 이 질문을 한다.
- 공통 답변(지원 동기를 뺀 5종)은 `core-answers.md`의 키(`self-intro`, `leaving-reason`,
  `strengths`, `weaknesses`, `failure`)에 면접 언어로 둔다. 답이 없으면 `facts.md`, `stories.md`,
  `positions.md`로 초안을 쓴다. 키별 형식은 [답변 형식](../../references/answer-shapes.md)을 따른다.
- 재료가 없으면 지어내지 않는다.
  - 이직 사유를 모르거나, 사용자가 약점을 말하지 않았거나, failure 스토리가 없으면 그 키를
    `상태: unprepared`로 둔다.
  - 한 턴에 3개까지만 사용자에게 묻는다. failure 스토리가 필요하면 `career-inventory`를 안내한다.
- 약점, 실패 경험, 부정적 계기가 있는 이직 사유는 해결·대응과 그 결과가 있어야 `ready`다.
- 지원 동기는 회사마다 `prep.md`의 `## HR 기본 질문`에 쓴다. 형식은 회사의 구체적 과제(`jd.md`·
  `product.md` 근거) → 그 과제와 닿는 내 사실 → 입사 후 기여다. 회사 이름을 지워도 통하면 다시
  쓴다.
- `prep.md`에는 6종의 상태와 링크를 표로 둔다.

## 라운드별 준비

`prep.md`의 `## 라운드별 준비`에 round마다 `###`을 만든다.

- 평가자와 그 평가자가 보는 것을 쓴다.
- 질문 목록은 이 순서로 우선한다: 이 회사에서 실제로 받은 질문 > 다른 회사에서 같은 분류로 실제로
  받은 질문 > `sourced` > `inferred`. 질문마다 Q-ID, 상태, 연결 스토리를 함께 쓴다.
- 상위 질문에는 면접 언어로 60초 답변을 쓴다. 여러 회사에 쓸 수 있는 답변은 `stories.md`의
  `#### 답변`에 두고, `prep.md`에는 회사 맞춤 부분만 둔다.
- hiring-manager·first(一次)·second(二次) round에는 프로덕트 질문 두 개를 넣고, 둘 다 `product.md`로
  답한다.
  - "Have you used our product? What would you improve, and how would you build it?"
  - 약점 질문

## 제출 서류 심층 질문

1차 기술 면접관은 면접 직전이나 면접 중에 제출 서류를 펼쳐 보고 질문을 고른다. 그 서류에서 나올
질문을 준비한다.

- 대상 서류는 `companies/<slug>/`의 서류(`resume-en`, `shokumu-keirekisho-ja`, `skill-sheet-ja` 중
  가장 최근 것)다. 없으면 `documents/`의 기본 서류를 쓰고, 둘 다 없으면 건너뛰고 결과에 적는다.
- 최근 직무부터, 수치가 있거나 기술 선택이 드러난 bullet·프로젝트마다 질문을 하나씩 만든다. 최대
  10개다.
  - 질문 유형: "왜 그 방법을 골랐나", "어떻게 측정했나", "가장 어려웠던 문제와 대응"
  - `questions.md`에는 `분류: resume-deep-dive`, `출처: inferred:document/<파일명>`, `위험: -`로
    넣는다.
- 답변 메모에는 이유, 해결·대응, 결과와 F-를 적는다. 이유가 사실에 없으면 "이유 정리 필요"로
  표시하고 사용자에게 묻는다.

## 곤란한 질문

[곤란한 질문 스캔](../../references/risk-probes.md)의 탐지 규칙을 다음 자료에 적용한다.

- `profile/` 파일들
- `documents/`와 이 회사 폴더의 서류
- 이 회사 `jd.md`의 `## 요구사항 대응`
- 지원 round

걸린 신호마다 곤란한 질문을 하나 만든다. 자료에 없는 약점을 상상해 만들지 않는다.

- 정렬: 위험 코드의 심각도 순서로 놓고, 같은 코드 안에서는 근거 ID 순서로 놓는다.
- 개수: 최대 10개다. `leaving-reason`은 탐지 결과와 무관하게 항상 하나 넣는다.

`prep.md`의 `## 곤란한 질문`에 항목마다 아래 형식으로 쓴다.

```
### <위험 코드> · Q-0xx
- 질문(면접 언어):
- 근거: <ID와 파일 위치>
- 확인하려는 것:
- 피할 답:
- 답변 방향:
- 보완: <skill 이름 또는 없음>
```

- 답변 방향은 [답변 형식](../../references/answer-shapes.md)의 부정적 사건 형식(인정 → 사실 →
  해결·대응과 결과 → 지금/다음)을 따른다. 쓸 수 있는 사실만 쓴다.
- private 사실의 내용은 질문과 답변 방향에 넣지 않는다.

### 질문 은행 반영

- 각 질문을 `questions.md`에 추가한다. `출처`는 `inferred:risk/<코드>/<근거 ID>`, `위험`은 해당
  코드, `상태`는 `unprepared`다. 근거 ID가 없는 `leaving-reason`의 출처는
  `inferred:risk/leaving-reason`이다.
- 재사용 규칙: 같은 출처(코드와 근거 ID)의 행이 이미 있거나 같은 의도의 질문이 이미 있으면 새 행을
  만들지 않는다. 그 행의 `위험`이 `-`이면 코드로 바꾸고, `출처`에는 `; `로 새 출처를 덧붙인다.
  `prep.md` 항목의 Q-ID는 재사용한 행의 ID를 쓴다.

### 회사 없는 모드

- 회사 정보가 필요한 `jd-missing`, `seniority-gap`, `stale-tech`, `work-authorization`(market 필요)은
  빼고 나머지 신호만 탐지한다.
- 면접 언어는 요청에 나오면 그대로 쓰고, 없으면 en/ja 중 하나를 한 번 묻는다.
- 결과는 `questions.md`에 반영하고, 위와 같은 항목 형식으로 대화에 보고한다. `prep.md`는 만들지
  않는다.

## 기술 라운드

- technical(경험 심층): 상위 스토리마다 "왜 → 어떻게 측정했나 → 대안과 트레이드오프 → 지금이라면"
  연쇄 질문을 만든다.
- system-design: [프론트엔드 시스템 설계](../../references/frontend-system-design.md)를 읽는다.
  - 회사 제품 맥락에서 출제 가능성이 있는 주제 3~5개를 `inferred`로 고른다. `product.md`의 핵심
    흐름을 우선한다.
  - 내 사실과 연결할 깊이 파기 영역을 짚는다.
- 알고리즘 문제 풀이 연습은 이 스킬의 범위 밖이라고 알린다.

## 마무리 섹션

- 전할 메시지: 3개를 쓰고 각각 S-/F-에 연결한다.
- 약점과 대응: 곤란한 질문으로 다루지 않은 리스크만 쓴다. 예를 들어 PSR 빈칸 가운데 질문 형태로
  만들기 어려운 것을 사실 범위 안에서 정직하게 설명한다. 곤란한 질문과 같은 내용을 반복하지 않는다.
- 역질문 3~5개: 궁금한 것을 묻는 질문이 아니라, 입사 후 그 자리에서 일하는 내 모습을 면접관에게
  심는 질문으로 만든다.
  - 구조: 입사 후 맡을 일이나 과제(`jd.md`·`product.md` 근거) + 그와 닿는 내 경험(F-/S-) + 팀의
    현재 방식이나 기대를 묻는 질문.
  - 예: "입사하면 checkout 성능 개선을 맡게 될 것 같습니다. 저는 이전에 INP를 개선한 경험이
    있는데, 지금 팀은 성능 지표를 어떤 기준으로 관리하고 있나요?"
  - 각 질문에 근거 ID를 단다.
  - 뺄 질문: 순수한 호기심 질문, 검색하면 알 수 있는 질문, 연봉부터 묻는 질문, 예/아니오 질문.
- 조건 답변:
  - `positions.md`의 `## 조건 답변` 문장을 쓴다.
  - recruiter 라운드에서는 하한선과 현재 연봉을 먼저 말하지 않는다. `positions.md`에 정한 조사
    범위를 base·bonus·equity 전체로 제시한다.
- 직전 15분 요약: 앵커 문장 하나, 메시지 3개, 나올 만한 질문 3개, 역질문 2개, 프로덕트 개선 제안
  1개(U-).

## 준비 계획

- 날짜가 있으면 남은 시간에 맞춰 다음 순서로 정한다.
  1. 면접관 체크리스트의 `unprepared`
  2. HR 기본 질문의 `unprepared`
  3. 곤란한 질문의 `unprepared`
  4. 해당 라운드의 `weak`
  5. 프로덕트 직접 사용
  6. 연습
- 면접 60~90분 전에는 준비를 멈추고 직전 15분 요약만 보게 한다.

## 질문 은행 갱신

- 새 추정 질문은 `inferred:` 출처, `위험: -`로 `questions.md`에 Q-로 추가한다.
- 같은 의도의 질문이 이미 있으면 새 행을 만들지 않고 `출처`에 `; `로 덧붙인다.
