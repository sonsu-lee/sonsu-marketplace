# 경력 棚卸し 질문

경험 유형마다 Evidence 질문 ①~⑦을 구체화한 예와 측정 자료가 있을 만한 곳을 적는다. 질문은
①부터 순서대로 고르고, 한 턴에 3개까지만 묻는다. 사용자의 작업 언어로 바꿔 묻는다. "기억 안 남"은
`미상`으로 기록하고 다음 질문으로 넘어간다.

번호는 다음 뜻이다: ① 역할과 책임 범위 ② 문제와 제약 ③ 내가 한 것과 팀이 한 것 ④ 내린 결정과
대안, 판단 이유 ⑤ 문제가 생겼을 때의 해결·대응 ⑥ 결과 ⑦ 수치의 측정 방법·시점·출처.

## 프론트엔드 성능 개선

1. 어떤 화면이나 흐름의 성능을 맡았고, 개선 목표는 누가 정했나?
2. 어떤 지표(LCP, INP, CLS, 번들 크기 등)가 문제였고, 일정·호환성·트래픽 같은 제약은 무엇이었나?
3. 병목 분석, 수정, 배포 가운데 직접 한 것은 무엇이고 다른 사람이 한 것은 무엇인가?
4. 어떤 개선안을 골랐고 다른 안은 무엇이었나? 왜 그 안이 맞다고 판단했나?
5. 개선 뒤 회귀나 부작용이 생겼다면 어떻게 찾아서 대응했나?
6. 사용자나 비즈니스에 무엇이 바뀌었나?
7. 이전·이후 값을 어디서, 어떤 조건(p75, 기기, 기간)으로 쟀나?

측정 자료가 있을 만한 곳: RUM 대시보드, Lighthouse·WebPageTest 결과, 번들 분석 리포트, PR 설명,
릴리스 노트.

## 마이그레이션·교체

1. 무엇을 무엇으로 바꿨고, 전체 범위 가운데 내가 맡은 범위는 어디까지인가?
2. 왜 바꿔야 했고, 서비스 중단·병행 운영·일정 같은 제약은 무엇이었나?
3. 계획, 공통 기반 작업, 화면별 이전 가운데 내가 한 것과 팀이 한 것은 무엇인가?
4. 점진 이전과 일괄 교체 같은 대안 가운데 무엇을 골랐고, 그 이유는 무엇인가?
5. 이전 중 깨진 기능이나 일정 지연이 있었다면 어떻게 대응했나?
6. 이전이 끝난 뒤 무엇이 나아졌고, 남은 것은 무엇인가?
7. 이전한 페이지·모듈 수, 기간, 개선 수치는 어디에 기록되어 있나?

측정 자료가 있을 만한 곳: 이전 추적 이슈·프로젝트 보드, PR 목록, CI 로그, 릴리스 노트, 회의록.

## 디자인 시스템·공통 UI

1. 디자인 시스템이나 공통 컴포넌트에서 내가 맡은 컴포넌트나 영역은 무엇인가?
2. 화면마다 UI가 달랐던 문제, 디자이너와의 합의, 접근성 요구 같은 제약은 무엇이었나?
3. 설계, 구현, 문서화, 도입 지원 가운데 내가 한 것과 팀·디자이너가 한 것은 무엇인가?
4. API 설계나 스타일링 방식을 어떻게 정했고, 다른 선택지와 비교해 왜 그렇게 판단했나?
5. 도입을 꺼리는 팀이나 깨지는 변경이 있었다면 어떻게 대응했나?
6. 몇 개 팀·화면이 썼고, 개발 속도나 일관성에 무엇이 바뀌었나?
7. 채택 수, 컴포넌트 수, 작업 시간 변화는 어디서 확인할 수 있나?

측정 자료가 있을 만한 곳: 패키지 다운로드·의존 저장소 목록, Storybook, PR, 디자인 리뷰 회의록,
대시보드.

## 장애·버그 대응

1. 장애 당시 내 역할은 무엇이었나(당번, 담당자, 지원)?
2. 무엇이 어떻게 고장 났고, 영향 범위와 시간 압박은 어땠나?
3. 원인 분석, 임시 조치, 근본 수정, 사후 보고 가운데 내가 한 것과 팀이 한 것은 무엇인가?
4. 롤백과 핫픽스 같은 선택지 가운데 무엇을 골랐고, 왜 그렇게 판단했나?
5. 대응 중 예상과 다른 일이 생겼다면 어떻게 해결했나?
6. 복구까지 걸린 시간과 재발 방지책은 무엇인가?
7. 영향 범위와 복구 시간은 어디에 기록되어 있나?

측정 자료가 있을 만한 곳: 인시던트 보고서, 모니터링·에러 트래킹 대시보드, 알림 기록, PR, 회의록.

## CI·빌드·DX

1. 어떤 파이프라인이나 개발 환경을 맡았고, 개선은 누가 요청했나?
2. 빌드·테스트 시간, 불안정한 테스트, 로컬 환경 같은 문제와 비용·권한 제약은 무엇이었나?
3. 병목 분석과 개선 작업 가운데 내가 한 것과 팀이 한 것은 무엇인가?
4. 캐시, 병렬화, 도구 교체 같은 선택지 가운데 무엇을 골랐고, 왜 그렇게 판단했나?
5. 개선 뒤 빌드가 깨지거나 결과가 달라졌다면 어떻게 대응했나?
6. 개발자들의 대기 시간이나 배포 빈도에 무엇이 바뀌었나?
7. 이전·이후 시간을 어떤 기간의 어떤 값(중앙값 등)으로 쟀나?

측정 자료가 있을 만한 곳: CI 로그·실행 기록, CI 대시보드, PR, 팀 회고 문서.

## 이해관계자와 함께 한 기능 출시

1. 이 기능에서 내 역할과 책임 범위는 무엇이었나?
2. 기획·디자인·백엔드·비즈니스 쪽의 요구와 일정·범위 제약은 무엇이었나?
3. 요구 정리, 구현, 출시 조율 가운데 내가 한 것과 다른 사람이 한 것은 무엇인가?
4. 범위를 줄이거나 바꾼 결정이 있었다면 대안은 무엇이었고 왜 그렇게 판단했나?
5. 의견 충돌이나 일정 위험이 생겼다면 어떻게 해결했나?
6. 출시 뒤 사용자나 비즈니스에 무엇이 바뀌었나?
7. 전환율 같은 결과 지표는 누가 어떤 방법으로 쟀나?

측정 자료가 있을 만한 곳: 제품 분석 대시보드, A/B 테스트 결과, 기획 문서, 릴리스 노트, 회의록.

## 멘토링·코드 리뷰

1. 누구를, 몇 명을, 어떤 기간 동안 맡았나? 공식 역할이었나?
2. 상대가 막힌 지점과 시간·조직 제약은 무엇이었나?
3. 리뷰, 페어 작업, 문서 작성 가운데 내가 직접 한 것은 무엇인가?
4. 가르치는 방식을 어떻게 정했고, 다른 방식 대신 그 방식을 고른 이유는 무엇인가?
5. 의견이 맞지 않거나 성장이 더뎠을 때 어떻게 대응했나?
6. 상대나 팀에 무엇이 바뀌었나?
7. 그 변화를 보여 줄 기록이 있나?

측정 자료가 있을 만한 곳: PR 리뷰 기록, 1on1·온보딩 문서, 평가 피드백, 회의록.

## OSS·기술 글

1. 어떤 저장소나 매체에 어떤 형태(메인테이너, 기여자, 저자)로 참여했나?
2. 어떤 문제를 해결하려 했고, 메인테이너 합의나 호환성 같은 제약은 무엇이었나?
3. 기여나 글 가운데 내가 직접 쓴 범위와 다른 사람이 한 범위는 무엇인가?
4. 구현이나 글의 방향을 어떻게 정했고, 다른 선택지 대신 그렇게 판단한 이유는 무엇인가?
5. 리뷰에서 반대가 있거나 문제가 생겼다면 어떻게 대응했나?
6. 머지, 릴리스, 반응 가운데 실제로 일어난 결과는 무엇인가?
7. 링크와 수치(스타, 다운로드, 조회 수)는 어디서 언제 확인한 값인가?

측정 자료가 있을 만한 곳: 저장소의 PR·이슈·릴리스, 패키지 레지스트리 통계, 글 분석 화면.

## AI 활용 개발

1. AI 도구를 쓴 작업에서 내 역할은 무엇이었나? 도입을 정한 사람은 누구인가?
2. 무엇을 자동화했는가? 자동화하기 전의 문제와 보안·품질 제약은 무엇이었나?
3. 프롬프트·워크플로 설계, 결과 검토, 수정 가운데 내가 한 것과 도구·팀이 한 것은 무엇인가?
4. 어떤 도구와 방식을 골랐고, 쓰지 않는 선택지와 비교해 왜 그렇게 판단했나?
5. 품질은 어떻게 보장했는가? 잘못된 결과가 나왔을 때 어떻게 찾아서 대응했나?
6. 작업 시간이나 품질에 무엇이 바뀌었나?
7. 그 변화를 어떤 기록으로 쟀나?

측정 자료가 있을 만한 곳: PR과 리뷰 기록, CI 로그, 작업 추적 이슈, 팀 가이드 문서, 대시보드.
