# 산출물별 작업 경계

운영형 신규 설계·재설계는 요청 내용으로 자동 선택하며 스킬 이름 지정도 지원한다. 명시적
선택을 우선하고 대상 차이는 설명한다. 운영 업무가 아닌 일반 UI의 자동 선택은 해당 일반
디자인 스킬에 맡기고, 없거나 직접 지정한 경우에는 현재 과업에 필요한 범위만 적용한다.

시작할 때 사용자 요청·현재 프로젝트에서 `proposal`, `figma`, `implementation` 중 요청 산출물을
확인한다. 여러 산출물을 요청하면 각각 완료하고 증거를 분리한다. 불명확하고 작업 범위가 크게
달라질 때만 묻는다. 모드 선택은 실제 권한·호스트의 쓰기 제한을 확대하지 않는다.

## 일반 UI에서의 직접 호출과 대체 경로

일반 콘텐츠·탐색 화면이면 자동 선택에서는 일반 디자인 스킬을 우선한다. 사용자가 이 스킬을
직접 지정했거나 일반 디자인 스킬 없이 이 지침을 적용하는 경우에는 대상과 전문 범위의 차이를
설명하고, 현재 과업에 맞는 정보 우선순위·상태·행동·접근성 기준으로 요청 산출물을 완성한다.
운영 업무 여부가 불명확해 결과가 달라질 때만 필요한 범위를 확인한다. 비운영 UI라는 이유만으로
요청 전체를 중단하거나 스킬 재호출·다른 플러그인 설치를 요구하지 않는다.

일반 UI의 제안/Figma는 아래 산출물 기준을 적용한다. 일반 UI 구현은 기존 프로젝트의 도구·
컴포넌트·검증 절차로 화면과 요청 동작을 완성하고, 원본의 값·상태·행동과 실제 렌더링·조작을
확인한다. 운영 전용 Screen Contract·pattern·G0–G7의 적용 대상으로 분류하거나 운영형
Quality Report의 `overall: passed`를 발행하지 않는다. 관련 운영 과업이 실제로 포함되면 그 범위에는
아래 운영형 구현 계약을 그대로 적용한다. 주 담당과 각 산출물의 완료·미확인을 분리해 보고한다.

## Proposal

코드 변경이나 실행용 Screen Contract JSON 전에 사용자·핵심 업무·정보·상태·권한·행동과
기존 화면의 보존/변경 사항을 짧은 명세로 정리한다. 미결정은 영향과 함께 남긴다.
관련 비교 기준, 필터·선택 범위, 대량 처리와 부분 실패·복구를 다루고 불필요한 기능을 만들지 않는다.
B2B라는 이유로 고밀도 테이블을 강제하지 않고 주 과업에 맞는 pattern을 선택한다.

명세와 실제 시각적 제안에서 주요 과업·상태·공간·내부 정보 자산을 확인한다. 지도·차트·표의
관계가 문제라면 바깥 카드뿐 아니라 데이터 대응·기하·밀도·조작 범위를 다시 설계한다.
실제 값·상태와 디자인용 예시를 구분하고 정적 시안을 동작 구현으로 보고하지 않는다.
제작 도구가 없으면 명세만 준비됐고 시안은 `blocked`/`not_run`임을 알린다.

## Figma

위 명세를 Figma frame·state·component·variable과 연결한다. 요청된 prototype이 있으면 reaction과
playback까지 확인한다. Figma가 정본이며 텍스트는 결정과 보충 설명을 담당한다.
`figma-operations-flow`와 현재 사용 가능한 공식 Figma 지침으로 제작·readback을 수행한다.
다른 플러그인 설치는 요구하지 않되 필수 제작 capability가 없으면 해당 산출물을 미완료로 보고한다.

Proposal/Figma는 산출물·명세 리비전, 보존/변경 사항, 실제 확인한 화면·상태·구조·상호작용과
미확인을 읽기 쉬운 보고로 반환한다. 이 보고는 implementation의 Quality Report JSON이 아니다.
코드 경로·브라우저 scenario 매핑, 실행용 validator와 G0–G7을 선행 조건으로 요구하지 않는다.
설계 요청에 코드 구현까지 이어가거나 G7을 억지로 N/A/통과 처리하지 않는다.

## Implementation

운영형 웹 구현에는 기존 Screen Contract·Change Contract·validator와 G0–G7, actual target app의 Browser Evidence Receipt를
그대로 적용한다. 앞선 명세를 입력으로 재사용하되 구현에 필요한 미결정·scenario·매핑을 완성한다.
Figma·시안·schema 적합성은 runtime 통과가 아니다. 실제 코드 요청은 설계 결과만으로 완료하지 않는다.
현재 구현 계약은 웹 운영 화면을 대상으로 한다. 네이티브 구현 요청에서는 이 한계를 설명하고
기존 네이티브 프로젝트·검증 지침과 조합하며, 브라우저 검사로 네이티브 실행 검증을 대신하지 않는다.

각 모드의 결과는 해당 산출물에서만 `passed / failed / blocked / inconclusive / not_run`으로 보고한다.
기존 implementation report의 `overall: passed` 의미와 validator schema는 변경하지 않는다.
