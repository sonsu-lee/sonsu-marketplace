# plan: 계획 작성

기존 코드와 승인된 요구사항을 바탕으로 다른 실행자도 이해할 구현 계획을 작성한다. 순서는 **동작 의사코드 → 파일·작업·의존성 대응 관계 → 검증 방법과 이유 → 구현·검증**이다.

요구사항 출처는 원래 구현 요청, 이전 사용자 승인, 승인된 문서·이슈·티켓일 수 있다. [brainstorming의 실행 권한](../brainstorming/SKILL.md)에 따라 승인된 범위는 계속한다. 절차 전환·재개를 이유로 재승인을 요구하지 않는다. 설계 전용 요청은 산출물 완성으로 종료한다. 명시적 구현 전 확인은 먼저 요청된 산출물을 완성한 뒤 의존 작업만 보류한다. 미결정 계약과 독립적인 승인 작업은 계속한다.

주 조정자의 여러 단계 작업은 [연속성 참고 자료](../../references/continuity.md)에 기록한다. 위임된 작업자와 새 문맥의 검토자는 별도 연속성 기록을 만들지 않는다.

## 적용 범위와 위치

여러 단계·파일·구성 요소, 인터페이스·상태 전이·오류·마이그레이션·회귀 위험을 조정해야 하면 계획을 작성한다. 오탈자나 명백한 기계적 수정처럼 범위 설명과 검증으로 닫을 수 있으면 긴 의사코드를 만들지 않는다. 설계 깊이와 검증은 현재 계약·위험으로 선택한다.

기본 산출물은 대화의 계획이다. 실행 도구에 파일이 필요하면 Git에서 제외한 `.engineering/plans/<feature-name>.md`에 임시 자료 사본을 둔다. 저장소의 이슈·티켓 관례나 사용자 지정 위치가 있으면 따른다. 날짜 기반 계획이나 `docs/engineering/plans/`를 자동 생성하지 않는다. 격리가 필요하면 실행 시점에 `engineering:worktree`를 적용한다.

작업 정의 전에 요구사항과 관련 문서를 읽고 문서 영향을 `없음 / 기존 문서 갱신 / 승인된 영속 문서 생성 / 기존 결정 대체`로 기록한다. 계획 자체를 영속 설계 문서로 취급하지 않는다. 내부 선택은 자료로 해결하고, 사용자 결정이 필요한 계약 공백은 의존 작업과 함께 표시한다.

앞선 단계에서 결정한 문서 영향·목적·경로·갱신 범위를 이어받고 달라진 부분만 확인한다.
문서 작업에는 그 결정을 전달하며, 작업이 생겼다는 이유로 README 갱신을 추가하지 않는다.

## 1. 동작 흐름 정의

구현 세부사항·파일별 단계·TDD 적용 여부를 정하기 전에 언어 중립적인 의사코드를 작성한다. 이는 구현자와 검토자가 동작과 책임을 확인하는 외부 산출물이다.

안정적인 `F1`, `F2` ID를 부여하고 해당 작업에 필요한 입력·관찰 결과·처리 순서·상태 변화·분기·반복·오류·경계·책임·가정을 표현한다. 없는 상태나 반복을 형식적으로 추가하지 않는다. 구현 방향을 바꾸는 미확인 가정은 결정 항목으로 남긴다.

```text
FLOW F1: [관찰 가능한 결과]
  INPUT: [호출자나 사용자 입력]
  READ: [기존 코드 또는 상태]
  IF [조건]:
      CHANGE [데이터 또는 상태]
  ELSE:
      RETURN [경계 또는 오류 결과]
  OUTPUT: [호출자 또는 다음 흐름에 전달할 결과]
  BOUNDARY: [기존 책임] / [새 책임]
  ASSUMPTION OR DECISION: [확인할 내용]
```

## 2. 흐름을 작업에 연결

생성·수정할 정확한 파일과 책임을 정하고 기존 프로젝트 패턴을 따른다. 검토자가 독립적으로 승인·거부할 수 있는 산출물 경계에서 작업을 나눈다. 각 작업의 인터페이스·의존성을 명시하고 설정·문서·마이그레이션은 이를 필요로 하는 산출물에 포함한다. 여러 하위 시스템을 독립적으로 구현·검증할 수 없다면 실행 가능한 경계로 계획을 나눈다.

각 작업에서 독립 완료·검증 가능성, 선행 관계, 공유 쓰기와 격리 비용을 확인한다. 이득이 있는
독립 작업은 [병렬 위임 경계](../../references/delegation.md)에 따라 같은 실행 묶음의
작업자로 배정하고, 나머지는 root의 순차 작업으로 둔다. 작업별 담당 역할·실행 묶음·쓰기
범위를 기록한다. 나눌 수 있어 보이지만 직접 처리할 작업은 구체적인 의존성이나 조정 비용을
기록한다. 작업자 수를 파일 수나 고정 비율로 정하지 않는다.

| 흐름 | 요구사항 | 입력과 결과 | 파일과 책임 | 작업과 의존 관계 | 검증과 이유 |
| --- | --- | --- | --- | --- | --- |
| `F1` | [기존 REQ/NFR ID 또는 실제 요구 출처] | [입력 → 결과] | [`path`: 기존/새 책임] | [Task N; 선행 흐름/작업] | [다음 단계에서 선택한 검증과 이유] |

PRD 여부와 관계없이 입력에 이미 있는 요구사항·품질 ID를 출처와 함께 보존한다. 출처에 없는 REQ/NFR ID는 만들지 않으며 ID가 없는 계획에는 실제 이슈·티켓·사용자 요청을 요구 출처로 적는다. 셀에 연결할 별도 출처가 없으면 `-`로 두고 `Requirements source`의 원래 요청을 따른다.

각 요구사항의 관련 수용 기준을 해당 흐름과 검증에 연결하고 동작 검증의 `expected_source`에서 그 기준을 식별할 수 있게 한다. 정상·실패·재방문 등 합의된 조건 중 빠진 것이 없는지 확인한다. 티켓 없이 PRD-lite에서 넘어오는 계획에도 적용하며, 한 흐름에 여러 기준을 연결할 수 있다. 새 기준이나 기준별 별도 작업·테스트를 형식적으로 만들지 않는다.

합의된 P1/P2 등 우선순위도 해당 요구사항 셀이나 `Requirements source`에 보존한다. 합의된 구현 범위·출시 순서가 있으면 관련 흐름·작업에 연결하되, 우선순위 라벨만으로 P2를 제외하거나 새 출시 순서·구현 승인을 확정하지 않는다. 티켓을 거치지 않는 PRD-lite 인계에도 적용한다.
관련 비목표·제외 범위는 전역 제약 또는 영향을 받는 흐름·작업의 경계에 보존한다. 제외한 작업을 구현 범위에 넣거나 무관한 작업마다 반복하지 않는다.

해당 범위와 관련된 기존 SUCCESS ID·신호·합의된 측정 방법·기준·근거를 보존하고 이미 승인된 계측·측정 작업은 해당 흐름·검증에 연결한다. 성공 목표를 기능 수용 기준·코드 완료 조건으로 바꾸지 않는다. 측정 방법만으로 새 구현을 승인하거나 인터뷰·출시 후 분석을 구현 작업으로 만들지 않고, 없는 ID·목표값을 만들거나 무관한 흐름에 지표를 반복하지 않는다.

관련 RISK ID·영향·합의된 완화 조건 또는 남은 확인 작업을 해당 흐름의 경계·작업·검증에 연결한다. 우선순위 등 미정 사항의 OPEN ID와 영향도 미결정 항목으로 보존한다. 근거 없는 완화책이나 우선순위를 확정하지 않는다.

한 흐름이 여러 작업에 걸치거나 여러 흐름이 한 작업에 모이면 책임 경계와 순서를 명시한다.

## 3. 검증과 이유 선택

입력·출력·상태·오류 결과를 바꾸거나 자동 검사(정적 검사 포함)를 추가·확장하는 흐름에는 구현과 검사 작성 전에
`initial_state`, `action`, `observed_result`, `expected_source`, `fault_example`을 기록한다.
각 필드의 값과 결측 처리, 기존 검사 확인 및 새 파일 판정 순서는
[test-driven-development](../test-driven-development/SKILL.md#검증-방식을-테스트-작성-전에-정한다)를
따른다. `contract_unresolved`면 해당 흐름의 기대 결과를 확인할 때까지 자동 검사 파일을 만들지
않는다. 흐름마다 선택한 `verification_mode`와 판정 근거를 대응 관계와 작업에 연결한다.

| 변경 | 검증 선택 |
| --- | --- |
| 기능·로직·상태·오류 처리 | 동작 기록과 `verification_mode`를 선택한다. `extend_existing_test`·`new_test_file`이면 RED·GREEN 명령을 포함한다. |
| 버그 | 원래 결함의 입력·결과를 동작 기록에 넣고 `verification_mode`를 선택한다. `one_time_reproduction`이면 전후 명령·결과와 자동 검사 공백을 기록한다. |
| 동작에 민감한 리팩터링 | 바뀌면 안 되는 `observed_result`와 이를 거부할 `fault_example`을 기록하고 `verification_mode`를 선택한다. 순수 기계적 변경은 필요한 결정론적 검사를 사용한다. |
| 자동 검사만 추가·확장 | 프로덕션 변경이 없어도 검사할 결과의 기록과 `verification_mode`를 선택한다. |
| 문서·스킬 | 기존 링크·경로·예시·문서 일관성 검사와 스킬 앞부분 메타데이터 검사를 실행한다. 새 자동 검사를 작성·확장하면 위 선택 절차를 적용한다. 경로 선택·권한·작업 절차 위험에 필요하면 현실적인 동작 평가를 추가한다. |
| 매니페스트·메타데이터 | 기존 구문·참조 경로 검사와 사용 가능한 플랫폼 기본 로더를 실행한다. 새 자동 검사를 작성·확장하면 위 선택 절차를 적용한다. |
| 단순 설정 | 변경 설정을 실제로 소비하는 가장 작은 명령을 실행한다. |

`extend_existing_test`·`new_test_file`에는 테스트 우선 순서를 적용한다. `existing_check`는
기존 검사를, `one_time_reproduction`은 재현 명령을 작업에 명시한다. 정적 변경에는
구문·경로·로더·빌드·실제 소비 명령 중 변경 결과를 확인하는 검사를 지정한다.
정적 문구나 구현을 그대로 반복하는 테스트는 추가하지 않는다.

## 계획 형식

`Requirements source`, `Documentation impact`, `Commit authorization`, `Quality policy`는 대화 계획에도 유지한다. 짧은 계획은 본문에 접근이 있고 전역 제약이 없을 때 `Approach`, `Global Constraints`를 생략할 수 있다. 구현 접근과 파일별 세부사항은 의사코드 뒤에서 도출한다.
`Quality policy`는 **계획서 자체의 형식 검사**가 아니라 계획한 구현의 완료 게이트다. 새 API·오류 응답처럼
관찰 가능한 동작이 바뀌면 `independent`를, 고위험 경계가 확인되면 `red-team`을 적는다.
동작과 공개 계약이 그대로인 기계적 변경만 `checks`로 둔다.

선택과 판단의 근거에는 종류를 붙인다: `[사용자 결정]`, `[제공 자료: 대화 발췌 또는 파일 위치]`, `[저장소: 경로:줄]`, `[공식문서: URL]`, `[실험: 명령 → 관찰 결과]`, `[논문/실무자: URL]`. 제공 자료는 실제로 식별할 수 있는 발췌·위치를 남기고 고정 locator가 없으면 그 한계를 밝힌다. 이 태그는 출처만 나타내며 내용의 검증·대표성·합의·승인을 뜻하지 않는다. 인터뷰·피드백을 사용자 결정으로 바꾸지 않고 없는 위치를 만들지 않는다. 근거가 없는 판단은 `[추론]`으로 표시하고 결정 근거로 쓰지 않는다. 결정에 꼭 필요한 추론은 먼저 확인 작업(조회·실험)을 계획하거나 미결정 항목으로 남긴다.

```markdown
# [기능 이름] 구현 계획

**Goal:** [한 문장 목표]
**Requirements source:** [원래 구현 요청·이전 승인·승인 문서; PRD가 있으면 경로와 다루는 REQ ID 목록; 버전 있는 출처의 사용 리비전 또는 고정 snapshot과 해당 범위의 승인 근거; 명시적 구현 전 확인 조건 포함]
**Documentation impact:** [없음·갱신 경로·승인된 생성 경로·대체할 결정]
**Commit authorization:** [granted for this plan | not granted]
**Quality policy:** checks | independent | red-team (현재 위험과 근거)

## 전역 제약
[모든 작업이 보존할 정확한 제약]

## 동작 흐름 의사코드
FLOW F1: [구현 세부사항보다 먼저 정의한 동작·제어 흐름]
  INPUT: [입력]
  OUTPUT: [관찰 결과]

## 접근 방식
[흐름에서 도출한 접근]

## 흐름 대응 관계
| 흐름 | 요구사항 | 입력과 결과 | 파일과 책임 | 작업과 의존 관계 | 검증과 이유 |
| --- | --- | --- | --- | --- | --- |
| F1 | [기존 REQ/NFR ID 또는 실제 요구 출처] | [입력 → 결과] | [파일·책임] | [작업·의존성] | [검증·이유] |
```

버전 있는 요구 출처는 실제 사용한 리비전 또는 고정 snapshot·범위와 그 범위에 적용되는 승인 근거를 연결한다. 기존 고정 입력이나 승인 기록에 이 연결이 있으면 그 위치를 참조한다. 버전 없는 대화·이슈에 리비전이나 승인 metadata를 만들지 않는다. 실행·재개 시 현재 출처와 대조하고 변경되었거나 승인이 불명확한 범위에 의존하는 작업만 보류한다. 원래 사용자 요청·이전 승인의 효력과 독립적으로 승인된 작업은 유지한다.

PRD·티켓·일반 승인 문서 등 요구 출처에 관련 NFR이 있으면 그 ID와 근거 있는 조건을 해당 흐름과 검증에 연결한다. 미결정 품질 기대는 OPEN ID·영향·확인 작업으로 보존하며 임의의 목표 수치를 검증 기준으로 만들지 않는다.

동작 변경 또는 자동 검사 추가·확장 흐름의 검증란에는 `initial_state`, `action`, `observed_result`, `expected_source`,
`fault_example`, `verification_mode`와 선택에 사용한 기존 검사·복구·보조 장치·재발 근거를
실제 값으로 적는다. 기존 정적 검사만 실행하는 변경에는 해당 검사 명령과 기대 결과를 적는다.

영속 요구사항 문서가 없으면 원래 대화를 읽을 수 없는 실행자도 이해할 만큼 승인 맥락을 포함한다. 아래 예시의 대괄호는 작성 시 실제 값으로 채운다. 파일 기반 계획은 checkbox로 실행 상태를 추적하고, `task-brief` 보조 도구가 소비하는 `Task N` heading을 유지한다.

````markdown
### Task N: [산출물]

**Flows:** `F1`
**Files:**
- Create: `exact/path/new.py`
- Modify: `exact/path/existing.py:123`
- Verify: `tests/exact/path/test.py` 또는 실제 검증 대상

**Interfaces:**
- Consumes: [정확한 선행 입력·인터페이스]
- Produces: [후속 작업이 의존하는 인터페이스]

**Execution:** [root 순차 실행 | worker 역할과 병렬 실행 묶음; 쓰기 범위·worktree]

**Verification:** [`verification_mode` 또는 정적 검사 명령]
**Verification reason:** [검사 단언·실패 근거 또는 `recovery_proven`·`new_support_count`·`recurred_fault`의 실제 값]

- [ ] **단계 1: 기대 동작·불변식 확인**
[실제 테스트·명령·불변식. TDD이면 실패 테스트와 예상 실패.]

- [ ] **단계 2: 최소 변경**
[정확한 수정 내용이나 코드]

- [ ] **단계 3: 결과 검증**
Run: `[정확한 명령]`
Expected: `[관찰 가능한 결과]`

- [ ] **단계 4: 차이와 문서 정합성 리뷰**
[대조할 경로와 요구사항]
````

## Git 권한과 실행 방법

현재 사용자 승인에 맞게 `Commit authorization: granted for this plan` 또는 `Commit authorization: not granted`를 기록한다. 계획은 Git 권한을 부여하지 않는다. `git add`·`git commit`을 자동 작업 단계로 추가하지 않으며 푸시·PR·병합·배포도 각각의 권한을 따른다.

직접 실행과 위임은 `engineering:execute-plan` 절차를 사용한다. 계획한 실행 묶음은
진입 시 현재 의존성·도구 수용량을 다시 확인하고 적격 작업자를 실제로 할당한다. 파일 계획과
작업별 커밋은 위임의 선행 조건이 아니다. 작은 brief는 직접 전달하고, 큰 계획의 파일 사본은
선택적으로 사용한다.

## 자체 리뷰와 준비 상태 게이트

인계 전에 요구사항(PRD가 있으면 REQ ID) → 흐름 → 파일·작업·의존성 → 검증의 추적성을 대조한다. 실제 경로·인터페이스·type·값, 문서 영향, 권한과 실행 가능성을 확인한다. 자리표시자, 미정 오류 처리, 명령·예상 결과 없는 검증, 정의되지 않은 인터페이스와 추측성 작업을 해소한다.

[품질 게이트 계약](../../references/quality-gates.md)에 따라 정확한 계획 리비전의 자체 리뷰 근거를 기록한다. 여러 구성 요소·장기·고위험 계획 또는 독립 리뷰가 위험을 줄이는 경우 [계획 검토자](plan-document-reviewer-prompt.md)를 사용한다. 선택적 리뷰 제외는 `not_applicable`, 필수 검토자 부재는 `blocked` 또는 `not_run`이다.

준비 상태 리뷰는 초기 리뷰 포함 최대 5회이며 세션·담당자 변경으로 초기화하지 않는다. 재시도에는 변경된 작업·요구사항 근거·인터페이스·평가 문맥이 있어야 한다. 작업 결함은 계획으로, 요구사항 모순은 `engineering:brainstorming`에 돌린다. 산출물·리비전·근거·지적·상태·반환 대상·회차·의사결정 담당자를 기록한다. `passed` 또는 정확한 리비전에 대한 사람의 명시적 `accepted_risk`가 인계 근거다. 상한 도달은 통과가 아니다.

## 계획 변경과 재개

입력·결과·외부 상태·분기·오류·인터페이스·책임·의존성·범위·위험·검증 전략을 바꾸는 차이는 중대한 계획 변경이다. 흐름을 보존하는 보조 도구 이름·동등한 표현·작은 배치는 작업 안에서 처리한다.

1. 차이와 이유를 기록하고 의존 작업을 보류한다. 독립적인 승인 작업은 계속한다.
2. 승인된 요구사항·설계·관찰 가능한 계약이 바뀌면 `engineering:brainstorming`으로 변경안을 보내 사용자 재승인을 받는다. 기존 계약 안의 계획 수정은 새 승인 대화 없이 처리한다. 계획 준비 상태는 사용자 승인을 대신하지 않는다.
3. 의사코드 → 대응 관계 → 작업·검증 순서로 갱신한다.
4. 영향받은 완료 작업의 이전 근거가 새 흐름을 다루지 않으면 `reopened`로 표시하고 구현·검증·리뷰를 다시 수행한다.
5. 변경된 계획의 자체 리뷰·준비 상태 게이트를 적용하고 가장 이른 실행 가능한 미완료·reopened 작업부터 재개한다.

## 완료 계약 인계

계획 위치·권한·준비 상태·남은 결정, unit 의존성·산출물·검사·정책을 실행자에게 전달한다.
설계와 계획의 gate는 읽을 수 있는 고정 문서 패키지를 식별하며, 이후 구현 workspace 변화로
그 문서의 근거를 자동 만료시키지 않는다. 실제 계약 변화는 의존 근거를 다시 연다.
`checks`, `independent`, `red-team`은 위험에 따라 선택한다. 계획이 있다는 이유만으로
red-team을 추가하지 않는다. 실행 방식은 Git·외부 권한을 늘리지 않는다.
