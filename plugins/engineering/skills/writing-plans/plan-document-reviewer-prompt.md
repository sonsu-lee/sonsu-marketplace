# 계획 문서 리뷰 프롬프트

전체 계획을 작성했고 독립 리뷰가 구현 위험을 줄일 때 사용한다. 조정자는 정확한 계획 리비전·요구사항 출처와 [공통 실행 계약](../using-engineering-skills/references/agent-execution.md)에 맞는 문맥을 제공한다.

```text
계획이 실행 가능하고 승인된 요구사항을 충족하는지 읽기 전용으로 검토한다.

리뷰할 plan: [계획 파일 경로]
요구사항 출처: [요구사항 출처]

원래 구현 요청·이전 사용자 승인도 유효한 출처다. 별도 설계 승인 메시지가 없다는 사실만으로
결함을 만들지 않는다. 설계 전용 요청·명시적 구현 전 확인 조건·실제 승인 계약 변경을 구분한다.

다음을 확인한다.
- 요구사항: 승인된 결과·제약을 빠짐없이 다루고 범위를 불필요하게 넓히지 않았는가.
- 순서: 동작 의사코드 → 파일·작업·의존성 대응 관계 → 검증 방법·이유를 따르는가.
- 의사코드: 필요한 입력·결과·순서·상태·분기·반복·오류·경계·책임·미확인 가정이 드러나는가.
- 추적성: 각 흐름이 파일·작업·의존성·검증에 연결되고 작업에서 흐름 ID를 찾을 수 있는가.
- 실행 가능성: 실제 경로·인터페이스·정확한 값·명령·예상 결과가 있고 자리표시자가 해소됐는가.
- 검증: TDD 또는 다른 방법을 흐름과 회귀 위험에 맞게 골랐고 이유가 있는가.
- 변경 처리: 승인 계약 변경에 필요한 재승인과 영향받은 완료 작업의 reopened·재검증이 있는가.
  기존 계약 안의 계획 갱신을 새 사용자 승인으로 취급하지 않았는가.
- 문서·권한: 문서 영향과 커밋·외부 작업이 실제 승인 범위 안에 있는가.
- 완료: 일반 전체 변경 리뷰 뒤 fresh-context 레드팀과 지적의 반환 경로가 있는가.

잘못된 구현이나 실행 차단을 일으킬 공백만 차단 지적으로 보고한다. 표현·문체 선호와
비차단 개선은 권고로 구분한다. 필수 근거 공백은 확인할 항목과 함께 명시한다.

출력:
## 계획 리뷰
**Status:** Approved | Issues Found
**Issues:**
- [작업 X, 단계 Y]: [구체적인 문제·근거와 구현 영향]
**Recommendations:**
- [비차단 개선 제안]
```

조정자는 [품질 게이트 계약](../using-engineering-skills/references/quality-gates.md)에 따라 실제 근거와 `Status`를 기록한다. 필수 근거 공백은 `Approved`만으로 해소되지 않는다.
