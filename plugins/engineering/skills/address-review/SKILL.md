# 리뷰 피드백 처리

리뷰 의견은 검토가 필요한 주장이다. [공통 리뷰 기준](../../references/review-criteria.md)으로
현재 코드·요구사항·사용 중인 버전의 기본 동작과 유효 설정을 대조한 뒤 수정 여부를 정한다.

## 절차

1. 동작 문제는 발생 조건을, 구조 문제는 현재의 이해·수정 비용과 영향을 확인한다.
   심각도 이름보다 실제 근거를 보고, 기존 처리로 요구를 충족하면 이유와 함께 지적을 닫는다.
2. 유효한 차단 지적과 사용자가 수정을 요청한 지적은 최소 변경으로 해결하고 영향받은 동작을
   검증한다. 추가 설정·timeout·추상화가 필요하면 기존 처리로 부족한 이유를 확인한다.
3. 미확인 가정은 관련 코드·설정·문서로 확인한다. 이전 PR의 선택 이유나 공식 권장이 현재
   버전·환경·문제에도 적용되는지 대조한다. 판정에 필수인 근거 공백만 반환한다.
   근거 있는 비차단 구조 지적은 보고하며, 후속 구현은 요청된 범위에서 다룬다.
4. 승인된 계약이나 권한을 바꿔야 하면 해당 결정만 확인한다. 기존 승인으로 해결할 수 있는
   선택은 직접 처리하고 독립적인 승인 작업은 계속한다.

### 작업 연속성

여러 단계 작업이나 외부 쓰기를 맡은 조정자는 [연속성 참고 자료](../../references/continuity.md)를 적용한다.

## 결과

지적마다 수정·근거로 기각·비차단 보고·필수 확인 필요 중 실제 상태와 이유를 짧게 보고한다.
차단 지적의 원래 리비전과 근거를 보존하고 [품질 게이트 계약](../../references/quality-gates.md)에
따라 변경 영향과 집중 재리뷰 결과를 현재 리비전에 연결한다.

## 예시

입력: “업로드 처리의 `suggestion`대로 파일 이름 정규화를 한 번 더 넣어 줘.”
현재 업로드 경계와 모든 호출자를 확인한 결과 같은 정규화가 이미 적용된다면
`근거로 기각 — 경계의 정규화 결과만 소비하므로 중복 처리 불필요`로 보고한다.
우회 호출자가 원문 이름을 넘긴다면 해당 경계를 최소 수정하고 영향받은 검증 근거를 연결한다.

## 경계

- 질문형 표현·`suggestion` 여부 대신 현재 근거로 판정한다. 효과 주장·중복 지적·추가 증적
  요구를 공통 기준과 대조하고 필요한 조건·예외를 보존한다.
- 관찰 도구의 `ready`·무알림과 의미적 통과를 구분한다. 기존 필수 검증·독립 리뷰는 유지하며
  선택적 개선은 새 등록·필수 수정·재검토 조건으로 승격하지 않는다.
- GitHub 리뷰 답글은 사용자가 전송을 승인한 경우 해당 인라인 댓글 대화에 남긴다.
