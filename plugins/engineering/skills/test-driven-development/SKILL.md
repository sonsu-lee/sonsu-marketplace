# 테스트 주도 개발(TDD)

기대 동작을 테스트로 표현하고 의도한 이유로 실패하는지 확인한 뒤, 통과하는 최소 구현을 만든다.
RED–GREEN–REFACTOR는 테스트가 결함을 포착하는지 확인하면서 동작을 구현하는 절차다.

## 작업 연속성

여러 단계의 작업이나 외부 쓰기를 맡은 조정자는 [연속성 참고 자료](../../references/continuity.md)에
따라 진행을 기록하고, 재개할 때 현재 근거와 대조한다. 단발 작업, 위임된 에이전트와 독립
리뷰어는 별도 기록을 만들지 않는다. 읽기 전용 작업에서는 기록 파일과 Git exclude를 기존 상태로 둔다.

## 검증 방식을 테스트 작성 전에 정한다

계획이 있으면 검증할 흐름마다, 직접 변경이면 검증할 결과마다 아래 기록을 만든다. 새 기능,
로직·상태·입력 검증·오류 처리와 동작이 바뀔 수 있는 리팩터링에 적용한다. 프로덕션 코드를
바꾸지 않고 자동 검사(정적 검사 포함)를 추가하거나 기존 검사에 단언·사례를 추가할 때도 적용한다.

| 필드 | 기록할 값 |
| --- | --- |
| `initial_state` | 실행 전 입력 자료·파일·외부 상태와 필요한 환경 |
| `action` | 호출할 명령·함수와 인수 또는 사용자 동작 |
| `observed_result` | 종료 코드·반환값·파일 내용·외부 상태 중 확인할 대상과 예상 값 |
| `expected_source` | 예상 값을 정한 사용자 요구·이슈·기존 계약의 위치 |
| `fault_example` | 검사에서 거부해야 할 실제 결과 한 가지 |

한 필드라도 채울 근거가 없으면 `contract_unresolved`로 기록하고 기대 동작 또는 재현
조건을 확인한다. 해당 동작의 구현과 자동 검사 파일 작성을 보류하고 예상 값을 추측하지 않는다.
정적 변경에 기존 검사만 실행할 때는 아래 표의 검사 명령과 기대 결과를 기록한다. 정적 변경을
검증하는 새 자동 검사를 작성하거나 기존 자동 검사를 확장할 때는 위 필드와 선택 절차를 적용한다.

기록이 완성되면 다음 순서로 한 가지 `verification_mode`를 선택한다.

1. 기존 검사가 `observed_result`를 직접 단언하고, `fault_example`에 해당하는 결함 상태에서
   실패한 실행 근거가 있으면 `existing_check`다. 기존 검사의 검출력이 `unknown`이면 단언과
   실패 근거를 조사한다. 근거를 얻지 못하면 `unknown`과 이유를 기록하고 다음 단계로 간다.
2. 위 근거가 없고 `action`의 명령·함수·API 경계를 호출하는 기존 검사에
   필요한 보조 장치와 `observed_result` 단언을 추가할 수 있으면 `extend_existing_test`다.
   보조 장치가 필요하다는 사실만으로 기존 검사 확장을 제외하지 않는다.
3. 그 밖에는 새 영속 자동 검사 파일을 후보로 둔다. `new_test_file`은 테스트 파일과 정적 검사
   스크립트를 포함한다. 다음 세 조건이 모두 참이면
   `one_time_reproduction`, 하나라도 거짓이면 `new_test_file`이다.
   - `recovery_proven=true`: 사용자 소유 데이터 손실 없이 원래 상태를 되찾는 명령과
     복구 후 확인 결과를 기록했다.
   - `new_support_count >= 1`: 새 자동 검사를 영속화할 때 필요한 외부 명령 대역, 테스트
     의존성, 실행기 설정, 테스트 전용 프로덕션 인터페이스를 각각 세어 합계가 1 이상이다.
     같은 종류라도 별도 항목이면 각각 센다. 기존 도구와 입력 자료만 사용하면 0이다.
   - `recurred_fault=false`: 관련 저장소 이력과 연결된 이슈를 확인했으며 같은 결함을
     고친 후 재발한 기록이 없다. 재발이 확인되면 `true`와 근거 위치를 기록한다.
     이력을 확인할 수 없으면 `unknown`으로 두고 일회성 검증을 선택하지 않는다.

`one_time_reproduction`은 재현 명령, 구현 전 결과, 수정 후 `observed_result`, 남는 자동
검사 공백을 계획 또는 결과 보고에 남긴다. `existing_check`는 기존 검사를 변경 전후에 실행한다.
`extend_existing_test`와 `new_test_file`은 아래 RED–GREEN–REFACTOR를 따른다. 새 테스트가
기존 단언을 반복하거나 구현 내부만 확인하면 `fault_example`을 잡는 관찰 결과로 다시 설계한다.
선택한 자동 검사를 실행할 도구·환경이 없으면 `blocked`와 부족한 조건을 기록하고, 근거 없이
`one_time_reproduction`으로 바꾸지 않는다.

| 변경 | 기본 검증 |
| --- | --- |
| 문서·주석·표현, 정적 메타데이터 | 정확성·구문·경로·링크 검사 |
| 동작을 유지하는 포맷·이동·기계적 이름 변경 | 참조·구문 및 관련 소비 명령 |
| 생성 코드 | 원본과 생성 결과의 일치, 실제 소비 결과 |
| 단순 설정 | 파서·로더 또는 설정을 소비하는 최소 명령 |
| 입력·출력·오류 결과를 바꾸는 설정·실행 문서 | 실제 소비 동작에 위 `verification_mode` 선택 절차 적용 |

## RED–GREEN–REFACTOR

TDD를 선택한 동작은 실패 테스트를 확인한 뒤 구현한다. 이미 작성한 구현에 테스트를 추가하는
경우에는 사후 검증으로 기록한다. 필요하면 격리된 사본이나 안전하게 되돌릴 수 있는 자신의
수정 범위에서 결함 상태를 재현해 테스트의 검출력을 확인한다. 기존 작업을 일괄 삭제하지 않는다.

### RED: 실패할 동작을 표현한다

테스트 하나가 포착할 결함과 기대 결과를 명시한다. 기대값은 구현과 독립적으로 도출하며,
실제 코드의 관찰 가능한 결과를 검사한다. 외부 경계를 대체해야 하면 해당 경계 계약을 유지한다.

```typescript
test('retries failed operations 3 times', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

관련 테스트 명령을 실행하고 실패 원인을 읽는다.

```bash
npm test path/to/test.test.ts
```

기능 부재나 결함 때문에 예상한 단언이 실패해야 한다. 구문·의존성·테스트 준비 오류라면
그 준비부터 고친다. 바로 통과하면 기존 동작이 이미 요구를 충족하는지 또는 테스트가 결함을
놓치는지 확인한 뒤 테스트나 작업 범위를 조정한다.

### GREEN: 최소 구현으로 통과시킨다

실패한 동작을 만족하는 가장 단순한 변경을 적용한다. 같은 테스트를 실행해 통과를 확인하고,
영향받는 회귀 검사와 선언된 필수 검사를 수행한다. 출력의 오류·경고는 현재 변경과 관련성을
판단한다. 테스트가 실패하면 구현과 기대 계약을 대조하며, 통과시키기 위해 기대값만 바꾸지 않는다.

### REFACTOR: 동작을 유지하며 정리한다

통과 상태에서 필요한 중복 제거·이름 개선·구조 정리를 수행하고 영향받은 테스트를 다시 실행한다.
새 동작이 필요하면 다음 RED 주기로 다룬다. 현재 리비전의 필수 검사가 충족되고 새 변경·실패가
없으면 검증을 마친다. 같은 내용의 검사나 무관한 전체 검사를 반복하지 않는다.

## 예시: 빈 email 거부

아래 출력은 절차 설명용 예시이며 현재 작업의 실행 증거가 아니다.

```typescript
test('rejects empty email', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
```

```text
FAIL: expected 'Email required', got undefined
```

실패를 확인한 뒤 빈 입력을 처리하고 같은 테스트가 통과하는지 확인한다.

```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
```

## 결과를 확인한다

[writing-good-tests.md](writing-good-tests.md)의 기준으로 테스트가 포착할 고장, 독립된 기대값,
실제 동작과 외부 경계 대체의 타당성을 확인한다. 선택한 동작의 RED 실패 이유, GREEN 결과,
관련 회귀 검사와 현재 리비전을 남긴다. 실행하지 못한 검사는 `not_run`, 준비 환경 부재는
`blocked`처럼 실제 상태로 보고한다.

테스트 준비가 과도하면 더 작은 소비 경계나 기존 테스트 도구를 찾는다. 테스트를 위해 공개
인터페이스나 승인된 설계를 바꿔야 한다면 해당 결정을 확인한다. 사소한 코드나 산문에는
절차를 충족하기 위한 테스트를 추가하지 않는다.
