# executing-plans: 계획 실행

승인된 계획을 검토하고 작업을 실행·검증한 뒤 현재 변경의 근거를 보고한다. 이 경로는 작업별 커밋 없이도 실행할 수 있다. 파일 기반 계획과 하위 에이전트 기능이 있고 작업별 커밋까지 명시적으로 승인됐다면 `engineering:subagent-driven-development`를 선택할 수 있다.

주 조정자의 여러 단계 작업은 [task-continuity](../task-continuity/SKILL.md)에 기록한다. 위임된 작업자와 새 문맥의 검토자는 별도 연속성 기록을 만들지 않는다.

## 1. 실행 준비

1. `engineering:using-git-worktrees`로 현재 작업 공간과 격리 필요성을 확인한다.
2. 계획을 원래 구현 요청·이전 승인·승인 문서와 대조한다. 대화 계획은 정확한 작업을 할 일에 보존한다.
3. `engineering:writing-plans`의 의사코드가 구현 세부사항보다 앞서고 각 흐름 ID가 파일·작업·의존성·검증 방법과 이유에 연결되는지 확인한다.
4. 계획의 커밋 권한을 현재 사용자 승인과 대조한다. 미승인 커밋 단계는 보류하고 승인된 수정·검증은 계속한다.
5. [품질 게이트 계약](../using-engineering-skills/references/quality-gates.md)에 따라 현재 계획 리비전의 준비 상태를 확인한다. 오래된 근거나 `failed`, `blocked`, `inconclusive`, 필수 `not_run`은 해당 계획·근거 소유 단계로 돌린다.
6. 기존 자료로 해결할 내부 선택은 반영한다. 사용자 결정이 필요한 계약 공백은 의존 작업만 보류하고 실행 가능한 승인 작업을 선택한다.

Fast Path 탈락·일반 경로 전환·재개는 기존 구현 승인을 취소하지 않는다. [brainstorming의 실행 권한](../brainstorming/SKILL.md)을 따른다. 설계 전용은 요청된 산출물까지 완성하고 구현 전에 종료한다. 명시적 구현 전 확인도 산출물을 먼저 완성해 제시하며, 그 확인에 의존하지 않는 승인 작업은 계속한다.

## 2. 작업 실행

[공통 실행·문맥 계약](../using-engineering-skills/references/agent-execution.md)에 따라 작업/게이트 ID, 소스 리비전, 쓰기 범위, 실행 환경·임시 자료, 소비·남은 예산, 요청·관측한 모델/추론 수준과 완료 상태를 기록한다.

각 실행 가능한 작업에서 다음을 수행한다.

1. `in_progress`로 표시하고 지정한 단계와 검증을 실행한다.
2. 정확한 작업 차이 또는 산출물 리비전에 명령·결과·지적과 작업 게이트를 기록한다.
3. 실패 원인이 알려져 있으면 가장 작은 구현 단계로 돌린다. 원인이 불명확하면 `engineering:systematic-debugging`을 적용한다.
4. 검증과 리뷰의 필수 조건이 `passed`이거나 사람이 정확한 리비전의 위험을 명시적으로 `accepted_risk`로 수용하면 `completed`로 표시한다.
5. 보류 작업을 남긴 채 완료로 처리하지 않는다. 독립적인 승인 작업이 있으면 이를 계속한다.

도구·실제 접근 권한·의존성·외부 서비스 부재는 `blocked`로 기록하고 재개 조건을 밝힌다. 승인 부재와 실행 환경 부재를 구분한다. 실패했다는 사실만으로 사용자 결정을 요구하지 않고 아래 수정 예산 안에서 원인을 해결한다.

## 수정 회차와 인계

유효한 차단 지적만 수정 대상으로 삼는다. 근거로 반박된 지적은 이유와 함께 닫고, 작업·인터페이스 결함은 `engineering:writing-plans`, 승인된 요구사항·설계의 모순은 `engineering:brainstorming`, 환경·기능 부재는 해당 소유 단계로 보낸다.

수정은 작업마다 최대 5회이며 회차·소비 예산을 진행 기록에 남긴다. 더 낮은 작업·게이트 상한과 남은 부모 예산이 우선한다. 세션 재개·문맥 압축·담당자 변경·새 패키지 때문에 초기화하지 않는다.

| 회차 | 구현 담당 |
| --- | --- |
| 1~3 | 직접 구현한 조정자 또는 원래 구현자가 집중 수정한다. 원래 담당자를 사용할 수 없거나 새 반례에도 같은 잘못된 가정으로 진전이 없으면 새 문맥의 구현자로 전환할 수 있다. |
| 4~5 | 이전 대화를 상속하지 않는 새 문맥의 구현자를 사용한다. Codex에서는 `fork_turns: "none"`을 사용한다. |

역할 적합성과 앞선 실패를 기준으로 필요한 기능을 선택하고 공통 실행 계약에 요청·관측 설정을 기록한다. 특정 등급 순서를 강제하지 않는다. 필요한 기능이 없으면 `blocked`와 `decision_required`로 기록한다. 새 문맥으로 조기 전환해도 같은 예산을 소비하며 3+2는 운영값이다.

[fix-implementer-prompt.md](fix-implementer-prompt.md)에 다음 사실을 전달한다.

- 승인된 작업 요약과 정확한 현재 리비전
- 작업 최초 구현 전 기준점부터 현재까지의 누적 바이너리를 보존하는 산출물 패키지
- 현재 열린 지적
- 관찰한 명령·결과와 이미 시도한 실패. `Fact:`와 `Hypothesis:`로 관찰과 원인·해법 가설을 구분한다.
- 같은 작업/게이트 ID, 소비·남은 부모 예산·기한, 허용된 쓰기·실행 환경·임시 자료 범위

전체 대화나 구현 서사·자기변호·자체 리뷰·검토자 칭찬·통과 판정·에이전트 식별자는 제외한다. 별도 엄격한 JSON 스키마나 수정 전용 tar 형식은 필요하지 않다. 현재 패키지와 리비전을 결합할 수 없거나 필수 근거를 읽을 수 없으면 `blocked`다. 마지막 수정 변경분는 누적 산출물을 대체하지 않으며 재리뷰에만 사용한다.

각 수정 뒤 원래 지적과 수정이 만든 회귀를 집중 검증·재리뷰한다. 재시도에는 산출물·근거·가설·문맥·평가자·기능·사용자 결정 중 바뀐 입력이 있어야 한다. 5회 뒤 유효한 필수 지적이 남으면 `failed`, `decision_required`와 반환 대상을 기록하고 해당 자동 반복을 끝낸다. 위험은 정확한 리비전에 대해 사람만 명시적으로 수용할 수 있다.

## 계획과 구현이 달라질 때

`engineering:writing-plans`의 중대한 계획 변경 기준을 적용한다. 차이와 이유를 설명하고 의존 작업을 보류하되 독립적인 승인 작업은 계속한다. 승인된 요구사항·설계·관찰 가능한 계약이 바뀌면 `engineering:brainstorming`에서 재승인한다. 기존 계약 안의 계획 수정은 의사코드 → 대응 관계 → 작업·검증 순서로 갱신하고 준비 상태를 다시 확인한다. 이전 근거가 새 흐름을 다루지 않는 완료 작업은 `reopened`로 표시해 구현·검증·리뷰를 재개한다.

## 3. 전체 변경의 완료 게이트

모든 작업이 완료되면 다음 순서를 적용한다. 상세 판정과 근거 연결은 [품질 게이트 계약](../using-engineering-skills/references/quality-gates.md), 검토자 입력은 `engineering:requesting-code-review`를 따른다.

1. 승인된 계획·관련 문서와 전체 차이를 대조하고 전체 변경에 필요한 결정론적 검증을 실행한다. 실패는 구현·통합·검증 소유 단계로 돌린다.
2. 독립적인 일반 전체 변경 리뷰를 수행한다. 필수 검토자 부재는 `blocked` 또는 `not_run`이며 자체 리뷰로 대체하지 않는다.
3. 유효한 지적을 소유 단계에서 수정한다. 국소 수정이면 이전 전체 게이트 리비전, 수정 차이, 다룬 지적·검사, 영향이 제한됐다는 근거와 현재 리비전의 새 집중 게이트를 기록한다. 이 연결로 영향받지 않은 기존 근거를 유지한다.
4. 승인된 목표·계약·설계·의존 경계가 바뀌었거나 영향 범위를 확정할 수 없으면 전체 패키지를 다시 만들고 새 문맥의 전체 변경 검토자로 일반 게이트를 다시 연다. 일반 리뷰는 집중·전체 재개방을 합해 게이트당 최대 5회이며 담당자·세션 변경으로 초기화하지 않는다.
5. 현재 리비전의 일반 게이트가 `passed` 또는 사람의 명시적 `accepted_risk`이면 아래 새 문맥의 레드팀을 수행한다.

### 새 문맥의 레드팀

레드팀 직전에 저장소 루트에서 현재 전체 변경을 다시 고정한다.

검토할 저장소를 현재 작업 디렉터리로 유지하고, 설치된 `requesting-code-review` 스킬의
`scripts/` 절대 경로를 `REVIEW_SCRIPTS`로 확인한다. 도구는 이 작업 디렉터리의 Git 변경을 읽는다.

```text
"$REVIEW_SCRIPTS/review-package" range BASE HEAD
"$REVIEW_SCRIPTS/review-package" working-tree
```

커밋 작업은 전체 범위, 직접 실행은 전체 작업 트리에 맞는 방식을 선택한다. 수정 범위나 이전 리비전의 패키지를 재사용하지 않는다.

원래 목표, 승인된 요구사항·설계, 계획 의사코드·대응 관계, 결정론적 검증 보고서, 관찰 결과·제약, 지적에서 수정까지의 근거 이력을 여섯 파일로 고정한다. 근거 이력에는 지적 원문·근거와 적용 리비전·path를 담고 판정·칭찬은 제외한다. 해당 변경이 없으면 `none`을 기록한다. 이 파일들과 전체 변경 패키지를 같은 설치 경로의 `"$REVIEW_SCRIPTS/red-team-package"`에 전달해 시도별 변경 불가능한 묶음과 SHA-256을 만든다.

[red-team-reviewer.md](../requesting-code-review/red-team-reviewer.md)에 따라 이전 작업·리뷰의 대화나 결론을 상속하지 않는 검토자에게 묶음 경로와 해시만 전달한다. 별도의 변경 가능한 소스 경로는 전달하지 않는다. 최초 레드팀은 현재 전체 목표와 변경을 검토한다.

| 판정 | 처리 |
| --- | --- |
| `survives_challenge` | 일반 통과로 기록한다. |
| `invalidated` | 목표·요구사항·설계·계획·구현·검증 중 지적 원인을 바꿀 소유 단계로 보낸다. |
| `inconclusive` | 필수 근거 공백을 해소한다. |
| `blocked` | 필요한 산출물·기능·외부 상태의 재개 조건을 기록한다. |

레드팀 뒤 국소 수정은 집중 검증·재리뷰를 먼저 마치고 기존 일반 게이트 근거를 현재 리비전에 연결한다. 현재 전체 입력을 새 묶음으로 고정한 뒤 새 문맥의 집중 레드팀 검토자가 이전 반례 검토와 수정 회귀만 판정한다. 이전 레드팀 리비전·변경분·반례 검토·검사·제한된 영향 근거·새 집중 게이트를 기록한다.

목표·계약·설계·의존 경계가 바뀌거나 영향이 불명확하면 전체 결정론적 검증과 일반 전체 리뷰를 갱신한 뒤 전체 레드팀을 다시 연다. 근거·기능만 바뀌고 산출물이 같으면 일반 게이트를 유지할 수 있으나 레드팀 입력은 다시 고정한다. 레드팀도 게이트당 최대 5회이며 담당자·세션 변경으로 초기화하지 않는다. 상한의 미해결 위험은 `decision_required`로 남기며 사람의 정확한 `accepted_risk` 없이 완료로 처리하지 않는다.

## 4. 결과 보고와 Git 전달

정확한 작업 트리 또는 커밋 리비전에 결정론적 검증·일반 리뷰·레드팀 상태를 각각 기록한다. 변경 내용·검증 근거·미실행 검사·남은 위험·보류 작업을 보고한다.

커밋 권한이 없으면 검증된 변경을 커밋하지 않은 상태로 전달한다. 커밋 결정 요청은 사용자가 전달 작업까지 요청했거나 다음 단계에 실제로 필요할 때만 한다. 별도 승인 없이 스테이징·커밋·푸시·PR·병합·배포로 범위를 넓히지 않는다.

커밋이 승인됐다면 해당 범위만 처리하고 커밋된 트리와 검증 산출물의 일치를 확인한다. 이전 근거가 다루지 않는 변경에는 필요한 검사를 실행한다. 기존 커밋의 통합·보존 방법을 정해야 할 때 `engineering:finishing-a-development-branch`를 사용한다.
