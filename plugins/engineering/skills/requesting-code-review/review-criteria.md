# 공통 리뷰 기준

현재 동작의 결함과 아키텍처·유지보수성 문제, 근거 있는 단순화 기회를 검토한다.

1. **맥락부터 확인한다.** 변경 내용과 관련 호출자·설정·검증 근거를 읽는다. 잘못된 동작을
   가정한 채 수정안을 만들지 않는다. 판단에 필요한 부분만 추가로 확인한다.
2. **이미 제공되는 동작을 확인한다.** 처리가 빠졌다고 지적하기 전에 사용 중인 버전의
   framework·library·provider 기본 동작과 현재 설정·override를 확인한다. 기존 근거가
   충분하면 확인을 마치고, 판정에 영향을 주는 불확실성만 공식 문서·소스·집중 검사로 해소한다.
3. **문제에 맞는 근거를 제시한다.** 동작 결함은 발생 조건과 요구사항·불변식 위반을
   재현이나 실행 경로로 설명한다. 구조 문제를 지적할 때는 현재의 책임·의존 관계, 중복된 도메인 지식,
   불필요한 간접 참조가 어디에서 이해·수정 비용을 늘리는지 설명하고, 같은 동작을 유지하는 대안을 제시한다.
   구조 지적에 런타임 버그 재현은 필요하지 않다. 파일 길이·호출자 수 자체나 취향·미래
   요구만으로 판단하지 않는다. 승인된 설계의 문제는 근거와 함께 설계 소유자에게 반환한다.
4. **가장 작은 수정을 제안한다.** 삭제·기존 동작 재사용·국소 수정을 먼저 검토한다.
   timeout·retry·validation·설정·추상화를 추가하려면 기존 처리로 부족한 이유를 제시해야 한다.
   필요한 보호와 명시된 요구사항은 유지한다. 짧은 코드나 적은 줄 수 자체는 목표가 아니다.
5. **보고와 차단을 구분한다.** 같은 원인의 지적은 합치고 심각도는 실제 영향으로 정한다.
   Critical/Important로 분류하려면 진행 전에 해결해야 하는 이유를 제시해야 한다. 근거 있는 구조 개선도
   보고하되 차단할 정도가 아니면 비차단으로 표시한다. 비차단 지적만으로 재리뷰·수정 loop나
   backlog를 만들지 않는다. 취향·가상 엣지케이스·추측성 hardening은 기본 finding이 아니다.

출력은 **판정 → finding(위치·근거·영향·최소 수정) → 판정에 필수인 근거 공백**이다.
finding과 공백이 없으면 판정과 짧은 근거만 쓴다. 필수 검증이 빠졌다면 지적이 0개라는 이유만으로
통과 처리하지 않는다. 칭찬, 빈 심각도별 항목과 일반적인 개선 제안은 채우지 않는다.
