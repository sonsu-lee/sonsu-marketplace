# brainstorming: 설계 구체화

요청과 기존 코드를 읽고 작업 경로, 관찰 가능한 결과, 필요한 결정을 정한다. 분류와 다음 단계를 짧게 알린다.

## 실행 권한

현재 요청, 이전 사용자 승인, 승인된 문서·이슈에서 실행 범위를 확인한다. 구현 요청의 목표·결과·제약이 충분하면 기존 코드와 관례에 따른 내부 선택을 설명하고 진행한다. 별도의 설계 승인 메시지는 필수 조건이 아니다.

| 조건 | 수행 범위와 다음 단계 |
| --- | --- |
| 승인된 구현이며 미결정 계약이 없음 | 필요한 탐색·설계·계획·수정·검증을 계속한다. |
| 설계·검토 전용 요청 | 요청한 산출물을 완성하고 구현 전에 종료한다. |
| 아직 충족되지 않은 명시적 구현 전 확인 조건 | 먼저 요청된 설계·문서·계획을 완성해 제시한다. 응답을 기다리는 의존 작업만 보류하고 독립적인 승인 작업은 계속한다. |
| 미결정 제품 규칙, 충돌하는 요구사항, 승인된 목표·설계·관찰 가능한 계약의 변경 | 결정에 필요한 근거와 변경안을 제시한다. 해당 의존 작업은 사용자 확인까지 보류하고 독립적인 승인 작업은 계속한다. |
| 이미 충족된 확인 조건 | 그 승인 범위에서 계속한다. 절차 전환이나 재개를 이유로 다시 열지 않는다. |

Fast Path 적합성, 작업 복잡도, 계획 필요 여부와 품질 판정은 실행 권한을 부여하거나 취소하지 않는다. Git·배포·외부 쓰기는 각각의 권한을 확인한다. 응답이 없다는 사실은 승인이 아니다.

주 조정자의 여러 단계 작업은 [task-continuity](../task-continuity/SKILL.md)에 기록한다. 위임된 작업자와 새 문맥의 검토자는 별도 연속성 기록을 만들지 않는다.

## 작업 경로

| 경로 | 판정 기준 | 산출물과 순서 |
| --- | --- | --- |
| `spike` | 유지할 구현보다 가능성·원인·대안을 조사하는 요청 | 질문과 확인 범위를 2~3문장으로 정리하고 승인된 조사 범위에서 확인한다. 지적과 권고안을 보고하고 시험 조사 코드는 폐기용으로 표시한다. 유지할 코드로 전환하려면 그 구현의 범위와 권한을 새로 확인한다. |
| `bounded` | 저장소에 존재하는 읽을 수 있는 흐름을 범위가 명확하게 수정 | 아래 Fast Path를 먼저 판정한다. 일반 경로에서는 필요한 탐색 뒤 접근·예상 동작·수정 파일을 대화에 정리한다. 여러 단계·인터페이스·상태·오류·회귀 위험을 조정해야 하면 `engineering:writing-plans`, 그 외에는 직접 구현과 비례적 검증으로 진행한다. 별도 명세 파일은 만들지 않는다. |
| `architectural` | 새 프로젝트·하위 시스템, 구성 요소 구성 재편, 다른 대상이 의존하는 인터페이스 변경 | 문맥 확인 → 필요한 명확화와 접근 비교 → 설계와 문서 영향 정리 → 필요한 문서 검증 → `engineering:writing-plans` 순서로 진행한다. |

앱 종류에 익숙하다는 사실만으로 `bounded`로 분류하지 않는다. 경로가 불명확하거나 숨은 복잡성이 드러나면 더 충분한 절차로 올리고 이유를 알린다. 같은 작업에서 경로를 다시 낮추거나 Fast Path에 재진입하지 않는다. 전환 뒤에도 위 실행 권한은 유지한다.

## 범위가 한정된 Fast Path

Fast Path는 의도·영향 범위·변환 규칙·검증을 짧고 결정론적으로 닫을 수 있는 계획 없는 `bounded` 작업이다.

### 1. 식별자와 상태 확인

대상 탐색 전에 고정된 할 일 ID 또는 한 번 생성한 UUID로 `TASK_ID`를 고정한다. 대상, 재개, 문맥 압축, 인계 때문에 다시 만들지 않는다. `EXECUTION_ID`는 현재 중단 없는 조정자 실행에만 쓴다. 재개·문맥 손실·재진입 시 새로 만들며 이전 값을 상태나 대화에서 복구하거나 인계하지 않는다.

작업할 저장소 루트에서 실행한다. 현재 읽은 스킬의 설치 위치에서 `scripts/`의 절대 경로를
확인해 `BRAINSTORMING_SCRIPTS`로 둔다. `STATE_ROOT`는 작업 저장소 안의 정본 절대 경로로 지정한다.

```bash
STATE_ROOT="$REPOSITORY_ROOT/.engineering/fast-path"
STATE_FILE="$STATE_ROOT/$TASK_ID.state"
"$BRAINSTORMING_SCRIPTS/fast-path-state" begin \
  "$STATE_ROOT" "$TASK_ID" "$EXECUTION_ID"
```

`disqualified`이면 아래 적합성 판정과 Fast Path 실행을 건너뛰고 일반 경로로 보낸다. 이전 형식 v1 상태, 다른 `EXECUTION_ID`로 돌아온 실행, 이미 탈락한 작업도 영구 `disqualified`다. `active`는 예산 추적 상태이며 적합성이나 승인 증거가 아니다. 조정자가 문맥 손실과 실행 경계를 판정한다.

### 2. 현재 파일에서 적합성 판정

참조·소비자·공개 계약 위험·미확인 사항·검증 기준을 한 번 묶어서 확인한다. 별도 분류기는 필요하지 않다. 필요한 표적 탐색은 작업 전체에서 최대 2회이며 각 탐색 직전에 예약한다.

```bash
"$BRAINSTORMING_SCRIPTS/fast-path-state" reserve \
  "$STATE_ROOT" "$TASK_ID" "$EXECUTION_ID" search
```

다음 조건이 모두 입증되고 숨은 위험 신호가 없어야 한다.

- 요청의 대상, 관찰 가능한 결과, 완료 조건이 명확하다.
- 효과가 국소적인 국소 Fast Path 또는 동일 규칙을 재현할 수 있는 기계적 Fast Path다.
- 직접 참조·호출자·소비자 범위를 최대 2회의 표적 탐색으로 닫을 수 있다.
- 새로운 제품·설계 판단이 필요하지 않다.
- 공개 인터페이스, 스키마, 상태 모델, 권한, 마이그레이션, 호환성 계약을 바꾸지 않는다.
- 저렴하고 결정론적인 검증 방법이 있다.
- 변경이 가역적이고 승인된 범위 안에 있다.

국소 Fast Path에는 소비 위치가 명확한 내부 상수·비공개 보조 도구·오탈자·링크·검증용 자료·설정이 해당한다. 실행 중 동적 호출, 리플렉션, 플러그인 로딩으로 소비자를 닫을 수 없으면 일반 경로를 사용한다.

기계적 Fast Path에는 포매터, 정확한 키·가져오기·경로 변경, 정해진 스키마의 데이터 갱신, 정본 생성기, 명시된 문자열 정규화가 해당한다. 스크립트·AST·명령·Code Mode로 같은 규칙을 재현할 수 있어야 한다. 공개 API, DB 마이그레이션, 인증·권한, 의존성 주 버전 갱신, 대량 삭제, 의미가 다른 문자열의 일괄 치환은 제외한다. 파일 수나 Code Mode 사용 가능성만으로 판정하지 않는다.

입증한 적합성은 현재 실행에서 즉시 사용하며 상태에 승인으로 저장하지 않는다. 같은 `HEAD`라도 이후 실행의 미커밋 파일과 문맥이 그대로라는 보장은 없다.

### 3. 실행 예산과 이탈

최초 구현 1회와 집중 수정 1회만 수행한다. 각 수정 작업 직전에 예약한다.

```bash
"$BRAINSTORMING_SCRIPTS/fast-path-state" reserve \
  "$STATE_ROOT" "$TASK_ID" "$EXECUTION_ID" action
```

현재 실행에서 알고 있는 자기 변경과 그에 대한 집중 수정은 예상하지 못한 파일 변화가 아니다. 다음이 드러나면 남은 예산과 관계없이 먼저 탈락 상태를 기록하고 Fast Path를 종료한다.

- 적합성 조건이 거짓 또는 미확인이다.
- 예상하지 못한 파일 변화·소비자, 문맥 손실·재진입이 있다.
- 두 번째 의미 판단, 여러 책임, 공개 계약, 관련 없는 리팩터링으로 범위가 넓어진다.
- 원인 불명의 검사 실패, 검토자 없이는 판정하기 어려운 상태, 두 번째 수정 필요가 있다.

```bash
"$BRAINSTORMING_SCRIPTS/fast-path-state" disqualify \
  "$STATE_ROOT" "$TASK_ID" "$EXECUTION_ID" "$REASON"
```

### 4. 일반 경로로 인계 또는 완료

| 이탈 원인 | 담당 단계 |
| --- | --- |
| 원인이 불명확한 실패 | `engineering:systematic-debugging` |
| 여러 흐름·인터페이스를 조정하는 확장 | `engineering:writing-plans` |
| 요구사항·설계 변경 | `engineering:brainstorming`에서 해당 결정 확인 |
| 예산 소진·재개·문맥 손실·그 밖의 적합성 탈락 | 일반 `bounded` 절차에서 필요한 탐색·계획 여부 판단 |

인계에는 `TASK_ID`와 상태 파일 경로를 포함하고 `EXECUTION_ID`는 전달하지 않는다. 탈락 상태와 소비 예산은 유지되며 Fast Path 판정으로 돌아가지 않는다. 기존 구현 승인은 계속 유효하고 새 계약 결정에 의존하는 작업만 보류한다.

Fast Path를 완료하면 판정 근거, 실제 변경 범위, 결정론적 검증 결과, 원래 목적과의 정렬을 짧게 보고한다.

## 설계와 문서 작성

기존 파일·문서·최근 변경을 읽고 목적·제약·완료 기준을 확인한다. 결과를 바꾸는 사용자 결정만 질문하고, 기존 자료로 해결할 내부 선택은 직접 정한다. 대안 비교가 유용하면 2~3개 접근의 장단점과 추천안을 제시한다. 설계 깊이는 복잡성에 맞춘다.

영속 문서가 필요하면 기존 README, CONTEXT, docs, ADR, 구조, 제품, 안내, 참고 자료, 운영 절차, 이슈와 티켓을 먼저 확인한다. 문서 영향을 `없음 / 기존 문서 갱신 / 영속 문서 생성 / 기존 결정 대체`로 분류한다. 구조 설명은 구조, 장기 결정은 ADR, 제품 의도는 요구사항, 사용 절차는 안내, 정확한 계약은 참고 자료, 운영·복구는 운영 절차에 둔다. 기존 관례와 안정적인 주제 이름을 사용한다.

새 문서나 큰 재구성은 경로·목적·범위를 제시한다. 이미 승인된 작업에 필요한 문서는 작성하고 검증한다. 설계 전용·명시적 구현 전 확인·새 계약 결정에는 실행 권한 표를 적용한다. 날짜 기반 명세 파일을 자동 생성하지 않는다.

문서의 자리표시자, 모순, 잘못된 구현을 유발할 모호함, 범위와 관련 문서 정합성을 확인하고 문제를 수정한다. [품질 게이트 계약](../using-engineering-skills/references/quality-gates.md)에 따라 정확한 리비전에 링크·경로·스키마 등 적용 가능한 검사를 기록한다. 구조·고위험 문서 또는 독립 리뷰가 계획 위험을 줄이는 경우 [설계 문서 검토자](spec-document-reviewer-prompt.md)를 사용한다. 저위험 선택적 리뷰는 `not_applicable`, 필수 검토자 부재는 `blocked` 또는 `not_run`으로 기록한다.

설계 문서 게이트는 초기 리뷰를 포함해 최대 5회이며 세션·담당자 변경으로 초기화하지 않는다. 지적은 원인이 있는 설계·문서 섹션으로 돌린다. 입력이 바뀐 경우에 재검토하며 국소 수정은 기존 근거와 집중 검증을 연결한다. `passed` 또는 정확한 리비전에 대한 사람의 명시적 `accepted_risk`가 진행 근거다. 요청된 사용자 리뷰에는 완성한 문서를 먼저 제시하고 의존 작업만 기다린다.

설계 전용 작업은 산출물 보고로 끝낸다. 구현이 승인된 구조 변경 작업은 `engineering:writing-plans`로 넘기며 의사코드·대응 관계·검증 선택 규칙은 그 스킬을 따른다.

## 시각 보조 도구

화면 시안·배치·시각 비교처럼 직접 보는 편이 명확한 질문에 브라우저 보조 도구를 사용할 수 있다. 필요할 때 사용을 제안하고 기존 사용자 선택을 따른다. 수락하면 [visual-companion.md](visual-companion.md)를 읽고 시작한다. 거절하면 다시 요청받기 전까지 텍스트로 진행한다. 요구사항·개념·장단점처럼 글이 적합한 질문은 대화에서 다룬다.
