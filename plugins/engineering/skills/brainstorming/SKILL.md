# brainstorming: 설계 구체화

요청과 기존 코드를 읽고 작업 경로, 관찰 가능한 결과, 필요한 결정을 정한다. 분류와 다음 단계를 짧게 알린다.

## 실행 권한

현재 요청, 이전 사용자 승인, 승인된 문서·이슈에서 실행 범위를 확인한다. 구현 요청의 목표·결과·제약이 충분하면 기존 코드와 관례에 따른 내부 선택을 설명하고 진행한다. 별도의 설계 승인 메시지는 필수 조건이 아니다.

| 조건 | 수행 범위와 다음 단계 |
| --- | --- |
| 승인된 구현이며 미결정 계약이 없음 | 필요한 탐색·설계·계획·수정·검증을 계속한다. |
| 설계·검토 전용 요청 | 요청한 산출물을 완성하고 구현 전에 종료한다. |
| 아직 충족되지 않은 명시적 구현 전 확인 조건 | 먼저 요청된 설계·문서·계획을 완성해 제시한다. 응답을 기다리는 의존 작업만 보류하고 독립적인 승인 작업은 계속한다. |
| 미결정 제품 규칙, 충돌하는 요구사항, 승인된 목표·설계·관찰 가능한 계약의 변경 | 결정에 필요한 근거와 변경안을 제시한다. 해당 의존 작업은 사용자 확인까지 보류하고 독립적인 승인 작업은 계속한다. |
| 이미 충족된 확인 조건 | 그 승인 범위에서 계속한다. 절차 전환이나 재개를 이유로 다시 열지 않는다. |

작업 경로, 복잡도, 계획 필요 여부와 품질 판정은 실행 권한을 부여하거나 취소하지 않는다. Git·배포·외부 쓰기는 각각의 권한을 확인한다. 응답이 없다는 사실은 승인이 아니다.

주 조정자의 여러 단계 작업은 [task-continuity](../task-continuity/SKILL.md)에 기록한다. 위임된 작업자와 새 문맥의 검토자는 별도 연속성 기록을 만들지 않는다.

## 깊이와 작업 경로

현재 계약·소비자·관찰 결과·검증 방법을 함께 확인한다. 탐색 횟수나 파일 수에 고정 상한을
두지 않는다. 의미 변화 없는 기계적 작업은 스크립트·AST·생성기·Code Mode로 처리하고 실제
소비 검사로 닫는다. 동작 변화는 독립 리뷰, 고위험 설계·상태·권한·복구 경계는 red-team까지
[품질 게이트](../using-engineering-skills/references/quality-gates.md)에 선언한다.

조사 요청은 질문·확인 범위·관찰을 정리한다. 유지할 구현의 권한이 없으면 조사 결과까지
완성한다. 범위가 명확한 변경은 접근·예상 결과·검사를 짧게 정리한다. 여러 흐름·의존성·
인터페이스를 조정하는 변경은 writing-plans로 연결한다. 필요한 설계 깊이와 병렬 실행 가능성은
따로 판단하며 생략한 산출물을 대신할 근거를 남긴다.

재개 시 현재 소스·계약과 이전 근거를 대조한다. task ID·이력·소비 라운드를 유지하지만
재개 자체를 영구 탈락으로 취급하지 않는다. 새 위험이 드러나면 영향받은 정책을 높이고 근거를
갱신한다. 게이트 통과를 위해 확인한 위험을 낮추지 않는다. 구형 fast-path 상태는 역사적
근거로 보존하고 새 정책의 통과 증거로 자동 변환하지 않는다.

## 설계와 문서 작성

기존 파일·문서·최근 변경을 읽고 목적·제약·완료 기준을 확인한다. 결과를 바꾸는 사용자 결정만 질문하고, 기존 자료로 해결할 내부 선택은 직접 정한다. 대안 비교가 유용하면 2~3개 접근의 장단점과 추천안을 제시한다. 설계 깊이는 복잡성에 맞춘다.

영속 문서가 필요하면 기존 README, CONTEXT, docs, ADR, 구조, 제품, 안내, 참고 자료, 운영 절차, 이슈와 티켓을 먼저 확인한다. 문서 영향을 `없음 / 기존 문서 갱신 / 영속 문서 생성 / 기존 결정 대체`로 분류한다. 구조 설명은 구조, 장기 결정은 ADR, 제품 의도는 요구사항, 사용 절차는 안내, 정확한 계약은 참고 자료, 운영·복구는 운영 절차에 둔다. 기존 관례와 안정적인 주제 이름을 사용한다.

결정한 문서 영향·목적·경로·갱신 범위는 후속 계획과 작성에 전달하고 바뀐 부분만 다시 확인한다.
작업 완료 자체를 README 갱신 사유로 삼지 않는다. 주요 사용 안내와 진입 경로가 바뀔 때 README를
갱신하며, 일회성 작업·검사 기록만 있다면 작업 보고에 남긴다.

새 문서나 큰 재구성은 경로·목적·범위를 제시한다. 이미 승인된 작업에 필요한 문서는 작성하고 검증한다. 설계 전용·명시적 구현 전 확인·새 계약 결정에는 실행 권한 표를 적용한다. 날짜 기반 명세 파일을 자동 생성하지 않는다.

문서의 자리표시자, 모순, 잘못된 구현을 유발할 모호함, 범위와 관련 문서 정합성을 확인하고 문제를 수정한다. [품질 게이트 계약](../using-engineering-skills/references/quality-gates.md)에 따라 정확한 리비전에 링크·경로·스키마 등 적용 가능한 검사를 기록한다. 구조·고위험 문서 또는 독립 리뷰가 계획 위험을 줄이는 경우 [설계 문서 검토자](spec-document-reviewer-prompt.md)를 사용한다. 저위험 선택적 리뷰는 `not_applicable`, 필수 검토자 부재는 `blocked` 또는 `not_run`으로 기록한다.

설계 문서 게이트는 초기 리뷰를 포함해 최대 5회이며 세션·담당자 변경으로 초기화하지 않는다. 지적은 원인이 있는 설계·문서 섹션으로 돌린다. 입력이 바뀐 경우에 재검토하며 국소 수정은 기존 근거와 집중 검증을 연결한다. `passed` 또는 정확한 리비전에 대한 사람의 명시적 `accepted_risk`가 진행 근거다. 요청된 사용자 리뷰에는 완성한 문서를 먼저 제시하고 의존 작업만 기다린다.

설계 전용 작업은 산출물 보고로 끝낸다. 구현이 승인된 구조 변경 작업은 Codex의 `engineering:writing-plans` 또는 OMP의 `skill://writing-plans`로 넘기며 의사코드·대응 관계·검증 선택 규칙은 그 스킬을 따른다.

## 시각 보조 도구

화면 시안·배치·시각 비교처럼 직접 보는 편이 명확한 질문에 브라우저 보조 도구를 사용할 수 있다. 필요할 때 사용을 제안하고 기존 사용자 선택을 따른다. 수락하면 [visual-companion.md](visual-companion.md)를 읽고 시작한다. 거절하면 다시 요청받기 전까지 텍스트로 진행한다. 요구사항·개념·장단점처럼 글이 적합한 질문은 대화에서 다룬다.
