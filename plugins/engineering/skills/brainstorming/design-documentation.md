# 설계 문서의 배치와 검토

## 문서 영향을 정한다

기존 README, CONTEXT, docs, ADR, 구조, 제품, 안내, 참고 자료, 운영 절차, 이슈와 티켓을 먼저 확인한다. 문서 영향을 `없음 / 기존 문서 갱신 / 영속 문서 생성 / 기존 결정 대체`로 분류한다.

| 정보 | 위치 |
| --- | --- |
| 구조 설명 | 구조 문서 |
| 장기 결정 | ADR |
| 제품 의도 | 요구사항 |
| 사용 절차 | 안내 |
| 정확한 계약 | 참고 자료 |
| 운영·복구 | 운영 절차 |

기존 관례와 안정적인 주제 이름을 사용한다. 외부 계약(API·데이터·통합·대외 SLO)이나 권한·보안 계약이 바뀌는 기능은 [기능 설계 문서 템플릿](design-doc-template.md)으로 영속 설계를 남긴다. 여러 기능의 공통 내부 품질 목표가 바뀌어 책임·제약·검증을 함께 조정해야 할 때도 필요한 품질 설계를 남긴다.

적절한 기존 설계 문서가 있으면 영향받는 계약·위험·품질 설계를 갱신한다. 없을 때 필요한 문서를 만든다. 품질 목표와 계약을 유지한 내부 구현 변경은 계획에 기록한다. 구현 변경 없는 제품 결정은 기존 기록·추적 정보만 갱신하며 L 판정만으로 새 설계를 요구하지 않는다. 위치는 기존 설계 관례를 따르고 없으면 `docs/design/<feature-slug>.md`를 쓴다.

결정한 문서 영향·목적·경로·갱신 범위를 후속 계획과 작성에 전달하고 바뀐 부분만 다시 확인한다. 버전 있는 요구 출처는 실제 리비전 또는 고정 snapshot·범위와 적용 승인 근거를 설계나 기존 고정 입력 참조에 연결한다. 출처가 바뀌면 영향받은 설계·승인 범위를 대조하고 [실행 권한](SKILL.md#실행-권한)에 따라 의존 작업을 처리한다. 버전 없는 요청은 실제 주어진 근거로 다루며 리비전·승인 metadata나 새 승인 단계를 만들지 않는다.

README는 주요 사용 안내와 진입 경로가 바뀔 때 갱신한다. 일회성 작업·검사 기록은 작업 보고에 둔다. 새 문서나 큰 재구성은 경로·목적·범위를 제시하고 승인된 작업에 필요한 문서를 작성·검증한다. 설계 전용·구현 전 확인·새 계약 결정에는 실행 권한 표를 적용한다.

## 현재 리비전을 검토한다

자리표시자, 모순, 잘못된 구현을 유발할 모호함, 범위와 관련 문서 정합성을 확인해 수정한다. [품질 게이트](../../references/quality-gates.md)에 따라 정확한 리비전에 링크·경로·스키마 등 적용 가능한 검사를 기록한다. 구조·고위험 문서 또는 독립 리뷰가 계획 위험을 줄이는 경우 [설계 문서 검토자](spec-document-reviewer-prompt.md)를 사용한다. 저위험 선택적 리뷰는 `not_applicable`, 필수 검토자 부재는 `blocked` 또는 `not_run`으로 기록한다.

문서 리뷰의 라운드 예산·재개·진행 판정은 품질 게이트를 따른다. 지적은 원인이 있는 설계·문서 섹션으로 돌리고 입력이 바뀌면 재검토한다. 국소 수정은 기존 근거와 집중 검증을 연결한다. 요청된 사용자 리뷰에는 완성한 문서를 먼저 제시하고 의존 작업만 기다린다.

예: 내보내기 파일의 보존 기간을 바꾸는 요청은 기존 운영 절차와 데이터 계약 설계를 갱신한다. 같은 보존 기간을 유지한 내부 함수 분리는 계획에만 기록한다.
