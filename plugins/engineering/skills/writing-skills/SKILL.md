# 스킬 작성

에이전트가 반복해서 수행할 작업의 판단 기준과 절차를 작성한다. 기존 지식만으로 놓치기 쉬운
도메인 규칙, 도구 사용법과 실제 실패 조건을 중심으로 남긴다.

## 역할과 결과를 정한다

사용자가 요청한 작업, 입력, 기대 결과와 적용 시점을 확인한다. 기존 스킬·참고 자료·생성기를
읽어 같은 책임의 정본을 찾는다. 여러 역할을 조합할 때는 각 역할이 한 결과에 기여하는 방식을
설명한다. 프로젝트에만 해당하는 관례는 해당 프로젝트 지침에 둔다.

스킬을 수정할 때에는 유지할 계약과 바꿀 동작을 구분한다. 설명을 줄이는 과정에서도 권한,
상태 전이, 실패 처리와 실행 도구가 읽는 필드를 대조한다. 생성되는 스킬은 원본을 고친 뒤 재생성한다.

## 형식과 설명을 작성한다

[Agent Skills 규격](https://agentskills.io/specification)에 맞춰 YAML frontmatter 뒤에 Markdown
본문을 둔다. 필수 필드는 `name`과 `description`이다.

- `name`: 기존 호출명을 유지한다. 새 이름은 소문자 영문·숫자·하이픈으로 1–64자 안에 정하고
  디렉터리 이름과 맞춘다. 앞뒤 하이픈과 연속 하이픈은 사용할 수 없다.
- `description`: 역할과 사용하는 상황을 1–1,024자로 설명한다. 선택에 필요한 대상·증상·도구를
  포함하고 세부 절차는 본문에 둔다. 이 길이 제한은 frontmatter 전체가 아닌 description 값에 적용된다.
- `license`, `compatibility`, `metadata` 등 선택 필드는 실제 필요한 정보가 있을 때 사용한다.
  플랫폼 전용 필드는 해당 로더의 지원 범위를 확인한다.

```markdown
---
name: reviewing-api-contracts
description: API 변경을 검토할 때 입력·응답·오류와 기존 호출자의 호환성을 확인한다.
---

# API 계약 검토

변경 전후의 공개 동작과 기존 호출자가 받는 영향을 확인한다.

## 검토 방법

1. API 정의와 실제 호출자를 읽고 입력·응답·오류의 변경을 비교한다.
2. 바뀐 계약을 사용하는 호출자의 동작과 검증 근거를 확인한다.
3. 호환성에 영향을 주는 지적을 재현 조건과 함께 보고한다.
```

본문 목차는 작업에 맞춰 고른다. 짧은 지침은 바로 설명하고, 여러 단계의 작업은 진행 순서를
보여 준다. 예시·완료 기준·참고 자료는 실제로 필요한 곳에 추가한다.

## 판단과 행동을 연결한다

설명과 지침은 자연스러운 한국어 `~한다` 문체로 쓴다. 호출명, 코드, 명령어, 상태값과 직접
인용문은 원문을 유지한다. 언어 자체를 가르치는 용례는 해당 언어로 제시한다.

- **기본 행동:** 무엇을 확인하고 어떤 결과를 만드는지 쓴다.
- **조건부 행동:** 관찰할 조건과 그때 수행할 행동을 같은 단계에 둔다.
- **필요한 제약:** 실제 실패 사례나 도메인 계약 때문에 피해야 할 동작과 이유를 짧게 설명한다.

예를 들어 “항상 결론부터 쓰지 않는다”는 “독자가 먼저 알아야 할 정보를 앞에 둔다”로,
“실패했다고 다시 게시하지 않는다”는 “응답이 불명확하면 정확한 대상의 현재 상태를 조회하고,
아직 반영되지 않은 작업만 재시도한다”로 작성할 수 있다.

한 문단은 함께 판단해야 하는 내용을 다룬다. 조건·행위자·대상을 가까이 두고, 의무·권장·허용의
차이를 보존한다. 명령의 반복보다 입력·행동·결과를 보여 주는 짧은 예시를 사용한다.

각 문장이 없을 때 판단이나 결과가 달라지는지 확인한다. 일반론, 같은 규칙의 반복,
가상의 핑계·합리화 목록과 근거 없는 효능 주장은 삭제한다. 이미 확인한 사용자 승인은
후속 절차에서도 이어서 적용하고, 새 결정이 필요한 의존 작업에만 확인 조건을 둔다.

## 필요한 자료를 연결한다

매번 필요한 판단은 `SKILL.md`에 두고, 특정 상황에서만 필요한 긴 설명은 참고 파일로 연결한다.
링크 옆에 읽을 조건을 적고 본문에서 바로 접근할 수 있게 한다. 단순 중복은 삭제한다.

공식 권장은 본문 500줄 미만·5,000토큰 미만이다. 이를 상한을 채우는 목표로 삼기보다 각
스킬에 필요한 분량으로 작성한다. `scripts/`는 반복 실행할 도구, `references/`는 세부 자료,
`assets/`는 양식과 자원에 사용할 수 있으며 디렉터리는 필요할 때 만든다.

- 공식 작성 원칙을 대조할 때 [공식 지침 요약](anthropic-best-practices.md)을 읽는다.
- 호출 조건·권한·작업 순서의 실제 적용을 평가할 때 [동작 평가 방법](testing-skills-with-subagents.md)을 읽는다.
- 호출 지침의 대조 사례가 필요하면 [적용 조건 평가 예시](examples/CLAUDE_MD_TESTING.md)를 읽는다.
- 기존 DOT 흐름을 사람이 확인해야 하면 `render-graphs.js <skill-directory>`로 SVG를 만든다.
  선형 절차는 번호 목록, 같은 기준의 비교는 표로 설명할 수 있다.

## 변경에 맞춰 검증한다

| 변경 | 확인할 근거 |
| --- | --- |
| 설명·frontmatter | YAML 파싱, 이름·길이·지원 필드와 실제 사용 시점 |
| 경로·참고 파일·생성 원본 | 상대 경로, 링크·코드 fence, 생성 결과의 동기화 |
| 실행 도구 | 실제 입력·출력과 실패 조건에 대한 집중 회귀 검사 |
| 호출 조건·권한·작업 흐름 | 영향받는 대표 작업의 실제 실행과 결과 |
| 언어·구성 지침 | 의미·조건·불확실성·보호 문자열·요청 형식과 편집 범위 |

사용 가능한 validator와 로더로 형식·설치를 확인한다. 예를 들어 `skills-ref validate ./my-skill`은
frontmatter와 이름을 검사한다. 로더의 발견·설치, 명시적 지침 적용, 자동 호출과 실제 결과 품질을
각각 구분해 보고한다. 문구·경로 정리에는 같은 구현을 되풀이하는 테스트 대신 해당 검사를 사용한다.

마지막으로 전체 diff를 승인된 범위와 대조하고 수정된 계약, 실제 검사 결과와 남은 불확실성을
보고한다. 여러 단계의 스킬 작업을 맡았다면 [작업 연속성](../task-continuity/SKILL.md)에 원본과
검증 근거 위치를 기록한다. Git·게시 작업은 해당 사용자 승인 범위에서 진행한다.
