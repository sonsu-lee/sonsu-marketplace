# Engineering 품질 게이트 계약

각 산출물을 만드는 단계가 그 품질 게이트와 반환 경로를 소유한다. 게이트는 현재 산출물이
다음 단계로 진행할 근거를 갖췄는지 판단한다. 문서 작성·구현·staging·commit·push·PR·merge·
배포·게시 등 작업 권한은 기존 승인으로 별도 확인한다.

계획 기반 작업의 누락·stale 근거를 기계적으로 관찰하려면
[완료 근거 관찰 도구](evidence-gates.md)를 사용한다. 명시적으로 등록한 작업의 검사 실행과
리뷰 근거를 연결하는 선택적 pilot이며, 관찰 결과가 이 계약이나 사람의 위험 수용을 대신하지 않는다.

## 실행 전에 정의한다

대화·계획·진행 기록·리뷰 패키지 중 기존 기록에 다음을 연결한다.

```text
Gate: <고정 게이트 ID>
Artifact: <경로·작업·변경 등 정확한 범위>
Revision: <커밋 SHA·내용 digest·고정 리뷰 패키지 식별자>
Required checks: <근거가 필요한 필수 검사>
Pass condition: <관찰 가능한 결과>
Evidence: <명령·출력·리뷰 결과·사람의 결정>
Findings: <없음 또는 미해결 지적>
Status: <아래 정의한 상태>
Return target: <실패한 입력을 바꿀 수 있는 가장 가까운 단계>
Attempt: <현재 횟수>/<상한>
Decision owner: <단계 소유자 또는 지명된 사람 의사결정자>
```

필수 검사·통과 조건·반환 대상·유한한 시도 상한을 첫 실행 전에 정한다.
[실행 계약](agent-execution.md)의 세션·설정·환경·결과를 같은 작업·게이트 ID에 연결한다.
`Attempt`는 세션별 횟수가 아니라 동일 작업·게이트의 누적 횟수다.

미커밋 변경은 내용 digest나 고정 리뷰 패키지로 식별한다. 독립 평가자에게는 digest와 함께
읽을 수 있는 고정 내용을 제공한다. 현재 커밋 범위만 넘기면 미커밋 변경의 근거가 되지 않는다.
산출물이 바뀌면 아래 영향 규칙에 따라 이전 근거와 새 근거를 현재 리비전에 연결한다.

자동 검토·수정은 최대 5회이며 더 낮은 단계별 상한이 우선한다. 상한은 목표 횟수가 아니다.
작업·게이트 ID와 소비량을 유지하고 세션·담당자·패키지 변경이나 이전 단계 반환으로 예산을
초기화하지 않는다. 하위 호출도 남은 상위 예산 안에서 실행한다.

## 상태

| 상태 | 의미 | 필수 게이트 진행 조건 |
| --- | --- | --- |
| `passed` | 현재 리비전의 모든 필수 검사와 통과 조건을 충족한다 | 진행한다 |
| `failed` | 필수 조건 위반이 근거로 확인됐다 | 해결이 필요하다 |
| `blocked` | 기능·권한·의존성·외부 상태 부재가 필수 검사나 수정을 막는다 | 방해 요인을 해결한다 |
| `inconclusive` | 판정에 충분한 근거가 없다 | 필수 근거를 보완한다 |
| `not_run` | 검사를 실행하지 않았다 | 필수 검사이면 실행이 필요하다 |
| `not_applicable` | 적용되지 않아 실행 전에 대상에서 제외했다 | 나머지 필수 조건을 충족한다 |
| `accepted_risk` | 권한 있는 사람이 현재 리비전의 명시된 위험을 수용했다 | 위험 수용을 보고하고 진행한다 |

`accepted_risk`는 사용자 또는 지명되고 권한 있는 사람의 명시적인 결정이다. 조정자·구현자·
리뷰어, 예산 소진이나 일정은 이를 대신하지 않는다. 지적·영향·범위·리비전·결정 근거를
보존하며 `passed`로 보고하지 않는다.

## 검사와 리뷰 근거를 구분한다

먼저 질문을 판정할 수 있는 저렴한 결정론적 검사를 실행한다. 테스트, 타입 검사, 빌드,
파서, 설치 환경의 로더, 경로·링크 검사와 실제 소비 명령을 변경 위험에 맞게 선택한다.
독립 리뷰는 판단이 위험을 줄이는 곳이나 현재 절차가 요구하는 곳에 사용한다.

실행 상태와 검사 유효성은 품질 상태와 별도로 기록한다.

- 완료 이벤트 없이 취소·제한 시간 종료가 발생하면 `execution: incomplete`와 원인을 남긴다.
  일부 출력이나 수정 파일만으로 완료를 선언하지 않는다. 확인한 환경 부재는 `blocked`,
  원인·판정 근거 부족은 `inconclusive`, 미실행 검사는 `not_run`으로 구분한다.
- 실행 환경·권한·의존성 오류는 해당 계층에서 해결한다. 실행하지 못한 사실을 제품 코드나
  특정 모델의 품질 실패로 계산하지 않는다.
- 검사가 계약에 없는 출력 문자열·내부 위치·인터프리터를 강제하거나 입력 자료를 잘못
  구성했다면 `check_validity: invalid_oracle_setup`과 근거를 남긴다. 원 결과를 보존하고
  검사 소유 단계에서 고친 뒤 현재 산출물에 다시 실행한다. 실제 코드 실패는 별도로 유지한다.
- 오류 주입이 대상 경계에 도달하지 않았다면 그 경계는 `inconclusive`다. 검사 횟수를 독립
  결함 수로 세지 않는다. 필수 미검증이 남으면 전체 게이트는 `passed`가 아니다.

`incomplete`와 `invalid_oracle_setup`은 품질 상태의 새 값이 아니다.

리뷰어에게 [공통 리뷰 기준](../../requesting-code-review/review-criteria.md)을 전달한다.
조정자는 반환된 지적을 실제 동작·구조, 기본 동작·설정과 영향에 대조해 유효한 차단 지적만
수정 절차에 넣는다. 무효화한 지적은 근거와 함께 닫고, 근거 있는 비차단 지적은 보고한다.
비차단 발견만으로 새 필수 게이트나 할 일 목록을 추가하지 않는다.

## 전체 변경의 독립 검토

아키텍처·고위험 설계, 복잡한 구현 계획, 위임 구현과 크거나 위험한 직접 변경에서는 독립
리뷰의 실익을 판단한다. 구현 계획이 있는 작업은 위험도와 관계없이 일반 최종 리뷰 뒤
새 문맥의 red-team이 필요하다. 계획 없는 Fast Path에는 이 조건을 적용하지 않는다.

red-team 직전에 목표, 요구사항·설계, 계획·대응 관계, 전체 변경, 검증 보고, 관찰 결과·제약,
지적과 수정의 근거 이력을 하나의 고정 묶음으로 복사하고 전체 digest를 고정한다. 검토자는
가변 원본 대신 그 내용을 읽는다. 도전 판정은 품질 상태와 별도 기록한다.

| Challenge verdict | Quality status | 의미 |
| --- | --- | --- |
| `survives_challenge` | `passed` | 전체 전제를 뒤집을 근거가 없고 필수 검사가 충족됐다 |
| `invalidated` | `failed` | 목표·요구사항·설계·계획·구현 또는 리뷰 방향이 반증됐다 |
| `inconclusive` | `inconclusive` | 판정에 필요한 근거가 부족하다 |
| `blocked` | `blocked` | 산출물·기능·외부 상태가 검토를 막는다 |

선택 리뷰를 적용 대상에서 제외했다면 `not_applicable`로 기록한다. 필수 리뷰를 수행할 수
없으면 `blocked` 또는 `not_run`으로 남긴다. 일반 리뷰 통과가 red-team을 대신하지 않는다.

## Fast Path의 현재 판단과 누적 예산

자격과 실행은 [brainstorming](../../brainstorming/SKILL.md)의 제한된 절차를 따른다. 조정자가
현재 파일과 소비자를 직접 확인한다. `HEAD` 일치나 과거 `eligible` 기록은 미커밋 변경을
포함한 현재 자격의 증거가 아니다. 긍정 판정은 중단 없는 현재 실행에만 유효하다.

영속 상태에는 동일 작업 ID의 소비한 탐색·실행 예산과 `disqualified`를 남긴다. 재개·문맥
손실·인계·설명되지 않는 파일 변경에서는 일반 절차로 전환하며 기존 구현 승인은 유지한다.
같은 실행에서 확인한 자신의 수정과 허용된 집중 수정은 재개가 아니다. ID 변경·재분류로
예산이나 탈락 기록을 초기화하지 않는다. 이 판정 자체는 구현·위임·Git 권한을 부여하지 않는다.

## 가장 가까운 소유 단계로 반환한다

| 실패 또는 발견 | 반환 대상 |
| --- | --- |
| 동작·테스트 실패 | 해당 구현. 원인이 불명확하면 systematic-debugging |
| 유효한 작업 리뷰 지적 | 해당 작업의 집중 수정·재리뷰 |
| 계획·작업·인터페이스 모순 | 영향받은 writing-plans 범위 |
| 요구사항·설계·해법 모순 | 해당 결정의 brainstorming |
| 통합에서만 발생한 실패 | 통합 단계 또는 영향받은 구현 |
| 기능·권한·외부 상태 부재 | `blocked`, 해당 환경이나 권한 담당자 |
| 리뷰 의견 불일치 | 결정적 근거 수집, 요구 명확화 또는 사람의 판정 |
| 원래 문제 정의·사용자 목표 반증 | 사용자 재승인 |
| 실제 효과 근거 부족 | 검증 단계 또는 제품 실험 |
| 기존 지적·수정 방향 반증 | 근거로 지적을 무효화하고 영향받은 작업을 `reopened` |

red-team도 같은 반환 기준을 사용한다. 마지막 검증 완료 지점과 유효한 작업을 보존하고
영향받은 범위만 다시 연다. 새로운 목표나 승인 계약 변경에는 해당 결정의 승인이 필요하다.

## 변경 영향에 따라 근거를 갱신한다

최초 일반 최종 리뷰와 최초 red-team은 전체 변경을 검토한다. 수정 뒤에는 기존 지적의 해결과
새 회귀를 확인한다. 승인 범위의 결함과 새로운 요구를 구분하며 후자는 별도 결정으로 올린다.

국소 수정의 영향이 확인되면 다음 근거를 현재 게이트에 연결한다.

- 이전 전체 리뷰의 산출물·리비전과 여전히 유효한 범위
- 이전부터 현재 리비전까지의 실제 차이와 영향받은 계약·소비자
- 변경 부분의 검증 결과, 지적별 재리뷰 판정과 회귀 확인
- 영향받지 않은 근거의 재사용 이유, 남은 필수 조건과 현재 리비전

집중 검토 하나가 아니라 이 근거들의 합이 현재 전체 필수 조건을 충족해야 한다. 영향 경계가
불명확하거나 목표·승인 계약·설계·의존 경계가 바뀌면 해당 전체 게이트를 다시 연다.
필수로 선언된 전체 테스트는 유지하되, 같은 내용에 이미 유효한 근거가 있으면 중복 실행하지 않는다.

red-team 재검토도 현재 전체 묶음을 새 문맥에 제공하되 기존 반례와 수정 회귀에 집중할 수
있다. 전체 전제 변경이나 영향 불명확성은 전체 검토를 다시 여는 조건이다. 일반 게이트와
red-team 게이트 각각을 현재 리비전에 연결한다.

## 재시도와 종료

재시도에는 산출물·가설·구현·근거·문맥·평가자·실행 가능 기능·사람의 결정 중 새로운 정보가
필요하다. 같은 입력으로 같은 결정론적 검사나 동일한 판단을 반복하지 않는다.

상한에 도달하면 근거로 무효화하거나 범위 밖임이 확인된 지적만 닫는다. 유효한 필수 미해결
지적은 가장 가까운 소유 단계로 반환하고 `failed` 또는 `blocked`와 함께 산문으로
`decision_required`를 기록한다. 남은 예산을 초기화하지 않으며, 진행에는 현재 리비전의
필수 조건 충족 또는 사람의 명시적인 `accepted_risk`가 필요하다.
