# 코드 품질 원칙

코드 구조는 확인된 제품·도메인 계약을 직접 표현해야 한다. 타입과 상태는 실제로 허용되는 값과
전이만 나타내고, 금지된 경로를 처음부터 표현할 수 없게 만들 때 사용한다. 아직 확인되지 않은
variant, abstraction과 extension point를 미래 가능성만으로 추가하지 않는다.

## 신뢰 경계에서 보증을 만든다

사용자 입력, 네트워크 응답, 환경 변수, 파일, 데이터베이스 역직렬화와 외부 라이브러리 결과는
그 값을 소유하는 trust boundary에서 검증·정규화한다. 경계를 통과한 값에는 확인된 타입과
불변식을 전달하고, 내부 함수마다 같은 guard를 반복하지 않는다.

다음 경우에는 경계 안에서도 검사를 유지한다.

- mutable state나 외부 호출자가 불변식을 깨뜨릴 수 있다.
- 별도 entry point가 최초 trust boundary를 우회할 수 있다.
- 실패를 더 가까운 책임 경계에서 구분해야 복구하거나 올바르게 보고할 수 있다.

검사를 줄일 때에는 실제 경계·mutable 경로·대체 entry point를 먼저 확인한다. 타입 선언만으로
외부 값의 runtime 보증을 가정하지 않는다.

## 타입 보증을 우회하지 않는다

`as`, non-null assertion인 `!`, 넓은 `any`로 compiler 오류를 숨기지 않는다. 이 표현이 필요한
경우에는 어떤 runtime 근거가 값을 보증하는지 확인하고, 가능하면 소유 경계의 parse·validation,
정확한 narrowing 또는 더 좁은 API 계약으로 보증을 코드에 남긴다.

새 wrapper, factory, layer와 범용 모델은 제거되는 잘못된 상태·중복 규칙·분기보다 유지 비용이
낮을 때만 도입한다. 현재 자료구조와 직접적인 제어 흐름이 계약을 충분히 표현하면 그대로 쓴다.
