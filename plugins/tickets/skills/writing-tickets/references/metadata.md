# Ticket metadata

Inspect actual fields, allowed values, template defaults, and repository or team
conventions. Apply explicit choices and established rules before proposing
grounded candidates:

- **Labels and type:** use existing classifications fitting the problem and
  area, not every possible match or near-duplicates.
- **Assignee:** use explicit assignment or established ownership, not an
  assumption that the reporter or current user owns it; other owners are proposals.
- **Priority:** use known impact, severity, and time constraints on the team's
  scale; a bug is not automatically urgent.
- **Estimate:** use the actual scale and defensible scope; leave unset when
  investigation or assignee judgment is needed. Unknown is not zero; points
  are not hours unless the team defines them so.
- **Project and milestone:** use existing destinations whose goals and scope fit
  the outcome, not just similar names; an unresolved project leaves its
  milestone unresolved.

Keep metadata out of the body unless required. Explain proposals briefly; leave
optional unknowns unset and batch only unresolved required or consequential
questions. Resolve ambiguous identities before publication. Do not turn
proposals into commitments or create metadata to fill a ticket. Never call
unreadable fields unset; disclose fields tools cannot read or write.
