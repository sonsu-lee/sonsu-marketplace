# 티켓 작성 지침

티켓에는 무엇을 왜 하는지와 끝났다고 판단할 상태를 쓴다([문서별 역할](../../../references/tracker-prose.md#문서별-역할)). 이 지침과 [공통 정보 선택 기준](../../../references/tracker-prose.md#티켓pr에서-설명할-내용을-고른다)을 함께 적용한다.

## 티켓으로 만들지 정한다

- 티켓은 결과가 분명한 작업 하나를 전달하는 문서다. 작업이 아닌 아이디어·큰 기능은 문서·논의로 넘기거나 작은 작업으로 나눈다. 탐색이 먼저 필요하면 결과물 형태(예: "설계안 작성")로 만든다.
- 한 티켓에는 문제 하나만 담는다. 만들기 전에 제목과 본문으로 중복을 검색한다.

## 양식을 고른다

사용자가 지정한 양식을 먼저 따른다. 그다음 대상 공간에 issue form·template이 있으면 그것을 따르고, 없으면 아래 기본형을 쓴다.

| 종류 | 고르는 경우 | 템플릿 |
| --- | --- | --- |
| 작업 | 할 사람이 직접 쓰고 해법이 정해짐 | [`task.md`](../assets/templates/task.md) |
| 요청 | 다른 사람에게 기능·개선을 요청하고 해법은 담당자가 정함 | [`request.md`](../assets/templates/request.md) |
| 버그 | 잘못된 동작을 보고함 | [`bug.md`](../assets/templates/bug.md) |
| 조사 | 답을 얻어야 다음 작업을 정할 수 있음 | [`exploration.md`](../assets/templates/exploration.md) |

기본형의 `<!-- -->` 안내는 자산에만 둔다. 출력할 때는 지운다.

저장소의 issue 양식·form·기여 지침과 tracker의 팀 양식을 확인한다. 여러 양식이면 해당 공간의 선택 규칙을 따른다. 저장소에 파일이 없다는 사실만으로 팀 양식도 없다고 판단하지 않는다.

주어진 양식의 제목·순서·필수 항목·체크리스트·고정 문구를 보존하고 그 항목에 내용을 채운다. 기본형의 제목을 뒤에 덧붙이지 않는다. 외부 양식의 HTML comment는 자동화 표식이나 숨은 지침일 수 있으므로 양식이 제거·치환하도록 지정한 부분만 바꾼다. 기존 티켓을 부분 수정할 때는 현재 구조(제목 체계·순서 포함)와 요청받지 않은 내용을 보존하고, 전체 재작성을 요청받았을 때만 양식을 바꾼다.

필수 AI 공개 항목과 자동 표기 금지의 충돌은 [공통 AI 사용 표기 규칙](../../../references/tracker-prose.md#ai-사용-표기)을 따른다. 양식의 구조를 보존하는 것과 그 항목을 채울 권한은 구분한다.

버그 접수에는 대상 공간의 버그 보고용 양식·form과 필수 입력을 먼저 찾고, 적용할 버그 양식이 없다고 확인된 경우에만 기본 버그 양식을 쓴다. 대상 공간에 다른 종류의 양식만 있다고 해서 그 양식에 버그를 억지로 맞추지 않는다. 대상 버그 양식에 접근할 수 없어 확인하지 못했다면 `unverified`로 보고하고, 기본 버그 양식을 적용하지 않은 채 확인된 사실을 형식 미확정의 임시 초안에 보존한다.

양식을 확인할 수 없는 상태와 양식이 없는 상태를 구분한다. 양식 확인이 안 된 초안은 임시임을 본문 밖에서 알린다. 게시 전에는 적용 양식과 필수 필드를 확인하거나, 미확인 한계를 안내한 뒤 사용자가 명시적으로 선택한 기본형을 쓴다. 어느 경우에도 interface의 필수 필드는 생략하지 않는다. 임시 초안을 썼다는 사실은 원격 양식의 부재, 양식 확정, 게시 조건·권한이나 원격 필수 필드 충족의 근거가 아니다.

## 출력 언어와 섹션 제목

티켓 언어는 사용자 지정, 대상 공간의 지침·양식·일관된 관례, 기존 티켓이나 승인 문서의 주 언어, 영어 순으로 정한다. 대화 언어는 티켓 언어의 근거가 아니다. 결과 보고는 사용자가 요청한 언어를 따른다. 고정된 양식 문구는 해당 양식이 허용할 때만 번역한다.

기본형의 섹션 제목은 출력 언어에 맞춰 아래 대응으로 쓴다. 영어 제목은 GitHub issue form의 label과 같다.

| 한국어 | English |
| --- | --- |
| 결과 | Outcome |
| 문제 | Problem |
| 원하는 결과 | Desired outcome |
| 고려한 대안 | Alternatives considered |
| 재현 단계 | Steps to reproduce |
| 기대 결과 | Expected result |
| 실제 결과 | Actual result |
| 환경 | Environment |
| 로그 | Logs |
| 증거 | Evidence |
| 추정 | Hypothesis |
| 답할 질문 | Questions |
| 결과물 | Deliverable |

## 제목과 본문

- 제목은 할 일을 짧고 직접적으로 쓴다. 목록에서 훑어보는 용도다. 요청·버그 제목에는 해법을 쓰지 않는다.
- "As a … I want …" 같은 유저 스토리 형식은 쓰지 않는다.
- 본문은 담당자가 일을 하고 팀이 상황을 이해하는 데 필요한 만큼만 쓴다.
- 사용자 피드백은 요약하지 않는다. 원문을 인용하고 출처를 링크한다.
- 요청·버그에는 해법이 아니라 문제를 쓴다. 해법은 담당자가 정해 작업 티켓으로 다시 쓴다.
- 끝났다고 판단할 상태는 종류별로 한 곳에만 쓴다.
  - 작업은 `결과`, 요청은 `원하는 결과`, 버그는 `기대 결과`, 조사는 `결과물`이다.
  - 제목만으로 분명한 작업은 `결과`를 지운다.
  - CI가 확인하는 항목과 체크리스트는 쓰지 않는다. 다만 요청한 산출물인 테스트·문서·CI 작업은 남긴다.

## 버그를 쓴다

- 제목은 60자 안팎으로 증상을 쓴다. 좋은 예: "파일 복사 대화상자를 취소하면 파일 관리자가 종료됨". 나쁜 예: "프로그램이 죽음".
- 재현 단계가 가장 중요하다. 재현 빈도(항상 / N회 중 M회 / 재현 못 함)를 먼저 쓰고, 단계마다 조작 방법과 그 단계의 의도를 쓴다.
- 기대 결과와 실제 결과를 나눈다. 실제 결과에는 관찰한 사실만 쓰고, 오류 메시지는 원문 그대로 둔다.
- 환경에는 재현되는 가장 이른 버전을 쓰고, 알면 마지막 정상 버전도 쓴다.
- 종류별로 추가할 증거:
  - 크래시: 스택 트레이스와 시그니처. 시그니처는 제목에도 넣는다.
  - 느림·CPU: 프로파일
  - 메모리: 스냅샷과 증가를 재현하는 단계
  - 회귀: 정상·비정상 버전 범위(bisect 결과)
  - 특정 입력·페이지: 최소 재현 사례
  - 간헐적 발생: 발생 조건과 빈도

## 사실과 추정을 구분한다

확인된 사실과 추정을 섞지 않는다. 원인 추정은 버그의 `추정`에만 쓴다.

관찰, 가설, 제안, 선호, 합의와 실행 결과를 구분한다. “Next.js를 선호한다”를 필수 조건으로 바꾸지 않는다. 원인·해결 방법·코드 구조·작업 순서·구체적 테스트를 새로 지시하지 않는다. 이미 합의된 설계·ADR, 보안·호환성, 전환 순서·복구 조건처럼 방법 자체가 제약인 내용은 보존한다. 조사 결과의 보고서·비교표 형식과 일정도 요청되거나 합의된 경우에만 지정한다.

확인되지 않은 배경·결정·수치·제약을 만들어 채우지 않는다. 작업이나 완료 판정에 꼭 필요한 정보가 없으면 미정 사항으로 표시한다. 그 밖의 모르는 값을 채우려고 빈 항목이나 반복적인 `미확인` 문구를 만들지 않는다.

### 관찰에서 원인을 만들지 않는다

입력이 “일정표에서 같은 회의가 두 번 표시된다. 한 번만 표시되어야 한다”뿐이고 환경·재현 순서·원인은 모르는 경우다.

- 잘못된 확장: “중복 이벤트 구독을 제거하고 일정 라이브러리를 교체한다.” 원인과 방법을 새로 결정했다.
- 작성 예시:

```markdown
## 기대 결과
같은 회의는 한 번만 표시된다.

## 실제 결과
일정표에서 같은 회의가 두 번 표시된다.
```

입력에 있는 사실만 썼다. 환경·재현 단계·자료가 작업 착수나 판단에 꼭 필요하면 필요한 입력으로 본문 밖에서 알리되, 본문을 채우려고 원인·단계·자료를 만들지 않는다.

### 외부 접근 없이 이해할 수 있게 근거를 남긴다

원래 콘솔·로그·계정에 접근할 수 없는 담당자도 문제와 기대 결과를 이해할 수 있게 필요한 관찰·환경·리비전과 짧은 재현 입력·출력을 본문에 보존한다. 링크는 보충 근거이며 필수 사실을 링크 뒤에만 두지 않는다. 비밀·개인 데이터를 제거한 fixture나 예시는 원본과의 관계를 설명한다. 원인 확정, 선택된 해결법과 정확한 테스트 구현을 모든 티켓의 필수 조건으로 만들지 않는다. 이미 합의된 내용만 추가하고 외부 양식의 구조와 고정 제목을 유지한다. 안전하게 보존할 수 없는 근거의 한계는 명시한다.

## 요구 출처와 외부 합의를 보존한다

PRD나 승인 문서에서 티켓을 나눌 때는 합의된 우선순위와 독립 완료 판단 단위로 자른다. 결과를 설명한 곳에 해당 범위의 수용 조건을 한 번 담고, 제약·결정 이유를 설명한 곳에 기존 REQ ID와 실제 출처를 연결한다. 외부 양식이 지정한 수용 기준·출처 필드가 있으면 그 위치를 따른다. 제공된 URL·파일 경로를 사용하고, 대화에 제공된 PRD처럼 링크가 없으면 제목·리비전 등 확인 가능한 식별 정보와 대화 출처를 남긴다. 없는 ID·링크는 만들지 않는다. 관련 NFR은 ID와 합의된 조건을 결과에 연결하고, 미결정 NFR은 OPEN ID와 영향으로 남기며 수용 기준으로 확정하지 않는다. 새 구현 계획·설계를 추가하지 않는다.

사용자·팀 양식의 제목을 바꾸거나 기본형 제목을 추가하지 않는다. 의미상 대응 필드가 없으면 양식이 허용하는 기존 자유 서술 필드에 조건·출처를 함께 보존한다. 그 위치도 없으면 추적 정보를 본문 밖 인계 메모에 남기고 양식의 제약을 알린다. 게시 대상에서 허용되는 보존 위치가 확인되기 전에는 추적 정보가 티켓에 반영됐다고 보고하지 않는다.

버전 있는 요구 출처는 링크뿐 아니라 분해에 사용한 리비전 또는 고정 snapshot과 해당 요구 범위를 위 허용 위치에 남긴다. 승인을 근거로 인계한다면 그 버전·범위에 적용되는 승인 기록 위치도 연결한다. 승인 근거가 없거나 미확인이면 그 상태를 보존하며 티켓 작성·게시 자체를 제품 승인으로 취급하지 않는다. 버전 없는 출처에 리비전이나 승인 metadata를 만들지 않는다.

PRD가 아닌 승인 문서에도 기존 요구사항·품질 ID가 있으면 실제 출처와 함께 보존한다. 위의 ID 생성 금지는 출처에 없는 ID를 새로 만드는 경우에 적용하며, 입력에 있는 ID를 삭제하라는 뜻이 아니다.

합의된 우선순위는 해당 REQ와 함께 위 허용 위치에 보존한다. 승인된 tracker 필드가 확인된 대응 관계로 그 값을 정확히 표현하면 본문에 중복하지 않아도 된다. P1/P2를 임의의 tracker 우선순위 값으로 변환하지 않는다.

해당 범위와 관련된 기존 SUCCESS ID·신호·합의된 측정 방법·기준·근거도 보존한다. 제품 성공 목표는 수용 기준 필드가 아닌 허용된 맥락·출처 위치에 두고, 이미 승인된 계측·측정 작업만 해당 티켓의 결과에 연결한다. 자유 서술 필드 하나뿐이면 제품 목표와 구현 완료 조건을 명시적으로 구분한다. 제품 성공 목표를 기능 수용 기준·코드 완료 조건으로 바꾸거나 측정 방법만으로 새 구현 작업을 승인하지 않는다. 구현 밖의 인터뷰·출시 후 분석을 자동 구현 작업으로 만들지 않고 없는 ID·목표값을 만들거나 무관한 티켓에 지표를 반복하지 않는다.

우선순위·품질·제품 규칙 등 해당 티켓과 관련된 OPEN ID·내용·영향을 위 허용 위치에 보존한다. 미결정 값을 P1/P2, tracker 우선순위나 수용 기준으로 임의 확정하지 않고 관련 없는 OPEN을 모든 자식 티켓에 복사하지 않는다. 관련 RISK ID·영향·합의된 완화 조건 또는 남은 확인 작업도 같은 방식으로 해당 티켓에 연결한다. 합의되지 않은 완화책을 새 구현 지시로 만들지 않는다.

외부 논의의 핵심 결론은 요약하고 근거를 연결한다. 긴 계획이나 회고는 필요한 부분만 요약하며 상세 계획을 새로 만들지 않는다. 합의가 바뀌면 최신 결론과 중요한 변경 이유·기존 근거를 함께 남긴다. 코드·수치·의무 수준·티켓 ID·URL은 문체를 다듬을 때도 보존한다.

## 상위·하위 티켓

부모·자식 티켓도 각각의 요청 목적에 맞는 양식을 쓴다. 부모는 전체 문제와 자식별 범위를, 자식은 맡은 작업과 필요한 공통 제약을 설명한다. 부모의 긴 배경을 복사하지 않는다. 이미 정해졌거나 합의된 제외 범위와 전체 제공 및 검증 조건을 보존한다.

실제 결과가 생겼을 때만 본문에 보강한다. 접수·채택과 구현 완료, 장애 복구와 재발 방지, 회고 작성과 후속 개선, 검증 수행과 기준 충족, 일부 대상의 전환과 전체 전환을 구분한다. 합의된 제공·복구·검증 조건을 충족했다는 근거 없이 완료로 표현하지 않는다. 한 자식의 완료나 코드 merge를 전체 작업 완료로 표현하지 않는다.

## 예시

한국어 공간 기준이다. 링크는 설명용이다.

작업 — 제목 `결제 페이지에 CSV 내보내기 추가`

```markdown
정산 담당자가 월별 결제 내역을 회계 도구로 옮길 수 있게 결제 페이지에서 CSV로 내보낸다. 열 순서는 [회계 연동 논의](https://example.com/doc/42)에서 정한 대로 따른다.

## 결과
선택한 기간의 결제 내역이 논의 문서의 열 순서대로 CSV로 내려받아지고, 금액은 통화 기호 없이 소수 둘째 자리까지 표시된다.
```

요청 — 제목 `팀 단위로 알림을 끌 수 없음`

```markdown
## 문제
팀 관리자가 특정 팀의 알림만 끌 방법이 없어, 끝난 프로젝트 팀의 알림까지 모든 구성원에게 계속 간다.
> "프로젝트가 끝난 팀 알림을 개인별로 하나씩 꺼 달라고 공지해야 해서 불편하다" — [지원 문의 #4821](https://example.com/support/4821)

## 원하는 결과
팀 관리자가 팀 단위로 알림을 끄면 그 팀의 알림이 구성원에게 가지 않는다. 구성원의 개인 알림 설정은 바뀌지 않는다.

## 고려한 대안
- 구성원마다 개인 설정에서 끄도록 안내: 지금 쓰는 우회 방법. 구성원이 많으면 누락된다.
```

버그 — 제목 `파일 복사 대화상자를 취소하면 파일 관리자가 종료됨`

````markdown
## 재현 단계
재현: 항상 (5회 중 5회)
1. 1GB 이상 파일을 다른 폴더로 끌어 놓아 복사를 시작한다.
2. 진행 대화상자가 뜨면 진행률이 50%가 되기 전에 `취소`를 누른다.

## 기대 결과
복사가 중단되고 대화상자만 닫히며 파일 관리자는 열려 있다.

## 실제 결과
파일 관리자 창이 바로 닫힌다. 다시 열면 대상 폴더에 0바이트 파일이 남아 있다.

## 환경
- 버전/커밋: 2.3.0부터 재현, 2.2.4에서는 정상
- 실행 환경: macOS 15.1

## 로그
```
FATAL CopyJob: cancel() called after handle released
```

## 추정
취소 시 이미 해제된 복사 핸들에 접근하는 것으로 보인다. 로그만 보고 한 추정이며 코드는 확인하지 않았다.
````

조사 — 제목 `알림 설정 구조 설계안 작성`

```markdown
## 답할 질문
- 팀 설정과 개인 설정이 충돌하면 무엇이 우선하는가?
- 지금의 사용자별 설정 테이블로 팀 단위 설정을 표현할 수 있는가?

## 결과물
`docs/design/notification-settings.md`에 선택지와 추천안을 쓰고, 추천안을 구현 티켓으로 나눌 수 있게 작업 단위를 적는다.
```

## 최종 점검

- 초안을 적용 양식의 필수 항목·실제 필드와 대조한다. 문체를 다듬은 뒤에도 고정 양식 문구, 코드·식별자·티켓 ID·링크·수치가 그대로 남았는지 확인한다.
- 끝났다고 판단할 상태를 종류별 위치에 한 번만 썼는지 확인한다.
- 입력에 없는 값·결정을 만들지 않았는지, 미정 사항은 필요한 것만 표시했는지 확인한다.
- 제목과 본문으로 중복 티켓 검색을 마쳤는지 확인한다.
