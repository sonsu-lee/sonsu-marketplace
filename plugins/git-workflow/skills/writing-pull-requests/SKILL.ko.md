# 풀 리퀘스트 작성하기

> 영문 정본: [SKILL.md](SKILL.md) (`b1f4e10` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

PR 설명은 리뷰어가 diff를 다시 짜 맞추지 않고도 무엇이 바뀌었고 어디에 집중해야
하는지 알게 해 준다. 왜 그 작업이 필요했는지는 연결된 티켓이 담는다. 저장소의
기여 규칙과 템플릿 필수 항목이 우선한다. 글을 작성하거나 수정할 때는 해당 언어
스킬도 읽는다.

## 작업 흐름

요청된 부분만 한다. 제목, 설명 초안, 또는 게시·수정·Ready 전환 중 하나다.

1. **변경 파악:** 저장소, head, base를 확인한다. base는 사용자가 지정한 대상이나
   프로젝트에 정해진 대상이고, 없으면 기본 브랜치다. base 대비 전체 diff와 관련
   티켓이나 설계 맥락을 읽는다.
2. **범위 확인:** 하나의 PR은 하나의 목적을 다루며 구현, 호출부, 테스트, 필수
   문서를 함께 포함한다. 독립적인 변경은 분리하되 분량을 줄이려고 관련 파일을
   나누지 않는다. 각 PR이 병합된 뒤에도 대상 브랜치는 정상 동작해야 한다. 미병합
   PR에 의존하면 base를 고르기 전에 [스택 PR](references/stacked-prs.md)을 읽고,
   독립적인 PR은 각각 trunk를 대상으로 한다.
3. **제목 작성:** 작업 순서가 아니라 최종 변경을 설명하는 커밋 subject로 쓴다.
   [writing-commits](../writing-commits/SKILL.md)로 검증하고, 수정할 때마다 다시
   검증한다.
4. **본문 작성:** 아래를 따른다.
5. **요청이 있을 때만 게시:** 게시, 수정, Ready 전환, 병합 메시지 준비 시
   [PR 게시](references/publishing.md)를 읽는다. 새 PR은 Draft로 만들고, 사용자가
   요청하고 저장소의 준비 요건을 충족했을 때만 Ready로 전환한다. 후속 변경에 맞춰
   제목, 본문, 링크, 미디어를 갱신한다.

## 본문 작성

저장소 템플릿이 없으면 다음 형태를 쓴다.

```markdown
## Summary

무엇이 바뀌었는지 몇 문장으로. 이유는 티켓 링크로.

## <필요할 때만, 내용에 맞는 소제목>
```

작은 변경은 Summary만으로 충분하다. 추가 섹션은 내용에 맞게 이름 붙이고, 문장,
목록, 표, 체크박스를 내용에 맞게 고른다.

이번 변경의 리뷰에 도움이 되는 내용을 넣는다.

- **바뀐 동작:** 기능, 인터페이스, 구현이 이제 어떻게 동작하는지. 중요하다면
  유지되는 동작도 포함한다.
- **중점적으로 볼 코드:** 조건, 처리 순서, 데이터 변환, 책임 경계처럼 리뷰에
  중요한 지점 몇 가지. 필요하면 짧은 코드 발췌나 링크를 붙인다.
- **구조나 흐름:** 구성요소 관계나 처리 흐름은 Mermaid 다이어그램으로.
- **제약:** 변경 이해나 병합 판단에 영향을 주는 호환성 변화, 배포 순서, 알려진
  제한.
- **UI 변경:** [UI 증거](references/ui-evidence.md)에 따라 준비하고 확인한 표시가
  있는 스크린샷이나 집중된 녹화로, 리뷰어가 앱을 실행하지 않아도 변경 위치와
  결과를 볼 수 있게 한다.
- **근거는 요구되거나 주장을 뒷받침할 때만:** 성능 개선 같은 경우다. 방법, 환경,
  장단점을 남기고 관찰 결과와 미검증 주장을 구분한다.
- **티켓에 없는 맥락:** 접근할 수 있는 티켓이 없으면 문제를 짧게 적고, 결정
  이유는 리뷰어에게 필요할 때만 보충한다.

넣지 않는다.

- 링크가 이미 담고 있는 티켓의 배경.
- diff를 파일별로 나열하는 설명, 다이어그램을 반복하는 문장.
- 통상적인 검증 결과, 명령, 작업 일지.

## 이슈 링크

이슈와 의존 관계는 내용을 복사하지 않고 링크한다. 이슈마다 적힌 목표를 최종
diff, 그리고 그 전이나 함께 반영되는 작업과 대조해, 이 PR이 그 이슈를
완료하는지, 일부만 진행하는지, 관련만 있는지 정한다. 이 PR이 완료하는 이슈는
머지되면 닫히도록 링크하고, 그 밖의 이슈는 머지 뒤에도 열려 있도록 링크한다.

## 주의할 점

- 저장소 PR 템플릿은 기본 브랜치에 있거나 소유자의 공개 `.github` 저장소에서
  상속된다. CLI나 API로 제출할 때도 필수 항목과 마커를 지키고, 요약은 템플릿의
  해당 섹션에 쓰며 중복 섹션을 만들지 않는다.
- GitHub는 PR 본문의 단일 줄바꿈을 줄바꿈으로 렌더링한다. 목록 항목을 포함해 각
  문단은 소스 한 줄로 유지하며, 저장소 Markdown의 줄 길이 제한은 적용하지 않는다.
- GitHub closing 키워드는 기본 브랜치를 대상으로 하는 PR에서만 동작한다. 다른
  base라면 [이슈 닫기](references/publishing.md#edge-cases)를 읽는다.
- 작업 중인 PR은 제목 접두사가 아니라 GitHub Draft 상태로 표시한다.
