# 풀 리퀘스트 작성하기

> 영문 정본: [SKILL.md](SKILL.md) (`b57290e` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

PR 설명은 리뷰어에게 무엇이 바뀌었고 어디를 봐야 하는지 알려 준다. 왜 필요했는지는
연결된 티켓이 담는다. 저장소 규칙과 템플릿이 우선한다. 글을 작성하거나 수정할 때는
해당 언어 스킬도 읽는다.

## 작업 흐름

요청된 부분만 한다. 제목, 설명, 게시 중 하나다.

1. **변경 읽기:** base는 사용자나 프로젝트의 대상이고, 없으면 기본 브랜치다. 전체
   diff와 관련 티켓을 읽는다.
2. **범위 확인:** PR 하나에 목적 하나, 테스트·호출부·문서를 함께 넣고 독립적인
   변경은 나눈다. 반영 뒤에도 대상 브랜치가 동작해야 한다. 미병합 PR에 의존하면
   [스택 PR](references/stacked-prs.md)을 읽는다.
3. **제목 작성:** 최종 커밋 subject로 쓰고
   [writing-commits](../writing-commits/SKILL.md)로 검증한다.
4. **본문 작성:** 아래를 따른다.
5. **요청이 있을 때만 게시:** [PR 게시](references/publishing.md)를 따른다. 새 PR은
   Draft로 시작하고, 요청이 있고 저장소 요건을 충족했을 때만 ready로 바꾼다.

## 본문 작성

`## Summary`로 시작해 무엇이 바뀌었는지 몇 문장으로 쓴다. 필요할 때만 내용에 맞는
소제목을 더한다.

리뷰에 도움이 되는 것만 넣는다.

- **바뀐 동작:** 중요하면 유지되는 동작도.
- **볼 코드:** 조건이나 처리 순서 같은 핵심 지점 몇 개와 짧은 발췌나 링크.
- **구조나 흐름:** Mermaid 다이어그램. 문장으로 반복하지 않는다.
- **제약:** 호환성, 배포 순서, 알려진 제한.
- **UI 변경:** [UI 증거](references/ui-evidence.md)에 따라 준비한 증거.
- **근거:** 저장소가 요구하거나 주장에 필요할 때만, 방법과 환경을 함께.
- **문제:** 접근할 수 있는 티켓이 없을 때만 짧게.

티켓의 배경, 파일별 설명, 통상적인 검증 결과, 작업 일지는 넣지 않는다.

## 이슈 링크

이슈마다 적힌 목표와 이 PR 전이나 함께 반영되는 작업을 기준으로, 이 PR이 그 이슈를
완료하는지, 일부만 진행하는지, 관련만 있는지 정한다. 완료하는 링크만 머지 시
이슈를 닫게 한다.

## 주의할 점

- 저장소 PR 템플릿은 소유자의 공개 `.github` 저장소에서 상속될 수 있다.
  `--body-file`이나 API 본문에서도 필수 항목과 마커를 지키고, 요약은 템플릿의
  해당 섹션에 쓴다.
- GitHub는 PR 본문의 단일 줄바꿈을 줄바꿈으로 렌더링한다. 문단과 목록 항목은 각각
  한 줄로 쓴다.
- GitHub closing 키워드는 PR이 기본 브랜치를 대상으로 할 때만 동작한다. 그 밖에는
  [이슈 닫기](references/publishing.md#edge-cases)를 읽는다.
- 작업 중인 PR은 제목 접두사가 아니라 GitHub Draft 상태로 표시한다.
