# 인계 계약

요구사항을 설계·티켓·구현 계획으로 넘길 때 읽는다. 고정 단계가 아니라 작업 크기에 따라 필요한
산출물만 고른다.
아래는 기본 경로다. 사용자가 크기 판정과 다른 산출물을 명시적으로 지정하면 그 요청을 우선하며, 그 산출물에 필요한 사실·승인·안전 기준은 유지한다.

## PRD가 다음 단계에 넘기는 것

- REQ ID와 합의된 우선순위(P1/P2, 미정이면 OPEN ID)
- 수용 기준
- 품질 기대(NFR)
- 비목표
- 위험(RISK)
- 미결정 항목(OPEN)

## 작업 크기 판정

| 크기 | 판정 기준 | 경로 |
| --- | --- | --- |
| S | 기존 사용자 동작과 외부 계약·데이터·권한이 그대로인 문구·표현·기계적 변경이다 | PRD 없이 바로 티켓 또는 구현 |
| M | 한 기능 안의 사용자 동작이 바뀌고 외부 계약은 그대로다 | PRD-lite(문제·기대 결과·REQ·수용 기준) + 구현 계획 |
| L | 여러 기능의 사용자 동작이 함께 바뀌거나, 외부 계약(API·데이터·통합) 또는 권한·보안 계약이 바뀌거나, 되돌리기 어렵다 | 전체 PRD → 필요한 외부 설계(화면·흐름, API·데이터 설계 문서나 ADR) → 티켓 분해 → 구현 계획 |

L 조건을 먼저 확인하고, 해당하지 않는 사용자 동작 변경은 M으로 판정한다. 여러 화면·파일에 걸쳐도 동작·계약을 그대로 유지하는 기계적 변경은 범위의 개수만으로 L이 되지 않는다. 한 문장으로 설명할 수 있다는 이유만으로 M이나 L을 S로 줄이지 않는다.

## 소유

| 산출물 | 담당 |
| --- | --- |
| 제품 요구 | Product |
| 화면·흐름 | 디자인 담당 |
| 설계 문서·구현 계획(흐름 F ↔ REQ) | 개발 계획 |
| 티켓 분해 | 티켓 작성 |

다른 플러그인이 설치되어 있다고 가정하지 않는다. 담당 스킬이 없으면 다음에 만들 산출물과 그
산출물이 담아야 할 내용을 대화로 안내한다.

## 추적

PRD가 있을 때만 REQ ID를 티켓의 출처 필드(기본형의 `참고`)와 구현 계획의 흐름 표에 보존한다. PRD가 없는 작업에는
ID를 만들지 않는다.

해당 REQ와 관련된 NFR ID·근거 있는 조건도 티켓의 결과 필드와 계획의 흐름·검증에 연결한다.
아직 미결정인 NFR은 OPEN ID와 영향으로 보존하며 확정된 수용 기준이나 임의의 수치로 바꾸지 않는다.

우선순위를 포함한 관련 OPEN ID·내용·영향을 후속 티켓과 계획의 미결정 위치에 보존한다.
관련 RISK ID·영향·합의된 완화 조건 또는 아직 필요한 확인 작업은 설계 문서의 횡단 관심사,
티켓의 허용된 결과·출처 필드, 계획의 해당 흐름·검증에 연결한다. 확인되지 않은 완화책을 만들거나
모든 위험을 무관한 산출물에 반복하지 않는다. 티켓에서는 실제 적용 양식의 대응 필드를 사용한다.
