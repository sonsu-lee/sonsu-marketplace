# 인계 계약

요구사항을 설계·티켓·구현 계획으로 넘길 때 읽는다. 고정 단계가 아니라 작업 크기에 따라 필요한
산출물만 고른다.
아래는 기본 경로다. 사용자가 크기 판정과 다른 산출물을 명시적으로 지정하면 그 요청을 우선하며, 그 산출물에 필요한 사실·승인·안전 기준은 유지한다.

## PRD가 다음 단계에 넘기는 것

- REQ ID와 합의된 우선순위(P1/P2, 미정이면 OPEN ID)
- 수용 기준
- 품질 기대(NFR)
- 비목표
- 위험(RISK)
- 미결정 항목(OPEN)
- 해당 범위와 관련된 성공 신호(SUCCESS)와 합의된 측정 방법·기준·근거

## 작업 크기 판정

| 크기 | 판정 기준 | 경로 |
| --- | --- | --- |
| S | 기존 사용자 동작·품질 기대와 외부 계약·데이터·권한이 그대로인 문구·표현·기계적 변경이다 | PRD 없이 바로 티켓 또는 구현 |
| M | 한 기능 안의 사용자 동작·품질 기대가 바뀌거나 우선순위·승인 범위 등 의미 있는 제품 결정만 바뀌며, L 조건에는 해당하지 않는다 | PRD-lite(문제·기대 결과·REQ·수용 기준) + 구현 계획 |
| L | 여러 기능의 사용자 동작이나 공통 품질 목표가 함께 바뀌거나, 외부 계약(API·데이터·통합·대외 SLO) 또는 권한·보안 계약이 바뀌거나, 되돌리기 어렵다 | 전체 PRD → 필요한 외부 설계(화면·흐름, API·데이터·품질·권한 설계 문서나 ADR) → 티켓 분해 → 구현 계획 |

L 조건을 먼저 확인하고, 해당하지 않는 사용자 동작·품질 기대 변경은 M으로 판정한다. 여러 화면·파일에 걸쳐도 동작·품질 기대·계약을 그대로 유지하는 기계적 변경은 범위의 개수만으로 L이 되지 않는다. 한 문장으로 설명할 수 있다는 이유만으로 M이나 L을 S로 줄이지 않는다.

성능·가용성·접근성 등 품질 목표만 바뀌어도 위 기준을 적용한다. 외부 계약이 그대로라는 이유만으로 S가 되지는 않는다. 한 기능의 내부 품질 목표 자체가 바뀌면 최소 M이고, 여러 기능의 공통 목표나 외부에 약속한 SLO가 바뀌면 L이다. 목표를 그대로 둔 문구나 측정 표기 정정은 S일 수 있지만, 목표·의무 자체의 변경을 표현 수정으로 취급하지 않는다. 미정인 목표값은 OPEN으로 남기며 크기 판정을 위해 수치를 만들지 않는다.

우선순위·승인 범위 등 제품 결정만 바꾸고 구현 변경은 없다면, M/L 판정 뒤에도 기존 PRD·결정 기록과
영향받는 티켓·계획의 추적 정보를 갱신하는 것으로 인계한다. 기존 PRD의 lite/full 형식을 재분류하거나
새 설계·티켓·구현 계획을 형식적으로 만들지 않는다. 새 기록이 필요한 M 결정은 PRD-lite로 남기고,
새 구현 계획은 실제 구현 변경이 있을 때 작성한다. 의미 변경의 리비전·재승인 기준은 그대로 적용한다.

## 탐색과 문서 변환

S의 기본 인계는 크기와 바로 이어갈 티켓·구현만 안내하며 PRD·REQ ID·탐색 결과 묶음은 생략한다. 이 경로에서는 PRD용 맥락을 보강하는 질문도 생략한다. 사용자가 문제 조사·대안 비교·평가를 요청하면 크기와 무관하게 요청한 탐색 결과를 먼저 제공한다. 크기는 제안의 타당성이나 구현 승인을 뜻하지 않는다.

사용자가 PRD 산출물을 명시적으로 지정하면 S라도 변환 가능성·사실 보존 기준을 적용해 작성한다. 스킬 이름 호출만으로 PRD 산출물이 지정됐다고 해석하지 않는다. 기존 PRD 갱신에는 생략 분기를 적용하지 않고 기존 형식과 영향받지 않는 내용·ID·metadata를 보존한다. 전체 재구성을 명시적으로 요청한 경우에 형식을 바꾼다.

M/L의 제품 결정이 부족해도 결정 이후 필요한 산출물의 크기와 순서를 안내한다. 문서 작성 준비 상태와 다음 산출물 선택은 따로 보고하며 탐색 중 계약 확인과 실제 설계 문서 작성을 구분한다.

## 소유

| 산출물 | 담당 |
| --- | --- |
| 제품 요구 | Product |
| 화면·흐름 | 디자인 담당 |
| 설계 문서·구현 계획(흐름 F ↔ REQ) | 개발 계획 |
| 티켓 분해 | 티켓 작성 |

다른 플러그인이 설치되어 있다고 가정하지 않는다. 담당 스킬이 없으면 다음에 만들 산출물과 그
산출물이 담아야 할 내용을 대화로 안내한다.

## 추적

PRD나 다른 승인된 요구 출처에 이미 있는 ID를 티켓의 출처 필드(기본형의 `참고`)와 구현 계획의 흐름 표에 보존한다.
합의된 우선순위도 관련 요구사항과 함께 티켓·계획에 보존한다. 우선순위와 승인된 범위·출시 순서를 구분하며 라벨만으로 범위를 추가하거나 제외하지 않는다.
관련 비목표·제외 범위는 티켓 양식의 허용된 범위·제약 위치와 계획의 전역 제약 또는 해당 흐름의 경계에 보존한다. 제외한 내용을 구현 작업으로 만들거나 무관한 하위 작업에 반복하지 않는다.
출처에 없는 REQ/NFR ID나 PRD 링크를 인계 과정에서 새로 만들지 않는다. ID가 없는 작업은 실제 요구 출처로 추적한다.

버전 있는 요구 출처는 사용한 리비전 또는 고정 snapshot과 범위를 Design·Dev Workflow 설계 산출물과 티켓·계획에 연결한다. 승인을 근거로 인계한다면 해당 버전·범위의 승인 기록도 연결하며, 미확인 상태를 승인으로 바꾸지 않는다. 기존 고정 입력을 참조해도 되며 버전 없는 출처에 metadata를 만들지 않는다.
Design 산출물은 관련 요구사항 ID·실제 출처·조건을 화면·상태·흐름에 연결한다. 일반 UI는 기존 명세·annotation을 활용하며 Operations 전용 필드를 강제하지 않는다.
수용 기준은 관련 계획 흐름·검증에 빠짐없이 연결하고 동작 검증의 `expected_source`에서 식별한다. M의 PRD-lite에서 계획으로 직접 넘길 때도 동일하다.

관련 SUCCESS ID·신호·합의된 측정 방법·기준·근거를 보존하고 이미 승인된 계측·측정 작업은 해당 티켓·계획 흐름과 검증에 연결한다. 성공 목표를 기능 수용 기준이나 코드 완료 조건으로 바꾸지 않는다. 측정 방법의 존재만으로 새 계측 구현을 승인하거나 인터뷰·출시 후 분석을 구현 작업으로 만들지 않으며, 없는 ID·목표값을 생성하거나 모든 티켓에 지표를 복사하지 않는다.
Design도 이번 평가와 관련된 성공 기준의 출처·범위와 metric·outcome의 관계를 기존 rationale이나 명세에 연결한다. 별도 사용성 평가와 제품 성공의 범위를 구분하며 모든 사업 지표를 Design 필수 지표로 만들지 않는다.

해당 REQ와 관련된 NFR ID·근거 있는 조건도 티켓의 결과 필드와 계획의 흐름·검증에 연결한다.
아직 미결정인 NFR은 OPEN ID와 영향으로 보존하며 확정된 수용 기준이나 임의의 수치로 바꾸지 않는다.

우선순위를 포함한 관련 OPEN ID·내용·영향을 후속 티켓과 계획의 미결정 위치에 보존한다.
관련 RISK ID·영향·합의된 완화 조건 또는 아직 필요한 확인 작업은 설계 문서의 횡단 관심사,
티켓의 허용된 결과·출처 필드, 계획의 해당 흐름·검증에 연결한다. 확인되지 않은 완화책을 만들거나
모든 위험을 무관한 산출물에 반복하지 않는다. 티켓에서는 실제 적용 양식의 대응 필드를 사용한다.
