# 제품 검증 설계

제품 가설을 관찰 계획으로 바꾸고 결과를 보기 전에 판정 계약을 고정한다. 문제·수요·가치·usability·viability·feasibility·제품 행동의 성격과 위험에 맞춰 방법을 고른다.

## 절차

1. 검증할 주장·현재 근거, 대상 사용자·상황·제외 범위, 결과에 따라 내릴 결정, 거짓 긍정·거짓 부정의 비용, 개인정보·동의·규제·브랜드·운영 위험을 확인한다. 시간·표본 접근·도구·예산은 실제 제약으로 기록하고 미정 수치·기간·표본·성공 기준은 `open`으로 둔다. 가설이나 다음 결정이 모호하면 작은 가설 하나로 좁힌다.
2. 가설을 대상·상황, 관찰 가능한 행동·결과, 예상 이유, competing explanation, 약화·반증 관찰로 표현한다. 선호·의향과 실제 행동, 사용량과 제품 가치, 상관관계와 인과관계를 구분한다.
3. 필요한 증거로 방법을 고른다. 문제·현재 행동에는 맥락 인터뷰·관찰·diary·기존 행동 자료, 이해·usability에는 prototype·task 관찰, 수요·commitment에는 선주문·신청·가격 선택·concierge·fake door·행동 신호를 검토한다. 제품 효과에는 cohort·quasi-experiment·controlled experiment·전후 비교, viability에는 가격·비용·공급자·정책 확인·operational rehearsal, feasibility에는 기술 spike·공급망·제약 검증을 검토한다. 선택 이유·bias·필요 증거 수준을 쓰고 표본은 목적·모집단 다양성·분석 방식·중단 조건에 연결한다.
4. plan ID·리비전·가설 ID, 대상·모집·선정·제외 기준, 절차·노출·비교 조건·최소 데이터, primary signal·guardrail·instrumentation 확인을 정한다. `supported`·`invalidated`·`inconclusive` 기준과 누락·중도 이탈·오염·중복·실행 편차 처리, 분석·경쟁 설명 확인, 개인정보·동의·중단·취소·피해 완화를 기록한다. 결과별 continue·revise·pivot·stop·추가 검증 선택을 연결한다. 미정 기준으로 실행할 때 판정이 왜 불가능하거나 약해지는지 밝힌다.

## 결과

실행 가능한 test plan, 미결정 기준, 예상 한계, 필요한 승인·외부 행동을 구분한다. 가설 → 관찰 → 사전 판정 기준 → 다음 결정이 추적되면 설계를 완료한다. 한 실험의 결론은 해당 대상과 범위에 한정한다.

## 예시

입력: “라디오 앱의 ‘나중에 듣기’ 표시를 이용자가 이해하는지 관찰하고 싶어. 판정 수치는 아직 합의하지 않았어.”

결과: 실제 저장 과제를 수행하는 prototype 관찰을 제안하고, 성공 행동은 ‘설명 없이 저장한 방송을 다시 찾음’으로 정의한다. 이해도와 기존 앱 경험을 경쟁 설명으로 구분한다. 정량 판정 기준은 `open`이며 합의 전 실행 결과는 성공 판정을 뒷받침하기 어렵다고 기록한다.

## 경계

- 코드 단위·통합·QA·보안 테스트 설계와 실행 결과 판정은 각 담당 작업으로 넘긴다.
- 모집·연락·노출·결제·수집·제품 변경을 실행하거나 제품 결정을 승인하지 않는다. 실행 요청은 별도 작업의 권한과 안전 조건을 확인해 인계한다.

## 참고 자료

- 결과 해석은 [제품 검증 판정](../assess-product-test/SKILL.md)을 따른다.
- 여러 단계의 주 조정자는 [작업 연속성](../../references/continuity.md)을 필요할 때 읽는다. 단발 작업과 위임된 작업자는 별도 기록을 만들지 않는다.
