# 제품 도메인 탐색

제품이 다루는 세계와 책임을 공통 언어로 설명할 수 있는 후보 모델을 만든다. 첫 모델은 탐색을
돕는 가설이며, 확인되지 않은 구조를 정본이나 구현 계약으로 고정하지 않는다.

## 경계

- 제품 관점의 용어, 행위자, 상태, 사건, 규칙, 불변 조건, 경계와 예외를 다룬다.
- 코드의 class, type, module, database schema와 제어 흐름을 설계하거나 수정하지 않는다.
- `CONTEXT.md`, 도메인 정본, ADR, PRD와 API 계약을 직접 작성하지 않는다.
- 제품 자료에 없는 개념을 업계 관행이나 모델 지식만으로 확정하지 않는다.
- 다른 제품 영역의 같은 단어를 하나의 의미로 자동 통합하지 않는다.

## 근거와 현재 리비전을 고정한다

현재 대화, 승인된 제품 문서, 인터뷰·피드백, 정책, issue, 구현과 테스트를 필요한 범위에서
읽는다. 각 자료가 무엇을 증명하는지 구분한다.

- 승인된 제품 정책은 의도와 규칙의 강한 근거다.
- 인터뷰와 사례는 해당 사용자의 상황과 언어에 대한 근거다.
- 코드와 테스트는 현재 구현의 근거이며 제품 의도의 자동 근거가 아니다.
- 이름이 비슷하다는 사실은 두 개념이 같다는 근거가 아니다.

입력 자료와 후보 모델에 리비전을 부여한다. 의미 있는 용어, 경계나 규칙이 바뀌면 새 리비전으로
갱신하고 이전 확인을 자동으로 승계하지 않는다.

## 구체적인 사례에서 모델을 찾는다

추상 명사만 나열하지 말고 실제 제품 시나리오를 사용한다.

1. 누가 어떤 계기로 행동하는지 확인한다.
2. 행동 전후에 무엇의 상태가 바뀌는지 찾는다.
3. 사용자가 관찰할 사건과 제품 또는 외부 주체의 책임을 구분한다.
4. 허용되는 전이, 금지되는 전이와 불변 조건을 적는다.
5. 실패, 취소, 재시도, 중복, 빈 상태, 권한 차이와 시간 경계를 대입한다.
6. 현재 모델이 설명하지 못하는 반례와 경쟁 모델을 남긴다.

행위자와 역할, 식별자와 표시 이름, 상태와 결과, 명령과 사건처럼 혼동하기 쉬운 개념을
구분한다. 같은 용어가 여러 의미로 쓰이면 조용히 하나를 선택하지 않고 각각의 후보 정의와
영향을 보여 준다.

## 후보 상태를 관리한다

각 항목은 다음 상태 가운데 근거에 맞는 상태로 표시한다.

- `observed`: 출처에서 직접 관찰했다.
- `inferred`: 관찰을 설명하기 위해 추론했다.
- `proposed`: 공통 언어 또는 규칙으로 제안했다.
- `confirmed`: 권한 있는 사용자가 현재 리비전과 범위를 명시적으로 확인했다.
- `conflicted`: 출처나 이해관계자의 정의가 충돌한다.
- `open`: 근거 또는 결정이 부족하다.

`confirmed`가 아닌 항목을 canonical 용어, 규칙이나 invariant로 표현하지 않는다. 초기 모델의
구조가 후속 질문을 제한하지 않도록 대안과 반례를 함께 유지한다.

## 결과

다음 내용을 필요한 만큼 제공한다.

1. 범위와 외부 경계
2. 용어·개념 후보, 정의, 상태와 근거 ID
3. 행위자, 책임과 권한
4. 상태, 사건, 허용·금지 전이와 불변 조건
5. 정상 사례, 예외와 반례
6. 충돌하는 정의, 경쟁 모델과 미해결 질문
7. 현재 리비전에서 확인된 내용과 확인이 필요한 내용
8. PRD, 도메인 정본, ADR 또는 코드 설계로 넘길 수 있는 후보와 필요한 별도 승인

모델이 현재 사례를 설명하고, 확인된 내용과 가설이 구분되며, 다음에 확인할 가장 영향이 큰
용어·규칙·경계가 분명할 때 완료한다.
