# 제품 도메인 탐색

제품이 다루는 세계와 책임을 공통 언어로 설명하는 후보 모델을 만든다. 첫 모델은 질문을 돕는 가설로 두고 대안과 반례를 함께 유지한다.

## 절차

1. 대화, 승인된 제품 문서, 인터뷰·피드백, 정책, issue, 구현과 테스트를 필요한 범위에서 읽고 입력·모델 리비전을 고정한다. 승인 정책은 의도·규칙, 인터뷰는 해당 상황·언어, 코드·테스트는 현재 구현의 근거로 사용한다. 의미 있는 용어·경계·규칙이 바뀌면 리비전을 갱신하고 확인 상태를 다시 평가한다.
2. 실제 시나리오에서 행위자와 계기, 행동 전후의 상태, 관찰할 사건, 제품과 외부 주체의 책임을 찾는다. 허용·금지 전이와 불변 조건에 실패·취소·재시도·중복·빈 상태·권한 차이·시간 경계를 대입한다. 설명되지 않는 반례와 경쟁 모델을 남긴다.
3. 행위자와 역할, 식별자와 표시 이름, 상태와 결과, 명령과 사건을 구분한다. 이름이 비슷한 개념도 사례와 책임으로 대조하고, 영역마다 의미가 다르면 후보 정의와 영향을 각각 보여 준다. 자료에 없는 관행은 확인할 가설로 둔다.
4. 항목마다 근거 ID와 상태를 붙인다. `observed`는 직접 관찰, `inferred`는 추론, `proposed`는 공통 언어·규칙 제안, `confirmed`는 권한 있는 사용자가 현재 리비전·범위를 명시적으로 확인함, `conflicted`는 정의 충돌, `open`은 근거·결정 부족이다. 정본 용어·규칙·불변 조건으로 인계할 때는 `confirmed` 여부를 확인한다.

## 결과

범위·외부 경계, 용어 후보·정의·상태·근거 ID, 행위자·책임·권한, 상태·사건·전이·불변 조건, 정상·예외·반례, 경쟁 모델·질문, 현재 리비전의 확인 범위와 확인할 항목을 제공한다. PRD·도메인 정본·ADR·코드 설계로 넘길 후보에는 필요한 별도 승인을 적는다. 현재 사례가 설명되고 다음에 확인할 핵심 용어·규칙·경계가 분명하면 완료한다.

## 예시

입력: “도서관에서는 ‘반납’이 이용자의 반납함 투입과 직원의 검수 완료를 모두 뜻해.”

결과: 두 사용례는 `observed`, ‘반납 접수’와 ‘검수 완료’라는 구분은 `proposed`로 둔다. ‘투입 뒤 대출 책임이 끝나는가?’를 `open`으로 남긴다. 권한 있는 담당자가 이번 모델의 범위를 확인한 항목만 `confirmed`로 바꾼다.

## 경계
