# PRD 품질 기준

PRD를 작성하거나 갱신할 때 읽는다.

## PRD-lite와 전체 PRD

새 문서의 크기와 기존 문서 갱신은 [인계 계약](../../../references/delivery-handoff.md)을 따른다. 파일 metadata·안전·승인은 [문서 계약](document-contract.md)에 둔다.

PRD-lite 본문은 문제·기대 결과·REQ·수용 기준으로 작성한다. 사용자·범위는 문제에, 행위자·조건·관찰 결과는 요구와 수용 기준에 필요한 만큼 담는다. 근거·미결정은 해당 항목 옆에 연결하고 합의된 우선순위·품질 기대도 보존한다. 전체 PRD의 추가 표·절은 lite의 필수 형식이 아니다.

REQ에는 문서 안에서 유일하고 안정적인 ID를 부여하고 기존 ID를 유지한다. 실제 포함하는 NFR은 관련 REQ·조건·근거, OPEN과 RISK는 내용·영향, SUCCESS는 합의된 신호·측정 방법·기준·근거에 연결한다. 관련 내용이 있을 때 ID를 부여하며, 형식 때문에 품질 기대·미결정·위험·완화책·신호·수치·계측 작업을 새로 만들지 않는다. 이 문서 작성 단계와 출처에 없는 ID를 새로 만들지 않는 후속 인계를 구분한다.

미정 품질 목표는 OPEN 항목으로 남기고 관련 REQ나 품질 기대 옆에 `목표 미정(OPEN-001)`처럼 실제 OPEN ID를 연결한다. OPEN에서 REQ를 가리키는 역방향 참조만으로 대체하지 않는다. lite에서도 연결을 유지하되 별도 품질 기대 표는 필요한 경우에만 쓴다.

전체 PRD는 [템플릿](../assets/prd-template.md)에서 관련 없는 항목과 자리표시자·작성 안내 주석을 제거해 작성한다. 핵심 요구마다 안정적 ID·상위 목표, 합의된 P1/P2(미정이면 OPEN ID), 관련 NFR ID(없으면 해당 없음), 행위자·계기/조건·관찰 결과, 출처·결정·가정/미결정 ID, 확인 방법·수용 기준을 연결한다.

## 근거 표기

선택·판단의 출처는 `[사용자 결정]`, `[제공 자료: 대화 발췌 또는 파일 위치]`, `[저장소: 경로:줄]`, `[공식문서: URL]`, `[실험: 명령 → 관찰 결과]`, `[논문/실무자: URL]`로 구분한다. 제공 자료는 식별 가능한 발췌·위치를 남기고 고정 locator가 없으면 한계를 밝힌다. 태그는 출처의 종류이며 검증·대표성·합의·승인 여부는 별도로 판단한다. 인터뷰·피드백은 해당 발화의 근거로 두고 위치를 확인할 수 없는 자료는 그 상태를 밝힌다.

근거 없는 판단은 `[추론]`으로 표시하고 결정에 필요하면 먼저 조회·실험으로 확인하거나 미결정으로 남긴다. 숫자·담당자·날짜·승인 상태는 입력에서 확인한 값만 확정한다. 구현 방법을 요구로 담을 때는 실제 제약의 출처와 이유를 적는다.

## 필수 품질

- 문제, 대상 사용자와 기대 결과가 기능 목록보다 먼저 설명되어 있다. 피드백이나 참고 서비스에서
  출발한 요구는 실제 사용 상황·관찰 근거에 연결되고, 현재 해결 방식의 한계와 제안한 해법이 구분된다.
- 제품 경계, 포함 범위와 비목표가 구분되어 있다.
- 핵심 용어와 제품 규칙이 일관되게 사용된다.
- 정상 동작은 사용 계기에서 핵심 행동을 거쳐 결과를 얻고 종료하는 흐름으로 설명되어 있다. 중요한
  실패, 빈 상태, 권한, 취소와 재시도는 그 흐름의 관련 지점에 연결되며 화면 목록만으로 대체하지 않는다.
- 각 요구사항은 행위자, 조건과 관찰 가능한 결과를 포함한다.
- 목표, 요구사항, 수용 기준과 검증 방식이 서로 추적된다. 기능이 명세대로 동작하는지 확인하는
  수용 기준과 사용자가 기대한 결과를 얻었는지 관찰하는 성공 신호를 구분한다.
- 사실, 결정, 가정, 충돌과 미결정 항목이 구분되어 있다.
- 숫자와 날짜에는 출처나 결정 근거가 있다.
- 구현 방법은 실제 제품 제약인 경우에만 이유와 함께 포함한다.
- 품질 기대는 제품 언어로 쓰고, 근거 없는 수치는 OPEN 항목으로 남긴다.
- P1/P2는 합의된 우선순위로 보존하고 출시 범위·순서와 구분한다. 사용자가 우선순위와 출시 조각의 대응을 명시적으로 합의했다면 그 결정도 별도로 보존하되, 라벨만으로 포함·제외나 출시 순서를 추정하지 않는다. 우선순위가 합의되지 않았으면 미정과 OPEN ID로 남긴다.

반복 이용이나 참여가 중요한 제품은 이미 합의된 재이용의 가치와 기대 행동을 문제·기대 결과,
정상 동작과 성공 신호에 이어서 담는다. 예를 들어 가입 완료와 참여자가 도움을 주고받는 결과는
다른 신호다. 근거가 부족하면 기존 가정·미결정 항목에 남기고, 일회성 도구에는 재방문 목표를
추가하지 않는다. 지표의 수치·기간과 새로운 제품 결정을 이 작성 단계에서 임의로 정하지 않는다.

새 피드백으로 기존 PRD를 갱신할 때에는 어떤 문제·기대 결과·요구사항의 근거가 달라졌는지부터
대조한다. 반영하기로 결정한 내용만 해당 요구사항과 수용 기준·성공 신호에 연결하고, 미채택 요청은
기능 범위로 승격하지 않는다. 화면 구성·컴포넌트·실험 절차의 상세 설계는 각 후속 작업에서 다룬다.

## 상태 검사

- 조건부 초안의 미결정 항목과 영향이 명확한가?
- 승인 상태가 현재 리비전과 정확한 승인 범위에 연결되어 있는가?
- 제품 합의와 디자인, 엔지니어링, QA와 운영 준비 상태를 구분했는가?
- 배포와 출시 상태를 코드 존재만으로 추정하지 않았는가?

## 문서 검사

- 저장소의 ID, 파일명, frontmatter와 링크 관례를 따르는가?
- 자리표시자와 관련 없는 템플릿 항목이 남아 있지 않은가?
- 같은 목적의 PRD가 중복되어 있지 않은가?
- 정본 도메인 문서나 ADR과의 충돌이 드러나 있는가?
- 허용 경로 밖의 파일을 수정하지 않았는가?

문장 품질이나 형식 검사만으로 제품 결정이 완전하다고 판정하지 않는다.
