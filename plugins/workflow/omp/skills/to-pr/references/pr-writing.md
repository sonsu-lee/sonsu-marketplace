# PR 제목과 본문

PR을 처음 읽는 리뷰어와, 나중에 history·blame에서 이 PR을 찾아온 독자가 변경 이유와 달라지는 동작을 이해하도록 쓴다. 근거는 실제 diff·설계·검증 결과이며, 작성 전에 실제 변경, 설계 근거와 rollout·migration·호환성·rollback 제약을 확보한다. Writing 설치 여부와 무관하게 이 지침으로 작성한다.

## 양식을 보존한다

사용자 또는 저장소가 지정한 양식이 기본형보다 우선한다. 제목·항목 순서·체크리스트·필수 필드·고정 문구를 유지하고 내용을 해당 위치에 채운다. 기본형의 제목을 추가하거나 여러 양식을 합치지 않는다. 부분 수정에서는 현재 구조와 요청받지 않은 내용을 보존한다.

양식의 HTML comment는 자동화 표식이나 숨은 지침일 수 있으므로 기본적으로 보존한다. 명시적으로 제거·치환하도록 지정한 작성 안내만 바꾼다. 필수 빈 항목과 체크리스트를 일반적인 빈 항목 정리 규칙으로 지우지 않으며 `N/A` 허용 여부도 해당 양식을 따른다. 고정 제목·체크리스트는 번역하지 않고, 채워 넣는 설명만 전달받은 출력 언어로 작성한다.

검토에 꼭 필요한 티켓·검증·주의사항·미디어를 위한 항목이 없으면 가장 가까운 자유 입력란에 쓴다. 추가 항목이 허용될 때만 최소 항목을 더한다. 담을 수 없는 필수 정보는 본문 밖에서 제약으로 알리고 Draft를 유지한다.

기본형 적용 조건과 `unverified` 처리는 [PR 템플릿 규칙](pr-template.md#기본-템플릿-적용-조건을-확인한다)을 따른다. [PR 기본 양식](../assets/templates/pull-request.md)은 설명할 정보와 필요할 때 사용할 언어별 제목을 안내하며 출력 섹션을 강제하지 않는다.

## 리뷰어와 이후 독자가 알아야 할 것만 쓴다

[공통 정보 선택 기준](../../../references/tracker-prose.md#티켓pr에서-설명할-내용을-고른다)을 PR에 적용할 때는 다음 세 질문으로 본문을 대조한다. 질문마다 제목을 만들 필요는 없다.

1. 왜 바꿨는가: 이번에 해결한 문제와 영향을 설명한다. 티켓 전체 배경을 복사하지 않되 PR만 읽어도 변경이 필요한 이유를 이해할 수 있게 쓴다.
2. 무엇이 어떻게 달라졌고 왜 이 방법을 택했는가: 사용자가 보게 될 동작이나 유지보수자가 알아야 할 처리 방식의 변화와 선택 이유를 연결한다. 함수 목록 대신 “여러 화면이 각자 권한을 판단하던 것을 공통 판정으로 바꿔 같은 사용자가 화면마다 다른 결과를 받지 않게 한다”처럼 설명한다. 이 이유는 실제 입력·최종 diff·확인된 결정에 있을 때만 쓴다.
3. 검토·배포할 때 무엇을 알아야 하는가: 처리하지 않은 관련 요구, 적용되지 않는 대상, 선행 배포 작업, 복구 제약, 확인하지 못한 중요한 동작을 해당할 때 설명한다. 수용 여부를 판단하는 데 필요한 환경별 수동 관찰과 재현 조건도 [검증 보고 기준](#검증은-다시-실행해-확인할-수-없는-것만-쓴다)에 따라 남긴다. `참고: 티켓 링크`나 자료 목록으로 대신하지 않는다.

무엇을 빼고 예외로 남길지는 [공통 제외 기준](../../../references/tracker-prose.md#불필요한-내용을-구별한다)을 따른다. 필수 외부 양식과 사용자 명시 요청은 유지하되 AI 공개 요구와 작성 권한의 충돌은 [AI 사용 표기](../../../references/tracker-prose.md#ai-사용-표기)를 따른다. 관련 티켓의 자동 연결 줄은 아래 연결 규칙으로 보존하며, 준비·게시 결과 보고는 본문 밖에 둔다.

## 결과와 이유를 연결한다

제목은 실제 결과를 한 문장으로 설명하고 전달받은 저장소의 semantic 제목·Conventional Commit 관례를 따른다. “파일 수정” 같은 행위만 쓰지 말고 어떤 동작이 달라지는지 드러낸다. 글쓰기 과정에서 commit을 바꾸지 않는다. squash 병합 저장소에서는 PR 제목이 기본 커밋 제목이 되므로 [커밋 메시지 기준](../../../references/commit-message.md)의 제목 규칙을 함께 따른다.

기존 문제와 실제 바뀐 동작, 확인된 선택 이유를 연결한다. 변경은 파일이 아니라 동작·관심사 단위로 묶고 조건·인과관계가 전달될 만큼 설명한다. 제목·목록은 내용을 구분해 읽는 데 필요할 때 쓴다([경량형](../../../references/tracker-prose.md#경량형)). 정본 문서에 있는 세부 목록은 복사하지 않되, 독자가 public API의 사용법·호환성 변화를 알아야 하면 필요한 이름과 조건을 설명하고 정본으로 연결한다. 여러 독립 주제가 섞였으면 PR 경계를 점검하고 복잡한 변경의 배포·전환·복구 제약을 분량 때문에 지우지 않는다.

## 구조 변경은 설계 수준으로 설명한다

새 모듈·계층·경계, 데이터·제어 흐름, 생성 방식이나 공개 계약을 바꾼 PR은 코드를 한 줄씩 해설하지 않고 다음을 설명한다.

- 따른 설계 원칙이나 제약. 예: 정본 하나에서 생성한다, 외부 입력은 경계에서 한 번만 검증한다. 원칙이 실제로 없으면 만들지 않는다.
- 구성 요소별 책임과 그 사이의 흐름. 구성 요소가 셋 이상이고 흐름이 문장으로 전달되지 않을 때만 짧은 Mermaid 다이어그램을 쓴다.
- 받아들인 tradeoff와, 리뷰어가 물을 만한 대안을 고르지 않은 이유

## 리팩터링은 근거로 설명한다

동작을 바꾸지 않는 구조 변경이 PR의 목적이면 `기존 방식 → 바꾼 방식 → 근거` 순서로 쓴다. 근거는 다음 중 하나 이상이어야 한다.

- 측정값: 변경 전후 수치와 측정 방법. 예: 응답 시간, bundle 크기, build 시간, 중복 코드 위치 수, 순환 의존 수
- 표준·공식 문서: 언어·framework의 공식 지침, 명세, RFC, deprecation 공지와 그 링크
- 실제 결함: 기존 구조 때문에 발생했거나 재현한 버그·장애와 그 링크
- 후속 변경: 이 리팩터링이 필요한 다음 PR·티켓의 링크와, 기존 구조로는 그 변경이 어려운 이유. 같은 stack에서 함께 게시하는 위층이면 링크 대신 그 층의 branch와 주제를 쓴다.

기능·버그 수정 PR 안의 작은 정리(지역 변수 rename, import 정리, 그 변경에 필요한 작은 함수 추출)는 근거를 요구하지 않고 따로 설명하지도 않는다.

근거가 없으면 평가어로 채우지 않는다. 게시 전에 근거가 없다는 사실을 사용자에게 알리고 근거를 요청하며, 다른 PR이 그 리팩터링에 의존하지 않으면 빼는 방안도 제안한다. 답을 받기 전에는 게시하지 않는다. 동작 불변을 지키는 테스트의 부재가 실제 변경의 병합 판단에 영향을 주는 경우에만 그 위험과 이유를 `참고`나 해당 설명에 남긴다.

## 검증은 다시 실행해 확인할 수 없는 것만 쓴다

검증 수행과 본문 보고는 별개다. CI 밖의 리뷰 핵심 동작을 고르고 사용할 수 있는 환경에서 직접 시도해 관찰 근거를 확보한다. 현재 CI 상태를 읽지 않고 성공이라고 표현하지 않으며, 본문에서 보고를 생략해도 게시 전 검증 근거 확인은 생략하지 않는다.

자동 검사 명령·성공·개수는 CI가 있든 없든 기본 본문에서 제외한다. 수동 관찰도 변경 설명이나 영상 caption과 같은 정보를 반복하면 다시 적지 않는다. 리뷰 판단에 새 정보를 주는 다음 내용만 `참고` 또는 해당 미디어 caption·설명에 둔다. 별도 `검증` 제목을 기본으로 만들지 않는다.

- 실제 브라우저·기기·OS·외부 연동·배포 등의 환경별 관찰: 무엇을 어디서 확인했고 어떤 결과였는지 설명한다.
- 리뷰어가 재현해야 수용 여부를 판단할 수 있는 변경의 필요한 확인 절차
- 확인하지 못해 병합 판단에 영향을 주는 중요한 동작과 미확인 이유

미확인 위험을 알릴 때는 빠진 관찰과 판단에 미치는 영향만 설명한다. 앞에서 설명한 변경 동작을 “확인해야 한다”는 검수 목록으로 다시 나열하지 않는다. 다만 재현에 필요한 새로운 환경·입력·조작 순서가 있으면 그 정보를 남긴다.

미검증 상태를 설명하는 것과 새 병합 조건을 정하는 것은 다르다. 확인된 사용자·저장소 합의 없이 “병합 전에 반드시” 같은 승인 조건을 추가하지 않는다. 이 구분은 기존 게시·필수 첨부의 안전 조건을 생략할 권한이 아니다.

관련 없는 브라우저 미확인 목록을 자동으로 붙이지 않는다. 일회성 관찰을 회귀 테스트나 전체 동작의 보장으로 바꾸지 않는다. 본문 보고를 생략해도 티켓의 합의된 수용 조건은 유지하며, 완료 여부는 그 조건을 실제로 다룬 검증 근거로 판단한다.

## 근거의 범위를 넓혀 쓰지 않는다

실행 결과, 정적 검사, 브라우저 확인, mock·fixture, `not_run`, `inconclusive`와 환경 부족을 구분한다. 좁은 검사가 통과했다고 전체 동작이 검증됐다고 쓰지 않는다. 예를 들어 입력이 “파서 단위 테스트 통과, 실제 Excel 미확인”이면 “Excel 호환성 검증 완료”로 요약하지 않는다.

확인된 관계는 [연결 규칙](ticket-linking.md#티켓-id에-링크를-건다)의 형식으로 본문에 한 번 남긴다. 이를 위해 별도 관련 작업 섹션이나 티켓 요약을 만들지 않는다. 티켓 ID·자동 종료 토큰·상태 효과가 있는 문구를 문체 개선을 이유로 추가·삭제·변경하지 않는다. 이미지·영상에는 볼 지점을 설명하고 로컬 파일·placeholder·실제 업로드 URL을 구분한다. URL이 있다는 사실로 표시·재생 성공을 주장하지 않는다.

## 최종 점검

- 게시 전 마지막으로 본문의 각 문장을 [포함 기준](#리뷰어와-이후-독자가-알아야-할-것만-쓴다)에 대조해 어느 질문에도 답하지 않는 문장과 배제 목록에 해당하는 문장을 지운다. 포함 기준이 정한 예외는 지우지 않는다.
- 제목·본문이 최종 head의 실제 변경 범위와 같은 결과를 설명하는지 확인한다.
- 캡처가 보여 주는 동작, 마킹·설명과 현재 diff가 일치하는지 확인한다.
- 작성과 문장·항목 배치를 마친 최종 제목·본문에서 고정 양식·코드·식별자·링크·의무 수준과 보호할 연결 문법이 보존됐는지 확인한다. 저장소 양식을 썼다면 실제 템플릿의 제목·순서·체크리스트·필수 항목·HTML comment와도 대조한다. `Fixes`·`Part of`·`Ignore`, ticket ID와 HTML marker가 원래의 연결 의도·상태 효과·양식 계약을 유지하는지 확인한다. 첨부 URL과 위치도 검증한 미디어 계획과 대조한다. 작성 결과만으로 새로운 연결·상태 변경 권한을 만들지 않는다.
- 비밀·token·개인정보, 공개 범위에 맞지 않는 내부 URL·자료와 제한된 보안 정보를 넣지 않는다. 양식 조회·캡처·검사·업로드·게시의 내부 절차와 원격 상태 보고는 PR 설명 밖에 둔다.
- [공통 정보 선택·문장 기준](../../../references/tracker-prose.md)으로 불필요한 내용과 모호한 설명을 고친다. 외부 필수 양식·사용자 명시 요청이 아니면 자동 검사·테스트 개수·로그를 본문에서 제외하고, 수동 관찰은 리뷰에 필요한 정보가 있을 때 해당 설명이나 caption에 한 번만 남긴다.
