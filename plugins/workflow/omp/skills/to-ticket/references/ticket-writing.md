# 티켓 작성 지침

티켓을 새로 쓰거나 고칠 때 읽는다. 티켓은 작업 지시를 세세하게 나열하는 문서가 아니라 작업의 목적·방향·필요한 맥락·완료 기준을 공유하는 문서다. 다른 사람이 이전 대화를 모두 읽지 않아도 무엇을 왜 해야 하는지 이해하고 판단할 수 있게 쓴다. 작성자는 문제·목적·합의된 방향과 제약을 전달하고, 작업자는 정하지 않은 원인 분석과 해결 방법을 정한다. Writing 설치 여부와 무관하게 이 지침으로 작성한다.

## 양식을 고른다

다음 순서로 적용한다.

1. 사용자가 지정한 양식
2. 대상 저장소·팀·프로젝트의 양식과 작성 지침
3. 요청 목적에 맞는 번들 기본형

저장소의 issue 양식·form·기여 지침과 tracker의 팀 양식을 확인한다. 여러 양식이면 해당 공간의 선택 규칙을 따른다. 저장소에 파일이 없다는 사실만으로 팀 양식도 없다고 판단하지 않는다.

주어진 양식의 제목·순서·필수 항목·체크리스트·고정 문구를 보존하고 그 항목에 내용을 채운다. 기본형의 제목을 뒤에 덧붙이지 않는다. HTML comment는 자동화 표식이나 숨은 지침일 수 있으므로 양식이 제거·치환하도록 지정한 부분만 바꾼다. 기존 티켓을 부분 수정할 때는 현재 구조(제목 체계·순서 포함)와 요청받지 않은 내용을 보존하고, 전체 재작성을 요청받았을 때만 양식을 바꾼다.

플랫폼 중립 초안이나 적용할 양식이 없다고 확인된 대상에는 기본형을 사용한다. 버그 접수에는 대상 공간의 버그 보고용 양식·form과 필수 입력을 먼저 찾고, 적용할 버그 양식이 없다고 확인된 경우에만 번들 버그 양식을 사용한다. 대상 공간에 다른 종류의 양식만 있다고 해서 그 양식에 버그를 억지로 맞추지 않는다. 대상 버그 양식에 접근할 수 없어 확인하지 못했다면 `unverified`로 보고하고, 번들 버그 양식을 적용하지 않은 채 확인된 사실을 형식 미확정의 임시 초안에 보존한다.

양식을 확인할 수 없는 상태와 양식이 없는 상태를 구분한다. 양식 확인이 안 된 초안은 임시임을 본문 밖에서 알린다. 게시 전에는 적용 양식과 필수 필드를 확인하거나, 미확인 한계를 안내한 뒤 사용자가 명시적으로 선택한 기본형을 사용한다. 어느 경우에도 interface의 필수 필드는 생략하지 않는다. 글을 썼다는 사실로 원격 양식의 부재, 접수 가능 여부나 게시 준비 완료를 판단하지 않으며, 임시 초안 작성은 양식 확정, 게시 조건·권한이나 원격 필수 필드 충족의 근거가 아니다.

## 출력 언어를 정한다

티켓 언어는 사용자 지정, 대상 공간의 지침·양식·일관된 관례, 기존 티켓이나 승인 문서의 주 언어, 영어 순으로 정한다. 대화 언어는 티켓 언어의 근거가 아니다. 결과 보고는 사용자가 요청한 언어를 따른다. 고정된 양식 문구는 해당 양식이 허용할 때만 번역한다.

## 기본형을 고른다

| 요청한 최종 작업 | 기본형 |
| --- | --- |
| 기능·개선·리팩터링·문서 등 변경·추가·정리 | [일반 작업](../assets/templates/default.md) |
| 잘못된 동작 수정 | [버그](../assets/templates/bug.md) |
| 질문에 대한 답변이나 판단 근거 마련 | [조사 작업](../assets/templates/investigation.md) |

버그 수정에 원인 조사가 포함되어도 버그형을 쓴다. 조사 결과 자체를 전달하는 것이 요청이면 조사형을 쓴다. 이 구분은 본문 양식이며 tracker의 type·label·status를 지정하지 않는다. 준비 상태 분류를 강제하지 않고, 실제 필드는 대상 공간의 기존 설정과 관례를 따른다. 문제나 질문을 이해할 수 있으면 알려진 내용으로 작성한다. 무엇을 다루는지도 불명확하거나 접수 가능한 정보가 부족하면 보존 가능한 초안과 필요한 입력을 반환하며, 미확인 사실을 채워 넣지 않는다.

항목별로 담을 내용은 아래 기준과 각 기본형의 작성 안내(HTML comment)를 따른다. 완성된 초안에서는 기본형의 작성 안내와 빈 선택 항목을 제거한다. 주어진 양식의 필수 빈 항목에는 이 삭제 규칙을 적용하지 않는다. 작은 작업은 항목을 합쳐도 된다. 배경·목적(버그는 현상)과 완료 상태를 한 문단으로 설명할 수 있고 조건부 항목이 모두 비면 제목 없이 본문만 쓴다([경량형](../../../references/tracker-prose.md#경량형)).

## 항목별로 담을 내용

일반 작업 기본형은 배경·목적 / 방향성·범위 / 전제·유의사항 / 완료조건으로 구성한다. 버그형과 조사형은 유형별 제목을 유지하고 같은 의미를 담는다. 버그형의 `현상`·`재현 정보`는 배경과 전제를, `참고`는 범위와 유의사항을, `완료조건`은 수정 후 기대 상태를 맡는다. 조사형의 `확인할 질문`은 배경·목적을, `남길 결과`는 완료조건을, `참고`는 범위와 전제를 맡는다. 사용자·팀 양식을 쓸 때도 같은 의미를 그 양식의 대응 항목에 담는다.

### 배경·목적: 왜 이 작업을 하는가

현재 어떤 문제나 필요가 있고 누구에게 어떤 영향을 주는지, 이 작업으로 무엇을 바꾸거나 해결하려는지 쓴다. 작업의 필요성을 설명하는 맥락만 남기고 논의 경위나 일반론으로 분량을 늘리지 않는다.

### 방향성·범위: 무엇을 어떤 기준으로 해결하는가

이번 작업에서 다룰 대상과 바뀌어야 할 상태를 쓴다. 범위가 혼동될 수 있으면 하지 않을 일도 쓴다. 우선할 가치, 지켜야 할 원칙, 중요한 선택의 이유는 추상적인 구호가 아니라 실제 판단에 쓸 수 있는 기준으로 쓴다. 합의된 방향과 제약은 보존하되 아직 정하지 않은 구현 방법·파일 구조·작업 순서를 임의로 확정하지 않는다.

### 전제·유의사항: 작업자가 무엇을 알아야 하는가

기존 동작, 관련 결정, 의존 관계, 기술·운영 제약처럼 판단에 필요한 정보를 쓴다. 안전·보안·호환성·데이터 보존처럼 놓치면 잘못된 결과로 이어지는 사항은 구체적으로 남긴다. 확인된 사실과 가정·미정 사항을 구분한다. 참고 링크는 첨부하되 필수 맥락은 링크를 열지 않아도 이해할 수 있게 요약한다.

### 완료조건: 어떤 결과가 나오면 끝났다고 보는가

완료조건은 담당자와 리뷰어가 완료 여부를 같은 기준으로 판단하게 돕는 항목이다. 작업을 묶어 두는 검수 목록이 아니므로 짧게 쓴다. 일반 작업에서는 기본으로 둔다. 합의된 조건이나 수용 기준이 있으면 반드시 이 항목에 모은다. 합의된 조건이 없고 방향성·범위의 바뀔 상태만으로 완료 판단이 분명한 작은 작업만 생략하거나 한 문단에 합친다. 버그는 기대 동작이 완료조건이다.

본문에 설명한 목적과 범위에서 도출하고, 본문에 없는 요구사항을 완료조건에서 새로 추가하지 않는다. “구현한다”, “검토한다”, “테스트한다” 같은 활동이 아니라 무엇이 가능해지거나 해결·확정되어야 하는지 확인 가능한 결과나 상태로 쓴다. 각 조건은 “이 조건이 빠지면 이 티켓의 수용 여부가 달라지는가?”를 통과해야 한다. 서로 다른 실패를 구분해야 하는 조건만 나누고, 같은 결과의 세부 경우·절차·유사 사례를 따로 늘어놓지 않는다.

조건은 결과만 고정하고 방법은 묶지 않는다. 작업 중 더 나은 방법을 찾았을 때 조건이 걸림돌이 되지 않게 한다. 다음은 사용자가 요청했거나 합의된 요구, 또는 안전·호환성에 필수인 경우가 아니면 완료조건에 넣지 않는다.

- 특정 구현·파일·함수, 개별 테스트 케이스, 검증 절차·도구·측정 방법
- 빌드·lint·일반 테스트 통과·코드 리뷰처럼 모든 작업에 적용되는 팀 공통 완료 기준(Definition of Done). 테스트·문서·CI 작업 자체가 요청한 결과라면 결과로 남긴다.
- 근거 없는 목표 수치·지원 환경·실패 정책. 필요한 결정은 미정 사항으로 한 곳에만 남기고 알려진 내용으로 작성을 계속한다.
- 새 검수·승인 단계, 스크린샷·근거표 같은 증빙 요구, 충분한 자동 검증과 같은 내용의 수동 재검수

합의된 조건은 그 의미대로 보존한다. 이미 합의된 동작이 “빈 검색 결과에서 다운로드 버튼을 숨긴다”라면 그 동작을 임의의 테스트 명령으로 대체하지 않는다. “회귀가 없다”처럼 합의의 의미가 불명확하면 대상과 기대 상태를 필요한 입력으로 표시한다. 자동 검증될 예정이라는 이유로 요구사항을 지우지 않는다. 승인된 PRD·명세·실행 가능한 인수 테스트가 정본이면 해당 결과를 짧게 요약하고 정확한 절·REQ ID·시나리오를 참조할 수 있다. 전체 명세나 테스트 목록은 복사하지 않는다.

완료조건, 팀 공통 완료 기준과 검증 근거는 서로 다른 정보다. 조건을 적거나 검사를 실행했다는 사실만으로 충족된 것이 아니다. CI 통과는 그 검사가 다룬 조건·리비전·환경 범위의 근거이며, CI의 존재나 전체 성공 표시만으로 완료라고 쓰지 않는다.

조사의 `남길 결과`는 질문에 대한 근거 있는 판단과 확인 범위다. 원인 발견·특정 대안 채택·제품 배포를 종료조건으로 만들지 않는다. 판단 불가로 종료할 수 있는지는 합의된 조사 범위·종료 기준을 따르고, 없으면 임의로 정하지 않고 필요한 결정으로 남긴다.

## 상세 수준을 정한다

세부사항은 그 내용이 없을 때 작업 범위, 구현 판단, 안전성 또는 완료 판정이 달라지는 경우에만 남긴다. 더 자세해 보이게 하는 내용은 생략한다.

다음은 사용자가 요청했거나 이미 합의된 요구사항, 또는 안전·호환성에 필수인 제약이 아니면 쓰지 않는다.

- 함수명·변경할 파일별 수정 목록, 작업 순서·단계 체크리스트, 개별 테스트 케이스, PR 분할 계획
- 작성 경위: 대화·조사 과정, 사용한 도구·agent·모델
- 요청과 무관한 배경 설명, 같은 내용의 반복
- 모든 작업에 적용되는 팀 공통 절차(빌드·lint·테스트 통과·코드 리뷰). 사용자가 함께 알려 줬어도 이 티켓만의 제약이 아니면 옮겨 적지 않는다.

“정상 동작”, “품질 향상”, “문제없음”처럼 해석이 갈리는 표현은 대상과 기대 상태가 드러나도록 구체화한다. 항목 수를 맞추려고 조건을 추가하거나, 간결하게 쓰려고 중요한 예외와 제약을 삭제하지 않는다.

## 제목과 본문을 구체적으로 쓴다

제목은 주된 문제나 요청을 바로 드러낸다. 버그는 "조건 + 관찰된 동작 + 대상", 작업은 "대상 + 달라질 상태"로 쓴다([예시](../../../references/tracker-prose.md#예시)). 같은 내용을 여러 항목에서 반복하지 않는다. 한 문단에는 관련된 내용을 모으고, 재현처럼 순서가 있는 절차는 번호 목록으로 쓴다. 주체·조건·이유가 바뀌는 지점에서 문장을 나눈다.

## 사실과 판단을 구분한다

원인 추정은 요청 여부와 관계없이 가설로 표시하고 사실처럼 쓰지 않는다.

관찰, 가설, 제안, 선호, 합의와 실행 결과를 구분한다. “Next.js를 선호한다”를 필수 조건으로 바꾸지 않는다. 원인·해결 방법·코드 구조·작업 순서·구체적 테스트를 새로 지시하지 않는다. 이미 합의된 설계·ADR, 보안·호환성, 전환 순서·복구 조건처럼 방법 자체가 제약인 내용은 보존한다. 조사 결과의 보고서·비교표 형식과 일정도 요청되거나 합의된 경우에만 지정한다.

확인되지 않은 배경·결정·수치·제약을 만들어 채우지 않는다. 작업이나 완료 판정에 꼭 필요한 정보가 없으면 미정 사항으로 표시한다. 그 밖의 모르는 값을 채우려고 빈 항목이나 반복적인 `미확인` 문구를 만들지 않는다.

## 요구 출처와 외부 합의를 보존한다

PRD나 승인된 요구사항 문서에서 티켓을 나눌 때는 합의된 우선순위와 독립 완료 판단 단위로 자른다. 적용 양식의 완료·수용 기준 필드(기본형의 `완료조건`)에 해당 요구사항의 수용 기준을 합의된 조건으로 옮긴다. 출처·링크 필드(기본형의 `전제·유의사항`)에 기존 REQ ID와 실제 요구 출처를 보존한다. PRD의 URL·파일 경로가 제공되었으면 그 링크를 사용하고, 대화에 작성되거나 붙여 넣은 PRD처럼 링크가 없으면 제공된 PRD의 제목·리비전 등 확인 가능한 식별 정보와 대화 출처를 기록한다. 없는 REQ ID나 PRD 링크를 만들지 않는다. 관련 NFR이 있으면 그 ID와 근거 있는 조건을 완료조건에 연결하고, 미결정 NFR은 OPEN ID와 영향으로 보존한다. 미결정 값을 수용 기준으로 확정하지 않는다. 구현 계획과 설계는 넣지 않는다.

사용자·팀 양식의 제목을 바꾸거나 기본형 제목을 추가하지 않는다. 의미상 대응 필드가 없으면 양식이 허용하는 기존 자유 서술 필드에 조건·출처를 함께 보존한다. 그 위치도 없으면 추적 정보를 본문 밖 인계 메모에 남기고 양식의 제약을 알린다. 게시 대상에서 허용되는 보존 위치가 확인되기 전에는 추적 정보가 티켓에 반영됐다고 보고하지 않는다.

버전 있는 요구 출처는 링크뿐 아니라 분해에 사용한 리비전 또는 고정 snapshot과 해당 요구 범위를 위 허용 위치에 남긴다. 승인을 근거로 인계한다면 그 버전·범위에 적용되는 승인 기록 위치도 연결한다. 승인 근거가 없거나 미확인이면 그 상태를 보존하며 티켓 작성·게시 자체를 제품 승인으로 취급하지 않는다. 버전 없는 출처에 리비전이나 승인 metadata를 만들지 않는다.

PRD가 아닌 승인 문서에도 기존 요구사항·품질 ID가 있으면 실제 출처와 함께 보존한다. 위의 ID 생성 금지는 출처에 없는 ID를 새로 만드는 경우에 적용하며, 입력에 있는 ID를 삭제하라는 뜻이 아니다.

합의된 우선순위는 해당 REQ와 함께 위 허용 위치에 보존한다. 승인된 tracker 필드가 확인된 대응 관계로 그 값을 정확히 표현하면 본문에 중복하지 않아도 된다. P1/P2를 임의의 tracker 우선순위 값으로 변환하지 않는다.

해당 범위와 관련된 기존 SUCCESS ID·신호·합의된 측정 방법·기준·근거도 보존한다. 제품 성공 목표는 수용 기준 필드가 아닌 허용된 맥락·출처 위치에 두고, 이미 승인된 계측·측정 작업만 해당 티켓의 결과에 연결한다. 자유 서술 필드 하나뿐이면 제품 목표와 구현 완료 조건을 명시적으로 구분한다. 제품 성공 목표를 기능 수용 기준·코드 완료 조건으로 바꾸거나 측정 방법만으로 새 구현 작업을 승인하지 않는다. 구현 밖의 인터뷰·출시 후 분석을 자동 구현 작업으로 만들지 않고 없는 ID·목표값을 만들거나 무관한 티켓에 지표를 반복하지 않는다.

우선순위·품질·제품 규칙 등 해당 티켓과 관련된 OPEN ID·내용·영향을 위 허용 위치에 보존한다. 미결정 값을 P1/P2, tracker 우선순위나 수용 기준으로 임의 확정하지 않고 관련 없는 OPEN을 모든 자식 티켓에 복사하지 않는다. 관련 RISK ID·영향·합의된 완화 조건 또는 남은 확인 작업도 같은 방식으로 해당 티켓에 연결한다. 합의되지 않은 완화책을 새 구현 지시로 만들지 않는다.

외부 논의의 핵심 결론은 요약하고 근거를 연결한다. 긴 계획이나 회고는 필요한 부분만 요약하며 상세 계획을 새로 만들지 않는다. 합의가 바뀌면 최신 결론과 중요한 변경 이유·기존 근거를 함께 남긴다. 코드·수치·의무 수준·티켓 ID·URL은 문체를 다듬을 때도 보존한다.

## 사례: 관찰에서 원인을 만들지 않는다

다음은 이 저장소의 작성 기준을 설명하기 위한 로컬 예시다. 입력은 “다운로드한 CSV의 한글이 깨진다. 원문대로 표시되어야 한다”뿐이며, 환경·재현 순서·원인은 아직 모른다고 가정한다.

- 잘못된 확장: “UTF-8 BOM 누락을 수정하고 CSV 라이브러리를 교체한다.” 원인과 방법을 새로 결정했다.
- 작성 예시:

```markdown
다운로드한 CSV의 한글이 깨져 표시됩니다. 원문의 한글이 그대로 표시되어야 합니다.
```

현상과 기대 상태를 한 문단에 담을 수 있고 조건부 항목이 모두 비어 제목 없이 썼다. 두 번째 문장이 완료 상태이며, 원인이나 수정 방법을 완료조건으로 만들지 않았다. 환경·재현 단계·자료가 작업 착수나 판단에 꼭 필요하면 필요한 입력으로 알리되, 본문을 채우기 위해 원인·단계·자료를 만들지 않는다.

## 외부 접근 없이 이해할 수 있게 근거를 남긴다

원래 콘솔·로그·계정에 접근할 수 없는 구현자도 문제와 기대 동작을 이해할 수 있게 필요한
관찰·환경·리비전과 짧은 재현 입력·출력을 본문에 보존한다. 링크는 보충 근거이며 필수 사실을
링크 뒤에만 두지 않는다. 비밀·개인 데이터를 제거한 fixture나 예시는 원본과의 관계를 설명한다.
원인 미확정 버그는 증상·확인한 근거·가설을 구분해 기록할 수 있다. 원인 확정, 선택된 해결법과
정확한 테스트 구현을 모든 티켓의 필수 조건으로 만들지 않는다. 이미 합의된 내용만 추가하고
기존 간결한 양식·영어 고정 제목을 유지한다. 안전하게 보존할 수 없는 근거의 한계는 명시한다.

## 범위와 결과를 정확히 남긴다

부모·자식 티켓도 각각의 요청 목적에 맞는 양식을 쓴다. 부모는 전체 문제와 자식별 범위를, 자식은 맡은 작업과 필요한 공통 제약을 설명한다. 부모의 긴 배경을 복사하지 않는다. 이미 정해졌거나 합의된 제외 범위와 전체 제공 및 검증 조건을 보존한다.

실제 결과가 생겼을 때만 본문에 보강한다. 접수·채택과 구현 완료, 장애 복구와 재발 방지, 회고 작성과 후속 개선, 검증 수행과 기준 충족, 일부 대상의 전환과 전체 전환을 구분한다. 합의된 제공·복구·검증 조건을 충족했다는 근거 없이 완료로 표현하지 않는다. 한 자식의 완료나 코드 merge를 전체 작업 완료로 표현하지 않는다.

## 최종 점검

- 초안을 적용 양식의 필수 항목과 실제 필드에 대조하고, 확인되지 않은 정보와 필요한 입력을 표시한다.
- 완료조건이 본문의 목적·범위에서 도출됐는지, 활동이 아니라 확인 가능한 결과·상태인지, 본문에 없는 요구사항을 새로 추가하지 않았는지 대조한다. 각 조건이 수용 여부를 바꾸는지 확인하고, 방법을 묶는 조건·팀 공통 절차·근거 없는 수치·새 검수 단계를 뺀다. 공통 절차를 빼면서 요청 산출물인 테스트·문서·CI 작업까지 지우지 않았는지, 같은 내용이 여러 항목에 반복되지 않는지 확인한다.
- 문체를 다듬은 뒤에도 고정 양식(제목·순서·필수 항목·체크리스트·고정 문구), 코드·식별자·티켓 ID·링크·URL·수치·의무 수준, 기존 결정과 보호할 연결 문법이 보존됐는지 대조한다. 플랫폼이 해석하는 필드와 marker는 일반 설명문처럼 번역하거나 재작성하지 않는다.
- [문장 형식 기준](../../../references/tracker-prose.md)의 서두·서식 밀도·어조 규칙을 대조한다.
