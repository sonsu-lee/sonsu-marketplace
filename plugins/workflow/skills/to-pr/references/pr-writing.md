# PR 제목과 본문

PR을 처음 읽는 리뷰어와, 나중에 history·blame에서 이 PR을 찾아온 독자가 변경 이유와 달라지는 동작을 이해하도록 쓴다. 근거는 전달받은 실제 diff·설계·검증 결과다. Workflow는 변경 범위와 유효한 양식·언어·연결 대상을 확인하고 게시를 수행한다. Writing이 있으면 공통 구성 지침을 함께 적용하며, 없어도 이 지침으로 설명을 작성한다.

## 양식을 보존한다

사용자 또는 저장소가 지정한 양식이 기본형보다 우선한다. 제목·항목 순서·체크리스트·필수 필드·고정 문구를 유지하고 내용을 해당 위치에 채운다. 기본형의 제목을 추가하거나 여러 양식을 합치지 않는다. 부분 수정에서는 현재 구조와 요청받지 않은 내용을 보존한다.

양식의 HTML comment는 자동화 표식이나 숨은 지침일 수 있으므로 기본적으로 보존한다. 명시적으로 제거·치환하도록 지정한 작성 안내만 바꾼다. 필수 빈 항목과 체크리스트를 일반적인 빈 항목 정리 규칙으로 지우지 않으며 `N/A` 허용 여부도 해당 양식을 따른다. 고정 제목·체크리스트는 번역하지 않고, 채워 넣는 설명만 전달받은 출력 언어로 작성한다.

검토에 꼭 필요한 티켓·검증·주의사항·미디어를 위한 항목이 없으면 가장 가까운 자유 입력란에 쓴다. 추가 항목이 허용될 때만 최소 항목을 더한다. 담을 수 없는 필수 정보는 본문 밖에서 제약으로 알리고, 게시 판단은 Workflow에 넘긴다.

기본형을 적용하기로 정해졌으면 [PR 기본 양식](../assets/templates/pull-request.md)의 항목·언어별 제목·정리 규칙을 따른다. 양식이 `unverified`이면 기본형을 확정하지 않는다. 확인된 사실로 준비 가능한 설명만 작성하고, 양식 확인 상태와 남은 게시 조건을 본문 밖에서 알린다.

## 리뷰어와 이후 독자가 알아야 할 것만 쓴다

본문의 각 문장은 다음 질문 중 하나에 답해야 한다. 어느 질문에도 답하지 않는 문장은 지운다.

1. 왜 바꿨는가: 기존 문제나 필요
2. 무엇이 달라지는가: 관찰 가능한 동작·계약·구조
3. 왜 이 방식인가: 코드만으로는 보이지 않는 결정과, 리뷰어가 물을 만한 대안을 고르지 않은 이유
4. 어떻게 확인할 수 있는가: CI가 대신할 수 없는 확인과 화면 자료의 설명
5. 무엇을 조심해야 하는가: 배포·migration 순서, 호환성, 롤백, 알려진 제한, 후속 작업
6. 무엇과 연결되고 어떻게 보면 되는가: 티켓·PR 연결 줄, 건너뛸 수 있는 생성 파일, 먼저 볼 곳

사용자가 명시적으로 요청한 내용과, 사용자·저장소가 지정한 양식의 고정 문구·체크리스트·필수 항목은 이 필터로 지우지 않는다.

다음은 저장소 양식이나 사용자가 명시적으로 요구하지 않는 한 본문에 쓰지 않는다. 필요한 정보는 결과 보고로 본문 밖에 둔다.

- 작업 과정: 조사·시행착오, 사용한 도구·agent·모델, 리뷰 반영 이력과 횟수, “확인해 보니” 같은 경위
- CI가 실행하는 검사 명령, 테스트 개수, lint·format·typecheck 통과 여부
- 파일·함수별 변경 목록, diff를 문장으로 옮긴 설명, 코드 줄 단위 해설
- 바꾸지 않은 것의 나열. 리뷰어가 바뀌었다고 오해할 구체적 이유가 있을 때만 한 문장으로 쓴다.
- 이 PR과 무관하게 발견한 기존 문제. 리뷰나 운영 판단에 영향을 줄 때만 `참고`에 한 줄로 쓰고, 아니면 결과 보고에서 별도 티켓 후보로 알린다.
- 티켓 배경의 복사, 요약과 상세의 중복, 같은 사실의 반복
- 근거 없는 평가어: “깔끔하게”, “가독성 향상”, “안정성 개선”, “더 나은 구조”
- 작성 도구 표기와 서명. 실행 환경이 자동으로 덧붙이면 그 설정 위치를 본문 밖에서 알린다.
- 위험과 무관한 미확인 항목의 목록

## 결과와 이유를 연결한다

제목은 실제 결과를 한 문장으로 설명하고 전달받은 저장소의 semantic 제목·Conventional Commit 관례를 따른다. “파일 수정” 같은 행위만 쓰지 말고 어떤 동작이 달라지는지 드러낸다. 글쓰기 과정에서 commit을 바꾸지 않는다.

본문은 기존 문제 → 달라지는 동작 → 검토에 필요한 선택의 이유 순서로 구성한다. 작은 변경은 짧은 배경과 변경 설명으로 충분하다. `변경 사항`은 파일이 아니라 동작·관심사 단위로 묶고 항목마다 1–2문장으로 쓴다. 필드·검사 규칙·옵션처럼 정본 문서에 이미 있는 세부 목록은 옮겨 적지 않고 그 문서 경로를 가리킨다. 항목이 많아지면 PR 경계가 맞는지 먼저 의심한다. 복잡한 변경에는 배포·전환·호환성·복구 시 주의점을 필요한 만큼 설명한다. 선택 이유가 근거에 없으면 그럴듯한 이유를 만들어 넣지 않는다.

아래는 배대준의 [공통시스템개발팀 코드 리뷰 문화 개선 이야기](https://techblog.woowahan.com/7152/)에 실린 한국어 MR 사례의 짧은 발췌다. 원문은 빌드 오류와 의존성 버전 변경을 설명한 뒤 해결을 연결한다.

> TS2305: Module '"react-router"' has no exported member 'useHistory'. 에러를 내면서 빌드가 깨집니다.
>
> 사용하는 react-router의 버전을 package.json에 명시합니다.

이 사례에서 가져올 점은 “버전 명시”라는 수정 행위를 독자가 겪는 빌드 실패와 연결하는 구조다. 원인·결과는 해당 MR의 설명이며 다른 PR에 자동 적용할 근거가 아니다. 글의 평가는 팀의 실무 경험에 따른 것이고, 모든 PR에 동일한 길이·항목을 강제하는 규칙은 아니다.

일본어 원문 [Wantedly의 PR 작성법](https://docs.wantedly.dev/fields/dev-process/how-to-write-a-pull-request)은
라우팅·controller 수정 목록을 나쁜 예로, 데모 화면에서 할 수 있는 동작과 접근 범위를 좋은 예로
제시한다. 그중 제한을 밝히는 원문은 “デモメニューは本番環境以外でのみアクセスできる。”다.
파일 이름을 지우라는 규칙이 아니라, 변경 목록을 읽고 사용 동작과 적용 범위를 추론해야 하는 부담을
줄이는 예시다. 이 문서는 일본어 저자의 원문으로 참고했으며 번역판을 별도 표본으로 세지 않는다.

영어 원문 [Google의 CL 설명 지침](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)은
첫 줄에서 구체적인 변경을 식별하고 본문에서 문제·접근 방법·제약을 설명하는 예를 제시한다. 같은 지침은
코드가 소프트웨어가 무엇을 하는지는 보여 줘도 왜 존재하는지는 보여 주지 않으므로, 이후 독자가 결정을
바꿔도 되는지 판단할 맥락을 남기라고 설명하며 benchmark 결과와 설계 문서 링크를 그 맥락의 예로 든다.
CL은 Google의 코드 변경 단위이며 이 저장소 PR 양식과 같지는 않다. 구조의 판단 근거로 참고하고,
원문의 길이나 제목 규칙을 팀 양식보다 우선하지 않는다.

## 구조 변경은 설계 수준으로 설명한다

새 모듈·계층·경계, 데이터·제어 흐름, 생성 방식이나 공개 계약을 바꾼 PR은 코드를 한 줄씩 해설하지 않고 다음을 설명한다.

- 따른 설계 원칙이나 제약. 예: 정본 하나에서 생성한다, 외부 입력은 경계에서 한 번만 검증한다. 원칙이 실제로 없으면 만들지 않는다.
- 구성 요소별 책임과 그 사이의 흐름. 구성 요소가 셋 이상이고 흐름이 문장으로 전달되지 않을 때만 짧은 Mermaid 다이어그램을 쓴다.
- 받아들인 tradeoff와, 리뷰어가 물을 만한 대안을 고르지 않은 이유

## 리팩터링은 근거로 설명한다

동작을 바꾸지 않는 구조 변경이 PR의 목적이면 `기존 방식 → 바꾼 방식 → 근거` 순서로 쓴다. 근거는 다음 중 하나 이상이어야 한다.

- 측정값: 변경 전후 수치와 측정 방법. 예: 응답 시간, bundle 크기, build 시간, 중복 코드 위치 수, 순환 의존 수
- 표준·공식 문서: 언어·framework의 공식 지침, 명세, RFC, deprecation 공지와 그 링크
- 실제 결함: 기존 구조 때문에 발생했거나 재현한 버그·장애와 그 링크
- 후속 변경: 이 리팩터링이 필요한 다음 PR·티켓의 링크와, 기존 구조로는 그 변경이 어려운 이유. 같은 stack에서 함께 게시하는 위층이면 링크 대신 그 층의 branch와 주제를 쓴다.

기능·버그 수정 PR 안의 작은 정리(지역 변수 rename, import 정리, 그 변경에 필요한 작은 함수 추출)는 근거를 요구하지 않고 따로 설명하지도 않는다.

근거가 없으면 평가어로 채우지 않는다. 게시 전에 근거가 없다는 사실을 사용자에게 알리고 근거를 받도록 요청하며, 다른 PR이 그 리팩터링에 의존하지 않으면 빼는 방안도 제안한다. 답을 받기 전에는 게시하지 않는다. 동작 불변을 지키는 테스트가 없으면 그 사실을 `검증`의 미확인 위험으로 쓴다. 테스트가 있고 CI가 실행하면 따로 쓰지 않으며, CI가 없으면 4번 형식으로 쓴다.

## 검증은 CI가 대신할 수 없는 것만 쓴다

`검증` 항목에는 다음에 해당하는 것만 쓴다. 해당하는 것이 없으면 항목을 만들지 않는다.

1. 사람이나 agent가 직접 확인한 결과 중 CI가 실행하지 않는 것: 화면·상호작용, 실제 브라우저·기기·OS, 외부 서비스·실데이터 연동, 배포·migration·설정 적용, 성능 측정. 무엇을, 어떤 환경에서, 어떤 결과를 관찰했는지 한 줄로 쓴다.
2. 리뷰어가 직접 재현해야 판단할 수 있는 변경의 짧은 확인 절차
3. 확인하지 못했고 merge 판단에 영향을 주는 위험과 그 이유
4. CI가 없거나 CI가 실행하지 않는 자동 검사 중, 저장소 문서(`CONTRIBUTING`, `AGENTS.md`, README, 해당 영역의 테스트 안내)나 `package.json` scripts·Makefile 같은 task 정의에 있는 해당 변경의 검사를 실제로 실행해 통과한 것. `` `명령` 통과 `` 형식의 한 줄로 쓰고 개수·로그는 넣지 않는다. 실행하지 않았으면 명령을 쓰지 않고 3번으로 다룬다.

CI가 다루는지는 이 PR에 실제로 붙는 check로 판정한다. base 저장소의 workflow 설정에 이 PR의 base branch·변경 경로를 대입해 실행될 job을 찾고, 최근 PR의 check run·commit status로 외부 CI도 확인한다. workflow도 최근 PR의 check도 없을 때만 CI가 없다고 본다. 판정할 수 없으면 자동 검사는 쓰지 않고 1–3만 쓴다. “확인했습니다”처럼 대상·환경·결과가 없는 문장은 쓰지 않는다.

## 근거의 범위를 넓혀 쓰지 않는다

실행 결과, 정적 검사, 브라우저 확인, mock·fixture, `not_run`, `inconclusive`와 환경 부족을 구분한다. 좁은 검사가 통과했다고 전체 동작이 검증됐다고 쓰지 않는다. 예를 들어 입력이 “파서 단위 테스트 통과, 실제 Excel 미확인”이면 “Excel 호환성 검증 완료”로 요약하지 않는다.

관련 작업에는 확인된 관계와 canonical URL을 쓴다. 티켓 ID·자동 종료 토큰·상태 효과가 있는 문구를 문체 개선을 이유로 추가·삭제·변경하지 않는다. 이미지·영상은 무엇을 보여 주는지 설명하고, 로컬 파일·placeholder·실제 업로드 URL을 구분한다. URL이 있다는 사실로 표시·재생 성공을 주장하지 않는다.

최종 본문이 실제 변경 범위와 같은 결과를 설명하는지 확인한다. 비밀·개인정보·공개 범위에 맞지 않는 내부 자료를 넣지 않는다. 양식 조회·캡처·검사·업로드·게시의 내부 절차와 원격 상태 보고는 PR 설명 밖에 둔다.
