# 양식과 티켓 범위

## 적용할 양식을 확인한다

다음 순서로 선택한다.

1. 사용자가 지정한 양식
2. 대상 저장소·팀·프로젝트의 양식과 작성 지침
3. 아래 요청 목적에 맞는 기본 양식

저장소의 issue 양식·form·기여 지침과 tracker의 팀 양식을 확인한다. 여러 양식이면 해당 공간의 선택 규칙을 따른다. 저장소에 파일이 없다는 사실만으로 팀 양식도 없다고 판단하지 않는다.

버그 접수에는 대상 공간의 버그 보고용 양식·form과 필수 입력을 먼저 찾는다. 적용할 버그 양식이 없다고 확인된 경우에만 번들 [버그 양식](../assets/templates/bug.md)을 사용한다. 대상 공간에 다른 종류의 양식만 있다고 해서 그 양식에 버그를 억지로 맞추거나, 버그 양식의 조회 실패를 부재로 간주하지 않는다.

플랫폼 중립 초안이나 적용할 양식이 없는 대상에는 기본형을 사용한다. 접근할 수 없어 확인하지 못했다면 `unverified`로 보고하고 임시 초안을 작성한다. 게시 전에는 적용 양식과 필수 필드를 확인하거나, 미확인 한계를 안내한 뒤 사용자가 명시적으로 선택한 기본형을 사용한다. 어느 경우에도 interface의 필수 필드는 생략하지 않는다.

기존 티켓을 부분 수정할 때는 현재 제목 체계와 순서를 보존한다. 전체 재작성을 요청받았을 때만 양식을 교체한다. 적용 양식이 있으면 필요한 내용을 그 항목에 담고 기본형을 뒤에 붙이지 않는다.

## 기본 양식과 내용을 구성한다

기본 양식의 선택, 항목별 내용과 표현은 번들 [티켓 작성 지침](ticket-writing.md)을 따른다. Writing 설치 여부와 무관하게 이 지침과 번들 양식으로 작성한다.

일반 작업·버그·조사 작업은 본문 작성 방식이며 tracker의 type·label·status가 아니다. 준비 상태 분류를 강제하지 않고, 실제 필드는 대상 공간의 기존 설정과 관례를 따른다. 접수 가능한 정보가 부족하면 보존 가능한 초안과 필요한 입력을 반환하며, 미확인 사실을 채워 넣거나 interface의 필수 필드를 생략하지 않는다.

## 독립적으로 추적할 때만 나눈다

같은 문제의 조사·결정·검증 내용은 기존 티켓에 보강한다. 별도로 맡거나 추적할 결과가 있을 때만 나누고, 사용자가 지정한 분해 경계는 유지한다. 조사나 배포 단계가 생겼다는 이유만으로 새 티켓을 만들지 않는다.

부모·자식 본문도 번들 작성 지침을 따른다. 상하위·선행 관계는 실제 tracker 기능으로 연결하고, 그 기능이 없을 때만 본문에 의미를 남긴다. parent라는 이유로 Epic·project를 자동 생성하지 않는다.

각 실행 범위가 중복되거나 누락되지 않는지 확인한다. 합의된 제외 범위와 전체 제공·검증 조건도 보존한다. 한 자식의 완료나 코드 merge를 전체 작업 완료로 바꾸어 표현하지 않는다.
