# 공통 티켓 작성 기준

## 사실과 결정의 경계를 보존한다

티켓은 필요한 이유, 관찰·원하는 결과, 범위와 완료 또는 검토 종료 조건을 기록한다. 접수 단계에서는 확인된 사실과 미해결 질문을 쓰고 미승인 구현 계약을 만들지 않는다. 실행 티켓에서는 관찰 가능한 완료 판정을 제공한다.

- `why`: 현재 상태와 원하는 상태의 차이 또는 답할 질문
- `what`: 필요한 결과, 포함 범위·비목표와 이미 결정된 제약
- `done`: 합의된 결과의 수용 기준 또는 조사·검토의 종료 조건

파일 목록·함수 구조·작업 순서·해결책은 기본 body가 아니다. 승인된 설계·ADR, 공개 계약, 보안·호환성, migration·rollback이나 검증 절차처럼 방법 자체가 제약이면 보존한다. 구체적 테스트 설계·명령·도구는 작업자에게 남긴다. 요청·가설·관찰·결정·실행 결과를 서로 바꾸어 쓰지 않는다.

선택한 양식의 heading·순서·필수 field를 보존한다. 종류별 기본형은 필요한 section만 사용하며, `<...>` placeholder를 사실로 채울 근거가 없으면 생략 가능한 section을 빼거나 중요한 미정 사항으로 표시한다. 빈 항목·`없음`을 모든 티켓에 반복하지 않는다. 필수 section은 삭제하지 않고 확인 불가와 필요한 입력을 표시한다. 출처·준비 상태 같은 초안 관리 정보는 대상 양식이 요구하지 않으면 본문 밖에 둔다.

## 언어와 Fluent Languages를 선택한다

새 제목·본문과 기존 내용 수정에는 다음 순서로 언어를 정한다.

1. 사용자가 명시한 티켓 언어
2. 대상 공간의 지침·유효한 template 또는 일관된 최근 티켓 관례
3. 수정할 canonical ticket이나 승인된 specification·제품 문서의 명확한 주 언어
4. 사용자가 요청한 출력 언어, 그것도 없으면 현재 대화의 주 언어

결과 보고는 사용자가 요청한 보고 언어를 따르고 없으면 대화 언어를 사용한다. 티켓과 보고 언어가 다르면 각 산출물에 해당하는 문체를 적용한다. 고정 template heading·checklist·안내 문구는 양식이 허용하지 않는 한 번역하지 않는다. 기본형 heading은 결정된 티켓 언어로 자연스럽게 작성한다.

**작성·수정·결과 보고 때 해당 언어의 Fluent Languages 스킬 사용을 권장한다.** 현재 skill inventory에서 사용할 수 있는 경우에만 함께 선택한다.

| 출력 언어 | 권장 스킬 |
| --- | --- |
| 한국어 | `fluent-languages:fluent-korean` |
| English | `fluent-languages:fluent-english` |
| 日本語 | `fluent-languages:fluent-japanese` |

Fluent는 표현을 다듬고 `to-ticket`이 내용·권한·게시 책임을 유지한다. 미설치 언어 스킬을 전제하거나 작성 중 설치·연결을 시도하지 않는다. 사용할 수 없어도 티켓 작성은 계속한다. 의미, 사실, 확실성, 의무 수준, 수용 기준, 양식과 코드·명령·로그·identifier·ticket ID·URL을 보존한다. 문체 개선을 근거로 기존 결정을 바꾸지 않는다.

## 상황에 맞는 내용만 추가한다

| 확인된 상황 | 보존할 내용 |
| --- | --- |
| 범위 혼동 가능 | 포함 범위·비목표, 연결된 계약 |
| 외부 의존 | 정확한 대상·방향·진행을 막는 조건 |
| 운영·데이터·보안 위험 | 실제 영향 경계, 승인된 안전 조건·복구 제약 |
| 호환성 변경 | 확인된 소비자·계약, 필요한 전환 조건 |
| 완료 보고를 본문에 반영 | 변경 결과·검증 근거·미확인 범위, 기존 기록 |
| reopen·cancel·duplicate 맥락 기록 | 확인된 이유·남은 범위·canonical 대상; 실제 상태·관계는 lifecycle 책임 |

예를 들어 “CSV 다운로드에서 한글이 깨진다”는 보고만 있으면 발생 환경·관찰 증거·기대 결과와 미확인 조건을 담은 bug intake를 만든다. 원인을 encoding 문제로 확정하거나 특정 라이브러리 교체를 완료 조건으로 만들지 않는다. 이후 승인된 복구 조건과 검증 결과가 생기면 같은 티켓을 보강한다.

## 최종 점검

제목이 주된 문제·요청·결과를 드러내는지, 본문이 스스로 이해 가능한지 확인한다. 부모와 자식, 단계별 티켓 사이의 범위·판정 중복을 없앤다. 완료·기각·검토 결론은 기록할 내용이며 원격 status 변경 권한이 아니다. 작성한 payload와 실제 적용한 변경을 구분하고 `not_run`·`unknown`을 성공으로 표현하지 않는다.
