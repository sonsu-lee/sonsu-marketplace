# 티켓 품질 기준

플랫폼 중립적인 초안을 작성하거나 tracker payload를 준비할 때 읽는다.

## 중립적인 티켓 구조

```text
client_key: <게시 전까지 사용할 로컬 식별자>
제목: <관찰 가능한 결과>
문제와 기대 결과: <필요한 이유와 완료 후 변화>
근거: <PRD, ADR, architecture, plan, 대화 또는 기존 티켓의 위치>
범위: <포함하는 동작>
비목표: <명시적으로 제외하는 내용>
수용 기준: <관찰 가능한 완료 조건>
검증 방법: <테스트, 검토, 분석 또는 운영 확인>
blocked_by: <client_key 또는 원격 ID, 없으면 없음>
blocks: <client_key 또는 원격 ID, 없으면 없음>
병렬 가능 여부: <가능, 불가능 또는 조건>
미해결 질문: <질문 ID 또는 없음>
rollout·migration·운영: <필요한 내용 또는 없음>
tracker metadata: <근거가 있는 값 또는 없음>
```

필드명이 대상 tracker에 없으면 의미를 본문에 보존한다. 빈 선택 필드를 억지로 출력하지 않아도 되지만, 비목표와 선행 관계처럼 범위 판단에 필요한 정보는 생략하지 않는다.

## 티켓 단위 검사

- 하나의 관찰 가능한 결과로 설명할 수 있는가?
- 독립적으로 검토하고 완료 상태를 판정할 수 있는가?
- 근거 문서의 요구사항 또는 결정과 연결되는가?
- 구현 단계만 나열하지 않고 필요한 이유와 기대 결과를 설명하는가?
- 인접한 티켓과 범위가 중복되지 않는가?
- 새로운 제품 정책이나 기술 결정을 수용 기준 안에 숨기지 않았는가?

## 분해 검사

- 첫 티켓이 종단 불확실성을 줄이는 가장 얇은 경로인가?
- 조사·결정 티켓의 결과가 후속 구현과 선행 관계로 연결되는가?
- API, schema, migration, UI와 관찰 가능성이 서로 단절된 레이어 작업으로만 나뉘지 않았는가?
- 실패, 복구, migration과 rollout이 실제 범위에 필요하면 포함했는가?
- 독립적으로 승인, 배포 또는 되돌릴 목적을 하나의 티켓에 숨기지 않았는가?
- 전체 범위가 하나의 티켓 또는 비목표에 정확히 한 번 포함되는가?

## 게시 전 검사

- tracker와 대상 공간, 공개 범위와 접근 주체가 정확한가?
- 대상 공간의 issue template이나 team·project 관례를 확인했는가?
- 같은 목적의 기존 티켓을 제목, 설명과 범위로 검색했는가?
- 제목, 본문, 첨부, metadata와 관계를 포함한 실제 payload가 권한 범위 안에 있는가?
- 각 중립 필드가 실제 tracker field 또는 본문에 손실 없이 매핑되는가?
- 입력에 없는 담당자, 일정, 공수, 우선순위, 상태 또는 label을 만들지 않았는가?
- 비밀, token, 불필요한 개인정보와 제한된 보안 세부 정보를 제거했는가?

## 게시 후 검사

- 원격 ID와 URL을 얻고 실제 티켓을 다시 읽었는가?
- 제목, 본문, metadata와 관계가 의도한 payload와 일치하는가?
- 일부 실패나 불명확한 응답을 성공으로 간주하거나 중복 생성하지 않았는가?
