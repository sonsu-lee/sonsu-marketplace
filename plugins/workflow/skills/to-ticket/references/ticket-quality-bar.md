# 티켓 작성 기준

## 문제와 필요한 맥락을 간결하게 쓴다

제목은 주된 문제나 요청을 바로 드러낸다. 본문에는 담당자가 상황을 이해하는 데 필요한 배경과 정보를 담는다. 짧은 티켓에서 배경·목적·기대 결과를 나누어 같은 설명을 반복하지 않는다.

작성자는 확인된 문제, 요청과 이미 정해진 제약을 전달한다. 원인 분석, 해결 방법, 코드 구조, 작업 순서와 구체적인 테스트 설계는 작업자가 정한다. 합의된 설계·ADR, 보안·호환성, 전환 순서·복구 조건처럼 방법 자체가 제약인 내용은 보존한다.

관찰, 가설, 제안, 선호, 합의와 실행 결과를 구분한다. “Next.js를 선호한다”를 “Next.js를 반드시 사용한다”로 바꾸지 않는다. 완료조건이나 종료조건을 기본 항목으로 요구하거나 새로 만들지 않되, 이미 합의된 조건은 `고려 사항`에 담는다.

## 필요한 정보만 해당 위치에 담는다

| 정보 | 기본형에서의 위치 |
| --- | --- |
| 현재 상황, 요청 이유, 영향, 확인할 질문 | 문제 |
| 재현 순서, 발생 환경, 실제·기대 동작, 재현을 보여 주는 자료 | 재현 정보 |
| 기술적 제약, 합의된 범위·조건, 선호·아이디어, 외부 의존 | 고려 사항 |
| 관련 논의·문서·이슈, 추가 로그와 근거 | 관련 자료 |

선택한 양식의 항목·순서·필수 필드는 지킨다. 기본형의 빈 선택 항목과 작성 안내는 완성된 초안에서 제거한다. 확인되지 않은 필수 정보는 미확인 사실과 필요한 입력을 표시한다. 양식 출처와 원격 작업 상태 같은 관리 정보는 본문 밖에서 필요한 만큼 보고한다.

논의로 정해진 내용은 본문에 요약하고 근거를 연결한다. 기존 결정·기록·자료는 보존한다. 긴 구현 계획이나 회고 문서가 있으면 링크로 연결하고, 요청받지 않은 상세 계획을 새로 작성하지 않는다.

## 언어와 문장 구조를 맞춘다

티켓 언어는 사용자 지정, 대상 공간의 지침·양식·일관된 관례, 기존 티켓이나 승인 문서의 주 언어, 현재 대화 언어 순으로 정한다. 결과 보고는 사용자가 요청한 언어를 따른다. 고정된 양식 문구는 해당 양식이 허용할 때만 번역한다.

현재 사용할 수 있는 출력 언어의 Fluent Languages 스킬을 함께 적용한다. 한국어는 `fluent-languages:fluent-korean`, 영어는 `fluent-languages:fluent-english`, 일본어는 `fluent-languages:fluent-japanese`를 사용한다. 해당 스킬이 없어도 작성은 계속하며 자동 설치하지 않는다.

한 문단에는 관련된 내용을 모으고, 순서가 있는 절차는 번호 목록으로 쓴다. 주체·조건·이유가 드러나도록 문장을 나누되 같은 뜻을 반복하지 않는다. 코드, 식별자, 링크, 수치와 의무 수준은 문체를 다듬을 때도 보존한다.

## 결과를 정확히 기록한다

실제 결과가 생겼을 때만 본문에 보강한다. 접수·채택은 구현 완료가 아니며, 장애 복구는 재발 방지 완료가 아니다. 회고 작성과 후속 개선, 검증 수행과 기준 충족, 일부 대상의 전환과 전체 전환도 구분한다. 합의된 제공·복구·검증 조건을 충족했다는 근거 없이 완료로 표현하지 않는다.

본문의 결론은 원격 상태 변경 권한이 아니다. 실제 게시 결과와 준비한 초안을 구분하고, `not_run`·`unknown`을 성공으로 보고하지 않는다.
