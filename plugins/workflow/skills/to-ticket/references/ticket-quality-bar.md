# 티켓 품질 기준

플랫폼 중립적인 초안을 작성하거나 tracker payload를 준비할 때 읽는다.

## 티켓이 책임질 내용을 고정한다

티켓은 하나의 관찰 가능한 결과 또는 하나의 명확한 불확실성을 기록한다. 작성자는 `why`, `what`, `done`을 정하고 작업자는 범위 안의 `how`를 정한다.

- `why`: 현재 상태와 원하는 상태의 차이 또는 해소할 불확실성
- `what`: 필요한 결과, 범위와 이미 결정된 제약
- `done`: 관찰 가능한 수용 기준 또는 조사 종료 조건

작업 순서, 파일 목록, 함수 구조와 해결 방법은 기본 body가 아니다. 작성자는 결과의 완료 여부를 구분하는 최소 관찰 상태를 정한다. 승인된 요구사항이나 실제 위험이 결과 외에 증거·안전 조건을 요구할 때만 이를 포함한다. 작업자는 구체적인 테스트 설계·명령·도구를 정한다. 승인된 설계·ADR, 공개 계약, 보안·호환성, 안전한 migration·rollback이나 승인된 검증 절차처럼 접근 방법 자체가 제약일 때만 그 방법을 보존한다.

## 개념을 섞지 않는다

| 개념 | 역할 | 예 |
| --- | --- | --- |
| `kind` | 해결하는 차이나 불확실성 | `defect`, `delivery`, `investigation`, `maintenance` |
| hierarchy | 범위와 분해 수준 | project, epic, parent, sub-ticket |
| intake schema | 필요한 정보를 받는 양식 | bug form, request template |
| workflow metadata | 처리 순서와 운영 정보 | status, priority, assignee, cycle, sprint |
| relation | 의존·중복·연관 연결 | blocked by, blocks, duplicate, related |

tracker나 업무 도메인에 더 정확한 종류가 있으면 그 용어를 사용한다. 중립 `kind`는 body 구성을 고르는 내부 기준이며 존재하지 않는 tracker type이나 label을 만들 권한이 아니다.

여러 `kind`에 해당해 보이면 주된 완료 주장으로 하나를 고른다. 불확실성 해소 자체는 `investigation`, 깨진 기대 동작의 복구는 `defect`, 새롭거나 달라진 사용자·시스템 결과는 `delivery`, 외부 제품 동작을 새로 만들지 않고 보존 속성을 유지하는 내부 개선은 `maintenance`다.

## 출력 언어를 결정한다

title, body와 생성 보고의 언어는 다음 근거를 순서대로 따른다.

1. 사용자가 티켓 언어를 명시했으면 그 언어를 사용한다.
2. 대상 공간의 지침, 유효한 template 또는 일관된 최근 티켓 관례가 언어를 정하면 따른다.
3. 연결할 canonical ticket, 승인된 specification이나 제품 문서가 명확한 주 언어를 사용하면 그 언어를 따른다.
4. 근거가 없으면 사용자가 요청한 출력 언어를 사용하고, 그것도 없으면 현재 대화의 주 언어를 사용한다.

고정된 template heading, checklist와 안내 문구는 template이 허용하지 않는 한 번역하지 않는다. 대상 template이 없으면 아래 fallback heading을 결정된 언어의 자연스러운 표현으로 바꾼다. 채워 넣는 설명만 결정된 언어로 작성하고, 코드, 명령어, 로그, identifier, ticket ID와 URL은 번역하지 않는다.

결정된 언어에 해당하는 Fluent Languages 스킬이 현재 skill inventory에 있으면 `to-ticket`과 함께 선택하여 생성 문장에 적용한다.

- 한국어: `fluent-languages:fluent-korean`
- English: `fluent-languages:fluent-english`
- 日本語: `fluent-languages:fluent-japanese`

이 조합은 runtime에서 이루어지며 `to-ticket`이 티켓의 내용과 게시 책임을 계속 소유한다. Fluent Languages의 설치나 특정 스킬의 존재를 가정하지 않으며, 사용할 수 없다는 이유로 티켓 작성을 막거나 설치·연결을 시도하지 않는다.

## 기본 티켓 구조를 먼저 쓴다

```text
제목: <관찰 가능한 결과>

본문:
목적과 기대 결과:
<필요한 이유와 완료 후 변화. 짧은 문단 하나>

완료 조건:
- <완료 판정에 필요한 관찰 가능한 수용 기준 또는 종료 조건>
```

여러 티켓이나 관계를 검토·게시하기 위한 관리 정보가 필요하면 body와 분리해 필요한 값만 간단히 표시한다.

```text
client_key: <게시 전까지 사용할 로컬 식별자>
kind: <중립 kind 또는 확인된 tracker·domain type>
hierarchy: <확인된 parent·sub-ticket 정보만>
relations: <확인된 관계만>
tracker metadata: <근거가 있는 값만>
```

기본 티켓 구조와 관리 정보에 빈 항목이나 `없음`을 채우지 않는다. 관계가 없는 단일 초안에는 `client_key`와 별도 관리 정보 블록을 만들지 않는다. 대상 template이 특정 section을 요구하면 그 구조를 우선하고 같은 의미의 fallback heading을 덧붙이지 않는다.

## 종류에 맞는 내용만 추가한다

| `kind` | body에 추가할 내용 |
| --- | --- |
| `defect` | 실제 동작, 기대 동작, 재현 조건이나 직접 증거, 영향 범위 |
| `delivery` | 사용자·시스템 결과, 혼동 가능한 범위와 비목표, 이미 결정된 제약 |
| `investigation` | 답할 질문, 필요한 근거, 기대 산출물과 종료 조건, 후속 결정에 미치는 영향 |
| `maintenance` | 유지·변경 대상과 이유, 보존할 동작·호환성과 이를 입증해야 할 증거 |

다음 predicate가 참일 때만 조건부 section을 추가한다.

- 범위를 다르게 해석할 가능성이 있음 → `범위·비목표`
- 원문이나 결정의 추적이 필요함 → `근거`에 locator만 연결
- 승인된 요구사항이 특정 증거를 요구하거나 결과만으로 실제 보안·호환성·migration 조건을 판정할 수 없음 → `검증 근거`
- 실제 parent·sub-ticket 구조가 있음 → `hierarchy`
- 실제 의존·중복·연관 연결이 있음 → `관계`
- 배포·데이터·운영 위험이 있음 → `rollout·migration·운영`
- 작성자나 책임자의 결정 없이는 진행할 수 없음 → `미해결 질문`

구현자가 분석하거나 선택할 해결 방법은 `미해결 질문`으로 올리지 않는다.

## 짧고 실행 가능하게 쓴다

- 목적과 기대 결과는 짧은 문단 하나로 쓴다.
- 완료 조건은 완료 판정에 필요한 최소 항목만 쓴다. 한 항목으로 충분하면 더 추가하지 않는다.
- 각 완료 조건은 원하는 결과와 원하지 않는 결과를 실제로 구분해야 한다.
- 테스트·lint·typecheck·build·CI 통과, 테스트 코드 추가, 코드 리뷰, 문서 갱신과 구현 작업은 그 자체가 승인된 결과나 필수 증거일 때만 완료 조건으로 쓴다.
- 오류와 회귀 관련 조건은 `적절히 처리한다`, `regression이 없다` 같은 일반 문구 대신 합의된 외부 동작이나 보존할 상태를 직접 쓴다.
- 같은 내용을 제목, body, metadata와 여러 section에 반복하지 않는다.
- PRD, ADR, 대화, 로그와 구현 계획을 복사하지 않고 필요한 locator와 결론만 연결한다.
- 여러 독립 결과를 각각 판정해야 하면 티켓 분할을 먼저 검토한다.
- 하나의 원자적 결과에 필요한 증거·안전 조건은 분량을 줄이기 위해 삭제하지 않는다.

## 티켓 단위 검사

- 하나의 관찰 가능한 결과로 설명할 수 있는가?
- 독립적으로 검토하고 완료 상태를 판정할 수 있는가?
- 근거 문서의 요구사항 또는 결정과 연결되는가?
- 필요한 이유와 기대 결과를 설명하고 해결 방법은 작업자에게 남겼는가?
- 인접한 티켓과 범위가 중복되지 않는가?
- 새로운 제품 정책이나 기술 결정을 수용 기준 안에 숨기지 않았는가?

## 분해 검사

- 첫 티켓이 종단 불확실성을 줄이는 가장 얇은 경로인가?
- 조사·결정 티켓의 결과가 후속 구현과 선행 관계로 연결되는가?
- API, schema, migration, UI와 관찰 가능성이 서로 단절된 레이어 작업으로만 나뉘지 않았는가?
- 실패, 복구, migration과 rollout이 실제 범위에 필요하면 포함했는가?
- 독립적으로 승인, 배포 또는 되돌릴 목적을 하나의 티켓에 숨기지 않았는가?
- 전체 범위가 하나의 티켓 또는 비목표에 정확히 한 번 포함되는가?

## 게시 전 검사

- tracker와 대상 공간, 공개 범위와 접근 주체가 정확한가?
- 대상 공간의 issue template이나 team·project 관례를 확인했는가?
- 같은 목적의 기존 티켓을 제목, 설명과 범위로 검색했는가?
- 제목, 본문, 첨부, metadata와 관계를 포함한 실제 payload가 권한 범위 안에 있는가?
- 각 중립 필드가 실제 tracker field 또는 본문에 손실 없이 매핑되는가?
- 입력에 없는 담당자, 일정, 공수, 우선순위, 상태 또는 label을 만들지 않았는가?
- 비밀, token, 불필요한 개인정보와 제한된 보안 세부 정보를 제거했는가?

## 게시 후 검사

- 원격 ID와 URL을 얻고 실제 티켓을 다시 읽었는가?
- 제목, 본문, metadata와 관계가 의도한 payload와 일치하는가?
- 일부 실패나 불명확한 응답을 성공으로 간주하거나 중복 생성하지 않았는가?
