# 티켓 미디어 첨부

이미지나 동영상을 티켓에 넣을 때 적용한다. 양식에는 자료와 설명을 담고, 업로드 절차는 이 문서와 프로바이더별 규칙으로 처리한다.

## 자료와 삽입 위치를 준비한다

일반 작업의 자료는 `참고`, 버그의 재현 자료는 `재현 자료`, 조사 작업의 자료는 `관련 자료`에 둔다. 버그의 재현 외 참고 자료는 `관련 자료`에 둔다. 이미지에는 무엇을 보여 주는지와 해당 재현 단계를 설명하고, 영상에는 필요한 시점을 표시하며 같은 파일을 여러 항목에 중복으로 붙이지 않는다. 사용자·팀 양식이 있으면 지정된 첨부 위치를 따른다.

로컬 파일은 저장소 밖의 임시 폴더에 준비한다. 파일 경로, 실제 형식·크기, SHA-256, 설명, 삽입 순서와 대상 티켓을 기록한다. 공개 가능한 내용인지 확인하고 비밀·개인정보·제한된 자료를 제외한다. 원본을 변경할 때는 별도 사본을 만들고, 사용할 도구가 없다는 이유로 자동 설치하지 않는다.

`draft`는 자료와 삽입 위치만 준비한다. 첨부를 포함한 게시가 요청됐거나 기존 게시 권한에 포함될 때만 업로드한다. 자료를 확보하지 못한 상태와 준비한 자료의 업로드 실패를 구분한다. 미확보 상태로 접수할 수는 있지만, 첨부까지 요청받은 작업을 업로드 없이 완료했다고 보고하지 않는다.

## 현재 지원 경로로 게시한다

프로바이더 이름만으로 기능 지원 여부를 고정하지 않는다. 실행할 때 현재 도구 schema·CLI 도움말과 대상 권한·파일 제한을 확인한다.

- [GitHub](github.md#이미지와-동영상을-첨부한다): 지원되는 CLI attachment, 공식 브라우저 첨부 순서로 확인한다.
- [Linear](linear.md#이미지와-동영상을-첨부한다): 업로드 준비, 원본 파일 PUT, 첨부 연결과 본문 배치를 순서대로 처리한다.
- [Jira](jira.md#이미지와-동영상을-첨부한다): 현재 MCP의 업로드 도구를 확인하고, 없으면 허가된 공식 REST API나 브라우저 첨부를 사용한다.

기존 로그인과 인증 경로를 사용한다. connector 인증을 별도 API·CLI에서도 쓸 수 있다고 가정하거나 token을 추출하지 않는다. 브라우저 첨부를 자동 제어할 수 없으면 작성 화면과 파일을 준비하고 남은 수동 첨부를 알린다. 임의의 외부 저장소에 올리거나 첨부를 위해 파일을 저장소에 commit하지 않는다.

## 파일마다 결과를 확인한다

1. 정확한 티켓 ID와 최신 본문을 확인한다. 새 티켓이면 생성 결과를 재조회한 뒤 첨부한다.
2. 파일의 크기와 hash가 준비한 사본과 같은지 확인하고 한 파일을 업로드한다. 전송용 URL과 헤더는 해당 요청에만 사용하며 본문이나 보고서에 남기지 않는다.
3. 반환된 파일 URL·첨부 ID로 티켓에 연결한다. 본문에는 실제 파일 참조와 설명을 지정된 위치에 넣는다. 쓰기 전에 최신 원문을 확인하고 기존 기록·첨부를 보존한다.
4. 첨부 목록과 본문을 재조회한다. 이미지 열람·영상 재생과 순서·설명을 확인한다. 본문의 URL만 읽었으면 표시까지 검증했다고 보고하지 않는다.
5. 확인을 마친 뒤 다음 파일을 처리한다. 모든 요청 자료의 결과를 확인한 뒤 게시 결과를 보고한다.

업로드, 이슈 연결, 본문 배치와 열람·재생 결과를 구분해 기록한다. 파일은 올라갔지만 본문 반영이 실패했다면 확인된 URL을 보존하고 최신 본문에서 배치만 복구한다. 다시 업로드하지 않는다.

timeout이나 응답 유실이면 실제 반영부터 조회한다. 전송 여부를 모르면 `unknown`이며, 같은 업로드를 자동 반복하지 않는다. 전송되지 않았음이 확인되고 원인이 해결된 경우에만 재시도한다. 중간 실패로 기존 티켓·본문·첨부를 삭제하거나 이전 본문으로 되돌리지 않는다. 사용하지 못한 자료와 남은 작업을 정확히 보고한다.
