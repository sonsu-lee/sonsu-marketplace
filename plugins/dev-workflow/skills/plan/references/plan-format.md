# 구현 계획 형식

## 작성 순서와 보존할 계약

동작 의사코드 → 파일·작업·의존성 대응 관계 → 검증 방법과 이유 순서로 작성한다. 구현 접근과 파일별 세부사항은 의사코드 뒤에서 도출한다.

- `Requirements source`, `Documentation impact`, `Commit authorization`, `Quality policy`는 대화 계획에도 유지한다. 본문에 접근이 있고 전역 제약이 없는 짧은 계획은 `접근 방식`과 `전역 제약`을 생략할 수 있다.
- 요구 출처는 원래 구현 요청·이전 사용자 승인·승인된 문서·이슈·티켓이다. 영속 요구사항 문서가 없으면 원래 대화를 읽을 수 없는 실행자도 이해할 승인 맥락을 담는다.
- 버전 있는 출처에는 실제 사용한 리비전 또는 고정 snapshot·범위와 그 범위의 승인 근거를 연결한다. 기존 고정 입력이나 승인 기록에 연결이 있으면 그 위치를 참조한다. 버전 없는 대화·이슈에는 리비전이나 승인 metadata를 만들지 않는다. 실행·재개 시 현재 출처와 대조하고 변경되었거나 승인이 불명확한 범위에 의존하는 작업만 보류한다. 원래 요청·이전 승인과 독립적인 승인 작업은 유지한다.
- 문서 영향은 `없음 / 기존 문서 갱신 / 승인된 영속 문서 생성 / 기존 결정 대체`로 기록한다. 앞선 단계의 목적·경로·갱신 범위를 이어받고 달라진 부분만 확인한다. 계획 자체는 영속 설계 문서가 아니다. 문서 작업에도 같은 결정을 전달하며 작업이 생겼다는 이유만으로 README 갱신을 추가하지 않는다.
- `Quality policy`는 계획서 형식 검사가 아니라 구현 완료 게이트다. 관찰 가능한 동작·공개 계약 변경은 `independent`, 확인된 고위험 경계는 `red-team`, 동작과 공개 계약이 그대로인 기계적 변경은 `checks`를 선택한다. 계획이 있다는 이유만으로 red-team을 추가하지 않는다.
- 선택·판단의 근거에는 [공유 출처 태그](../../../references/provenance.md)를 사용한다.

## 흐름과 추적성

안정적인 `F1`, `F2` ID를 부여한다. 필요한 입력·관찰 결과·처리 순서·상태 변화·분기·반복·오류·경계·책임·가정을 언어 중립적으로 표현한다. 없는 상태나 반복은 추가하지 않는다. 구현 방향을 바꾸는 미확인 가정은 결정 항목으로 남긴다.

```text
FLOW F1: [관찰 가능한 결과]
  INPUT: [호출자나 사용자 입력]
  READ: [기존 코드 또는 상태]
  IF [조건]:
      CHANGE [데이터 또는 상태]
  ELSE:
      RETURN [경계 또는 오류 결과]
  OUTPUT: [호출자 또는 다음 흐름에 전달할 결과]
  BOUNDARY: [기존 책임] / [새 책임]
  ASSUMPTION OR DECISION: [확인할 내용]
```

대응표에는 다음 계약을 보존한다. 내용의 적합성·승인·완전성은 검토자가 판단하며 구조 검사기는 대신하지 않는다.

| 입력의 계약 | 계획에 남길 내용 |
| --- | --- |
| 요구사항·품질 ID | PRD 여부와 관계없이 기존 REQ/NFR ID와 출처·근거 있는 조건을 흐름·검증에 연결한다. 없는 ID를 만들지 않는다. ID가 없으면 실제 이슈·티켓·사용자 요청을 쓰고, 별도 출처가 없으면 셀을 `-`로 두어 `Requirements source`를 따른다. |
| 수용 기준 | 각 요구사항의 관련 기준을 흐름·검증에 연결하고 동작 검증의 `expected_source`에서 식별한다. 정상·실패·재방문 등 합의된 조건을 대조한다. 한 흐름에 여러 기준을 연결할 수 있으며 새 기준이나 기준별 독립 작업·테스트를 형식적으로 만들지 않는다. 티켓 없는 PRD-lite 인계에도 적용한다. |
| 우선순위·범위 | 합의된 P1/P2 등 우선순위를 요구사항 셀 또는 `Requirements source`에 보존한다. 합의된 구현 범위·출시 순서는 관련 흐름·작업에 연결한다. 우선순위 라벨만으로 P2를 제외하거나 출시 순서·구현 승인을 새로 확정하지 않는다. |
| 비목표·제외 범위 | 전역 제약 또는 영향을 받는 흐름·작업 경계에 보존한다. 제외한 작업을 구현 범위로 넣거나 무관한 작업마다 반복하지 않는다. |
| 성공 신호 | 관련 SUCCESS ID·신호·합의된 측정 방법·기준·근거를 보존하고 이미 승인된 계측·측정 작업만 흐름·검증에 연결한다. 성공 목표를 기능 수용 기준·코드 완료 조건으로 바꾸지 않는다. 측정 방법만으로 구현을 승인하거나 인터뷰·출시 후 분석을 구현 작업으로 만들지 않는다. 없는 ID·목표값과 무관한 흐름의 지표를 추가하지 않는다. |
| 위험·미결정 | 관련 RISK ID·영향·합의된 완화 조건 또는 남은 확인 작업을 흐름의 경계·작업·검증에 연결한다. 미정 우선순위 등 OPEN ID·영향·확인 작업을 보존하고 근거 없는 완화책·우선순위·품질 목표 수치를 확정하지 않는다. |

각 작업은 독립적으로 승인·거부할 산출물 경계로 나눈다. 정확한 생성·수정 파일과 책임, 인터페이스·의존성을 정하고 기존 패턴을 따른다. 설정·문서·마이그레이션은 이를 필요로 하는 산출물에 포함한다. 여러 하위 시스템을 독립적으로 구현·검증할 수 없다면 실행 가능한 경계로 다시 나눈다. 한 흐름이 여러 작업에 걸치거나 여러 흐름이 한 작업에 모이면 책임 경계와 순서를 적는다.

독립 완료·검증 가능성, 선행 관계, 공유 쓰기·격리 비용을 확인한다. 이득이 있는 독립 작업은 [병렬 위임 경계](../../../references/delegation.md)에 따라 같은 실행 묶음의 작업자로 배정하고 나머지는 root 순차 작업으로 둔다. 역할·실행 묶음·쓰기 범위를 기록하고, 나눌 수 있어 보이지만 직접 처리할 작업에는 구체적인 의존성·조정 비용을 적는다. 작업자 수는 파일 수나 고정 비율로 정하지 않는다.

## 검증 선택

입력·출력·상태·오류 결과를 바꾸거나 자동 검사(정적 검사 포함)를 추가·확장하는 흐름은 구현·검사 작성 전에 동작 기록을 만들고 `verification_mode`를 고른다. 필드·결측 처리·`contract_unresolved`·모드 선택 순서·정적 변경 기본 검증은 [검증 방식 선택](../../test-driven-development/verification-selection.md)이 정본이다. 계획에는 그 결과를 다음처럼 연결한다.

| 변경 | 계획에 남길 검증과 이유 |
| --- | --- |
| 기능·로직·상태·오류 처리 | 동작 기록과 `verification_mode`. `extend_existing_test`·`new_test_file`이면 RED·GREEN 명령을 작업 단계에 넣는다. |
| 버그 | 원래 결함의 입력·결과를 동작 기록에 넣는다. `one_time_reproduction`이면 전후 명령·결과와 자동 검사 공백을 남긴다. |
| 동작에 민감한 리팩터링 | 바뀌면 안 되는 `observed_result`와 이를 거부할 `fault_example`. 순수 기계적 변경은 필요한 결정론적 검사를 쓴다. |
| 자동 검사만 추가·확장 | 프로덕션 변경이 없어도 검사할 결과의 기록과 `verification_mode`. |
| 문서·스킬 | 기존 링크·경로·예시·문서 일관성 검사와 스킬 앞부분 메타데이터 검사. 경로 선택·권한·작업 절차 위험이 있으면 현실적인 동작 평가를 추가한다. |
| 매니페스트·메타데이터 | 기존 구문·참조 경로 검사와 사용 가능한 플랫폼 기본 로더. |

대응표의 검증란과 작업의 `Verification`·`Verification reason`에는 동작 필드, 선택한 `verification_mode`, 판정에 쓴 기존 검사·복구·보조 장치·재발 근거의 실제 값을 적는다. `existing_check`는 기존 검사를, `one_time_reproduction`은 재현 명령을 작업에 명시한다. 기존 정적 검사만 실행하는 변경은 검사 명령과 기대 결과를 적는다. `contract_unresolved` 흐름에 의존하는 자동 검사 파일 작성은 예정하지 않는다. 정적 문구나 구현을 그대로 반복하는 테스트는 추가하지 않는다.

## 계획과 Task 양식

대괄호는 실제 값으로 채운다. 파일 계획은 checkbox로 실행 상태를 추적하고 `task-brief`가 소비하는 `Task N` heading을 유지한다.

````markdown
# [기능 이름] 구현 계획

**Goal:** [한 문장 목표]
**Requirements source:** [원래 요청·이전 승인·승인 문서; 기존 ID; 버전 있는 출처의 사용 리비전 또는 고정 snapshot·범위·승인 근거; 구현 전 확인 조건]
**Documentation impact:** [없음·갱신 경로·승인된 생성 경로·대체할 결정]
**Commit authorization:** [granted for this plan | not granted]
**Quality policy:** checks | independent | red-team (현재 위험과 근거)

## 전역 제약
[모든 작업이 보존할 정확한 제약]

## 동작 흐름 의사코드
FLOW F1: [구현 세부사항보다 먼저 정의한 동작·제어 흐름]
  INPUT: [입력]
  OUTPUT: [관찰 결과]

## 접근 방식
[흐름에서 도출한 접근]

## 흐름 대응 관계
| 흐름 | 요구사항 | 입력과 결과 | 파일과 책임 | 작업과 의존 관계 | 검증과 이유 |
| --- | --- | --- | --- | --- | --- |
| F1 | [기존 ID 또는 실제 요구 출처] | [입력 → 결과] | [파일·책임] | Task 1; [선행 흐름/작업 또는 없음] | [검증·이유·동작 필드] |

### Task 1: [산출물]

**Flows:** `F1`
**Files:**
- Create: `exact/path/new.py`
- Modify: `exact/path/existing.py:123`
- Verify: `tests/exact/path/test.py`

**Interfaces:**
- Consumes: [정확한 선행 입력·인터페이스]
- Produces: [후속 작업이 의존하는 인터페이스]

**Execution:** [root 순차 실행 또는 worker 역할·병렬 묶음·쓰기 범위·worktree]
**Verification:** [verification_mode 또는 정적 검사 명령]
**Verification reason:** [검사 단언·실패 근거 또는 복구·보조 장치·재발 근거의 실제 값]

- [ ] **단계 1: 기대 동작·불변식 확인**
[실제 테스트·명령·불변식. TDD이면 실패 테스트와 예상 실패.]
- [ ] **단계 2: 최소 변경**
[정확한 수정 내용이나 코드]
- [ ] **단계 3: 결과 검증**
Run: `[정확한 명령]`
Expected: `[관찰 가능한 결과]`
- [ ] **단계 4: 차이와 문서 정합성 리뷰**
[대조할 경로와 요구사항]
````

## 구조 검사기가 받는 형식

plan 스킬 디렉터리에서 실행하는 `../../scripts/validate_plan.py <계획 절대 경로> --root <저장소 절대 경로>`는 위 Markdown 형식을 읽기만 한다. 계획을 재작성하거나 파일을 쓰거나 계획 안의 명령을 실행하지 않는다.

- 흐름 정의: 한 줄 `FLOW F<양의 정수>: 설명`. 본문 또는 언어가 없거나 `text`인 fenced block에 쓴다. ID는 선행 0 없이 사용한다. 일반 코드 fence 안의 구현 예시는 검사하지 않는다.
- 작업 정의: fence 밖 Markdown heading `### Task <양의 정수>: 산출물`(heading 깊이 1–6 허용). 각 작업은 정확히 하나의 비어 있지 않은 `**Flows:**` 필드에 쉼표·세미콜론·공백으로 나눈 흐름 ID를 쓴다. inline backtick도 허용한다.
- 대응표: 위 여섯 한국어 열 이름과 순서를 사용한다. 모든 셀을 채우고 별도 요구 출처가 없으면 `-`를 쓴다. 첫 셀에는 흐름 ID만, 다섯째 셀의 첫 세미콜론 앞에는 담당 `Task N`을 쓴다. 세미콜론 뒤에는 선행 `F1`·`Task 1` 등 의존 관계를 쓴다. 여러 담당 작업은 쉼표로 구분한다. 셀 안의 `|`는 지원하지 않으므로 풀어 쓴다.
- 모든 흐름·작업을 대응표에 연결하고 표의 각 흐름/담당 작업 쌍을 해당 작업의 `Flows`에도 선언한다. 같은 쌍은 한 번만 쓴다. 같은 흐름이 서로 다른 작업에 연결되는 것은 허용한다. ID 숫자가 연속일 필요는 없다.
- fence 밖 본문·inline code와 흐름 의사코드의 `F숫자`, fence 밖 `Task 숫자`는 ID 참조로 해석한다. 따라서 정의되지 않은 선행 흐름·작업도 오류다. `.`, `/`, `\`가 포함된 backtick 경로는 본문 ID 검색에서 제외한다. `REQ-F1`처럼 영문자·숫자·하이픈에 붙은 문자열은 흐름 ID가 아니다. 이 검사는 의존성 그래프의 실행 가능성·순환이나 요구사항의 의미적 누락을 판정하지 않는다.
- 각 작업의 `**Files:**` 아래에는 ``- Create: `path` ``, ``- Modify: `path:123` ``, ``- Verify: `path` `` 중 하나를 한 줄에 하나씩 쓴다. 경로 뒤 `:시작줄` 또는 `:시작줄-끝줄`은 존재 검사에서 제거한다. 다른 설명·검증 명령은 다음 `**Interfaces:**`·`**Verification:**` 등의 필드에 쓴다. `Flows`·`Files`는 Task heading 아래에만 쓴다. Task heading과 같거나 더 높은 수준의 다른 heading이 나오면 그 작업 범위가 끝난다.
- 경로는 `--root` 기준 상대 파일 경로다. 절대 경로·`..`·root 밖을 가리키는 symlink·디렉터리를 파일로 선언하면 오류다. 공백이 있는 파일명은 허용한다. glob·URL·디렉터리를 파일 대신 쓰지 않는다.
- `Create`는 없어도 된다. 재개 시 이미 생성된 파일도 허용하며 `exists`로 현재 상태를 보여 준다. 존재 여부만으로 새 파일 생성 권한·실행 상태를 판정하지 않는다. 없는 `Modify`·`Verify` 대상은 계획 어디엔가 같은 파일의 `Create` 선언이 있어야 한다. 앞 작업이 만든 파일을 뒤 작업이 고칠 때는 뒤 작업에 `Modify`를 쓴다. 작업 안의 동일 action/path 중복은 오류다. 공유 쓰기의 안전성은 별도 리뷰한다.
- 빈 계획, 중복 정의·참조·대응 쌍, 미정의 참조, 누락된 대응·Flows·Files, 비어 있거나 잘못된 대응표 셀, 잘못된 경로·선언, 닫히지 않은 fence를 오류로 보고한다. 승인 metadata·품질 정책·검증 검출력은 사람이 대조한다.

출력의 `status`는 `valid`, `invalid`, `input_error`다. `flows`·`tasks`는 정의된 ID, `mappings`는 흐름/담당 작업/줄, `files`는 작업·action·경로·줄·`exists`·`planned_new`, `errors`는 `code`·`line`·`message`다. 입력 전체에 관한 오류의 줄 번호는 0이다. 정상·구조 오류 출력에는 `plan`·`root`도 들어 있다. 종료 0은 구조 통과, 1은 계획 오류, 2는 읽기·경로·UTF-8 등 입력 오류다. argparse 사용법 오류는 stderr와 종료 2로 반환한다. 구조 통과는 승인·준비 상태 게이트 통과나 구현 완료 근거가 아니다.
