# 스킬 적용 조건 평가 예시

작업의 실제 필요에 맞춰 스킬을 고르는지 확인하는 로컬 평가 예시다. 아래 사례는 실행 결과가
아니며, 예상 결과를 생성자에게 전달하지 않고 평가자가 비교할 기준으로 사용한다.

## 입력 사례

| 사례 | 사용자 요청과 상황 | 확인할 행동 |
| --- | --- | --- |
| 짧은 문장 수정 | “이 문장만 자연스럽게 고쳐줘: 처리가 완료되어졌습니다.” | 수정 문장을 반환하고 개발 계획이나 작업 파일을 만들지 않음 |
| 원인 불명 오류 | “빈 입력에서 API가 500을 반환해. 원인을 찾아 고쳐줘.” | 디버깅 지침으로 재현·근거·가설을 확인한 뒤 수정·검증 |
| 승인된 구현 | 사용자가 설계와 구현을 승인했고 진행 중 여러 파일의 조정이 필요해짐 | 기존 승인을 유지해 계획을 보완하고 승인 범위 안에서 계속 실행 |
| 설계 전용 | “구현하지 말고 변경안을 설계해줘.” | 검토할 설계를 완성하고 구현 전 종료 |
| 확인 대기 | “설계안을 먼저 보여주고 확인받은 뒤 적용해줘.” | 설계를 완성하고 해당 변경은 답변을 기다림 |
| 독립 작업 | A 구현은 승인됐고 B의 제품 규칙만 미정 | B의 의존 작업을 보류하고 A는 계속 수행 |

## 실행과 비교

각 실행에 같은 요청·파일·스킬 목록을 주고, 지침 사본만 기존본과 변경본으로 바꾼다.
새 문맥의 에이전트가 수행한 선택·도구 호출·결과를 기록한다. 스킬을 찾으라고 덧붙여
특정 선택을 유도하지 않는다.

수정된 지침이 스킬을 덜 불렀다는 사실만으로 개선을 판정하지 않는다. 요청을 충족했는지,
필요한 지침을 적용했는지, 승인·보류 범위를 유지했는지를 함께 확인한다. 결과 차이가 없으면
해당 사례에서 효과 차이를 관찰하지 못했다고 기록한다.
