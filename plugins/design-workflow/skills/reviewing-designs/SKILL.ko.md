# 디자인 리뷰하기

> 영문 정본: [SKILL.md](SKILL.md) (`10e9691` 기준 번역).
> 사람이 읽기 위한 번역본이며 에이전트는 이 파일을 읽지 않는다.

기존 디자인을 수정하지 않고 검토한다. 요청받은 작업과 사용 가능한 증거를
바탕으로 발견을 서술한다.

## 워크플로

1. **범위와 증거 파악.** 요청받은 산출물과 작업만 검토한다. 사용자 목표, 요구
   사항, 실제 콘텐츠, 상태와 보는 맥락을 파악한다. 허용되고 가능하다면 추가
   상태나 렌더링된 뷰를 점검하고, 그렇지 않으면 관찰할 수 없는 것을 밝힌다.
   읽기 전용 리뷰에서는 파일 수정, 디자인 산출물 생성, 프로젝트 변경 명령이나
   결과 게시를 하지 않는다.
2. **증거 평가.** 중요한 문제를 관찰된 요소와 작업에 미치는 영향에 연결한다.
   입증된 결함과 가설이나 취향을 구분하고 부족한 증거를 설명한다. 계층, 그룹화,
   레이블, 상호작용과 복구 상태, 반응형 콘텐츠 보존, 관련 접근성 요건을 살핀다.
   임의의 글꼴이나 간격 수치를 강요하거나 겉모습만으로 적합성을 단정하지 않는다.
3. **보고.** 실행 가능한 발견을 영향 순으로 정렬하고 적절한 개선안과 범위, 한계를
   보고한다. 뒷받침되는 문제가 없다면 그렇게 말한다.

## 주의할 점

- 스크린샷이나 텍스트 스냅샷은 제공된 상태만 보여 줄 뿐 동작, 키보드 접근,
  반응형 전환, 준수 여부나 사용자 결과를 증명하지 않는다.
- 부정적인 발견은 증거 범위 안에서 서술한다. 안내가 보이지 않는 것은 관찰이지만
  복구 수단이 없거나 작업을 완료할 수 없다는 결론에는 추가 흐름 증거가 필요하다.
  한 상태만 보고 막힘이 영구적이라고 단정하지 않는다. 영향은 조건부로 서술한다.
  마지막 단서로 앞선 무조건적인 판정을 바로잡을 수 없다.

특정 시각 또는 흐름 판단, 상충하는 레퍼런스, 핸드오프 질문에 연구 맥락이 필요하면 [비평 증거](references/evidence.md)를
읽는다. 디자인이 이름, 개수, 날짜, 목록처럼 사용자나 시스템이 제공하는 값을 렌더링한다면
[최악의 데이터](references/worst-case-data.md)를 읽는다. 출처에서 얻은 이 제안은 검토 대상 제품에 대한 독립적인 검증도,
해당 표준과 테스트의 대체물도 아니다.

## 선택 사항: omp 엄격 실행

이 스킬은 Codex와 Claude Code에서는 가이드일 뿐이며, 거기서 omp의 런타임 제어를 제공하지 않는다. omp에서는 운영자가
`/design-start <plan-json-path>`를 시작하고 표시된 리뷰 계획을 확인하기 전까지 엄격 모드가 휴면 상태로 유지된다.
계획에는 모드 `review`(캡처 없는 비평은 `advisory`), 정확한 파일, 원래 요청, 확인된 프로젝트 사실, 캡처
대상/뷰포트/시나리오가 들어간다. 리뷰의 캡처 단계는 단언(assert)만 할 수 있고 상호작용은 할 수 없으며, 명령 점검은 허용되지 않는다.
직접 실행을 시작하거나 승인하지 않는다.

실행 중에는 범위 안에서 `design_status`, `design_read`, `design_capture`를
사용한다. 증거가 준비되면 멈추고, 운영자에게 `/design-report`를 실행한 다음
`/design-accept`로 리뷰를 그대로 게시해 달라고 요청한다. `/design-report`는
대화 밖에서 최종 리뷰를 작성하고 사실을 검증한다. 캡처는 특정 뷰에 대한
증거이지 품질이나 준수 여부에 대한 자동 판정이 아니다. 증거를
얻을 수 없거나 리뷰를 진행할 수 없다면 한계를 설명하고, 운영자에게 `/design-stop`, `/design-blocked reason`,
`/design-limited reason` 중 하나로 성공이 아닌 종료를 해 달라고 요청한다. 증거를 만들어 내거나 운영자 대신 수락하지
않는다. 이 확장은 프로세스 내에서 실행되며 OS 샌드박스가 아니다. 공식 결과는 게시된 보고서이며 어시스턴트의 서술이 아니다.
