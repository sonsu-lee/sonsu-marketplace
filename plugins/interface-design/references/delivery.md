# 선택과 산출물

자연어 요청에서 description에 맞으면 자동 선택하고, 사용자가 이름으로 지정하면 해당 선택을
우선한다. 대상·범위가 다르면 차이를 설명하고 필요한 정보만 확인한다. 별도의 router나
사용자의 정확한 호출 문법을 선행 조건으로 요구하지 않는다.

## 전문 지침과 조합

작업 담당 하나가 명세·범위·결과를 소유한다. 운영형 반복 업무·대량 처리·권한·부분 실패가
핵심이고 전문 스킬이 있으면 Operations UI가 업무 판단을 맡는다. Figma 파일의 컴포넌트·변수·
레이아웃·프로토타입 자체를 편집하는 요청은 Figma Workflow가 중심이다. 일반 디자인 요청에
Figma 결과물이 포함되면 일반 디자인 명세와 Figma 제작 지침을 조합한다.

다른 플러그인이 없어도 이 플러그인의 과업·디자인·검증 절차로 완료한다. 운영 화면에서는
비교 기준, 선택 범위, 권한별 행동, 대량 처리와 부분 실패·복구를 확인한다. B2B라는 이름만으로
고밀도 테이블을 강제하지 않는다. 전문 본문을 복제하거나 설치 경로를 직접 참조하지 않는다.
설치된 스킬을 조합하더라도 같은 명세를 다시 조사하거나 서로를 재귀 호출하지 않는다.

## 요청한 결과까지 수행

작업 계약의 `artifact_scope`는 `proposal`, `figma`, `implementation`, `live` 중 하나다. 각각
DQ0–DQ6, DQ0–DQ7, DQ0–DQ7, DQ0–DQ8을 요구한다. 앞 단계 통과는 뒤 단계 통과가 아니며 live
전에는 `end_to_end_status: passed`를 주장하지 않는다.

| 산출물 | 제작·완료 기준 |
| --- | --- |
| 제안 | 명세와 실제 시각적 제안을 제공하고 DQ0–DQ6을 평가한다. 기존 화면, 보존·변경 사항, 상태·흐름, 반응형과 인계 조건을 필요한 만큼 연결한다. |
| Figma | native frame, Auto Layout, component, variable과 요청된 prototype을 제작하고 DQ7 구조·화면·resize·reaction·playback 근거를 확인한다. |
| 기존 프로젝트 구현 | 기존 stack·component·token으로 화면·상태·동작을 구현하고 DQ7의 실제 렌더링·대표 조작 근거를 확인한다. |
| Live 평가 | 사전 등록 metric과 위험도에 맞는 대표 사용자·production·domain safety 근거로 DQ8을 평가한다. |

산출물이 불명확하면 현재 프로젝트·대화에서 먼저 해소하고 선택에 따라 작업이 크게 달라질 때만
질문한다. 코드 구현 요청을 제안만으로 끝내거나, 제안 요청을 제품 코드 수정으로 확대하지 않는다.
새 앱 기반 생성·패키지 설치·배포는 디자인 스킬의 자동 선택으로 허가되지 않는다.

Figma가 정본이면 컴포넌트·변수·상태·상호작용을 Figma에 유지하고 텍스트는 결정·제약을 보충한다.
Figma 제작에는 현재 도구가 요구하는 선행 스킬과 단일 writer·readback 계약을 따른다. 도구가
없으면 필요한 산출물을 `blocked`/`not_run`으로 표시하고 준비 가능한 명세를 제공한다.
텍스트나 생성 이미지로 Figma 완료를 대신하지 않는다.

이미지 생성은 시각적 제안이나 자산 제작이 필요한 경우의 한 방법이다. 도구에 전체 스킬·수정
이력을 보내지 않고 과업 → 구성·콘텐츠 → 자산 표현 → 시각 체계 → 보존 조건·출력 형식으로
정리한 명세를 전달한다. 이미지 생성 한 번을 반복 가능한 레이아웃 구현으로 취급하지 않는다.

자동 선택·이름 지정 자체는 쓰기 권한이 아니다. 실제 요청과 이미 확인한 승인을 이어받고
호스트의 Plan Mode·파일·외부 쓰기 제한을 따른다. 특정 모드 전환이나 별도 메시지로 재호출을
이 스킬의 추가 필수 절차로 만들지 않는다. 제한된 상태에서는 허용된 명세·제안과 미실행을 구분한다.
