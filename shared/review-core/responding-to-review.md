# 리뷰 지적 대응

작성자가 받은 리뷰 지적을 판정하고 수정·답글로 대응하는 기준이다. 리뷰어 쪽 기준은 공통 리뷰 기준이 맡는다.

## 지적을 판정한다

- 리뷰 의견은 검증할 주장이다. 현재 코드·요구사항·사용 버전의 기본 동작과 대조한다.
- 판정은 수정 필요 / 근거로 기각 / 추가 확인 필요 / 비차단 보고 중 하나다.
- 질문형인지, `suggestion`인지가 아니라 근거로 판정한다. outdated·중복 지적도 현재 코드로 확인하고, 같은 원인은 묶는다.
- 최소 수정 후 영향받은 동작을 검증한다. 추가 설정·timeout·추상화는 기존 처리로 부족할 때만 넣는다.

## 이해하지 못했다는 지적

코드를 먼저 명확하게 고친다. 그래도 안 되면 코드 주석을 단다. 리뷰 답글로 설명하는 것은 마지막 수단이다.

## 동의하지 않을 때

- 먼저 리뷰어가 옳은지 검토한다.
- 반론은 이 순서로 쓴다: X를 고른 이유와 트레이드오프 → Y가 더 나쁘다고 보는 이유 → 원래 트레이드오프를 다르게 봐야 한다는 뜻인지 묻는 질문.
- 거절만 하는 답글은 쓰지 않는다.

## 미루는 정리

이번 변경이 만든 복잡도는 지금 정리한다. 주변 문제는 이슈로 등록하고 링크한다.

## 어조와 문체

- 지적을 개인 공격으로 받아들이지 않고, 화난 채 답하지 않는다. 날 선 코멘트도 "리뷰어가 전하려는 건설적인 내용"으로 읽고 그 내용에 답한다.
- 간결하고 중립적으로 쓰고, 사람이 아니라 코드에 대해 쓴다.
- 리뷰어의 코멘트가 건설적이지 않다고 판단되면, 리뷰 대화에서 다투지 않고 사용자에게 알린다.
- 감사 표현은 기본으로 넣지 않는다. 리뷰어가 실제 결함을 찾아 줬을 때만 한 문장으로 짧게 쓴다.
- 한국어는 합니다체로 쓴다. 영어는 평이한 문장으로 쓰고, 느낌표와 이모지는 쓰지 않는다. 이 규칙은 리뷰어 쪽 공통 리뷰 기준과 같다.

## 수정 후

- 차단 지적의 원래 리비전과 근거를 보존하고, 현재 리비전의 검증 결과를 연결한다.
- PR이면 제목·본문이 최종 diff와 맞는지 PR 작성 기준으로 확인한다.
- GitHub 답글은 사용자가 전송을 승인했을 때만 해당 인라인 대화에 남긴다.

## 답글 형식

판정마다 다음 형식으로 짧게 쓴다.

- 수정함: "수정했습니다. <무엇을 어떻게 바꿨는지 한 문장> (<짧은 커밋 SHA>)"

  ```text
  수정했습니다. `??`로 바꿔 0을 그대로 쓰도록 했고 `timeout(0)` 테스트를 추가했습니다. (a1b2c3d)
  ```

- 근거로 기각: 근거 위치와 바꾸지 않은 이유를 쓰고, 다른 경로를 뜻했는지 묻는다.

  ```text
  `src/gateway.ts:12`에서 입력을 먼저 검증하므로 handler에는 빈 ID가 도달하지 않습니다. 그래서 여기에는 검사를 추가하지 않았습니다. gateway를 거치지 않는 호출 경로를 염두에 두셨다면 알려 주세요.
  ```

- 추가 확인 필요: 판단에 필요한 결정과 선택지를 쓴다.

  ```text
  만료된 세션을 401로 돌려줄지 로그인 화면으로 보낼지 정해야 판단할 수 있습니다. 어느 쪽인지 알려 주시면 반영하겠습니다.
  ```

- 범위 밖: "이번 변경 범위 밖이라 #<번호>로 등록했습니다."
- 반론: "동의하지 않을 때"의 순서로 쓴다.

  ```text
  여기서 `Map` 대신 배열을 유지한 이유는 항목이 최대 5개이고 입력 순서대로 출력해야 하기 때문입니다. `Map`으로 바꾸면 조회는 빨라지지만 이 크기에서는 차이가 없고, 순서를 보장하는 코드가 추가로 필요합니다. 원래 트레이드오프(가독성 우선)를 다르게 봐야 한다는 뜻인지, 항목 수가 늘어날 계획이 있는지 알려 주실 수 있을까요?
  ```
