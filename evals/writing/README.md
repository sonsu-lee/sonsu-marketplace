# Writing·개발자 블로그·Fluent·Git·Tickets 분리와 조합 검증

Writing의 정보 선별·문서 배치·공통 구성과 개발자 블로그의 흐름·근거 구성, 외부 원본으로
교체한 Fluent의 적용 범위, Git·Tickets의 티켓·PR 양식·운영을 각각 단독으로 사용하거나 함께 적용할
때의 범위를 검증한다. 원어민 선호나 일반적인 품질 개선을 입증하는 실험은 아니다. 과거 Fluent의
고정 protocol·snapshot·결과도 새 조합의 근거로 재표기하지 않는다.

## 결정론적 검사

```sh
python3 "${CODEX_HOME:-$HOME/.codex}/skills/.system/skill-creator/scripts/quick_validate.py" plugins/writing/skills/write-developer-blog
find .agents plugins evals -name '*.json' -print0 | xargs -0 -n1 python3 -m json.tool >/dev/null
python3 scripts/render-agent-policy.py --check
python3 scripts/render-continuity.py --check
python3 evals/language-style/eval.py validate
python3 -B -m unittest -v evals/task-continuity/test_runtime.py evals/plugin-compat/test_compat.py evals/language-style/test_eval.py evals/fluent-japanese/test_eval.py
python3 -B -m unittest discover -s evals/plugin-compat -p 'test_*.py' -v
git diff --check
```

JSON·frontmatter와 세 패키지의 스킬/참조 상대 경로를 확인한다. Fluent는 언어별 독립 정본을 대조한다. 이전 Fluent 사용자 지침의 평가 자료는 역사적 snapshot이며, 새 배포 스킬의 품질 결과로 사용하지 않는다.
원어 용례·보호 문자열과 법적 고지는 기존 main의 바이트를 기준으로 보존 여부를 확인한다. Tickets의 티켓 기본형 4종(작업·요청·버그·조사) 본문은 Tickets에서만 수정하며 Writing 변경으로 바뀌지 않아야 한다.
PR 기본 양식과 `unverified` 시 기본형을 확정하지 않는 정책, marker·연결 문법은 별도로 검토한다.
continuity 검사는 Writing 기록이 이전 Fluent 기록을 자동 복구하지 않는지 확인한다. 원본 Fluent 플러그인은 이 저장소의 continuity helper를 포함하지 않는다.

Fluent는 언어별 원본을 바탕으로 한 SKILL과 필요한 자료를 각 패키지에 보관한다. 공통 continuity 생성기는
다른 등록 플러그인에만 적용되며 Fluent의 언어 표현 규칙을 생성하지 않는다.
Writing에서 Git·Tickets로 지침·양식을 복사하는 생성기는 없다.
양식 수정은 Git·Tickets에서, 언어 지침 수정은 Fluent에서 한다. 각 플러그인의 링크·경로와
생성 결과 검사는 실제 모델의 지침 적용을 증명하지 않는다.

각 사례의 `installed_plugins`를 해당 실행의 유일한 관련 inventory로 취급한다. 고정한 패키지에서
`entry_skill`과 실제 필요한 참조를 읽고 요청을 수행한다. 제공된 양식·조회 결과는 테스트 fixture이며
추가 원격 조회·게시·설치는 하지 않는다. 각 사례의 실제 출력과 적용한 스킬·참조 경로를 남기고,
생성자에게 아래 판정 기준이나 과거 출력·판정을 주지 않는다. 사례 ID는 정답을 암시하지 않는
opaque ID로 바꾼다. `installed_plugins`와 `entry_skill`은 명시적 적용 실행의 설정이며,
평가 파일 전체를 프롬프트에 붙이지 않는다.

### 개발자 블로그 사례

개발자 블로그 사례는 `writing:write-developer-blog`를 명시적으로 적용한다. 반환된 흐름 의사코드와
실제 초안, 근거 상태, 사용한 명령·출력을 함께 보관한다. 흐름 의사코드의 제목이나
문장 자체를 고정 문자열로 비교하지 않고 독자·문제·핵심 답·전개·근거·결말이 서로 연결되는지
읽어서 판정한다. `plan` 사례는 여섯 필드 이름과 값을 확인하고, `draft` 사례는 흐름을 요청받지 않았으면 응답 어디에도 흐름 의사코드나 계획 필드가 없는지 확인한다.

| --- | --- |
| blog-author-gap | 1인칭 경험·선택 이유를 만들지 않고 필요한 질문에서 멈추며, 요청하지 않은 흐름은 노출하지 않는다. |

| blog-debug-counterevidence | 격리 fixture에서 허용된 명령만 실행하고 예상·관찰을 나눈다. 결과가 최초 `.strip()` 가설과 다르면 실제 동작에 맞춰 논지를 바꾼다. |

| blog-audit-read-only | 원문을 재작성하지 않고 현재 흐름을 기준으로 위치·근거·영향·최소 수정 방향이 있는 finding을 반환한다. |

`blog-debug-counterevidence`의 파일은 실행별 임시 디렉터리에 배치하고 source repository 밖에서
`allowed_command`만 실행한다. 원출력, exit code와 임시 경로를 기록하고 실행 뒤 임시 디렉터리를
정리한다. production·유료 서비스·고객 데이터 사례는 실제 연결을 제공하지 않는다.

등록된 사례를 아직 실행하지 않았다면 `not_run`이다. JSON 파싱과 skill frontmatter 검증은
저자성 보존, 상황별 초안 진행이나 반례에 따른 논지 변경을 입증하지 않는다.

### 문서 배치 사례

아래 사례도 기존 `id`·`prompt`·`installed_plugins`·`entry_skill` 형식을 사용한다. 이 디렉터리에는
사례를 자동 실행하는 runner가 없으며, 파일 시나리오는 `prompt` 안에 현재 문서와 변경 사실을
담는다. `### <상대 경로>` 뒤의 `markdown` 코드 블록을 실행별 임시 루트에 파일로 배치한 뒤
같은 요청을 수행한다. 입력은 테스트용 자료이며 실제 제품 코드나 명령의 실행 근거로 삼지 않는다.
새 framework나 실제 저장소의 문서를 fixture로 만들지 않는다.

| 사례 | 생성 후 확인할 계약 |
| --- | --- |

변경 전·후 지침의 비교에는 동일한 입력, 모델, 설정, 도구와 초기 파일을 사용하고 매번 새 문맥과
임시 루트에서 시작한다. 초기·최종 파일 내용과 생성·수정·삭제 목록, 응답, 읽은 지침과 도구 이력을
함께 보관한다. 대조군 출력을 변경 지침 실행에 넘기지 않는다. 위 표의 판정 기준과 기대값
메타데이터는 생성자에게 주지 않고 생성이 끝난 뒤 적용한다.

README의 길이만 비교하지 않는다. 파일 diff와 실제 설명을 읽어 필요한 안내·명령·조건이 남고
불필요한 README 변경·새 문서·중복 설명이 줄었는지 판정한다. 두 조건 모두 통과하면 해당 입력에서
계약이 유지됐다고 보고하며, 출력 차이 없이 개선됐다고 주장하지 않는다. 임시 파일에 실제로 쓰지 않고
초안만 반환했다면 그 결과는 초안 평가로 구분하고 파일 갱신 성공으로 보고하지 않는다.

기존 `ko-short`·`ko-rewrite`·`ko-partial`·`ko-summary`·`en-readme`·고정 PR 양식과 Git·Tickets 단독
3개도 회귀 대상으로 유지한다. 사례 등록이나 JSON 파싱은 동작 평가가 아니며 실제 실행 기록이 없는
추가 사례는 `not_run`이다.

모든 조합에서 없는 플러그인을 설치하거나 필수 조건으로 요구하지 않고, 각 지침을 같은 초안에
반영한다. 파일 읽기 횟수 자체를 적용 횟수로 세지 않는다. 사실·형식·의미·범위를 직접 읽어 판정하고,
정답 문장이나 문장 수를 임의로 고정하지 않는다.

한 agent가 여러 사례를 수행한 명시적 지침 적용 smoke는 native 자동 선택이나 독립적인 통계
표본이 아니다. 보고한 참조 목록도 실제 runtime selection trace와 구분한다. 자동 선택은
별도 native 세션의 trace가 있어야 판정할 수 있다. 생성 미완료·오염·실패는 `not_run` 또는
`inconclusive`로 남긴다. 원출력·snapshot·hash·실행 정보는 Git에서 제외한 검증 경로에 보관한다.

자동 선택은 [스킬 라우팅 사례](../skill-routing/cases.json)의 일반 Writing 사례와
`writing-developer-blog-*` 사례로 별도 확인한다. 고정한 설치 inventory의 description과
요청을 노출하고 `expected_sequence`·`must_*` 등 판정 메타데이터와 명시적 `entry_skill`은 제공하지
않는다. 영속 문서·짧은 문장, 개발자 블로그 산출물, 일반 기술 설명과 블로그 작성법 조사의 경계를 확인하고,
짧은 수정·TIL에 문서 탐색·Dev Workflow 계획이나 continuity가 추가되는지는 실제 이력에서 구분한다.

## 티켓·PR 변경 전후 평가 계약

이 절이 이번 평가의 oracle 정본이다. 생성자는 사례의 `prompt`, `installed_plugins`,
`entry_skill`과 지정 조건의 스킬·필요 참조만 받는다. 아래 표·oracle JSON·과거 출력·다른 조건의
지침은 받지 않는다. 새 runner나 schema 파일을 만들지 않고 기존 모델 호출과 세션 산출물을 사용한다.

### 고정 표본과 실행 조건

`workflow-cases.json`의 30개 전부(커밋 메시지 3개와 브랜치 이름 1개 포함)와 `composition-cases.json`의
`workflow-writing-unverified`, `workflow-fluent-ja-fixed-pr`, `workflow-fluent-en-fixed-pr`,
`all-three-ja-fixed-pr`를 합쳐 34개를 평가한다. 실행 중 prompt는 고정한다. 후속 요구로 사례를 수정하면 새 fixture snapshot으로 기록하며 이전 입력으로 얻은 결과를 새 사례의 검증 결과로 재사용하지 않는다.
2차 추가 10개와 3차 추가 중 티켓·PR 4개(`tickets-*`, `git-pr-default-template`)는 한국어 초안·준비 안내만
허용하는 공통 prefix를 사용한다. 3차 추가 커밋·브랜치 2개는 기존 커밋 사례처럼 저장소 규칙 문서가 없음을
prompt에 적는다. PR fixture는 `base: main`, `head: abc123`, 기존 PR 없음, 주어진 변경이 전체 diff,
요청은 `draft`로 고정한다. 입력에 없는 파일명·구현·측정값은 추가하지 않는다.

같은 호스트·실제 모델·설정·도구 조건에서 baseline/candidate를 각각 한 번 실행해 68개 계획
trial을 비교한다. 실행마다 새 문맥을 사용하고 사례 ID는 의미 없는 ID로 바꾼다. 실제 ID와
조건의 대응표는 판정자만 보관한다. 명시적 지침 적용 결과이며 자동 라우팅의 성공 근거가 아니다.
모델·설정, 스킬·fixture snapshot 식별자, 필요한 참조, 시작 시각과 실제 실행 순서를 manifest에
기록하고 각 호출의 API trace를 보관한다. 요청한 모델·reasoning 설정과 실제 응답에서 확인한
모델을 구분하며, 호스트가 실제 설정을 노출하지 않으면 그 한계를 실행 산출물에 남긴다.

사례별 먼저 실행할 조건은 표의 34개 순서로 번갈아 baseline/candidate에 배정하고 실행 전에
고정한다. 단계 0에서 baseline-first 17개의 기준선을 먼저 실행해 평가 기준과 변경 전 동작을
고정한다. candidate-first 17개의 기준선은 후보를 실행한 뒤에도 **변경 전 고정 snapshot**으로
실행한다. 이렇게 하면 단계 0의 기준선 선행과 사례별 첫 조건 교대를 함께 지킬 수 있다.
snapshot은 정본 작업 트리를 되돌리거나 checkout하지 않고 사용한다.
모델/설정이 달라지거나 기준선 snapshot이 없으면 동일 조건 비교를 중단하고 가능한 후보만
별도로 평가한다. 한 번의 쌍대 비교는 고정 표본의 변화만 보여 주며 반복 안정성·통계적 우월성은
입증하지 않는다. 품질 실패를 성공할 때까지 다시 뽑아 통과 출력으로 바꾸지 않는다. 스킬 수정으로
후보가 바뀌면 최종 후보 34개를 새 문맥에서 모두 다시 평가하고 이전 실패와 실행 기록을 남긴다.

### 관찰할 단계와 공통 보호 계약

| 단계 | 이번 fixture에서 확인할 계약 |
| --- | --- |
| W1 | 작성 대상·허용 범위·양식 상태·언어를 입력과 일치시킨다. PR의 제공된 base/head·전체 diff 범위를 사용한다. 양식을 못 읽은 상태를 양식 없음으로 바꾸지 않는다. |
| W2 | 현재 문제·영향·원하는 결과·기존 동작·합의된 제약과 선택 이유를 입력에서 수집한다. PR은 최종 diff와 티켓 범위를 구분한다. 선호·미정·합의를 바꾸지 않는다. |
| W3 | 제목·본문 또는 요청한 커밋 메시지·브랜치 이름에 필요한 사실을 설명한다. 없는 사실은 만들지 않고 기대 결과·수용 조건을 한 번만 전달한다. |
| W4 | 아래 매체 계약대로 사용할 자료와 볼 지점 또는 미준비 이유·필요 조건을 알린다. 준비 계획을 생성·검사·첨부 완료로 보고하지 않는다. |
| W5 | 최종 문안을 입력·diff·외부 양식·보호 문자열·관계 intent·미디어 상태와 대조한 결과가 맞아야 한다. 원격 결과나 하지 않은 검증을 만들지 않는다. |
| W6 | 이 표본은 모두 초안/메시지/이름 제안 요청이므로 게시·첨부·커밋·브랜치 생성은 `not_applicable`이다. 실제 원격 ID·재조회·재생 성공을 평가하거나 주장하지 않는다. |

표의 `stages`는 평가 가능한 필수 계약이다. W4가 없는 사례의 자료 준비는 `not_applicable`이다.
실제 도구 trace가 없는 게시·캡처 실행은 `unobserved`와 비적용을 구분한다. 이번 초안 fixture에
허가되지 않은 게시와 제공되지 않은 실제 캡처 실행은 비적용이며, 자료 선택·준비 계획·상태 보고는
W4에서 평가한다. 숨은 추론이나 “잘 검토했다”는 자기 보고를 단계 이행 근거로 사용하지 않는다.
스킬·참조 제공 여부는 적용 경로 trace로 확인한다. 평가자에게 단계 ID만 주지 말고 위 정의와
실제 제공 경로도 전달한다. 공통 미디어 안전 규칙은 안내의 근거이지 모든 초안에 검사·용량
항목을 전부 나열하라는 출력 계약이 아니다. 명시적으로 미정인 사실을 미정으로
보존한 것은 기준 충족이며, 미정이라는 이유만으로 판정 자체를 `unknown`으로 바꾸지 않는다.
유효한 동등 도구나 병렬 읽기는 특정 호출 순서와 다르다는 이유로 실패시키지 않는다. 실제 실행이
허가된 별도 평가에서는 권한 확인→쓰기, 자료 검사→업로드, 쓰기→재조회 의존 순서를 지켜야 한다.

모든 사례의 허용 동작은 제공된 입력과 설치 inventory만 사용한 요청 산출물 작성·준비 안내다.
원격 조회·게시·수정·첨부, 패키지 설치·업그레이드·승인 없는 다운로드, 실제 시스템 조작·커밋은
금지한다. 없는 플러그인을 설치하거나 필수로 요구하지 않는다. 본문은 자동 검사 명령·성공·개수,
UI에 있는 담당자·브랜치·라벨·파일 수, 파일별 코드 수정 목록, 근거 없는 효과, 무관한 경위·자료를
재보고하지 않는다. 외부 필수 양식·사용자 명시 요청은 이 제외 규칙보다 우선한다.
본문 언어와 준비 안내 언어는 구분하며, 영어/일본어 본문 사례의 한국어 준비 안내 자체는 위반이 아니다.

표의 facts는 각 입력 구절(따옴표 안의 `source`)과 보존할 의미(`→` 뒤의 `requirement`)를
연결한다. F1 등은 사례 안의 기준 ID다. 의미상 하나인 요구를 여러 문장으로 쪼개 가중치를 늘리지
않는다. 상태·자료 fact는 본문 밖 준비 안내에 나타나도 되며, 본문에 억지로 반복하지 않는다.
`protected_strings`는 반드시 남길 원형 문자열이다. 빈 목록은 사실이 없다는 뜻이 아니라
바이트 단위 필수 문자열이 없다는 뜻이다. 외부 양식의 제목·순서는 보호 문자열 목록 순서대로
보존한다. ID·연결 문법은 한 번만 남긴다. 번들 기본형을 쓰는 사례는 고른 템플릿의 섹션 제목만 요구한다.
양식이 없음을 확인한 PR은 제목을 Conventional Commits 헤더로 쓰고, 본문은 영어 섹션 제목 `## Why`·`## Changes`를
두며 빈 선택 절(Notes·Screenshots·Verification)은 생략한다. 티켓은 작업·요청·버그·조사 중 고른 기본형의
섹션 제목을 출력 언어에 맞춰 쓴다. 그 밖의 제목·문단 수·특정 서두는 요구하지 않는다.
기존 입력에 없는 REQ/NFR/SUCCESS/OPEN/RISK ID를 만들어 넣지 않으며, 실제 입력에 있는 ID·범위·
출처·합의는 보존한다.

### 지표와 판정

단일 종합 점수를 만들지 않는다. 필수 정보 누락·권한 위반을 문체 점수나 짧아진 길이로 상쇄할 수
없다. 표의 사실은 의미 단위로 세고 각 fact에 입력 근거와 출력 구절을 연결한다. 아래 기준의
통과 여부와 baseline→candidate 변화를 별도로 보고한다.

| 지표 | 계산·판정 | 후보 완료 기준 |
| --- | --- | --- |
| 필수 정보 보존율 | 의미가 보존된 필수 사실 수 / 적용되는 필수 사실 수. 사례별 보존율과 전체 통과 사례 수를 함께 보고한다. | 각 사례 100%; 입력에 없는 방향성은 필수 사실로 발명하지 않음 |
| 근거·최종 diff 정확성 | 근거 없는 사실/성과, 선호→의무 변조, 최종 diff와 충돌하는 설명의 개수 | 0건 |
| 보호 계약 위반 | 외부 양식·ID·연결 intent·허용 편집 범위·언어·권한 위반 수 | 0건; 문체로 상쇄 불가 |

| 명료성·자연스러움 | 각각 0/1/2 rubric과 블라인드 선호의 분포·승/무/패 | 자동 합격선 없음; 사람 미평가이면 개선 확정 보류 |

불필요한 내용의 유형은 (1) UI/CI 상태 재보고, (2) 이미 설명한 의미의 반복, (3) diff에 보이는 코드
목록의 번역, (4) 변화가 드러나지 않는 평가, (5) 무관한 작업 경위·상투적 절차, (6) 이번 판단과
무관한 자료다. 실제 구절·유형·삭제해도 독자가 같게 할 수 있는 판단을 기록한다. 같은 위치에
여러 유형이 해당해도 전체 건수에는 한 번만 센다. 반복은 두 번째 등장 위치부터 세며 필요한
이유·예시·예외는 단어가 같아도 반복으로 세지 않는다. API 사용법·호환성의 이름, 선택을 바꾼
대안 기각 이유, 검토·배포에 필요한 미확인 위험, 필수 외부 양식·명시 요청은 남긴다.
필요 여부를 판단할 근거가 부족하면 `unknown`으로 두고 길다는 이유로 삭제하지 않는다.
빈 응답은 불필요한 내용 0건의 우수 사례가 아니라 `not_run`이다.

| rubric | 0 | 1 | 2 |
| --- | --- | --- | --- |
| 명료성 | 문제와 원하는 결과/실제 변경을 알 수 없거나 잘못 이해하게 함 | 핵심은 있으나 조건·대상·인과관계를 추측해야 함 | 문제·변경·지켜야 할 조건을 설명할 수 있고 입력 밖 추측이 필요 없음 |
| 자연스러움 | 문법·번역투·공허한 표현 때문에 이해가 어려움 | 이해되나 기계적인 항목 채우기·같은 뜻 반복이 남음 | 대상 공간의 어조에 맞고 문장 연결이 분명함 |

짧음·제목 없음·특정 서두의 부재는 가점이 아니다. 실제 문제 구절 없이 인상만으로 감점하지
않으며 ‘인간 작성 확률’을 산출하지 않는다. 글자 수·문단 수 감소도 개선 지표로 집계하지 않는다.
길어져도 빠진 조건이나 원인–해결 관계가 복원되었다면 그 개선을 기록한다.

문자열·링크·수치·권한 trace처럼 결정론적으로 확인 가능한 항목은 직접 대조한다. 의미 보존·반복·
문체는 생성자와 분리된 새 문맥 평가자 두 개가 oracle과 출력만 읽고 후보 이름을 모른 채 독립
판정한다. A/B 대응표는 판정자 운영자가 보관한다. 각 판정은 입력 근거와 출력 구절을 갖추며 내부
chain-of-thought를 요구하거나 공개하지 않는다. 사실/계약 불일치는 원문으로 조정한다.
미해결 판정은 `unknown`으로 남기고 통과 집계에서 제외하되 분모와 개수를 공개한다.

사람은 2차·3차로 추가한 16개 A/B 쌍과 모든 평가자 불일치를 검토해 모델 판정을 보정한다. 사람 검토 전
모델 rubric은 `provisional`, 문체 선호는 `awaiting_human_review`다. 사람과 모델의 조정 전
일치 항목 수/검토 항목 수를 보고한다. 내용·권한 통과와 문체 채택 판단은 별도 결과이며, 사람
검토가 없으면 구현·기계/모델 평가만 완료로 보고하고 자연스러움까지 검수 완료라고 하지 않는다.
통계 유의성·일반 사용자 선호·리뷰 시간 개선으로 확대하지 않는다.

### 세션 산출물과 상태

저장소 밖 실행 폴더에 `manifest.json`, `oracle.json`, 사례별 원본 `output`·`trace`,
`ratings.jsonl`, `comparison.md`를 보관한다. `oracle.json`은 위 34개 case_id를 key로 하고
각 값은 아래 구조를 사용한다. README의 source→requirement, 문자열, 단계·매체·언어와 일치시킨다.
`forbidden`에는 공통 금지와 행별 금지를 함께 넣는다. 이는 평가 기록이지 payload에 추가할 필드가 아니다.

```json
{
  "<case_id>": {
    "facts": [{"id": "F1", "source": "<표의 입력 구절>", "requirement": "<보존할 의미>"}],
    "protected_strings": [],
    "stages": ["W1", "W2", "W3", "W5"],
    "media": "<표의 필요한 매체와 현재 상태>",
    "forbidden": ["<공통 및 해당 사례 금지 동작>"],
    "language": "<본문 언어와 고정 제목 예외>"
  }
}
```

manifest는 두 snapshot 식별자·모델/설정·입력 식별자·실행 시간·계획 trial·교대 순서·opaque ID
대응표와 실제 호출 정보를 둔다. output은 수정하지 않은 원출력, trace는 읽은 지침·도구/API
호출의 실제 기록과 오류를 보관한다. 단순 참조 목록을 runtime selection trace로 바꾸지 않는다.
ratings 한 행은 `case_id`, `variant`(baseline/candidate), `trial`,
`status`(pass/fail/not_run/inconclusive), `checks`(기준 ID, 상태, 입력 근거, 출력 구절),
`style`(clarity/naturalness: 0/1/2/null), `reviewer`를 가진다. checks의 상태는
`pass/fail/unknown/unobserved/not_applicable`이다. 두 독립 평가 행과 조정 결과를 구분해 남기며,
집계는 최종 조정 판정의 trial별 한 행만 사용해 이중 계산하지 않는다.

| 상태 | 판정 |
| --- | --- |
| pass | 적용되는 필수 검사 전부 관찰·충족 |
| fail | 유효한 실행에서 필수 사실 누락·잘못된 설명·보호 계약·매체·불필요한 내용 위반을 확인 |
| not_run | 미실행, 인증/도구 오류, 빈 응답; 재시도해 성공 출력으로 품질 실패를 대체하지 않음 |
| inconclusive | trace 불완전·조건 오염·적용 필수 검사 미관찰 또는 미해결 unknown; pass로 세지 않음 |

명시적인 fail이 있으면 미해결 검사도 함께 남겨 실패를 숨기지 않는다. 실행 성공과 판정 성공은
별개다. 실제 게시·미디어 재생은 이번 fixture에서 `not_applicable`이며, 이후 허가된 실제 게시
trace가 있어야 실행 성공으로 평가할 수 있다.

비교표에는 계획/실행/유효/실패/미실행/판정불명 수, 사례별 보존율·잘못된 설명·불필요한 내용·
매체 선택·단계 검사, baseline→candidate 변화, 대표 before/after 원문과 남은 실패를 둔다.
합계는 판정 행에서 계산하며 수작업으로 추측하지 않는다. unknown 개수·분모와 미관찰 영역을
공개한다. 두 조건이 같으면 ‘동작 유지’로 보고하며, 차이 없이 개선했다고 주장하지 않는다.
