# 일본어 문어 지침 조사·적용·측정 결과

**판정: 수정판의 기본 채택을 보류한다.** LLM 용례 목표 점수는 늘었지만, 문항 단위 차이는 통계적으로 뚜렷하지 않았고 새로운 의미 보존 위반과 일부 family의 과잉 교정 증가가 관찰됐다. 후보는 저장소와 개인 로컬 플러그인에 보존했으며, 현재 활성 항목은 기존 Git 마켓플레이스 배포판이다. 원어민 검토를 통과했다는 뜻이 아니며 beta 상태를 유지한다.

## 수행 범위

- `git pull origin main --rebase`는 `d8c08f0`에서 `bc6feb34d3b9f2dd2d01bf8c8063a9f9eb35bb00`으로 fast-forward 완료됐다. 충돌은 없었다.
- [연구 목록](../../docs/research/fluent-japanese-writing-catalog.md)은 85개 문맥·규칙·반례 항목이다. 표기·문체 45개, 한일 번역·용례 40개이며, 원문 초점 표현 확인 51개와 규칙에서 작성한 항목 34개를 구분한다.
- 일본어 source와 렌더링한 SKILL에 여섯 개 조건부 지침을 추가했다. 사례 목록 전체를 런타임 스킬에 넣지는 않았다.
- 신규 40문항과 기존 입력 10문항, 총 50문항으로 실제 생성 200회를 수행했다. 목록 85개 전체를 전수 평가한 것은 아니다.
- 실제 native 실행 2건에서 한국어 요청→일본어 스킬, 일본어 요청→영어 스킬의 캐시 파일을 각각 읽었고, 파일 읽기와 응답이 완료됐다.

## 측정 설계와 수정 이력

요청 모델은 `gpt-5.6-sol`, reasoning `medium`이다. 응답 trace에서 실제 model ID와 reasoning 설정은 확인할 수 없어 observed 값은 unknown으로 남긴다. 각 문항을 두 arm에서 두 번씩 실행하고, 문항 순서를 seed `20260906`으로 섞었다. 두 반복의 arm 순서는 AB/BA로 상쇄했다. 모델 입력에는 prompt/evidence만 문항 정보로 제공했다.

기본 스킬 설명과 global AGENTS가 남는 공통 호스트 문맥을 사용했다. preflight에서 양 arm의 정규화한 공통 context SHA-256이 `3a59b9cdf33096df4cfd2375871715a4e54019e99e5a4a63590aa4306b3af44e`로 같았고, 지정된 스킬 외의 Fluent 본문은 없었다. 200개 실행 trace에서 도구 호출은 0회였다. debug 입력 검사는 실제 exec 전송 payload 전체의 byte 단위 증명이 아니다.

생성 중 검토에서 번역된 일반 단어를 exact literal로 강제하는 오류, 의미 rubric 누락, 판정 ID·cache 결합과 family별 gate 누락을 발견했다. **judge 호출 전에** 이를 고쳤다. 날짜 표기의 동등성, code block의 1행/2행 참조와 목록 내부 들여쓰기도 오탐에서 제외했다. prompt/evidence와 두 스킬 snapshot은 바뀌지 않았다. 새 `analysis-v2` manifest는 원 manifest, 입력, arm/config, 200개 출력·trace·명령 파일 hash를 대조한 뒤 기존 생성 결과를 재사용했으며, 추가 생성은 0회였다.

따라서 이 결과는 **생성 입력은 고정됐지만 채점 계약을 수정한 진단 분석**이다. 수정 없이 끝난 사전등록 연구나 held-out 검증으로 표현하지 않는다. 원래 생성 source·fixture·protocol과 수정 전 결과를 삭제하거나 덮어쓰지 않았다.

100쌍을 10쌍씩 묶어, 각 묶음에 같은 고정 LLM rubric의 blind 판정을 3회 수행했다. X/Y 위치를 섞고 opaque item ID로 결과를 연결했다. 이는 동일 모델의 반복 판정이며 사람 평가자 3명의 독립 의견이 아니다. judge 30회, pair 100개, 두 반복이 있는 case 50개가 모두 완료됐다. 별도 계산으로 100쌍의 세 판정 majority를 재집계했고 저장된 집계와 모두 일치했다.

판정이 진행되는 동안 코드 리뷰가 요구한 완결성 gate를 추가했다. 측정에 사용한 grader source는 별도로 보존했다. 최종 코드의 완결성 조건을 실제 결과에 다시 적용했을 때 100 pair·30 judge·50 case가 모두 충족됐으며 `not_eligible` 판정은 같았다. 이 사후 확인은 새로운 모델 호출이 아니다.

## 관측 수치

아래 의미·용례·과잉 교정은 고정 LLM rubric의 majority 판정이다. 각 arm의 분모는 50문항 × 2회 = 100개 출력이다. 구조·literal은 수정한 deterministic 검사이며, 의미 검사를 대신하지 않는다.

| 지표 | 기존판 | 수정판 |
|---|---:|---:|
| 생성 완료 | 100/100 | 100/100 |
| 구조·보호 문자열 검사 | 100/100 | 100/100 |
| 용례 목표 충족 `target_ok` | 92/100 | 98/100 |
| 의미 보존 `semantic_ok` | 95/100 | 96/100 |
| 과잉 교정 지적 | 16/100 | 14/100 |
| 생성 지연 중앙값 | 8.411초 | 8.440초 |
| 생성 input tokens 합계 | 1,285,772 | 1,352,668 |
| 생성 output tokens 합계 | 14,938 | 16,124 |
| 위 output에 포함된 reasoning tokens | 10,258 | 10,448 |

한 문항의 두 반복 target 점수 합을 비교하면 **수정판 우세 8, 기존판 우세 2, 동률 40**, 양측 exact sign test `p=0.109375`다. 100개의 반복 pair를 독립 문항으로 계산하지 않았다. 선호도의 보조 지표는 두 반복 모두 같은 쪽을 선호한 경우만 세어 수정판 2승, 기존판 4승, 동률·반복 불일치 44건이다(`p=0.6875`).

100쌍 중 41쌍은 두 출력이 byte 단위로 같았다. judge 간 pairwise 선호 일치율은 86.7%이며, 81쌍에서 세 판정이 일치했다. 일치율은 판정의 정답률이 아니다. input 증가분은 약 5.2%였고, 위 토큰 수는 생성 호출만의 usage다. cached input은 input의 일부이고 reasoning은 output의 일부다. 이를 더해 중복 계산하거나 구독 quota 사용률로 해석하지 않는다.

## 개선 후보와 반례

`aux-award-preserve`에서 수정판은 본동사 `頂く`를 두 번 모두 유지했고, 기존판은 한 번 `授与されました`, 한 번 `いただきました`를 출력했다. 이는 표기·경의 유지의 관측 사례이며 일반적인 우열의 증명이 아니다. `formal-notice-correct` 첫 반복에서는 기존판이 발생 사실을 `発生している`로 바꾸었고 수정판은 `発生した`를 유지했다. 두 번째 반복은 양쪽 출력이 같았다.

명확하게 확인할 수 있는 수정판의 문제도 있었다.

| 문항·반복 | 입력의 구분 | 수정판 출력 | 문제 |
|---|---|---|---|
| `protected-uncertain-time-ambiguous-r1` | 담당자는 기록에 없음, 대응 시기는 미정 | `対応者および対応時期は未定です。` | 담당자의 미기록 상태를 미결정 상태로 바꿨다. |
| `protected-unknown-actor-ambiguous-r2` | 원인·담당자는 미확인, 지연 행위자는 미기록 | 지연 원인·지연 행위자를 미확인으로 기술 | 담당자 정보를 행위자 정보로 대체하고 상태 구분을 잃었다. |

LLM은 이 두 출력 외에 `teki-pos-ambiguous`의 두 반복도 신규 semantic 위반으로 판정했다. 그러나 첫 반복의 `効果的な案内が必要です。`는 대상의 모호함 자체를 유지한다. 불확실성 설명을 별도 문장으로 쓰지 않았다는 이유의 감점은 논쟁의 여지가 있다. 원 점수를 사후에 유리하게 수정하지 않았으며, **4건 전체를 사람이 확정한 의미 오류라고 주장하지 않는다.** 두 명확한 반례만으로도 무회귀 채택 조건은 충족하지 못한다.

전체 과잉 교정 수는 줄었으나 다음 family에서는 증가했다. 분모는 각 family의 10개 출력이다.

| Family | 기존판 지적 | 수정판 지적 |
|---|---:|---:|
| 한자·허용 표기·분야 용어 | 1 | 2 |
| 한일 어의 | 1 | 4 |
| `する`·자타·조사 | 0 | 1 |
| `的`과 품사 | 1 | 2 |

이 수치는 모델의 불필요한 재작성 판단도 포함하므로 일본어 문법 오류 건수와 같지 않다. 다만 정해 둔 family별 무회귀 조건을 통과했다고 쓸 수는 없다.

## 로컬 플러그인 상태

Git 마켓플레이스 항목에 worktree 소스를 직접 설치하면 다음 Codex 실행이 기존 snapshot으로 cache를 되돌리는 동작이 있었다. 첫 native probe에서 파일을 읽지 못한 trace를 보존했고 성공으로 세지 않았다. 이후 기본 개인 마켓플레이스에 후보를 설치해 새 native 실행 2건에서 올바른 스킬 파일 읽기를 확인했다.

- 설치 상태로 보존하되 비활성: `fluent-languages@personal`, `0.1.0-beta.4+codex.20260906021214`.
- 후보 source: `/Users/sonsu/plugins/fluent-languages`.
- 후보 일본어 SKILL SHA-256: `8bd9d7b8add7dc4486ab8116b86fd95ac13f8dc81e0571de72aa1894f25e738b`. 저장소, 측정 snapshot과 실제 로드된 cache의 hash가 같았다.

현재 열린 task가 과거에 로드한 스킬 본문은 설정 변경으로 대체되지 않는다. 새 실행의 활성 항목은 마지막 `codex plugin list --json`에서 확인했다. commit·push·PR은 수행하지 않았다.
