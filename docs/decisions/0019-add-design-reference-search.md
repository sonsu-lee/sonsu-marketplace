# ADR 0019: Design 플러그인에 레퍼런스 검색 스킬 추가

- 날짜: 2026-09-29
- 상태: 채택
- 관련 결정: [ADR 0018](0018-consolidate-ui-design.md)

## 배경

Design의 세 공개 스킬은 사용자가 준 레퍼런스를 출처·목적별로 정리해 사용하지만, 레퍼런스를
찾는 절차는 없었다. "로그인 화면 사례를 찾아 줘"처럼 설계 없이 검색만 원하는 요청을 받을
진입점도 없었다. 외부 도구는 큐레이션된 화면 라이브러리 MCP(Mobbin, Refero), 로컬 데이터와
BM25, `site:` 웹 검색, 브라우저 캡처로 나뉜다. 공개 정량평가는 드물고, 레퍼런스가 최종 디자인을
실제로 개선하는지 측정한 사례는 찾지 못했다.

## 결정

`design` 플러그인에 네 번째 공개 스킬 `find-references`를 추가한다. 이 스킬은 레퍼런스를
검색·선별·기록만 하고 화면을 설계하거나 제품 파일을 수정하지 않는다.

- 공통 절차는 [레퍼런스 검색 계약](../../plugins/design/references/reference-search.md)에 둔다.
  `design-interface`와 `redesign-interface`는 사용자가 레퍼런스 탐색을 요청하거나 동의했을 때
  같은 계약을 직접 적용한다. 설계 요청에 검색이 포함되어도 스킬을 따로 호출하지 않는다.
- 세 설계 스킬은 같은 계약으로 연동한다. 설계·재설계는 사용자 레퍼런스나 `find-references`
  결과를 입력으로 primary와 차용 범위를 잠그고, 검증은 결과를 primary와 대조해 `do_not_borrow`가
  옮겨지지 않았는지 확인한다. 감사는 레퍼런스와의 차이만으로 finding을 만들지 않는다. 여러 단계
  작업은 reference set 위치와 차용 범위를 작업 연속성 기록에 보존한다.
- 공급자는 현재 세션에 노출된 도구의 자격으로 고른다. Mobbin·Refero MCP, `research` 스킬은
  실행 조건이 아니며 없으면 호스트 웹 검색을 쓰거나 `no_verified_match`를 보고한다.
- 레퍼런스 카드는 공급자, locator, 출처 성격(`source_kind`), 확인 수준(`inspection`), 차용·비차용
  항목을 기록한다. primary 하나와 나머지 레퍼런스의 차용 상한 2개를 검증기로 강제한다.
- 기록 형식은 독립 문서 `design-reference-set-v1`과 Design Decision Contract의
  `extensions.references`다. 선택 확장이므로 계약 버전은 v1을 유지한다. 기존 계약은 그대로 유효하다.
- 평가는 [design-reference-search](../../evals/design-reference-search/README.md)에서 결정적 검사,
  라우팅·행동, 고정 후보 풀 위의 검색 품질, 레퍼런스 유무 비교, 비용의 다섯 층으로 나눈다.

## 대안

- **설계 스킬 안의 참고 자료만 추가**: 가장 가볍지만 검색만 원하는 요청의 진입점이 없다.
- **독립 플러그인**: 레퍼런스 사용 규칙이 `design`의 `delivery.md`에 있어 플러그인 간 의존이 생긴다.
- **스크린샷 코퍼스와 임베딩 검색을 저장소에 포함**: 결정적이지만 이미지 사용 권리와 최신성을
  보장할 수 없다. 저장소에는 locator와 출처만 둔다.
- **계약 v2로 전환**: 선택 확장만 추가하므로 기존 문서를 깨뜨릴 이유가 없다.

## 결과

- 검증기가 `references` 명령과 `extensions.references`를 검사한다. 통과는 형식과 추적성만
  보장하며 레퍼런스의 적절성을 뜻하지 않는다.
- 검색 품질과 레퍼런스 유무 비교는 정답 세트와 평가자가 필요하므로 현재 `not_run`이다.
  첫 측정값은 목표가 아니라 회귀 방지 최저선으로 고정한다.
- 공급자 도구 이름과 응답 형식이 바뀌어도 계약은 도구 이름이 아니라 능력과 스키마로 확인한다.
- Codex·Claude Code·omp가 같은 스킬 파일을 쓴다. 스킬 본문은 플러그인 접두어 없는 스킬 이름과
  호스트 웹 검색 같은 능력 표현만 사용하고, omp 카탈로그와 package 버전은 `render-omp-compat.py`로 생성한다.

## 다시 볼 때

- 정답 세트에서 held-out 성능이 calibration보다 크게 낮아 쿼리 규칙의 과적합이 보일 때
- 레퍼런스 유무 비교에서 개선이 확인되지 않거나 비용 증가가 효용보다 클 때
- 주요 공급자가 공식 API·MCP를 바꾸거나 이용약관이 자동 검색을 제한할 때
